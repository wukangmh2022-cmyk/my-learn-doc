10.4 图形驱动 vs 通用计算驱动: 差异与交集¶

概述¶

在同一个 GPU 硬件上，图形驱动的优化目标和计算驱动的优化目标看起来截然不同——一个追求帧率，一个追求吞吐。但当你深入到底层硬件和 KMD 层面，会发现两者正在快速收敛。

理解这个 \"差异中的统一\"，能让你同时看清图形渲染和 AI 推理的底层优化逻辑。

核心差异: 优化目标不同¶

图形驱动: 游戏驱动的优化¶

游戏的本质是实时交互——帧率必须稳定在 60~144 FPS，每帧必须在 7~16ms 内完成。这决定了图形驱动的优化方向：

优化维度 为什么重要 典型手段
状态切换开销 (State Switching) 游戏场景频繁切换 Shader、纹理、RT PSO 缓存 (Pipeline State Object Cache)、Barrier 合并
Draw Call 吞吐 每帧可能包含数千上万个 Draw Call Command List 合并、Instancing、Indirect Draw
纹理采样效率 游戏大量依赖纹理采样 (Texture Sample) Mipmap 自动选择、纹理压缩格式优化、L1/L2 缓存策略
帧时间稳定性 卡顿 (Stutter) 直接影响用户体验 着色器编译缓存 (Shader Cache)、预编译、异步编译
多帧并行 CPU 准备下一帧的同时 GPU 渲染当前帧 三重缓冲、Ring Buffer、Fence 轮询 
// 图形驱动的优化视角：减少状态切换
// 游戏引擎按材质排序 Draw Call，让驱动减少状态切换

// Bad: 频繁切换 PSO
DrawMesh(meshA, materialX);  // PSO = A
DrawMesh(meshB, materialY);  // PSO = B ← 状态切换！
DrawMesh(meshC, materialX);  // PSO = A ← 又切回来！

// Good: 按 PSO 排序，合并状态
DrawMesh(meshA, materialX);  // PSO = A
DrawMesh(meshC, materialX);  // PSO = A ← 命中缓存，零切换
DrawMesh(meshB, materialY);  // PSO = B ← 只切一次

一句话总结：图形驱动的核心挑战是 \"不确定性下的实时性能\"——你不知道玩家下一秒会看到什么场景，但必须保证帧率不崩。

计算驱动: 模型驱动的优化¶

AI 推理的本质是批量吞吐——模型结构固定，执行流程可预测，关键是让 GPU 算得越快越好：

优化维度 为什么重要 典型手段
Kernel Launch 延迟 每次 cudaLaunchKernel 都有 CPU 开销 CUDA Graph 录放、Kernel 融合、减少提交次数
显存带宽利用 AI 算子是带宽密集型 (Memory-Bound) 算子融合 (减少中间结果读写)、Shared Memory Tiling
计算吞吐 矩阵乘是核心计算模式 Tensor Core 指令、Warp 级矩阵运算
流水线并行 CPU 侧预处理与 GPU 计算重叠 CUDA Stream + Event 异步流水线
显存碎片管理 大模型显存占用巨大，碎片影响通过 显存池 (Memory Pool)、PagedAttention 
// 计算驱动的优化视角：减少 Kernel Launch 开销
// 使用 CUDA Graph 把多个 Kernel 录制成一个图，一次提交多次重放

// Bad: 每次 Token 都单独提交 Kernel
for (int i = 0; i < numTokens; i++) {
    launch_prefill_kernel<<<grid, block>>>(...);   // CPU 提交一次
    launch_attention_kernel<<<grid, block>>>(...); // CPU 提交一次
    launch_ffn_kernel<<<grid, block>>>(...);       // CPU 提交一次
}

// Good: 录制成 CUDA Graph，一次提交
cudaGraph_t graph;
cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);
    launch_prefill_kernel<<<grid, block>>>(...);
    launch_attention_kernel<<<grid, block>>>(...);
    launch_ffn_kernel<<<grid, block>>>(...);
cudaStreamEndCapture(stream, &graph);

cudaGraphExec_t graphExec;
cudaGraphInstantiate(&graphExec, graph, NULL, NULL, 0);

for (int i = 0; i < numTokens; i++) {
    cudaGraphLaunch(graphExec, stream);  // 一次提交，GPU 内部调度所有 Kernel
}

一句话总结：计算驱动的核心挑战是 \"可预测下的极致吞吐\"——模型结构是固定的，每步执行路径已知，目标是榨干每一瓦功耗的算力。

差异背后的根本原因¶

任务模型的差异¶

维度 图形渲染 (游戏) AI 推理 (模型)
工作负载特征 \"游击战\"：场景随机切换，Shader/纹理/材质变化频繁 \"阅兵式\"：模型结构固定，每层计算可预测
瓶颈 CPU 提交 Draw Call 和状态切换本身可能成为瓶颈 显存带宽和 Kernel 启动延迟是主要瓶颈
数据依赖 帧间独立，每帧的渲染内容可能完全不同 计算图固定，前向传播路径确定
执行模式 多样化的 Pass 序列，每帧可能不同 固定的 Kernel 序列，每次推理几乎相同
优化手段 RenderDoc 优化状态缓存，合并 Draw Call CUDA Graph (减少 CPU 提交)、算子融合 (减少显存读写)

你的直觉完全正确：\"游戏渲染像游击战，AI 推理像阅兵式\"——这个差异完美解释了为什么 AI 更需要 CUDA Graph 和算子融合。

为什么 AI 更需要算子融合而非状态缓存？¶

优化技术 图形渲染 AI 推理
PSO 缓存 / 状态合并 核心优化——减少状态切换开销 不适用——计算图固定，状态切换少
算子融合 (Fuse) 次要优化——合并 Draw Call 减少同步 核心优化——减少中间显存读写
Command List 录制 每帧构建新的 Command List CUDA Graph 一次录制多次重放
多帧/多步并行 CPU 准备下一帧与 GPU 渲染重叠 CPU 预处理与 GPU 计算重叠 (Communication behind compute)

游戏渲染中，状态切换（Shader 切换、RT 绑定）的开销远大于中间结果读写。而 AI 推理中，显存带宽是压倒性瓶颈——每个中间结果写回显存再读回，代价巨大。

交集: 底层硬件同源，KMD 同根¶

尽管 UMD 层面优化的侧重点完全不同，从硬件和 KMD 的角度看，两者正在快速收敛：

1. 相同的 KMD 基础设施¶

无论是图形驱动还是计算驱动，底层的 KMD 是同一个：

图形 UMD (DX12/Vulkan)     计算 UMD (CUDA Runtime)
       │                           │
       └───────────┬───────────────┘
                   │
          KMD  (同一内核驱动)
          ┌───────┼───────┐
          │       │       │
       Ring Buffer  页表    中断
  • NVIDIA：Windows 上使用同一个 nvlddmkm.sys KMD，提供图形（WDDM）和计算（CUDA）的共享内核服务。
  • AMD：Windows 上 amdgpu.sys KMD 同时服务图形 (DirectX/Vulkan) 和计算 (ROCm/OpenCL)。
  • Linux：开源 amdgpu / nvidia-open 内核模块同时提供图形 (DRM/KMS) 和计算接口。

2. 硬件单元共享¶

现代 GPU 的同一组 SM/CUDA Core/Tensor Core 既跑图形着色器也跑计算 Kernel：

// 同一个硬件，两种用途

// 图形用法：Pixel Shader 输出颜色
[Fragment Shader]
float4 main(float2 uv : TEXCOORD) : SV_TARGET {
    float4 color = texture.Sample(sampler, uv);
    return color;
}

// 计算用法：Compute Shader 做矩阵乘
[numthreads(16, 16, 1)]
void MatMulKernel(uint3 tid : SV_DispatchThreadID) {
    float sum = 0;
    // ... 矩阵乘计算 ...
    output[tid.xy] = sum;
}

在 SASS 指令级别，两者最终都是同一套指令集——区别仅在于调度器上下文和资源分配策略。

3. 优化技术相互借鉴¶

图形发明 → 计算采用 计算发明 → 图形采用
Indirect Draw → CUDA Graph (先录后放的思想) CUDA Graph → ExecuteIndirect 的新玩法
三重缓冲 → CUDA Stream 异步流水线 显存池 (Memory Pool) → DX12 Resource Heap 细化
RenderGraph → MPS (Multi-Process Service) 图调度 PagedAttention → GPU 显存虚拟化
Fence/Barrier → CUDA Event Tensor Core → AI 加速纹理过滤/超分

NVIDIA 正在做的：把图形和计算的调度器深度整合——Hopper 架构的 MIG (Multi-Instance GPU) 和 Grace-Hopper 的统一内存模型，都在模糊 \"这组 SM 跑图形还是计算\" 的边界。

一张表总结差异与交集¶

维度 图形驱动 计算驱动
核心场景 游戏、实时渲染、VR 训练、推理、科学计算
UMD 优化重心 状态切换、Draw Call 合并、纹理缓存 Kernel Launch、显存带宽、Tensor Core 利用率
KMD 职责 显存管理、上下文切换、多进程隔离 显存管理、上下文切换、多进程隔离 (相同！)
硬件基础 可编程 SM + Rasterizer/Texture/ROP 等图形单元 可编程 SM + Tensor/MMA 与内存/互联；具体 SKU 可能没有完整图形管线
工作负载 多样化、不可预测 固定化、可预测
性能指标 帧率 (FPS)、帧时间稳定性 吞吐 (Tokens/s)、延迟 (ms)
优化工具 PIX、RenderDoc、Nsight Graphics Nsight Systems、Nsight Compute、nvprof
发展趋势 更多计算化 (GPU Driven、Mesh Shader) 更多图形化 (CUDA Graph、Tensor Core 图形)

最终结论: 正在消失的边界¶

GPU 发展的历史就是图形和计算不断融合的历史：

早期: 图形卡 vs 计算卡 (物理隔离)
 │
 ├── 2007: CUDA 开启通用计算 (同硬件，不同软件栈)
 ├── 2012: Kepler → GPU 同时服务图形和计算
 ├── 2017: Volta → Tensor Core 为 AI 而生，但也可用于图形
 ├── 2020: Ampere → MIG 硬分区，图形/计算可共存
 └── 2023+: Hopper → 统一调度，边界模糊

你现在看到的 \"图形驱动\" 和 \"计算驱动\"，本质是同一个底层基础设施上的两种不同优化策略。 理解了这个底层统一性，你就能：

  1. 把图形渲染的状态优化经验迁移到 AI Kernel 的流水线优化中。
  2. 把 AI 推理的显存管理思路反向映射到图形引擎的资源管理中。
  3. 在不同的应用场景下，选择正确的 UMD 优化策略，共享同一个 KMD 基础。
