5.1 线程模型 (Thread, Block, Grid) 与映射¶

概述¶

CUDA 的线程组织方式延续了 GPU 硬件的分层并行设计哲学：从最细粒度的单一线程，到硬件调度单位 Warp，再到程序员控制的 Block，最后到整个 Grid。这套模型与图形 API (Vulkan/DX12) 的 Compute Shader 调度在本质上是同构的。

核心认知：CUDA Kernel 的 Launch Configuration（启动配置），和图形 Compute Shader 的 Dispatch(x, y, z)，是完全一回事。你事先根据数据尺寸，在 CPU 端计算出 GPU 需要启动多少个线程块，然后一次性提交给 GPU。

线程层次结构¶

四个层次的精确含义¶

层次 硬件单位 程序员控制粒度 对应图形概念
Thread (线程) 一个 CUDA Core 执行一个线程 单个线程 ID (threadIdx) 一个像素/顶点的处理单元
Warp (线程束) 32 个线程组成一个调度单位 不可直接控制（硬件决定） Wavefront (AMD) / Wave (NVIDIA 图形)
Block (线程块) 一组线程（通常 128-1024 个），运行在同一个 SM 上 blockDim（每 Block 线程数） [numthreads(x, y, z)]
Grid (网格) 所有 Block 的总和，覆盖整个任务 gridDim（每 Grid Block 数） Dispatch(x, y, z)

关键数据流图¶

Grid (Kernel 启动)
├── Block 0       ──►  SM #0
│   ├── Warp 0 (线程 0-31)
│   ├── Warp 1 (线程 32-63)
│   └── Warp 2 (线程 64-95)
├── Block 1       ──►  SM #1
│   ├── Warp 0 (线程 0-31)
│   └── Warp 1 (线程 32-63)
├── Block 2       ──►  SM #0 (并发)
│   └── ...
└── Block N       ──►  SM #M (自动负载均衡)

每个 Block 被调度到一个 SM 上，一个 SM 可以同时驻留多个 Block（取决于资源占用）。Block 内的线程通过 Shared Memory 和 __syncthreads() 协作，Block 之间完全独立。

与图形 Compute Shader 的直接映射¶

[numthreads] → blockDim + gridDim¶

你在 HLSL 中写 Compute Shader 时：

// 图形：每线程处理一个像素
[numthreads(8, 8, 1)]  // ← 这 ≈ blockDim = (8, 8, 1)
void main(uint3 id : SV_DispatchThreadID) {
    float color = tex2D(tex, id.xy);
    // ... 处理逻辑
}

// CPU 端：
Dispatch(width / 8, height / 8, 1);  // ← 这 ≈ gridDim

在 CUDA 里一模一样的逻辑：

// AI/CUDA：每线程处理一个输出元素
__global__ void conv_kernel(float* input, float* weight, float* output,
                            int C_out, int H_out, int W_out) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx >= C_out * H_out * W_out) return;
    // ... 卷积逻辑
}

// CPU 端：
int total_elements = C_out * H_out * W_out;
int block_size = 256;                 // ← blockDim
int grid_size = (total_elements + block_size - 1) / block_size;  // ← gridDim
conv_kernel<<<grid_size, block_size>>>(...);

SV_DispatchThreadID → threadIdx + blockIdx + blockDim¶

  • SV_DispatchThreadID = threadIdx + blockIdx * blockDim
  • SV_GroupThreadID = threadIdx
  • SV_GroupID = blockIdx
  • SV_GroupIndex = threadIdx.x + threadIdx.y * blockDim.x + ...

如何计算 Grid/Block 维度¶

原则：从数据维度推导¶

当你面对一个张量操作时，核心问题只有一个：你的 Kernel 里每个线程处理多少个输出元素？

策略一：One Thread Per Element（一元素一线程）¶

最朴素的映射，每个线程负责一个标量输出元素。

// 输入张量: [B, C, H, W]
// 输出张量: [B, C, H, W]（例如 ReLU、逐元素乘加）

int block_size = 256;  // 经验值：128-512 是安全区间
int total_elements = B * C * H * W;
int grid_size = (total_elements + block_size - 1) / block_size;

kernel<<<grid_size, block_size>>>(output, input, ...);

Kernel 内部：

__global__ void elementwise_kernel(float* out, const float* in, int N) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N) {
        out[idx] = max(in[idx], 0.0f);  // ReLU
    }
}

策略二：One Thread Per Row/Column（一线程一行/列）¶

适用于 Reduce 或 Softmax 等跨维度操作。每个线程处理一个 C 维度的切片。

// 输入: [B, C, H, W]，需要对 C 维度做 Softmax
// 每个线程处理一个 (b, h, w) 位置的 C 个元素

int block_size = 256;
int grid_size = B * H * W;

softmax_kernel<<<grid_size, block_size>>>(output, input, C);

策略三：2D/3D Block 处理 Tile¶

适用于卷积、矩阵乘等需要局部性的操作，每个 Block 处理一个输出 Tile。

// 卷积：每个 Block 处理一个输出 Tile [TILE_H, TILE_W]
dim3 blockDim(TILE_W, TILE_H);     // 例如 (16, 16)
dim3 gridDim(
    (W_out + TILE_W - 1) / TILE_W,
    (H_out + TILE_H - 1) / TILE_H
);

conv_kernel<<<gridDim, blockDim>>>(...);

Kernel 内部：

__global__ void conv_kernel(...) {
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    if (col >= W_out || row >= H_out) return;

    // 每个线程负责一个输出像素的累加
    float sum = 0.0f;
    for (int kh = 0; kh < K_h; kh++)
        for (int kw = 0; kw < K_w; kw++)
            sum += input[row + kh][col + kw] * weight[kh][kw];
    output[row][col] = sum;
}

动态形状处理¶

推理引擎面临的现实：Batch Size 和 Sequence Length 每帧都可能变化（不同于图形渲染中固定尺寸的 Render Target）。

运行时重计算¶

// 推理引擎的调度器代码（伪代码）
void launch_kernel_dynamic(cudaStream_t stream, const Tensor& input) {
    int N = input.batch;
    int total = input.num_elements();

    // 根据运行时尺寸动态计算 Launch 配置
    int block_size = 256;  // 固定值
    int grid_size = (total + block_size - 1) / block_size;

    my_kernel<<<grid_size, block_size, 0, stream>>>(input.data, total);
}

Grid 大小：并行度与工作粒度¶

  • 驻留 Block 上限随架构和 Kernel 资源用量变化。
  • Grid 太小可能无法覆盖所有 SM，也可能缺少隐藏尾部和访存延迟的并行度。
  • Grid 很大通常由硬件分批调度，不因超过某个固定数量就错误；真正需要关注的是每个 Block 工作太少时的 Launch/调度开销，以及索引范围。

不要为了满足固定的 2 * SM_count 人为启动没有工作的 Block。对逐元素 Kernel，Grid 应覆盖数据；若任务太小，考虑融合、批处理或 Grid-Stride Loop，并用 Occupancy API/Profiler 判断并行度。

int get_grid_size(int total_elements, int block_size) {
    return (total_elements + block_size - 1) / block_size;
}

选择 blockDim 的经验法则¶

场景 推荐 blockDim 原因
逐元素操作 256 填充 SM，256 线程 = 8 Warps，足够隐藏延迟
归约 (Reduce) 128-256 (1D) 需配合 Shared Memory 大小
矩阵乘 (GEMM) 128-256 (2D Tile) 兼顾 Shared Memory 占用和 Occupancy
Softmax 256-512 每个线程处理多个通道，线程多可加速
卷积 (16, 16) 或 (32, 32) 2D 模式匹配数据局部性

关键认知¶

"AI Kernel 的 Launch 配置，就是你写 Compute Shader 时算 dispatch 维度的同一个公式，只是把从编译时搬到了运行时。"

图形 (固定尺寸) AI (动态形状)
Dispatch(1920/8, 1080/8, 1) 编译时确定 grid = (total + block - 1) / block 运行时计算
Render Target 尺寸从不变化 Batch Size、Seq Len 每帧都可能变
你写死 [numthreads(8,8,1)] 你选一个 blockDim（通常 256）做基准，然后算 gridDim
本质相同：都是根据数据尺寸，在 CPU 端计算出 GPU 需要启动多少个线程块，然后一次性提交给 GPU。

你现在已经完全掌握了 CUDA 线程模型的映射——它和你写 Compute Shader 时的调度思维，完全是一回事。
