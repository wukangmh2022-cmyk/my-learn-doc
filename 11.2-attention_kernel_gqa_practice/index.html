11.2 Attention Kernel 实战：QK、Softmax、PV 与 GQA¶

这篇要带你走到哪¶

如果你已经知道 Attention 的公式，也知道 FlashAttention「很快」，但一直没搞明白：

  • 为什么 Decode 阶段的 Attention 值得单独写一个 Kernel，用 cuBLAS 拼三步不行吗？
  • Online Softmax 里那个 \(\alpha\) 校正因子到底是从哪冒出来的？
  • GQA 说「省显存」，到底省了多少？它对 Kernel 写法有什么影响？
  • 融合是不是越彻底越好？

那这篇就是写给你的。我们从一个 Head 的标量公式出发，一路推到融合 Kernel，中间每加一个机制，都先回答「不加会怎样」。

全篇聚焦 Decode：每条序列只有 1 个 Query Token，历史 K/V 全部来自 KV Cache。Prefill（一次进来几千个 Token）请直接用成熟的 FlashAttention 后端 —— 后面会讲为什么 Decode 特化的 Kernel 不能硬套到大 Query Length 上。

一、先搞清楚：Decode Attention 到底卡在哪¶

在写任何一行 Kernel 之前，先做一件事：判断这个算子是算力受限还是访存受限。判错了，后面所有优化都会用错力气。

1. 算一笔账¶

Decode 一个 Token 时，对每个 Query Head，我们要做的事是：

  • 拿 1 个长度为 \(D\) 的向量 \(q\)；
  • 和 KV Cache 里 \(T\) 行的 \(k_t\) 各做一次点积；
  • 再和 \(T\) 行的 \(v_t\) 做一次加权求和。

关键在于：每个 K/V 元素只被用一次。读进来一个 half（2 字节），做一次乘加（2 FLOP），然后就再也不用它了。

\[ \text{算术强度} \approx \frac{2\ \text{FLOP}}{2\ \text{Byte}} = 1\ \text{FLOP/Byte} \]

拿 A100 对照：HBM 带宽约 2039 GB/s，FP16 Tensor Core 算力约 312 TFLOPS。它的 Roofline 拐点是

\[ \frac{312 \times 10^{12}}{2039 \times 10^{9}} \approx 153\ \text{FLOP/Byte} \]

我们在 1，拐点在 153。差了两个数量级。

结论很硬：Decode Attention 是彻头彻尾的访存受限算子。这一篇后面所有的优化 —— 融合、Online Softmax、双缓冲、GQA 复用 —— 目标只有一个：少搬字节，别让 SM 干等 HBM。任何「我把 FLOP 减少了 30%」的优化在这里都是零收益。

2. 这笔账有多大¶

具体感受一下规模。假设一个 8B 级别的模型：36 层，\(H_q=32\)，\(H_{kv}=8\)，\(D=128\)，FP16 KV Cache，服务 32 条并发序列、每条上下文 4096 Token。

单层单步要读的 KV 字节数：

\[ B \times H_{kv} \times T \times D \times \underbrace{2}_{K \text{ 和 } V} \times \underbrace{2}_{\text{FP16}} = 32 \times 8 \times 4096 \times 128 \times 2 \times 2 = 512\ \text{MiB} \]

乘 36 层 = 每生成一个 Token，光读 KV Cache 就要搬 18 GiB。在 A100 上打满带宽也要约 9.5 ms —— 这还没算模型权重。

这就是为什么 KV Cache 是 LLM 服务的头号瓶颈，也是为什么 GQA 和 PagedAttention 这两个东西会同时出现在每一个现代推理框架里。

二、把公式手推一遍¶

1. 三步走¶

对一个 Query Head，设：

  • \(q \in \mathbb{R}^{D}\)，当前 Token 的 Query 向量；
  • \(K, V \in \mathbb{R}^{T \times D}\)，来自 KV Cache 的历史；
  • \(D\) 是 Head Size（常见 64/80/128）；
  • \(T\) 是 Context Length。

第一步，算 Score（QK）：

\[ s_t = \frac{q \cdot k_t}{\sqrt{D}} \]

为什么要除 \(\sqrt{D}\)？ 因为 \(q \cdot k_t\) 是 \(D\) 项的和。如果各分量近似独立、方差为 1，那么点积的方差就是 \(D\)，标准差是 \(\sqrt{D}\)。\(D=128\) 时，Score 的典型量级就被放大到 \(\pm 11\) 左右。这么大的输入喂给 Softmax，指数会把差距极度放大，输出几乎变成 One-hot，数值也不好看。除以 \(\sqrt{D}\) 把方差拉回 1，是个纯粹的量纲修正。

第二步，Softmax：

\[ m = \max_t s_t, \qquad p_t = \frac{e^{s_t - m}}{\sum_j e^{s_j - m}} \]

第三步，加权求和（PV）：

\[ o_d = \sum_{t=0}^{T-1} p_t\, v_{t,d} \]

数据流长这样：

flowchart LR
    Q["Q: D"] --> DOT["QK Dot"]
    K["K: T x D"] --> DOT
    DOT --> SCORE["Scores: T"]
    SCORE --> MAX["Row Max"]
    MAX --> EXP["Exp + Row Sum"]
    EXP --> PROB["Probabilities: T"]
    PROB --> PV["PV Reduction"]
    V["V: T x D"] --> PV
    PV --> O["Output: D"]

图里那两个中间态 —— Scores[T] 和 Probabilities[T] —— 是这篇文章的主角。朴素实现会把它们写回 HBM 再读回来；融合的全部意义就是让它们死在片上。 记住这条主线，后面每一步都是它的展开。

2. 为什么必须先减最大值¶

课本上写「减去最大值是为了数值稳定」，但不给数字，读者只能当口诀背。我们来算一次。

\(e^x\) 溢出的临界点，就是 \(x = \ln(\text{该精度的最大可表示值})\)：

精度 最大可表示值 \(e^x\) 溢出临界 \(x\)
FP32 \(3.40 \times 10^{38}\) 88.7
FP16 \(65504\) 11.1

FP32 的 88.7 看起来很安全 —— 训练好的模型 Logit 一般到不了 90。但注意 FP16 那一行：只要有一个 Score 超过 11.1，exp 出来就是 inf。而我们刚才算过，\(D=128\) 时 Score 的典型标准差就在 11 附近。也就是说，不减最大值、又用 FP16 存中间结果，溢出不是小概率事件，是日常事件。

一旦某个 \(e^{s_t}\) 变成 inf：

  1. 分母 \(\sum_j e^{s_j}\) 也是 inf；
  2. 那一项算出 inf / inf = NaN；
  3. NaN 乘任何 \(v\) 还是 NaN，累加进输出，整个 Head 的输出全废；
  4. 下一层继续传播，最后你看到模型输出一堆乱码，却完全定位不到是哪一层坏的。

减掉最大值之后：

  • 最大的那一项变成 \(e^0 = 1\)，不可能溢出；
  • 其他项都是 \(e^{\text{负数}}\)，落在 \((0, 1]\)，最差是下溢成 0 —— 下溢只是丢掉一个本来就微不足道的权重，无害；
  • 分母至少包含那个 1，所以分母恒 \(\ge 1\)，不可能除零。

而且这个保险是免费的。因为分子分母同乘了 \(e^{-m}\)：

\[ \frac{e^{s_t - m}}{\sum_j e^{s_j - m}} = \frac{e^{-m} \cdot e^{s_t}}{e^{-m} \cdot \sum_j e^{s_j}} = \frac{e^{s_t}}{\sum_j e^{s_j}} \]

和原公式完全等价，不是近似。所以业界不存在「要不要减 Max」的讨论 —— 只有「怎么在只扫一遍数据的前提下拿到 Max」的讨论。这正好引出第七节的 Online Softmax。

三、CPU Reference：你唯一的真理来源¶

写 GPU Kernel 时最痛苦的场景不是「慢」，是「结果不对，但不知道哪一步不对」。解法是先写一份慢到离谱但绝对正确的 CPU 版本。

void attention_ref(
    const float* q,
    const float* k,
    const float* v,
    float* out,
    int context_len,
    int head_size)
{
    std::vector<float> scores(context_len);
    const float scale = 1.0f / std::sqrt(static_cast<float>(head_size));

    // ---- 第一步：QK，顺便记录 row max ----
    float row_max = -std::numeric_limits<float>::infinity();
    for (int t = 0; t < context_len; ++t) {
        float dot = 0.0f;
        for (int d = 0; d < head_size; ++d)
            dot += q[d] * k[t * head_size + d];
        scores[t] = dot * scale;
        row_max = std::max(row_max, scores[t]);
    }

    // ---- 第二步：减 max、取指数、求和 ----
    float denominator = 0.0f;
    for (float& score : scores) {
        score = std::exp(score - row_max);   // 原地覆盖成未归一化权重
        denominator += score;
    }

    // ---- 第三步：PV 加权求和 ----
    std::fill(out, out + head_size, 0.0f);
    for (int t = 0; t < context_len; ++t) {
        const float probability = scores[t] / denominator;
        for (int d = 0; d < head_size; ++d)
            out[d] += probability * v[t * head_size + d];
    }
}

这份代码有三个刻意的选择，都不是随手写的：

  1. 全程 FP32，哪怕 GPU 上跑的是 FP16。 Reference 的职责是给出「数学上的正确答案」，让 GPU 版本有个基准去比对误差。如果 Reference 也用 FP16，你就分不清误差是来自精度还是来自 Bug。

  2. 结构完全照抄数学定义，不做任何优化。 不要在 Reference 里写 Online Softmax，也不要分块。一旦 Reference 和 GPU 版本用了同一套「聪明」结构，同一个逻辑错误会在两边同时出现，比对就永远通过 —— 这是最危险的假阳性。Reference 要笨，笨到一眼能看出它就是公式本身。

  3. scores 数组被原地复用了三次（先存 Score、再存 \(e^{s-m}\)、最后除以分母）。这在 Reference 里可以，因为它只求可读；但正是这个「必须留着一整个 [T] 数组」的特征，是 GPU 上要干掉的东西。

测试用例：每一个都在抓一类特定的 Bug¶

别把测试写成「跑一遍随机数据」。下面每一条都对应一个真实会犯的错：

用例 它专门抓什么 Bug
\(T = 1\) 只有一个 Token 时输出必须精确等于 \(v_0\)。抓「分母算错」「Max 初值写成 0 而不是 \(-\infty\)」
\(T\) 不是 2 的幂（如 4095） 抓 Tile 尾部越界、归约树补零补错
\(T\) = 最大 Context Length 抓索引整型溢出、Shared Memory 超限
随机极大 Logit（人为塞 \(s=100\)） 抓有没有真的减 Max。不减的话这里必出 inf/NaN
全部 Score 相等 输出应是所有 \(v_t\) 的均值。抓 Max/Sum 归约的对称性错误
FP16/BF16 输入 vs FP32 Reference 确立误差阈值基线，后面所有优化都跟这个阈值比

误差判据要同时看 max_abs 和 max_rel —— 只看平均误差，会让个别彻底错掉的元素被淹没在几千个正确元素里。

四、GQA：先看它省了什么，再看它给 Kernel 带来什么¶

1. 从显存账切入¶

MHA（Multi-Head Attention）里 Q、K、V 的 Head 数相同。GQA（Grouped-Query Attention）让多个 Query Head 共享同一个 KV Head。

回到第一节那个模型：36 层、\(D=128\)、FP16、\(H_q = 32\)。

每个 Token 每层的 KV Cache 字节数 = \(2 \times H_{kv} \times D \times 2\)：

方案 \(H_{kv}\) 每 Token 每层 每 Token 全模型 32 序列 × 4096 上下文
MHA 32 16 KiB 576 KiB 72 GiB
GQA (group=4) 8 4 KiB 144 KiB 18 GiB
MQA 1 0.5 KiB 18 KiB 2.25 GiB

72 GiB —— 一张 80GB A100 装不下模型权重之外的这堆缓存。GQA 不是「优化」，是让这个 Batch 能跑起来的前提。

不过要说清楚边界：这个 4× 是 KV Head 维度上的理论缩减。实际显存还包含 Block Padding、Allocator 元数据、对齐开销和其他模型状态，所以不能说「整个推理显存缩到四分之一」。说「KV Cache 这一项是 4×」才准确。

2. Head 映射¶

记 \(G\) 为组大小、\(h\) 为 Query Head 编号：

\[ G = \frac{H_q}{H_{kv}}, \qquad \text{kvHead}(h) = \left\lfloor \frac{h}{G} \right\rfloor \]

例如 \(H_q=16\)、\(H_{kv}=2\)，每 8 个 Query Head 共用一个 KV Head：

Query Head KV Head
0 – 7 0
8 – 15 1

映射本身只有一行整数除法。真正需要动脑的是：既然同组的 Query Head 读的是同一份 K/V，我们能不能只读一次？

3. GQA 给 Kernel 的机会（和陷阱）¶

回到第一节的结论：这是个访存受限算子。如果 4 个 Query Head 各自去读同一份 K/V，那同样的字节被搬了 4 遍，算术强度还是 1；如果让一个 CTA 同时处理这 4 个 Head，K/V Tile 读一次用 4 次，算术强度就变成 4。

在一个访存受限的算子里，把有效带宽利用率翻 4 倍，这是免费午餐里最大的一块。

但代价是片上资源：一个 CTA 现在要同时持有 4 个 Head 的 \(q\)、4 份运行状态（\(m\)、\(l\)、\(o\)）。\(o\) 是 \(D\) 维的，4 个 Head 就是 \(4 \times 128 = 512\) 个 FP32 累加器，分摊到 128 个线程是每线程 4 个 —— 还行；但如果 \(G = 8\)、\(D = 256\)，就顶不住了，编译器会 Spill 到 Local Memory（其实就是 HBM），性能直接崩盘。

所以三种映射各有适用区间：

CTA 映射 优点 风险 什么时候选
一个 CTA = 一个 Q Head 实现简单，CTA 数量多，Occupancy 好 同组 KV 被重复读，只能指望 L2 Cache 兜底 \(G\) 小，或 Batch 很大、CTA 已经足够多
一个 CTA = 一整组 Q Head KV Tile 显式复用，带宽利用率 × \(G\) 寄存器 / SMem 压力最大，CTA 数量少可能喂不饱 SM \(G\) 适中（2–4）、\(D \le 128\)
一个 CTA = 组内部分 Q Head 在复用和 Occupancy 之间折中 需要为每种 Shape 调参 热点 Shape 固定，值得特化

注意第一行那句「只能指望 L2 兜底」：L2 确实可能帮你命中，但那是被动的、不可控的。当 Batch 大、KV 总量远超 L2（A100 是 40 MB）时，重复读就是实打实的 HBM 流量。能显式复用就别赌 Cache —— 这条原则在图形里也一样，你不会指望纹理 Cache 帮你省掉一次本可以合并的采样。

五、先写三 Kernel 基线（真的别跳过）¶

融合 Kernel 一旦写错，症状是「最终输出偏了一点点」，而错误可能在 QK、可能在 Max、可能在 \(\alpha\) 校正、可能在 PV 累加。四个嫌疑人，没有目击证人。

三 Kernel 基线的价值就是制造目击证人：每一步的中间结果都在显存里躺着，可以逐个和 CPU Reference 对。

Kernel A：QK¶

Grid 按 [context_tile, q_head, batch] 组织，每个 CTA 负责一个 Q Head 的一段 K：

// 伪 CUDA，只表达线程映射，省略了边界检查
__global__ void qk_kernel(
    const half* q, const half* k, float* scores,
    int context_len, int head_size)
{
    int token  = blockIdx.x;   // 这个 CTA 负责第几个 K token
    int q_head = blockIdx.y;

    // 每个线程沿 D 维跨步累加自己那一份
    float partial = 0.0f;
    for (int d = threadIdx.x; d < head_size; d += blockDim.x)
        partial += __half2float(q[q_head * head_size + d])
                 * __half2float(k[(token * num_kv_heads + kv_head(q_head)) * head_size + d]);

    // CTA 内归约，把 D 维的分片和加起来
    float dot = block_reduce_sum(partial);

    if (threadIdx.x == 0)
        scores[q_head * context_len + token] = dot * rsqrtf(float(head_size));
}

几个值得停下来看的点：

  • 累加器是 float，输入是 half。 这是所有 GPU 归约的标配：输入用低精度省带宽，累加用高精度防误差堆积。\(D=128\) 项相加，FP16 累加的相对误差会肉眼可见。
  • kv_head(q_head) 就是 GQA 的那行整数除法，它决定了访存地址 —— 这一个函数就是 MHA / GQA / MQA 的全部区别。
  • for (d = threadIdx.x; d < head_size; d += blockDim.x) 这个跨步循环保证相邻线程读相邻地址，即访存合并（Coalescing）。如果写成 d = threadIdx.x * items_per_thread 让每个线程读一段连续区间，反而破坏合并 —— 这是新手最常踩的坑。

Kernel B：Row-wise Softmax¶

每个 CTA 处理一行 Score（长度 \(T\)）：先归约求 Max，__syncthreads()，再归约求 \(\sum e^{s-m}\)。

两次归约、一次同步，绕不开 —— 因为要减的 Max 必须在看完整行之后才知道。这个「必须扫两遍」正是第七节要破的局。

Kernel C：PV¶

每个 CTA 处理一个输出 Head，沿 Context 维归约 \(p_t \cdot v_t\)。输出的 \(D\) 维映射到 Warp Lane：Lane \(d\) 负责累加 \(o_d\)，这样每个线程持有一个独立累加器，不需要跨线程归约，只需要沿 \(T\) 循环。

基线要验收什么¶

跑完三个 Kernel，逐个拷回来和 CPU Reference 比：

  • scores 对不上 → 问题在 QK 的映射或 GQA 索引；
  • scores 对、probs 不对 → 问题在 Softmax 的归约或减 Max；
  • 前两个都对、out 不对 → 问题在 PV 的累加或 \(D\) 维映射。

三次比对把四个嫌疑人筛成一个。 这半小时省下的是后面三天的调试。

六、融合第一步：把 Row Max 吃进 QK¶

三 Kernel 版本里，Kernel A 刚刚算完每个 Score，转手就把它写回显存；Kernel B 再把整行读回来只为了找最大值。这一读一写完全是浪费 —— Max 完全可以在 Score 产生的那一刻顺手更新。

running_max = -inf
for each KV tile:
    scores_tile = Q dot K_tile
    running_max = max(running_max, max(scores_tile))

代价是零：max 是一条指令，而且 Score 本来就在寄存器里。

但要诚实地说清楚这一步的收益边界：如果你仍然把完整的 Score 写回显存，那这只是省掉了 Kernel B 的一次读遍历（约 \(T \times 4\) 字节）外加一次 Kernel Launch。有收益，但不大。

真正的大头在下一节：如果连 Score 都不必形成全局 Buffer，那这一整条数据通路都消失了。

七、融合第二步：Online Softmax（本篇核心）¶

1. 死结在哪¶

想把 Score 留在片上，就必须分块处理 KV（\(T\) 可能是几万，塞不进 Shared Memory）。但一分块就撞上一个死结：

Softmax 的分母需要所有 Score，而分块意味着你一次只能看到一部分。

传统解法是扫两遍：第一遍找全局 Max 和全局 Sum，第二遍算权重。但那意味着 KV Cache 要从 HBM 读两次 —— 在一个访存受限的算子里，这等于直接把性能砍半。

Online Softmax 的思路是：先按当前已知的 Max 算，等 Max 变了再回头修正。而修正的代价，恰好是一次乘法。

2. 推导 \(\alpha\)¶

维护三个运行状态（都是「相对于当前 \(m\)」的量）：

  • \(m\)：目前见过的最大 Score；
  • \(l\)：目前的分母，\(l = \sum_{i \in \text{seen}} e^{s_i - m}\)；
  • \(o\)：目前的未归一化输出，\(o = \sum_{i \in \text{seen}} e^{s_i - m} v_i\)。

现在来了新的一块，把最大值推到了 \(m' = \max(m, \max s_{\text{tile}})\)。旧的 \(l\) 和 \(o\) 是以 \(m\) 为基准算的，必须换基准。

关键的一步代数，就是指数的加法性质：

\[ e^{s_i - m'} = e^{(s_i - m) + (m - m')} = e^{s_i - m} \cdot e^{m - m'} \]

注意 \(e^{m - m'}\) 里不含 \(i\) —— 它对已见过的每一项都一样。所以它能从求和号里提出来：

\[ \sum_{i \in \text{seen}} e^{s_i - m'} = \underbrace{e^{m - m'}}_{\text{记作 } \alpha} \cdot \sum_{i \in \text{seen}} e^{s_i - m} = \alpha \cdot l \]

同一个提取对 \(o\) 也成立，因为 \(o\) 只是同一组指数项各自加了权重 \(v_i\)：

\[ \sum_{i \in \text{seen}} e^{s_i - m'} v_i = \alpha \cdot \sum_{i \in \text{seen}} e^{s_i - m} v_i = \alpha \cdot o \]

这就回答了开头那个问题 —— 为什么 \(l\) 和 \(o\) 要乘同一个 \(\alpha\)？ 因为 \(\alpha\) 是从同一个求和式里提出来的公因子，\(l\) 和 \(o\) 只是这个求和式的两种加权形式。它们共享同一个基准，换基准当然用同一个因子。

于是每来一块，更新规则是：

\[ m' = \max(m,\ \max_i s_i), \qquad \alpha = e^{m - m'} \]
\[ l' = \alpha\, l + \sum_i e^{s_i - m'}, \qquad o' = \alpha\, o + \sum_i e^{s_i - m'} v_i \]

处理完所有块后，最后才做一次除法：

\[ \text{output} = \frac{o}{l} \]

3. 三个容易被忽略的性质¶

\(\alpha\) 永远 \(\le 1\)。 因为 \(m' \ge m\)，所以 \(m - m' \le 0\)，\(\alpha = e^{\text{非正数}} \in (0, 1]\)。这意味着校正永远是在缩小旧状态，绝不可能放大成溢出。当新块带来一个远大于历史的 Score 时，\(\alpha\) 会非常接近 0 —— 那是数学上正确的行为：旧的那些 Token 在新的尺度下确实微不足道。

归一化只做一次。 中间过程一直用未归一化的 \(o\) 和 \(l\)，直到最后才相除。如果你每块都归一化一次，下一块又要反归一化回去，纯属自找麻烦（还多引入舍入误差）。

它和标准 Softmax 数学上完全等价。 不是近似、不是 trade-off。FlashAttention 之所以能在 Prefill 上做同样的事，靠的就是这个恒等式（见 6.4 FlashAttention）。这里的 Decode 版本是它 \(Q\) 只有一行时的特例。

4. 落到代码¶

float running_max  = -INFINITY;
float denominator  = 0.0f;
// output_fragment 是 D 维的 FP32 累加器，全程留在寄存器里
zero(output_fragment);

for (int tile = 0; tile < num_tiles; ++tile) {
    load_kv_tile_async(tile);          // 见第八节：这里可以和上一块的计算重叠
    wait_for_kv_tile();

    // ---- 算这一块的 Score ----
    compute_scores(q_fragment, k_tile, score_fragment);

    // ---- 更新基准，算出校正因子 ----
    float new_max    = max(running_max, reduce_max(score_fragment));
    float correction = expf(running_max - new_max);     // 这就是 alpha，恒 <= 1

    // ---- 把旧状态换算到新基准上 ----
    denominator     *= correction;
    output_fragment *= correction;

    // ---- 把这一块累加进来 ----
    for (int i = 0; i < valid_tokens_in_tile; ++i) {    // 注意是 valid，不是 TILE_SIZE
        float weight = expf(score_fragment[i] - new_max);
        denominator     += weight;
        output_fragment += weight * v_tile[i];
    }

    running_max = new_max;
}

output_fragment /= denominator;        // 全程唯一一次归一化

逐段说明：

  • correction 必须在更新 running_max 之前算，它用的是旧 running_max。这里写反了是最常见的 Bug，而且症状很阴险：输出只是「偏了一点」，随机数据下可能勉强过阈值，长上下文才暴露。
  • 两行 *= correction 的先后无所谓，但一个都不能漏。 只校正 denominator 不校正 output_fragment，得到的结果依然「看起来像个概率分布」，误差却是系统性的。
  • valid_tokens_in_tile 而不是 TILE_SIZE。 最后一块几乎总是不满的。多算的那几个位置如果是未初始化显存，exp 出来可能是任意大的数，直接污染 \(m\) 和 \(l\)。这是长上下文才复现、随机 Shape 才复现的经典越界 Bug。
  • 循环内两次用到 new_max：一次算 correction，一次算 weight。它俩指的是同一个新基准，不能一个用新一个用旧。

5. 融合不是越彻底越好¶

output_fragment 是 \(D\) 维 FP32。如果一个 CTA 按第四节的建议同时处理 \(G\) 个 Q Head，累加器需求是：

\[ \text{每 CTA 累加器数} = G \times D \]

\(G = 4\)、\(D = 128\) → 512 个 FP32。看着不多；但还要加上 \(q\) 的暂存、Score Fragment、地址计算的临时变量。一旦超出每线程 255 寄存器的硬上限，编译器会 Spill 到 Local Memory —— 而 Local Memory 物理上就是 HBM。你为了省 HBM 流量做的融合，最后把状态 Spill 回了 HBM，净效果是负的。

怎么判断你踩到了？ Nsight Compute 的 Launch Statistics 里看 Registers Per Thread，Memory Workload 里看 Local Load/Store 是否非零。有 Local 流量就说明 Spill 了，要么减 \(G\)，要么减 Warp 数，要么把 \(o\) 挪到 Shared Memory。

这就是「融合要有边界」的具体含义：融合的收益是省掉 HBM 往返，代价是片上资源压力。当代价超过收益，就该停。 判断依据是 Profiler，不是直觉。

八、让搬运藏在计算后面¶

到这里数据通路已经很干净了，但还有一个空转问题：Kernel 现在的节奏是「读一块 → 算一块 → 读一块 → 算一块」，读的时候 SM 在等，算的时候搬运单元在闲。

双缓冲把这两条路重叠起来：

stage 0:                 load tile 0
stage 1: compute tile 0 | load tile 1
stage 2: compute tile 1 | load tile 2
...

CUDA 上的实现手段是 cp.async（Ampere 及以后）或 TMA（Hopper 及以后），也可以用框架封装的异步 Copy；换到别的加速器上则可能对应 DMA 引擎或专用搬运指令。

但异步 API 只是「允许」重叠，不等于「发生」重叠。 下面五条任何一条不成立，你写的异步代码就是同步代码套了层皮：

  1. Copy 和 Compute 走的是不同硬件路径。 cp.async 绕过寄存器直接 Global → Shared，才有独立性；用普通 ld.global 加载再存 Shared，就是占着 LSU 的同步操作。
  2. Buffer 真的是双份，且没有覆盖仍在使用的数据。 单个 Buffer 上写 cp.async 是自欺欺人 —— 硬件必须等你算完才能覆盖。
  3. Commit / Wait 的位置正确。 Wait 放太早等于退化成同步；放太晚就是读到脏数据。
  4. 一块的计算量足以盖住一次加载的延迟。 Tile 太小，计算几微秒就结束了，搬运还没回来，重叠没意义。这是个需要实测扫参的量。
  5. Nsight Systems 的时间线上真的能看到两条重叠的带。 这是唯一的判据。

第五条不是废话。异步这件事上，「我按文档写了」和「它真的重叠了」之间的距离，比大多数人以为的远得多 —— 这和图形里 Async Compute 队列的情况完全一样：你把工作丢进 Compute Queue，不代表它真的和 Graphics Queue 并行了，得看 GPU Trace 才算数。

关于并发与重叠的完整讨论见 4.3 异步流水线。

九、Shape 特化：什么时候值得，什么时候是负担¶

一个通用 Kernel 必须在运行时处理任意 head_size、任意 Context Length、多种数据类型和对齐情况。这意味着：循环边界是变量（编译器无法展开）、分支要在运行时判断、寄存器要按最坏情况分配。

特化就是把这些条件变成编译期常量：

template<int HEAD_SIZE, int KV_TILE, int WARPS>
__global__ void decode_attention_specialized(...);

编译器立刻能做三件它之前做不到的事：完全展开循环（消除循环开销和分支）、把索引计算折叠成立即数、精确分配寄存器（不用按最坏情况留余量）。在一个 Kernel 只跑几十微秒的场景里，这些「开销」占比不低。

可特化的维度：

  • HEAD_SIZE：64 / 80 / 96 / 128 / 256（模型定死的，最值得特化）
  • Context Length 的上限或分桶
  • 组大小 \(G = H_q / H_{kv}\)
  • KV Cache 的数据类型：FP16 / BF16 / FP8
  • Block Size 与内存对齐
  • 是否有 Attention Mask / Sliding Window / ALiBi

但特化有实打实的成本：每多一个组合，编译时间、二进制体积、测试矩阵都要乘一遍。8 个 HEAD_SIZE × 3 个 KV_TILE × 2 个 dtype = 48 份 Kernel，编译几分钟，二进制几十 MB，而其中可能 44 份一年都不会被调用一次。

所以正确做法是：先测出真实流量里的 Shape 分布，只特化头部那几个，其余全部回退到通用实现。 Dispatch 层负责选最小覆盖的 Kernel，没命中就走通用路径 —— 慢一点，但对。

这也解释了开篇那句「Decode Kernel 别硬套到 Prefill 上」：Decode 特化 Kernel 的整个设计前提是 \(Q\) 只有一行，所以 \(o\)、\(m\)、\(l\) 都是单行状态、可以全放寄存器。Prefill 时 \(Q\) 有几千行，这些状态变成矩阵，寄存器方案直接崩溃 —— 那是 FlashAttention 的地盘，它的分块是二维的。不是「调调参就能通用」，是两套不同的算法结构。

十、怎么证明你做对了¶

1. 正确性¶

按第五节建立的分阶段比对，加上第三节的测试用例矩阵。融合版没有中间 Buffer 可比了，所以要留调试开关：写 Kernel 时加一个 #ifdef DUMP_INTERMEDIATE，调试构建下把每块的 \(m\)、\(l\) 落盘，和 CPU Reference 逐块比。

2. 性能：数字必须绑定上下文¶

一个脱离环境的加速比是没有意义的。任何性能结论都要带上：

GPU 型号 / 驱动 / CUDA 或后端版本
dtype（激活、KV Cache 各自的）
batch size
Hq / Hkv / head_size
context length（是固定值还是分布）
warmup 次数与测量次数、取中位数还是 P90
测量范围：单 Kernel / 单 Decode Step / 端到端
时钟单位与获取方式（CUDA Event / nsys / 墙钟）
正确性误差阈值

比如 32.2k → 13.6k cycles（约 2.37x） 这种数字，只有绑定了上述环境才有意义，不能当成「融合普遍带来 2.3x」来引用。换个 \(T\)、换个 Batch、换代硬件，结论都可能翻转 —— 尤其当 \(T\) 很小时，中间 Buffer 本来就装得进 L2，融合的收益会大幅缩水。

3. 验收清单¶

正确性：

  • [ ] CPU Reference 与三 Kernel 基线逐阶段对齐
  • [ ] MHA（group=1）、GQA（group=4）、MQA（\(H_{kv}\)=1）三种映射都有测试
  • [ ] 人为塞入极大 Logit，Online Softmax 输出无 NaN / inf
  • [ ] \(T\) 不是 Tile 整数倍时结果正确（这条抓 valid_tokens_in_tile）
  • [ ] \(T = 1\) 时输出精确等于 \(v_0\)

性能：

  • [ ] 融合版在 Profiler 里确认没有 Score / Probability 的全局 Buffer 写入
  • [ ] Nsight Compute 的 Local Load/Store 为 0（没有寄存器 Spill）
  • [ ] Nsight Systems 时间线上能看到 Copy 与 Compute 重叠
  • [ ] DRAM Throughput 接近带宽上限 —— 因为这是访存受限算子，这才是真正该盯的目标指标
  • [ ] 每个性能数字都绑定了硬件、Shape、版本和测量范围

十一、如果只记住一句话¶

能在片上立刻消费掉的数据，就不应该先写回 HBM 再读回来。

这一篇里的每一个技巧都是它的推论：

  • Online Softmax 让 Score 不必落盘，因为它一产生就被消费；
  • GQA 的 CTA 分组让 K/V Tile 读一次用多次；
  • 双缓冲让搬运的时间被计算盖住；
  • 而「融合有边界」是这条原则的反面 —— 当片上放不下时，强行留在片上会 Spill 回 HBM，反而更糟。

判断的依据始终是中间结果的生命周期：它下一步会被谁用？用完还需要吗？如果答案是「马上被同一个线程用掉，用完就死」，那它就不该出现在 HBM 里。

这套推理方式，和 6.4 FlashAttention、4.2 Tiling 与局部性、4.3 异步流水线 是同一套。记模板会过时，记这条推理链不会。
