7.2 RT Core：BVH 遍历专用电路

概述

RT Core 是 NVIDIA GPU 中专用于光线追踪的硬件单元。它的核心职责是加速BVH（Bounding Volume Hierarchy，层次包围盒）的遍历和求交计算。

但 RT Core 的设计意义远不止于图形——它完美示范了如何用硬件来解决通用处理器（CUDA Core）上的两大性能杀手：随机访存和分支分歧。这两个问题在 AI 计算中同样存在，因此理解 RT Core 的设计哲学，能帮你理解为什么 AI 领域也在呼唤类似专用硬件。

RT Core 是图形领域的狙击手，只做两件事：光线与 BVH 节点的求交测试 + 光线与三角形的求交测试。它不负责 BVH 的构建、更新、排序——那些全部在 CUDA Core 上完成。

为什么需要专用硬件

问题1：随机访存（Memory Divergence）

光线在 BVH 树中遍历时，访问模式是完全随机的：

  • 每条光线走不同的路径
  • 同一 warp 内 32 条光线，各自访问不同的 BVH 节点
  • Cache Miss 率极高，带宽利用率极低

这对于通用 CUDA Core 来说是一个致命问题——因为 CUDA Core 依赖合并访存来有效利用带宽，而光线的随机跳跃模式完全破坏了合并访问。

问题2：分支分歧（Control Divergence）

在 CUDA Core 上执行 BVH 遍历时，核心逻辑是：

if (ray_hits_bounding_box(node)) {
    traverse_children(node);  // 走 True 分支
} else {
    skip_node(node);          // 走 False 分支
}

同一个 warp 内 32 条光线，有的命中、有的不命中——导致 warp 内部分支分歧，两条分支被串行执行，有效吞吐减半甚至更低。

RT Core 的硬件解决方案

解决方案1：压缩 → 解决随机访存

RT Core 内部使用专用的压缩格式存储 BVH 节点：

  • 用 4 个 16-bit 浮点数代替 3 个 32-bit 浮点数表示包围盒
  • 节点体积压缩到最小
  • 同样大小的 Cache（如 16KB），能装入的节点数量翻倍

效果：Cache 命中率大幅提升，随机访问的延迟被有效降低。

解决方案2：专用电路 → 解决分支分歧

RT Core 内部是固定功能的硬件流水线，不执行通用指令，也不需要 Warp 调度器来判断分支：

  • 它使用硬件状态机来管理 BVH 遍历
  • 每条光线可以独立推进遍历状态，完全不受其他光线的影响
  • 不存在"分支串行化"这个概念——专用电路在物理上就没有分支判断的逻辑
问题 通用方案（CUDA Core） 专用方案（RT Core）
随机访存 依赖 Cache + 合并访问 节点压缩 + 更大有效 Cache 容量
分支分歧 Warp 串行化执行（吞吐减半） 固定功能硬件流水线（无分支概念）

RT Core 用"压缩"解决了随机访存问题（让数据更快到达），用"专用电路"解决了分支串行化问题（让判断不消耗算力）。两者合在一起，让光线追踪从"CUDA Core 勉强能跑"变成了"RT Core 跑得飞快"。

RT Core 与 BVH 的完整分工

RT Core 只是"执行者"，不是"建造者"：

任务 执行硬件
BVH 构建（Morton 码生成、基数排序） CUDA Core
BVH 树划分、AABB 计算、重平衡 CUDA Core
动态场景 BVH 增量更新（Refit/Rebuild） CUDA Core
光线与 BVH 节点求交（遍历加速结构） RT Core
光线与三角形求交（精确命中检测） RT Core

类比你的图形管线知识：

CUDA Core = 负责 BVH 构建的 Compute Shader（预处理阶段）
RT Core   = 负责光线遍历的固定功能硬件（同 ROP/TMU，只做单一操作）

图形到 AI 的映射：RT Core ≈ Attention 硬件

这里有一个极具启发性的类比：RT Core 解决的问题，和 Transformer Attention 机制面临的问题，本质上是同一类问题。

Attention 的两大难题

难题 在 BVH 遍历中 在 Attention 中
不规则访存 每条光线随机访问不同的 BVH 节点 每个 Query 随机访问不同的 Key/Value（尤其是稀疏 Attention）
分支分歧 不同光线走不同的遍历路径 不同 Query 关心不同的 Token 位置

这两大问题，正是为什么 Attention 计算无法被简单地"Tensor Core 化"的原因。

为什么 AI 还没有"Attention Core"

原因 说明
Attention 模式仍在演化 从 Full Attention 到 Sparse Attention、Sliding Window、FlashAttention，算法还没收敛到固定模式
市场需求不够大 相比矩阵乘（GEMM）占 AI 计算的绝对多数，Attention 在整体算力需求中占比小
硬件成本高 专用电路需要大量晶体管，NVIDIA 在 RT Core 上付出的芯片面积是巨大的
现有方案足够好 FlashAttention 等软件优化方案已经在很大程度上缓解了 Attention 的访存瓶颈

但趋势是明确的：随着 AI 模型规模持续增长，Attention 计算正在成为新的瓶颈。 未来出现专门的"Attention 加速硬件"并非不可能——事实上，NVIDIA 的 Transformer Engine 和某些稀疏计算加速器已经在向这个方向演进。

RT Core 设计的第一性原理启示

RT Core 的设计哲学可以被提炼为通用的硬件加速决策框架：

硬件加速的触发条件：
1. 任务模式是否固化？（BVH 遍历已固化 → 是）
2. 是否同时存在不规则访存 + 分支分歧？（光线追踪 → 是）
3. 任务体量是否足够大？（实时光线追踪 → 是）
4. 通用处理器是否能高效处理？（CUDA Core → 否，串行化严重）

当四个条件都满足时，专用硬件就是值得的。

当前 Attention 满足条件 2、3、4，但还不完全满足条件 1——这正是为什么我们没有"Attention Core"的根本原因。

前沿拓展

静态 vs 动态场景

  • 静态场景：BVH 一次构建，每帧复用。性能瓶颈在光线遍历，RT Core 完美胜任。
  • 动态场景：瓶颈转为每帧更新 BVH（尤其是蒙皮网格），RT Core 不动，CUDA Core 在处理更新。NVIDIA RTX Mega Geometry 技术通过重用拓扑相同的"集群模板"来加速更新。

学术界探索

技术 核心思想 理论加速比
UBVH（统一 BVH） 用倾斜有向包围盒统一表示内部节点和叶子节点，无需切换求交逻辑 最高 11.8 倍
BMA（概率采样框架） 利用相邻像素光线路径相似性，从更深公共祖先节点开始遍历 约 150%

关键结论

  1. RT Core 只做两件事：光线与 BVH 节点求交 + 光线与三角形求交。不负责 BVH 构建、排序、更新。
  2. 两个核心问题：随机访存（用压缩解决）+ 分支分歧（用专用电路解决）。
  3. 图形类比：RT Core 好比光栅化管线中的固定功能单元（如 ROP/TMU），只做单一操作但做得极快。
  4. AI 类比：RT Core 解决的两大难题——不规则访存和分支分歧——在 Transformer Attention 中同样存在。
  5. 为何没有"Attention Core"：Attention 算法仍在演化，模式未固化，且软件优化当前足够应对。
