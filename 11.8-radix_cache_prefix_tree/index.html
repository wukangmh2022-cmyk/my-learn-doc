11.8 Radix Cache：从块级前缀复用到 token 级前缀树¶

11.1 那节留下的坑¶

在 11.1 第五节 里，我们实现了 vLLM 风格的 Prefix Cache：把 KV Cache 按 block_size 切块，每块用链式哈希做内容寻址，命中就共享物理页。

它工作得很好，但有一个当时被跳过的问题：

哈希表只能告诉你「这个块在不在」，不能告诉你「这些块之间是什么关系」。

这句话在单轮问答场景里无关紧要，但在下面这几个场景里，它会变成一个真实的架构缺陷。

这一篇讲 SGLang 的 RadixAttention 用什么数据结构解决它，以及它真正的收益在哪、不在哪——后面这半句同样重要，因为 Radix Cache 被吹得有点过。

前置：11.1 第五节（块级 Prefix Cache）、11.3（分页 KV Cache）。这一篇假设你已经理解「物理页 + 引用计数 + 延迟回收」这套东西。

一、块级哈希在哪里不够用¶

先说清楚：块级哈希不是不能做前缀复用，它做得挺好。 链式哈希逐块往下匹配，能正确找到最长的公共块前缀。所以下面这三个问题不是「完全做不到」，而是「做得别扭或者做不好」。

场景 1：分叉点落在块内部¶

块大小 16，两条请求：

S0: [... 前 512 个 token 完全相同 ...][t512, t513, t514, A, ...]
S1: [... 前 512 个 token 完全相同 ...][t512, t513, t514, B, ...]
                                                        ↑ 第 515 个 token 开始不同

块级哈希能命中前 32 个整块（512 个 token），第 33 块因为内容不同而失配。但那一块里其实还有 3 个 token（t512、t513、t514）是相同的，它们的 K/V 被白算了。

平均而言，每次分叉会浪费 \(\frac{B-1}{2}\) 个 token 的重复计算。\(B=16\) 时是 7.5 个。

单看这个数字，说实话——不大。前缀 512 个 token 里浪费 7.5 个，1.5%。所以如果有人告诉你「Radix Cache 比块级 Prefix Cache 快很多，因为粒度更细」，这个理由站不住。

真正的问题在下面两个。

场景 2：多轮对话的树形结构¶

一个 Agent 或者聊天应用，对话是这样长的：

系统提示词 (2000 token)
    ├── 用户问 A ── 助手答 A ── 用户追问 A1 ── ...
    ├── 用户问 B ── 助手答 B ── 用户追问 B1 ── ...
    └── 用户问 C ── ...

这天然就是一棵树。 所有会话共享系统提示词，同一个会话的不同轮次共享历史。

用哈希表存这个结构，你会遇到一个具体的麻烦：显存不够要淘汰的时候，你不知道该淘汰谁。

哈希表里躺着一万个块，每个块只知道自己的 hash 和 token 内容。你想淘汰最久没用的那个——但如果它是「系统提示词的第 3 块」，淘汰它意味着所有以它为前缀的后续块全部失效（因为链式哈希的 parent_hash 断了）。你砍掉了树根，整棵子树跟着废掉。

而哈希表没有任何办法让你知道这件事，除非你额外维护父子关系——那你其实就是在实现一棵树了。

场景 3：Beam Search / Tree-of-Thought / 并行采样¶

prompt ──┬── 候选分支 1
         ├── 候选分支 2
         └── 候选分支 3

这些场景里「共享前缀 + 多路分叉」不是偶然，是算法本身的结构。用树来表示，插入和淘汰都是自然操作；用哈希表表示，每次分支都要重新走一遍链式哈希查找。

小结：Radix Tree 真正买到了什么¶

块级哈希（vLLM） Radix Tree（SGLang）
匹配粒度 block_size 1 个 token
匹配方式 \(N\) 次哈希查找 + \(N\) 次 token 比较 一次树遍历
知道谁是谁的前缀 ❌ 不知道 ✅ 父子关系显式存在
淘汰能否保证正确 需要额外机制 ✅ 叶子优先天然正确
实现复杂度 低 中（要处理节点分裂）

一句话：Radix Tree 的核心价值不是「粒度更细」，是「共享结构被显式表达出来了」，所以淘汰策略能做对。

二、Radix Tree 是什么¶

1. 从 Trie 说起¶

最朴素的前缀树（Trie）每条边存一个 token：

        root
       /    \
    [你]    [今]
      |       |
    [好]    [天]
      |       |
    [世]    [天]

问题很明显：一个 2000 token 的系统提示词会变成 2000 个节点，每个节点只存一个 token。指针的开销比数据还大。

2. 压缩：一条边存一整段¶

Radix Tree（也叫 PATRICIA Trie、压缩前缀树）的改进是：把「只有一个孩子」的链路压成一条边。

        root
       /     \
[你好世界...]  [今天天气...]      ← 一条边存几百上千个 token
      |
   [分叉后的内容]

于是：

  • 没有分叉的地方，一个节点搞定（系统提示词 2000 个 token = 1 个节点）；
  • 分叉的地方才产生新节点，节点数正比于「有多少个不同的对话分支」，而不是 token 总数。

这个结构和 Linux 内核的路由表（IP 前缀匹配）、Redis 的 rax、文件系统的路径树是同一个东西。

3. 节点里存什么¶

class TreeNode:
    def __init__(self):
        self.children: dict[int, "TreeNode"] = {}   # key = 该分支的第一个 token
        self.parent: "TreeNode | None" = None

        self.key: list[int] = []          # 这条边上的 token 序列
        self.value: torch.Tensor = None   # 对应的 KV Cache 槽位索引，和 key 等长

        self.lock_ref = 0                 # 有多少个正在跑的请求锁着这条路径
        self.last_access = 0.0            # LRU 时间戳

两个关键设计：

children 用「第一个 token」做 key。 因为 Radix Tree 的任意两个孩子，它们边上的第一个 token 一定不同（否则就该合并成一条边）。所以用第一个 token 就能 \(O(1)\) 定位该走哪个分支。

value 和 key 一一对应。 key[i] 这个 token 的 K/V 存在 value[i] 这个槽位。这是树结构和显存的接缝——树管「谁和谁共享」，value 管「数据在哪」。

三、三个核心操作¶

1. match_prefix：找最长公共前缀¶

def match_prefix(self, token_ids: list[int]) -> tuple[torch.Tensor, TreeNode]:
    """返回：命中的 KV 槽位索引 + 最后一个命中的节点"""
    matched_values = []
    node = self.root
    pos = 0

    while pos < len(token_ids):
        first = token_ids[pos]
        child = node.children.get(first)
        if child is None:
            break                                    # 没有这个分支，到头了

        # 比较这条边上能匹配多少个 token
        n = _common_prefix_len(child.key, token_ids[pos:])

        if n < len(child.key):
            # 部分匹配：必须把这条边劈开
            child = self._split_node(child, n)
            matched_values.append(child.value)
            node = child
            pos += n
            break                                    # 劈开后必然到头

        matched_values.append(child.value)
        node = child
        pos += n

    node.last_access = time.monotonic()
    matched = torch.cat(matched_values) if matched_values else torch.empty(0, dtype=torch.int64)
    return matched, node


def _common_prefix_len(a, b) -> int:
    n = min(len(a), len(b))
    for i in range(n):
        if a[i] != b[i]:
            return i
    return n

返回值里那个 node 很重要：调用方要拿它去加引用锁（第五节讲），也要拿它当插入的起点。

2. _split_node：节点分裂¶

这是 Radix Tree 唯一比 Trie 复杂的地方，但逻辑很直白。

场景：已有一条边 [A, B, C, D]，来了个新请求前缀是 [A, B, X]。公共部分是 [A, B]，需要把原来那条边从第 2 个位置劈开：

分裂前：              分裂后：
  parent                parent
    |                     |
 [A,B,C,D]             [A,B]            ← 新的父节点，承载公共部分
    |                  /     \
  (孩子们)          [C,D]    [X...]      ← 原节点降级成孩子；新分支挂上来
                      |
                   (孩子们)

def _split_node(self, node: TreeNode, split_at: int) -> TreeNode:
    """把 node 从 split_at 处劈开，返回上半截（新的公共父节点）"""
    parent = node.parent

    new_node = TreeNode()
    new_node.parent = parent
    new_node.key = node.key[:split_at]
    new_node.value = node.value[:split_at]
    new_node.lock_ref = node.lock_ref              # 锁要继承！
    new_node.last_access = node.last_access

    # 原节点降级成下半截
    node.parent = new_node
    node.key = node.key[split_at:]
    node.value = node.value[split_at:]

    new_node.children[node.key[0]] = node
    parent.children[new_node.key[0]] = new_node
    return new_node

lock_ref 必须继承，这是分裂里最容易写错的一行。如果有请求正锁着原节点（因为它正在用这段 KV），劈开之后上半截也在被那个请求使用，锁必须跟着上去。漏了这一行，上半截会被误判成「没人用」而被淘汰掉——而下半截还指着它，整条路径就断了。

注意分裂不移动任何显存数据，只是切了一下 value 张量（切片是 view，零拷贝）。树是纯粹的索引结构。

3. insert：把新算出的 KV 挂上去¶

def insert(self, token_ids: list[int], kv_indices: torch.Tensor) -> int:
    """返回已经存在（不需要新占显存）的 token 数"""
    node = self.root
    pos = 0

    while pos < len(token_ids):
        first = token_ids[pos]
        child = node.children.get(first)

        if child is None:
            # 剩下的全是新的，挂一个新节点
            leaf = TreeNode()
            leaf.parent = node
            leaf.key = token_ids[pos:]
            leaf.value = kv_indices[pos:]
            leaf.last_access = time.monotonic()
            node.children[first] = leaf
            return pos

        n = _common_prefix_len(child.key, token_ids[pos:])
        if n < len(child.key):
            child = self._split_node(child, n)

        node = child
        node.last_access = time.monotonic()
        pos += n

    return pos      # 全部命中，一个新槽位都不用占

返回值那个 pos 有实际用途：它等于「这次插入有多少 token 是重复的」，调用方可以据此把重复那部分的物理页还回去（因为已经有一份了，不需要留两份）。

四、和分页 KV Cache 怎么接¶

Radix Tree 只管索引，真正的 K/V 还在那块分页显存里。接口就是节点里的 value——一串槽位下标。

class RadixCache:
    def __init__(self, block_manager):
        self.root = TreeNode()
        self.block_manager = block_manager
        self.evictable_tokens = 0      # 当前可被淘汰的 token 总数

    def before_prefill(self, seq) -> int:
        """返回可以跳过的 token 数"""
        matched, node = self.match_prefix(seq.token_ids)
        if len(matched) == 0:
            seq.cache_node = self.root
            return 0

        self._inc_lock(node)           # 锁住整条路径，防止被淘汰
        seq.cache_node = node
        seq.prefix_slots = matched
        return len(matched)            # 这么多 token 不用重算

    def after_prefill(self, seq, new_slots: torch.Tensor):
        all_slots = torch.cat([seq.prefix_slots, new_slots])
        duplicated = self.insert(seq.token_ids, all_slots)
        # 插入时发现重复的那部分，物理页可以还回去
        if duplicated > len(seq.prefix_slots):
            extra = all_slots[len(seq.prefix_slots):duplicated]
            self.block_manager.free_slots(extra)

    def after_finish(self, seq):
        self._dec_lock(seq.cache_node)  # 请求结束，解锁，这条路径变成可淘汰

对照 11.1 第五节的块级实现，差别就三点：

块级 Prefix Cache Radix Cache
索引结构 dict[hash] → block_id 树，节点存 token 段 + 槽位段
复用单位 一个 block（16 或 32 个 token） 任意长度的 token 段
生命周期 block 上的 ref_count 节点上的 lock_ref + 树位置

注意最后一行的区别，它是下一节的全部内容。

五、淘汰：为什么必须「叶子优先」¶

显存满了要腾地方。这是 Radix Cache 真正比哈希表强的地方，也是最容易写出隐蔽 bug 的地方。

1. 一个错误的淘汰会发生什么¶

假设你按纯 LRU 淘汰，最久没访问的是「系统提示词」那个节点（因为它是很久以前插入的，之后大家都是命中它，如果你只在插入时更新时间戳，它的时间戳就一直很老）：

        root
          |
   [系统提示词 2000 token]     ← 淘汰它，释放 2000 个槽位
       /        \
   [会话 A]    [会话 B]         ← 这两个还在被使用！

释放了父节点的物理页，但两个子节点还指着「以它为前缀」的逻辑。下次匹配走到子节点时，前面 2000 个 token 的 K/V 已经是垃圾数据了。

又是一个「不崩溃、不报错、只是输出错」的 bug。

2. 两条规则¶

规则一：只能从叶子淘汰。

一个节点只要还有孩子，就说明有别的路径以它为前缀，它的数据还被依赖着。叶子节点是唯一「没有下游依赖」的节点。

淘汰一个叶子之后，它的父节点可能变成新的叶子，可以在下一轮被考虑。所以淘汰是自底向上逐层剥的。

规则二：lock_ref > 0 的节点不能碰。

正在运行的请求会锁住它匹配到的整条路径。哪怕这个节点是叶子，只要还有请求在用它的 KV，就不能释放。

def _inc_lock(self, node: TreeNode):
    while node is not self.root:
        if node.lock_ref == 0:
            self.evictable_tokens -= len(node.value)   # 从「可淘汰」里移出
        node.lock_ref += 1
        node = node.parent

def _dec_lock(self, node: TreeNode):
    while node is not self.root:
        node.lock_ref -= 1
        if node.lock_ref == 0:
            self.evictable_tokens += len(node.value)   # 变回可淘汰
        node = node.parent

注意锁是沿着 parent 链一路往上加的，不是只锁匹配到的那个节点。因为整条路径上的 KV 这个请求都要读。

3. 淘汰的实现¶

import heapq

def evict(self, num_tokens_needed: int):
    # 收集所有 lock_ref == 0 的叶子，按最后访问时间做小顶堆
    leaves = [n for n in self._collect_leaves() if n.lock_ref == 0]
    heap = [(n.last_access, id(n), n) for n in leaves]
    heapq.heapify(heap)

    freed = 0
    while freed < num_tokens_needed and heap:
        _, _, node = heapq.heappop(heap)
        if node is self.root:
            break

        self.block_manager.free_slots(node.value)      # 归还物理页
        freed += len(node.value)
        self.evictable_tokens -= len(node.value)

        parent = node.parent
        del parent.children[node.key[0]]

        # 父节点可能刚刚变成叶子，把它放进候选
        if not parent.children and parent.lock_ref == 0 and parent is not self.root:
            heapq.heappush(heap, (parent.last_access, id(parent), parent))

id(n) 那一项是给堆做 tie-breaker 的——时间戳相同时 heapq 会去比较第三个元素 TreeNode，而它没定义 <，会抛 TypeError。这是个很常见的小坑。

4. LRU 时间戳该在什么时候更新¶

匹配时也要更新，不能只在插入时更新。

系统提示词这类节点只在第一次被插入，之后全是「被命中」。如果只在插入时打时间戳，它会永远是最老的，然后被优先淘汰——恰好淘汰掉了最有价值的那个节点。

所以 match_prefix 里那句 node.last_access = time.monotonic() 不是可有可无的。更严格的做法是沿着命中路径整条更新，代价是每次匹配多走一遍 parent 链。

这条规则可以总结成一句：LRU 里的 "Used" 必须包含「被读」，不能只算「被写」。听起来是废话，但在树结构里很容易写漏。

六、算一笔真实的账¶

拿一个 Agent 场景估算收益。设定：

系统提示词 + 工具定义：3000 token
每轮用户输入：          100 token
每轮模型输出：          300 token
一次会话 5 轮
并发 50 个会话

第 \(k\) 轮的输入长度是 \(3000 + (k-1)\times 400 + 100\)。

没有任何前缀缓存，每轮都要 Prefill 全部历史：

\[ \sum_{k=1}^{5}\left[3000+(k-1)\cdot 400+100\right]=3100+3500+3900+4300+4700=19500\ \text{token} \]

有前缀缓存，每轮只需要 Prefill 新增的部分（上一轮的输出 300 + 本轮输入 100）：

\[ 3100+400\times 4=4700\ \text{token} \]

Prefill 计算量降到 24%。 而且这还只算了单个会话内部的复用；50 个会话共享同一份 3000 token 的系统提示词，跨会话又省掉 \(49\times 3000 = 147000\) token 的重复计算。

但注意：这个收益块级 Prefix Cache 也能拿到绝大部分。 3000 token 的系统提示词按 block_size=16 切成 187 个整块，块级哈希能全部命中，只在最后一个不满的块上损失几个 token。

Radix Cache 在这里的增量价值是： 当 50 个会话 + 5 轮历史把显存塞满，需要淘汰时，它能正确地先淘汰叶子（某个会话的最新一轮），而保住树根（系统提示词）。块级哈希做这件事需要额外维护依赖关系。

结论要说得诚实：

场景 块级 Prefix Cache Radix Cache
单轮问答，前缀不共享 都没收益 都没收益，还多了树维护开销
固定 system prompt + 大量单轮 ✅ 收益已经很大 增量很小
多轮对话 / Agent，显存不吃紧 ✅ 够用 增量小
多轮 + 显存紧张 + 需要淘汰 ⚠️ 淘汰策略难做对 ✅ 这才是它的主场
Beam Search / 树搜索 ⚠️ 结构不匹配 ✅ 结构天然对应

别因为「SGLang 用了 Radix 所以它更先进」就上。 先看你的流量形态里有没有上面那两个 ✅ 场景。

七、几个容易写错的地方¶

症状 原因
淘汰后偶发输出错乱 淘汰了非叶子节点，或者漏了 lock_ref 检查
分裂后某段 KV 变垃圾 _split_node 里 lock_ref 没继承
命中率随时间暴跌 LRU 时间戳只在 insert 时更新，树根被优先淘汰
显存缓慢泄漏 请求异常退出没走 _dec_lock，节点永远锁死
heapq 抛 TypeError 时间戳相同时去比较 TreeNode，缺 tie-breaker
树越来越深、匹配变慢 分裂后没有合并「只有一个孩子」的节点

最后一条补充一句：严格的 Radix Tree 在删除节点后应该把「只剩一个孩子」的父节点合并回去。SGLang 的实现里没做这个合并（因为淘汰总是从叶子开始，退化情况有限），但如果你自己实现并且支持任意删除，就得考虑它。

    """反复命中同一前缀后，它不能是最老的"""

最后一条是最重要的。 和 11.1 第十四节 说的一样：Radix Cache 是纯粹的性能优化，不应该改变任何输出。开关它做 A/B，token 序列必须逐个相同。不一致就是有 bug，没有「误差范围内」这一说。

回到全景¶

现在第 11 章的缓存演化线是完整的：

[11.7] 连续 KV Cache          按 max_len 预留，不能共享
   ↓
[11.3] 分页 KV Cache          按需分配，物理页可被多条序列指向
   ↓
[11.1 §5] 块级 Prefix Cache   链式哈希 + 引用计数，整块复用
   ↓
[11.8] Radix Cache            token 级复用，共享结构显式化，淘汰可控

每一步都在解决上一步暴露出来的具体问题。这条线比任何一个单点知识都值钱——面试里被问到任何一环，你都能说清它从哪来、要往哪去。
