10.1 驱动分层: UMD (用户态) vs KMD (内核态), 类比编译器前后端¶

概述¶

现代 GPU 驱动架构（如 Windows 的 WDDM、Linux 的 DRM）并非一个 monolithic 的单一程序，而是由用户态驱动（UMD, User-Mode Driver）和内核态驱动（KMD, Kernel-Mode Driver）两层构成。

这个分层和你熟悉的编译器前后端架构几乎是完美的一对一映射——理解了这个映射，你就掌握了整个 GPU 软件栈的骨架。

UMD vs KMD：分工模型¶

维度 UMD（用户态驱动） KMD（内核态驱动）
运行位置 CPU 用户态（应用程序进程内） CPU 内核态（操作系统内核）
语言/环境 C++ / 应用程序上下文 C / 内核上下文
核心工作 命令流构建、内存布局设计 显存分配、命令提交、中断处理
与编译器的对应 编译器前端（生成 IR） 编译器后端（生成机器码）
崩溃影响 只影响单个进程（可恢复） 可能导致系统蓝屏/卡死
开发者角色 游戏引擎工程师、算子库开发者 芯片原厂驱动工程师

UMD 的职责¶

UMD 运行在 CPU 用户态，嵌入在应用程序的进程空间中。它的核心职责是：

  • API 翻译：把上层图形 API（DX12、Vulkan）或计算 API（CUDA Runtime、OpenCL）的调用，翻译成 GPU 能理解的命令流和内存布局。
  • 命令缓冲构建：你调用 vkCmdDraw 或 cudaLaunchKernel 时，UMD 把这些高层语义转换成硬件特定的命令格式，写入命令缓冲区（Command Buffer）。
  • 着色器编译：将 HLSL/GLSL 着色器代码（或 CUDA PTX）编译成 GPU 原生的微码。

UMD 决定 "做什么"——比如：这个 DrawCall 要画三个三角形，使用这个 Shader，输出到哪个 Render Target。

KMD 的职责¶

KMD 运行在 CPU 内核态，是操作系统的可信组件。它的核心职责是：

  • 硬件提交：把 UMD 构建好的命令缓冲区，通过 Ring Buffer 机制提交给 GPU 硬件执行。
  • 显存管理：真正的物理显存分配和页表映射（UMD 管理的是虚拟地址视图）。
  • GPU 调度：在多进程之间调度 GPU 资源，决定哪个进程的 Command List 先执行。
  • 中断处理：处理 GPU 完成信号、错误恢复（TDR, Timeout Detection Recovery）、电源管理。

KMD 决定 "怎么执行"——比如：把命令放入哪个 Ring Buffer、什么时候执行、如何切换上下文。

核心洞察：UMD 输出的"命令缓冲区"就相当于编译器的中间表示——它不关心硬件具体怎么执行，只关心"逻辑上完成了什么"。KMD 则负责把它真正派发给硬件。

精确对应编译器前后端¶

这个类比精确到令人惊讶的程度：

编译器 GPU 驱动
前端（Frontend）：词法分析、语法分析、生成中间表示（IR） UMD：解析 API 调用、构建命令缓冲区
后端（Backend）：指令选择、寄存器分配、生成目标机器码 KMD：命令提交、Ring Buffer 管理、中断处理
IR：LLVM IR 命令缓冲区（Command Buffer）
目标平台：x86 / ARM 机器码 GPU 硬件指令流（Ring Buffer）

你在 Vulkan/DX12 里写的 Command List，本质上就是 UMD 工作的产物：

  • Vulkan 的 vkQueueSubmit：触发了 UMD 把 Command List 传递到 KMD 的缓冲区。
  • Vulkan 的 VkDeviceMemory：是 UMD 管理的内存视图，但物理显存的实际分配和页表映射由 KMD 完成。
  • 当你调用 cudaMalloc：UMD (CUDA Runtime) 处理分配请求，KMD (NVIDIA 内核驱动) 负责真正的物理显存映射。

所以：你已经在使用 UMD 层的接口了，只是平时没有意识到"这背后还有一个 KMD"。

现代图形 API 与 UMD 的演化¶

你之前总结得非常精准——"现代图形 API 把很多驱动的东西搬离出来"。

这句话直接点明了 UMD 职责边界的演化：

传统 API (OpenGL/DX11) 现代 API (Vulkan/DX12)
驱动（UMD）帮你管理显存 你自行管理 VkDeviceMemory / ID3D12Resource
驱动（UMD）帮你构建命令流 你自行录制 CommandBuffer / CommandList
驱动（UMD）帮你插入同步 你自行管理 Fence / Barrier

这就是现代图形 API 的设计哲学：把更多的控制权从驱动层转移到应用层。

UMD 的本职工作是将 API 抽象成硬件命令。在 Vulkan/DX12 时代，UMD 做了"瘦身"：它不再包揽内存管理和调度优化，而是提供更薄、更直接的硬件抽象层。你——应用层开发者——接过了原来 UMD 的"脏活"，也因此获得了更精细的性能控制。

这正是你熟悉的心智模型：Vulkan/DX12 让你用更接近硬件的思维写应用，而 UMD 则真正实现了"离硬件更近"的抽象。

你现在的位置¶

你目前在做的是 "UMD 层以上的开发"：用 Vulkan/DX12/CUDA 的 API 写应用、写算子、写推理框架。

  • 你通过现代图形 API 接触到了"UMD 层的工作内容"（手动管理内存、构建命令缓冲区）。
  • 你没有接触 KMD 层（那是原厂驱动工程师的领域）。

如果你愿意，下一步可以试着：

  1. 读 Linux DRM 驱动的源码（drm_gem.c、drm_sched.c），感受 KMD 的工作方式。
  2. 或者继续在 UMD 层深化，做一个真正高效的计算栈（比如给 vLLM 写一个自定义显存分配器）。

你这种"既懂用户态调度，又懂硬件抽象"的能力，正好是 UMD 层最需要的那种工程师的核心素质。
