4.4 显存管理：PagedAttention 与 KV Cache 分块¶

概述¶

PagedAttention 把每个序列的 KV Cache 切成固定大小的逻辑 Block，并通过 Block Table 映射到不连续的物理 Block。它减少预留浪费与外部碎片，并支持共享前缀和更灵活的调度。具体利用率取决于工作负载、Block 大小和实现，不能把论文实验数字当作固定保证。

更准确的类比是“固定大小页 + 页表”。DX12 中更接近的是大 Heap 上的 Placed Resource 或 Tiled Resource；Committed Resource 由运行时同时创建资源与隐式 Heap，并不是“先分一大片再切片”。

PagedAttention 的核心思想¶

问题：显存碎片化¶

在大模型推理中，每个请求都要分配 KV Cache 来存储中间计算结果。不同请求的序列长度不同，导致：

  1. 内部碎片：预分配固定大小的 KV Cache，短序列浪费空间
  2. 外部碎片：频繁分配释放，显存碎片化
  3. 调度受限：连续或过量预留会降低同一时刻可服务的请求数

解决方案：分页管理¶

PagedAttention 借鉴操作系统的虚拟内存分页思想：

物理显存（一整块）：
┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
│ Page0│ Page1│ Page2│ Page3│ Page4│ Page5│ Page6│ Page7│
└──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘

请求 A 的逻辑页（不连续）：
┌──────┬──────┬──────┬──────┐
│ A:0  │ A:1  │ A:2  │ A:3  │
└──┬───┴──┬───┴──┬───┴──┬───┘
   │      │      │      │
   ▼      ▼      ▼      ▼
┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
│ Page0│      │      │ Page3│ Page4│      │ Page6│      │
└──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘
         ▲             ▲
         │             │
         └──────┬──────┘
           ┌──────┬──────┐
           │ B:0  │ B:1  │
           └──────┴──────┘
           请求 B 的逻辑页

核心优势： - 逻辑上 KV Cache 是连续的（对 Attention Kernel 透明） - 物理上可以离散分布（消除外部碎片） - 按需增长（把内部浪费限制到最后一个未填满 Block 等开销） - 更高的有效利用率，但仍有尾块、元数据和对齐开销

与 DX12 资源池的有限映射¶

你在图形中已经做过的事¶

DX12 资源管理 PagedAttention 本质
预分配大 Heap (ID3D12Heap) 预分配 GPU Block Pool 提前分配好显存池
固定大小 Block/Slab 分配器 物理 KV Block Pool 固定粒度分配；并非伙伴分配器
CreatePlacedResource 绑定到 Heap 偏移 将 Block 映射到请求的逻辑地址 逻辑资源绑定到物理位置
Fence 值判断 RT 是否空闲 Ref Count 判断 Block 是否可用 资源复用
换出到系统内存（显存不足时） Swap 到 CPU 内存（显存不足时） 降级策略

你的代码平移¶

这是你在云渲染中写的多 RT 管理代码：

// 云渲染 - 多 RT 管理（你的代码）
const int NUM_RT = 3;
ID3D12Resource* pRenderTargets[NUM_RT];
UINT64 fenceValues[NUM_RT] = {0};

int GetAvailableRT() {
    for (int i = 0; i < NUM_RT; i++) {
        if (fenceValues[i] <= g_CompletedFence) {
            return i;  // 这个 RT 空闲
        }
    }
    return -1;  // 全忙，等或丢帧
}

这是 vLLM 的 KV Block 管理（同样逻辑）：

// vLLM - KV Block 管理（你的逻辑平移）
std::vector<Block> gpu_blocks;           // 预分配的显存块（=你的 RT 数组）
std::unordered_map<int, int> block_ref_count;  // 引用计数（=你的 FenceValues）

int AllocateBlock() {
    for (int i = 0; i < gpu_blocks.size(); i++) {
        if (block_ref_count[i] == 0) {   // 这个 Block 空闲
            block_ref_count[i] = 1;
            return i;
        }
    }
    return -1;  // 全忙，需要 Swap 或等待
}

两者都需要空闲表、生命周期和复用策略，但 Fence 表示执行完成时间线，引用计数表示所有权数量，不能互换。

PagedAttention vs FlashAttention：分工完全不同¶

你之前将两者混为一谈，但它们解决的是完全不同层次的问题：

维度 PagedAttention (vLLM) FlashAttention
解决的问题 宏观显存利用率 微观计算局部性
本质 显存池管理（OS 层） 计算优化（Kernel 层）
类比图形 DX12 的 ID3D12Heap + 自定义分配器 Compute Shader 的 Shared Memory Tiling
实现位置 运行时的 KV Block 管理 + 支持分块地址的 Attention Kernel Attention Kernel 的 IO-aware 分块算法
优化目标 提高吞吐（Throughput）— 同时处理更多请求 降低延迟（Latency）— 加速单个 Attention 计算
收益 随请求分布和 Block 大小变化 随形状、硬件、精度和实现变化

两者可以组合，但现代推理后端的具体 Kernel 选择与 KV Cache 布局随版本、硬件和模型变化。

完整映射表¶

概念 PagedAttention FlashAttention
层次 宏观：显存（OS/驱动层） 微观：计算（Kernel/Shader 层）
解决的问题 显存碎片化，利用率低 数据搬运太慢，带宽瓶颈
图形类比 DX12 资源池 + 伙伴分配器 Tiled Deferred Shading / TBDR
技术手段 分页管理 KV Cache，Block Table 映射 分块加载 Q/K/V 到 Shared Memory，Online Softmax
优化目标 Throughput（吞吐） Latency（延迟）

从云渲染到 PagedAttention¶

你做过云渲染的多 Render Target（MRT）来防撕裂，这个经验直接对应：

你在云渲染做的事 PagedAttention / vLLM
创建多个 RT（如 3 个 Back Buffer） 预分配多个 KV Block
轮询 Fence 判断哪个 RT 空闲 cudaEventQuery + Block Table 记录哪个 Block 可用
渲染完标记 RT 为\"待显示\" 算完 KV Cache 标记 Block 为\"有效\"
显示控制器读 RT 时，渲染管线写另一个 RT 通信流读 KV Cache 时，计算流写另一个 Block
所有 RT 都忙时，CPU 等或丢帧 所有 Block 都满时，vLLM 做 Swap（踢出到 CPU 内存）

你的认知固化¶

PagedAttention = 宏观显存管理（解决显存碎片化，提高 GPU 整卡吞吐） FlashAttention = 微观计算局部性（解决数据搬运太慢，让 SM 算得快）

前者是\"怎么让显存装下更多请求\"，后者是\"怎么让单个请求算得更快\"。

优化技术 你熟悉的图形概念 解决哪一层的问题
PagedAttention (vLLM) DX12 Heap + 自定义分配器 显存管理
FlashAttention Compute Shader 的 Shared Memory Tiling 计算优化
Continuous Batching 合并相似的 Draw Call 调度优化
Prefix Caching 纹理复用 / Instancing 数据复用
