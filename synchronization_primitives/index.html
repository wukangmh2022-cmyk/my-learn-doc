5.4 同步原语: __syncthreads, __syncwarp, 内存屏障¶

概述¶

GPU 是一个深度流水线的并行机器。没有同步，数据依赖就会出错。CUDA 提供了多层次的同步原语，从 Block 内的线程 Barrier，到 Device 级别的全局屏障，再到跨 Stream 的 Event 同步。理解每一层的正确使用场景，是写出正确且高效的 CUDA Kernel 的关键。

核心认知：同一 CUDA Stream 中提交的工作具有定义良好的顺序，跨 Stream 依赖通常用 Event 建立。这类似队列时间线，但 CUDA 运行时管理的内存依赖与 DX12/Vulkan 的资源状态转换不是同一个抽象。

同步层级总览¶

层级 原语 作用范围 对应图形概念
Block 内线程同步 __syncthreads() 同一 Block 内所有线程 GroupMemoryBarrierWithGroupSync()
Warp 内线程同步 __syncwarp() 同一 Warp 内 32 个线程 无直接对应（Wave 内可用类似机制）
Block 内内存屏障 __threadfence_block() 同一 Block 内内存可见性 GroupMemoryBarrier()
Device 级内存屏障 __threadfence() 整个 Device 内存可见性 DeviceMemoryBarrier()
系统级内存屏障 __threadfence_system() CPU + GPU 内存可见性 无直接对应
跨 Stream 同步 cudaEvent + cudaStreamWaitEvent GPU Stream 间依赖 Queue Signal/Wait 或 Semaphore；不涉及 CPU Wait
CPU-GPU 同步 cudaDeviceSynchronize() CPU 等待 GPU 完全完成 vkDeviceWaitIdle() / Fence Wait

Block 内同步: __syncthreads()¶

用途¶

__syncthreads() 是 CUDA 编程中使用最频繁的同步原语。它的作用是：

  1. 等待所有线程到达同步点。
  2. 确保之前的所有 Shared Memory 和 Global Memory 写操作对本 Block 内所有其他线程可见。

为什么必须用？¶

__shared__ float tile[TILE_SIZE][TILE_SIZE];

// 每个线程加载一个元素
tile[ty][tx] = global[row * stride + col];

// ⚠️ 如果没有 __syncthreads()，线程 1 可能在线程 0 写完之前就开始读 tile[0][0]
// 结果：读到未初始化的垃圾数据！

__syncthreads();  // ✅ 确保所有线程都写完了

// 现在安全读 Shared Memory
float val = tile[ty][k];

用你的渲染思维理解：__syncthreads() 就是领班站在仓库里喊——"所有人停下手里的活！确认一下你们手推车里的物料都齐了吗？如果齐了，就给我个信号，我们再开始下一道工序。"

GroupMemoryBarrierWithGroupSync() 是最接近的 HLSL 对应物；具体内存作用域与 API/Shader Model 语义仍应查各自规范。

使用陷阱¶

// ❌ 错误：在条件分支中，可能有些线程不执行 __syncthreads()
if (threadIdx.x < 16) {
    __syncthreads();  // 只有线程 0-15 执行！可能死锁
}

// ✅ 正确：所有线程都执行 __syncthreads()
compute_for_first_half();
__syncthreads();  // 放在 if 外面
compute_for_second_half();

规则：__syncthreads() 必须被 Block 中所有线程执行到，否则未定义行为。

Warp 内同步: __syncwarp()¶

用途¶

__syncwarp() 是比 __syncthreads() 更轻量的同步——它只同步同一个 Warp 内的 32 个线程。

为什么需要它？¶

即使线程在同一个 Warp 内，编译器可能会对指令进行重排，导致某些线程的访存操作被延迟。此外，在 Volta 架构之后，Warp 不再严格 Lockstep 执行，Warp 内的线程可能处于不同的指令进度。

// 在 Warp 级归约中，需要确保所有线程的写入对其他线程可见
__syncwarp();  // 比 __syncthreads() 更轻量，只同步当前 Warp

// 若后续通过 Shared Memory 交换数据，再读取时需要匹配的同步。
float sum = __shfl_down_sync(0xFFFFFFFF, val, 16);

内存屏障: __threadfence()¶

__threadfence_block()¶

确保在 Fence 之前的 Shared Memory / Global Memory 写入，对 Block 内的其他线程可见。与 __syncthreads() 的区别在于它不等待线程，只保证内存顺序。

__shared__ int flag;

if (threadIdx.x == 0) {
    // 主线程准备数据
    data[0] = compute_something();
    __threadfence_block();  // 确保 data[0] 写入对其他线程可见
    flag = 1;               // flag 写入也会在 data[0] 之后可见
}
// 其他线程还需要用正确的原子/同步协议读取 flag；Fence 本身不让它们等待。

__threadfence()¶

将 Fence 的可见性扩展到整个 Device（所有 SM），用于跨 Block 通信的场景。比 __threadfence_block() 开销更大。

__global__ void device_fence_kernel(int* global_flag, float* data) {
    if (threadIdx.x == 0 && blockIdx.x == 0) {
        data[0] = 42.0f;
        __threadfence();     // 确保写对整个 Device 可见
        atomicExch(global_flag, 1); // 消费者仍需原子读取与协议设计
    }
}

__threadfence_system()¶

将调用线程在 Fence 前的写入按系统作用域排序，适用于主机内存、Peer Device 等系统可见位置。它不是 CPU/GPU Barrier，具体可见性还取决于内存类型和平台能力。

对比表¶

原语 范围 等待线程？ 保证内存可见性？ 开销
__syncthreads() Block ✅ 是 ✅ 是 中
__syncwarp() Warp ✅ 是 ✅ 是 极低
__threadfence_block() Block ❌ 否 ✅ 是 低
__threadfence() Device ❌ 否 ✅ 是 中
__threadfence_system() CPU+GPU ❌ 否 ✅ 是 高

Stream 作为隐式同步边界¶

单 Stream = 自动维护依赖的 Command List¶

CUDA Stream 是 GPU 上的一个命令队列，cudaLaunchKernel 和 cudaMemcpyAsync 等操作被放入队列，按 FIFO 顺序执行。

cudaStream_t stream;
cudaStreamCreate(&stream);

// 在同一个 Stream 中，Kernel 按序执行，不需要显式同步
kernel_A<<<grid, block, 0, stream>>>(input, temp);
kernel_B<<<grid, block, 0, stream>>>(temp, output);
// ✅ CUDA 隐式保证 kernel_B 等 kernel_A 写完

类比边界：Stream 与 Command Queue 都表达提交顺序，但图形 API 还要求应用声明资源状态、访问范围和布局转换；CUDA 同一 Stream 的 Kernel 依赖通常由运行时内存模型覆盖。

多 Stream + cudaEvent = 手动插 Barrier¶

当你需要跨 Stream 建立依赖关系时，cudaEvent 就是你的手动 Barrier：

cudaStream_t streamCompute, streamComm;
cudaStreamCreate(&streamCompute);
cudaStreamCreate(&streamComm);

cudaEvent_t event;
cudaEventCreate(&event);

// 在通信流中做异步拷贝
cudaMemcpyAsync(dst, src, size, cudaMemcpyDeviceToDevice, streamComm);
cudaEventRecord(event, streamComm);  // 在通信流中打标记

// 让计算流等待通信流完成
cudaStreamWaitEvent(streamCompute, event);  // ≈ 图形里的 Barrier

// 计算流现在安全读数据
compute_kernel<<<grid, block, 0, streamCompute>>>(dst, ...);

Stream Comm:  cudaMemcpyAsync ──┤
                                 │ cudaEventRecord
Stream Compute:                  ├─ cudaStreamWaitEvent → compute_kernel
                                 │
                  (Barrier: 通信流完成后，计算流才能开始)

cudaEvent 的三种用法¶

用法 代码 对应图形概念 阻塞行为
GPU-GPU 同步 cudaEventRecord + cudaStreamWaitEvent Queue 间 Signal/Wait GPU 等待，不阻塞 CPU
CPU 轮询 cudaEventQuery(event) Fence 轮询 (GetCompletedValue) 非阻塞，查询进度
CPU 阻塞等待 cudaEventSynchronize(event) Fence Event + WaitForSingleObject 阻塞调用线程直到 GPU 完成 
// CPU 轮询：非阻塞，适合流水线
while (cudaEventQuery(event) == cudaErrorNotReady) {
    // CPU 可以干别的事，而不是空等
    poll_other_tasks();
}
// GPU 完成，继续

cudaEvent 的应用：跟踪批次完成¶

// 推理引擎的 Continuous Batching 场景
cudaEvent_t events[MAX_REQUESTS];

for (int i = 0; i < num_batches; i++) {
    launch_prefill_kernel<<<..., stream>>>(batch_input[i]);
    cudaEventRecord(events[i], stream);
}

// CPU 轮询哪些 Batch 完成了
while (true) {
    for (int i = 0; i < num_batches; i++) {
        if (cudaEventQuery(events[i]) == cudaSuccess) {
            // 这个 Batch 完成了；上层调度器可回收资源并重新组批
            schedule_new_batch(i);
        }
    }
}

与图形 Resource Barrier 的完整映射¶

概念 图形 API (DX12/Vulkan) CUDA
同一队列的数据依赖 Resource Barrier + 队列顺序 同一 Stream 的提交顺序
显式依赖 Semaphore (Vulkan) / Fence (DX12) cudaEvent + cudaStreamWaitEvent
等待队列 WaitForSingleObject(Fence) cudaEventSynchronize()
不阻塞查询 Fence->GetCompletedValue() cudaEventQuery()
线程组同步 GroupMemoryBarrierWithGroupSync() __syncthreads()
设备作用域内存排序 Shader memory barrier（语义随 API/Shader Model） __threadfence()；两者都不是全设备执行 Barrier
全局等待 vkDeviceWaitIdle() cudaDeviceSynchronize()

图形 API 经验能帮助区分执行顺序、内存可见性和 CPU 等待，但映射不是逐项等价。写协议时应分别回答：谁等待谁、哪些写入必须可见、作用域是什么、资源何时可复用。

最佳实践总结¶

  1. 优先用 Stream 隐式同步：在单 Stream 内按序排列 Kernel，不需要显式 Barrier。
  2. 只在跨 Stream 时用 Event：cudaEventRecord + cudaStreamWaitEvent 是 CUDA 版本的 Barrier。
  3. 优先用轮询代替阻塞：cudaEventQuery 在 CPU 端非阻塞查进度，适合流水线场景。
  4. __syncthreads() 必须在 Block 所有线程中统一执行：避免在条件分支中放同步点。
  5. Warp 内优先用 __syncwarp()：比 __syncthreads() 轻量，只同步 32 个线程。
  6. __threadfence 仅当需要跨 Block 通信时使用：日常 Kernel 中几乎不需要。
