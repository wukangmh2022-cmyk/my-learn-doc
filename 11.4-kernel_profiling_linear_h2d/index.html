11.4 性能分析：Nsight、Decode Linear 与 H2D¶

你写了一个 Decode Linear Kernel，测出来 0.82 ms，cuBLAS 是 0.28 ms —— 慢了 3 倍。问题是：慢在哪？

这种时候你打开代码盯着看，能看出来的只有明显的语法错误（比如忘了 __syncthreads()）。真正的瓶颈 —— 访存不合并、Cache Miss、Warp Stall、Launch Gap —— 全都藏在运行时，代码里看不见。这就是为什么需要 Profiler：它把「慢」分解成可证伪的工程假设。

本篇从一个真实的慢 Kernel 出发，走完「测基线 → Systems 找瓶颈 → Compute 下钻 → 改代码 → 再测」的完整闭环，并在 11.1 §7 的 cu_seqlens / block_table 元数据传输场景中展示 H2D 优化。

一、为什么你的性能报告没人信¶

「我的 Kernel 快了 10%」—— 快了 10% 相比什么？warmup 了吗？测了几次？GPU 开了省电模式吗？CUDA 版本一样吗？

不能复现的数字没有意义。先把这些全部固定下来：

GPU 型号与功耗模式        # nvidia-smi -q -d POWER  查当前功耗上限
Driver / CUDA 版本         # nvcc --version, nvidia-smi
PyTorch / TensorRT 版本    # python -c "import torch; print(torch.__version__)"
模型 + 精度                # Qwen2.5-7B-Instruct, FP16
Batch Size, K, N, Seq Len  # B=8, K=3584, N=18944, prefill_len=128
Warmup 次数                # 5 次
测量次数和统计量           # 50 次取 Median（别用 Mean，有毛刺）
是否启用 CUDA Graph / TP   # Graph=ON, TP=OFF

然后明确测的是什么时间：

端到端请求时间
├── Tokenize
├── Queueing（等前面的请求让出 GPU）
├── Scheduler 分配 Block + 编译 Metadata（11.1 §7）
├── H2D（cu_seqlens / block_table / slot_mapping）
├── GPU Decode Step
│   ├── Kernel Launch Gap
│   ├── Attention
│   ├── Linear（所有 MLP + QKV/O proj）
│   └── Sampling
└── Detokenize

优化 Kernel 前先确认它在端到端中占比够不够高。Amdahl 定律：一个只占总时间 10% 的 Kernel，就算加速到零耗时，端到端也只快 11%。

怎么测 GPU Kernel 时间¶

用 CUDA Event，不要用 time.time()：

start = torch.cuda.Event(enable_timing=True)
end = torch.cuda.Event(enable_timing=True)

start.record()
for _ in range(50):
    output = model(input_ids)  # warmup 在外面，别算进来
end.record()
torch.cuda.synchronize()
print(f"Median: {start.elapsed_time(end) / 50:.3f} ms")

Event 测的是 Stream 上的 GPU 时间，不包含 CPU 端的 Python 调用开销和 Queueing。如果要测端到端延迟（包括 Tokenizer、Scheduler），用 time.perf_counter() 并在需要的地方显式 torch.cuda.synchronize()。

二、案例：一个慢 3 倍的 Decode Linear¶

问题描述¶

Decode 阶段每个请求每步只生成 1 个 token，所以 Linear 的 shape 是：

\[ [M, K] \times [K, N], \quad M = 1 \]

这是一个 GEMV（矩阵-向量乘），不是 GEMM。对于 LLaMA-7B 的 gate_proj：K=4096, N=11008，权重 [K,N] 约 43 MiB（FP16），输入 x: [K] 只有 8 KiB。

我写了一个朴素 Kernel：

__global__ void decode_linear_v0(
    const half* x, const half* weight, half* y, int K, int N)
{
    int n = blockIdx.x * blockDim.x + threadIdx.x;
    if (n >= N) return;

    float sum = 0.0f;
    for (int k = 0; k < K; ++k)
        sum += __half2float(x[k]) * __half2float(weight[k * N + n]);
    y[n] = __float2half(sum);
}

Baseline 测试（A100-SXM4-40GB, CUDA 12.1, K=4096, N=11008, warmup=5, iters=100）：

decode_linear_v0:  0.82 ms
cuBLAS (cublasSgemv): 0.28 ms  ← 慢了 2.93 倍

现在问题是：这 0.54 ms 的差距在哪？

三、Nsight Systems：先看全局时间线¶

采集¶

nsys profile \
  --trace=cuda,nvtx,osrt \
  --capture-range=cudaProfilerApi \
  --capture-range-end=stop \
  -o decode_linear_v0 \
  ./bench

程序里只包围稳态区间：

cudaProfilerStart();
for (int i = 0; i < 100; ++i)
    decode_linear_v0<<<grid, block>>>(x, weight, y, K, N);
cudaProfilerStop();

PyTorch 可以用 NVTX Range 标记：

with torch.cuda.nvtx.range("decode_step"):
    output = model.forward(batch)

打开 decode_linear_v0.nsys-rep，看 5 件事¶

  1. GPU 是否有大段空闲？ → 如果有，说明 CPU Launch 太慢或者 Kernel 间有依赖没优化掉

  2. Kernel Launch 之间是否有明显缝隙？ → CUDA Graph 可以消除 Launch Gap（见 11.1 §11）

  3. H2D 拷贝是否在关键路径上？ → 如果 cudaMemcpy 和 Kernel 串行，考虑异步拷贝 + Stream（见本章 §5）

  4. NCCL 是否阻塞计算 Stream？ → TP 场景常见，需要把 AllReduce 放到专用 Stream 并用 Event 同步

  5. 哪类 Kernel 占据最多 GPU 时间？ → 用命令行统计：

nsys stats --report cuda_gpu_kern_sum decode_linear_v0.nsys-rep

输出类似：

Time(%)  Total Time (ns)  Instances  Avg (ns)   Name
-------  ---------------  ---------  ---------  ----
 78.3    82,143,200       100        821,432    decode_linear_v0
  8.1     8,521,100        50        170,422    cudaMemcpy
 ...

此时发现：decode_linear_v0 占了 78% 的 GPU 时间，确认它是瓶颈。但 Systems 只告诉你「它慢」，不告诉你为什么慢 —— 那是 Nsight Compute 的工作。

四、Nsight Compute：下钻单 Kernel¶

采集¶

ncu \
  --kernel-name regex:decode_linear_v0 \
  --launch-skip 5 \
  --launch-count 10 \
  --set full \
  -o decode_linear_v0 \
  ./bench
  • --launch-skip 5：跳过前 5 次（warmup）
  • --launch-count 10：只采 10 次（--set full 开销很高，别采 100 次）
  • --set full：采集所有指标；首次可以用 --set basic 快速看

打开 decode_linear_v0.ncu-rep，按这个顺序看¶

层级 观察项 要回答的问题
Duration Kernel Time 它是否真的重要？（已经在 Systems 确认了）
Memory Workload L1/L2 Throughput, Sector Efficiency 访存是否合并？Cache 是否有效？
Compute Workload SM Throughput, FP/INT Pipe 算力是否饱和？

我的 v0 报告（节选）¶

Duration:               821 μs
DRAM Throughput:        142 GB/s  ← A100 理论 1555 GB/s，只用了 9%
L2 Hit Rate:            8.3%
Sector Load Efficiency: 12.5%     ← 灾难：每次事务只用了 1/8 的数据
Achieved Occupancy:     31.2%
Stall Reason (top):     LG Throttle 58.4%  ← 访存指令堵塞

问题找到了：Sector Load Efficiency: 12.5% 说明每次从 DRAM 读 128B（一个 Sector），但只用了 16B —— 访存不合并。

五、为什么 v0 访存不合并¶

回看代码：

for (int k = 0; k < K; ++k)
    sum += ... weight[k * N + n];

权重 layout 是 [K, N]（Row-major），所以 weight[k * N + n]：同一个 Warp 内相邻线程的 n 相邻，但它们读的是 weight[0*N + n0], weight[0*N + n1], ... —— 这是连续的，合并访问。

那为什么还不合并？因为 k 在内层循环：

Thread 0 读 weight[0*N + 0], weight[1*N + 0], weight[2*N + 0], ...  ← stride = N
Thread 1 读 weight[0*N + 1], weight[1*N + 1], weight[2*N + 1], ...  ← stride = N

相邻线程在内层循环的同一步读的地址间隔 N = 11008 个 half，跨了 11 个 Cache Line（每行 128B = 64 half）—— 完全不合并。

六、v1：转置权重 layout¶

把权重改成 [N, K] layout（在 CPU 上转置好，或者训练时就存成这个 layout）：

__global__ void decode_linear_v1(
    const half* x, const half* weight_T, half* y, int K, int N)
{
    int n = blockIdx.x * blockDim.x + threadIdx.x;
    if (n >= N) return;

    float sum = 0.0f;
    const half* w_row = weight_T + n * K;  // 第 n 行起点
    for (int k = 0; k < K; ++k)
        sum += __half2float(x[k]) * __half2float(w_row[k]);
    y[n] = __float2half(sum);
}

现在 w_row[k] 在 k 循环内是 stride-1 访问，不同线程读不同行，但同一线程内的访问是连续的 —— 部分合并（Warp 内 32 个线程读 32 行，每行连续读 K 个，L2 Cache 能帮忙）。

测试：

decode_linear_v1:  0.51 ms  ← 从 0.82 快到 0.51，快了 1.6 倍
cuBLAS:            0.28 ms  ← 还差 1.8 倍

Nsight Compute：

Sector Load Efficiency: 78.3%  ← 从 12.5% 提升到 78%
DRAM Throughput:        520 GB/s  ← 从 142 提升到 520
L2 Hit Rate:            61.2%  ← x 能常驻 L2

好多了，但还差一半。继续看 Stall：

Stall Reason (top):  LG Throttle 42.1%  ← 还是访存堵
                     MIO Throttle 18.7%

七、v2：向量化 Load + 融合 Bias¶

向量化¶

现在每次 __half2float(w_row[k]) 读 2B，L1 Cache Line 是 128B —— Cache 利用率只有 1.5%。用 float4 一次读 16B（8 个 half）：

__global__ void decode_linear_v2(
    const half* x, const half* weight_T, const half* bias, half* y,
    int K, int N)
{
    int n = blockIdx.x * blockDim.x + threadIdx.x;
    if (n >= N) return;

    constexpr int VEC = 8;  // float4 = 8 * half
    const half* w_row = weight_T + n * K;

    float sum = 0.0f;
    for (int k = 0; k < K; k += VEC) {
        float4 w_vec = *reinterpret_cast<const float4*>(w_row + k);
        float4 x_vec = *reinterpret_cast<const float4*>(x + k);
        half* w_half = reinterpret_cast<half*>(&w_vec);
        half* x_half = reinterpret_cast<half*>(&x_vec);
        #pragma unroll
        for (int i = 0; i < VEC; ++i)
            sum += __half2float(w_half[i]) * __half2float(x_half[i]);
    }
    if (bias) sum += __half2float(bias[n]);
    y[n] = __float2half(sum);
}

测试：

decode_linear_v2:  0.34 ms  ← 从 0.51 快到 0.34
cuBLAS:            0.28 ms  ← 还差 21%

Nsight Compute：

Sector Load Efficiency: 96.1%
DRAM Throughput:        890 GB/s  ← 接近理论峰值的 57%
L2 Hit Rate:            82.4%
Achieved Occupancy:     52.3%  ← 从 31% 提升到 52%
Stall Reason (top):     Wait 28.3%  ← 现在主要在等指令发射，不是访存堵

八、v3：用 half2 和 __hfma2¶

上面还在用 __half2float + FP32 fma，A100 的 FP16 Tensor Core 吞吐是 FP32 的 2 倍（312 TFLOPS vs 156 TFLOPS）。用 half2：

float sum = 0.0f;
for (int k = 0; k < K; k += 8) {
    float4 w_vec = *reinterpret_cast<const float4*>(w_row + k);
    float4 x_vec = *reinterpret_cast<const float4*>(x + k);
    half2* w2 = reinterpret_cast<half2*>(&w_vec);
    half2* x2 = reinterpret_cast<half2*>(&x_vec);
    half2 acc = __float2half2_rn(0.0f);
    #pragma unroll
    for (int i = 0; i < 4; ++i)
        acc = __hfma2(w2[i], x2[i], acc);
    sum += __half2float(acc.x) + __half2float(acc.y);
}

测试：

decode_linear_v3:  0.29 ms  ← 和 cuBLAS 持平了
cuBLAS:            0.28 ms

Nsight Compute：

SM Throughput:          68.2%  ← FP16 Pipe 利用率大幅提升
DRAM Throughput:        1120 GB/s

九、为什么 cuBLAS 还快 3%¶

cuBLAS 用了 cublasSgemmEx / cublasGemmEx 的 Tensor Core 路径（需要 FP16 输入 + Tensor Core matmul），并且对 M=1 的 GEMV 做了专门优化：

  1. Warp Shuffle 归约：不用 Shared Memory，直接 __shfl_down_sync
  2. 多个输出 n 复用同一份 x：一个 Warp 算 2-4 个输出
  3. 更激进的向量化 + 循环展开：用 ldg.128 指令（16B 对齐 Load）

你的 v3 已经接近手写 GEMV 的上限了。再往下优化需要：

  • 用 inline PTX ldg.128 / sts.128
  • 手写 Warp Shuffle 归约
  • 针对固定 shape 特化（消除 if (n >= N) 分支）

但对于通用场景，直接调 cublasGemmEx 就够了 —— 除非你的 shape 非常特殊（比如 N 很小、K 很大），或者需要融合特殊的激活函数（比如 SwiGLU 的 gate * silu(up)），否则手写 GEMV 的收益不值得维护成本。

十、H2D 优化：先消除分配，再谈重叠¶

回到 11.1 §7 的场景：每个 Decode Step 需要把 cu_seqlens / block_table / slot_mapping 从 CPU 传到 GPU。

错误的做法（每步都分配）¶

def decode_step(batch):
    cu_seqlens_host = np.array([0] + list(accumulate(batch.seq_lens)))
    cu_seqlens_device = torch.from_numpy(cu_seqlens_host).cuda()  # ← 每步都分配

    block_table_host = np.array([seq.block_table for seq in batch.seqs])
    block_table_device = torch.from_numpy(block_table_host).cuda()  # ← 每步都分配

    attention(q, k_cache, v_cache, cu_seqlens_device, block_table_device)

Nsight Systems 会看到：

每个 Decode Step：
├── cudaMalloc (cu_seqlens)     ← 0.05 ms
├── cudaMemcpy H2D              ← 0.02 ms
├── cudaMalloc (block_table)    ← 0.05 ms
├── cudaMemcpy H2D              ← 0.03 ms
├── Attention Kernel            ← 0.18 ms
└── cudaFree × 2                ← 0.04 ms

每步 0.17 ms 浪费在内存管理上，Attention 只有 0.18 ms —— 几乎一半时间在搬砖。

正确的做法（预分配 + Pinned Memory）¶

class MetadataManager:
    def __init__(self, max_batch_size, max_blocks_per_seq):
        # 初始化时预分配
        self.cu_seqlens_pinned = torch.zeros(
            max_batch_size + 1, dtype=torch.int32, pin_memory=True)
        self.cu_seqlens_device = torch.zeros(
            max_batch_size + 1, dtype=torch.int32, device='cuda')

        self.block_table_pinned = torch.zeros(
            (max_batch_size, max_blocks_per_seq), dtype=torch.int32, pin_memory=True)
        self.block_table_device = torch.zeros(
            (max_batch_size, max_blocks_per_seq), dtype=torch.int32, device='cuda')

    def update(self, batch):
        B = len(batch.seqs)
        # 只写本次需要的 slice
        self.cu_seqlens_pinned[:B+1].copy_(
            torch.tensor([0] + list(accumulate([s.seq_len for s in batch.seqs]))))

        for i, seq in enumerate(batch.seqs):
            self.block_table_pinned[i, :len(seq.block_table)].copy_(
                torch.tensor(seq.block_table))

        # 异步拷贝
        self.cu_seqlens_device[:B+1].copy_(
            self.cu_seqlens_pinned[:B+1], non_blocking=True)
        self.block_table_device[:B, :max_blocks].copy_(
            self.block_table_pinned[:B, :max_blocks], non_blocking=True)

Nsight Systems 现在看到：

每个 Decode Step：
├── cudaMemcpyAsync (cu_seqlens, 2 KiB)    ← 0.005 ms，与上一步 Kernel 重叠
├── cudaMemcpyAsync (block_table, 8 KiB)   ← 0.008 ms，与上一步 Kernel 重叠
└── Attention Kernel                       ← 0.18 ms

H2D 时间从 0.05 ms 降到几乎为零（因为和前一个 Kernel 的尾部重叠了）。

三个关键点¶

  1. pin_memory=True 必须配 non_blocking=True 才有效
  2. Pinned Memory 绕过 OS 页表，DMA 可以直接读

  3. 没有 Pinned，non_blocking=True 会退化成同步拷贝

  4. 只更新本次需要的 slice，不要每次都拷完整 buffer

  5. cu_seqlens 每次只需要 B+1 个元素（几十字节），别拷 max_batch_size + 1

  6. 验证是否真的重叠了

  7. 在 Nsight Systems 时间线上，H2D 和前一个 Kernel 应该有垂直重叠
  8. 如果没重叠，可能是：
    • 前一个 Kernel 用了 Default Stream，隐式同步了
    • torch.cuda.synchronize() 调太早
    • H2D 数据量太大（几十 MiB），把重叠窗口吃完了

十一、Roofline 视角：为什么 Decode Linear 是 Memory-Bound¶

回到 LLaMA-7B gate_proj: [1, 4096] × [4096, 11008]：

计算量：

\[ \text{FLOPs} = 2 \times M \times K \times N = 2 \times 1 \times 4096 \times 11008 \approx 90.2 \text{ MFLOP} \]

访存量（FP16）：

\[ \begin{aligned} \text{Bytes} &= (M \times K + K \times N + M \times N) \times 2 \\ &= (4096 + 45.1\text{M} + 11008) \times 2 \\ &\approx 90.2 \text{ MiB} \end{aligned} \]

算术强度：

\[ I = \frac{90.2 \text{ MFLOP}}{90.2 \text{ MiB}} = \frac{90.2 \times 10^6}{90.2 \times 2^{20}} \approx 0.95 \text{ FLOP/Byte} \]

A100 的 Ridge Point（带宽与算力交点）：

\[ I_{\text{ridge}} = \frac{312 \text{ TFLOPS (FP16)}}{1555 \text{ GB/s}} = \frac{312 \times 10^{12}}{1555 \times 10^9} \approx 200 \text{ FLOP/Byte} \]

0.95 远小于 200 —— 这个 Kernel 在 Ridge Point 左边 200 倍，纯粹的 Memory-Bound。

所以优化的重点是：

  1. 访存合并（v0 → v1，1.6× 提升）
  2. 向量化 Load（v1 → v2，1.5× 提升）
  3. 用 FP16 指令降低精度转换开销（v2 → v3，1.17× 提升）

而不是去调 Block Size、Occupancy、Shared Memory Tiling —— 那些是 Compute-Bound Kernel（比如大 Batch Prefill GEMM）才需要考虑的。
