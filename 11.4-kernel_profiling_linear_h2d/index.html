11.4 性能分析实战：Nsight、Decode Linear 与 H2D¶

实战目标¶

本篇完成三个闭环：

  1. 用 Nsight Systems 从端到端时间线定位瓶颈；
  2. 用 Nsight Compute 下钻单个 Kernel 的计算、访存和占用率；
  3. 针对 Decode M=1 Linear 和逐步 H2D 元数据更新实施优化。

nvprof 是旧 CUDA 工具链中的命令行 Profiler，已被 Nsight Systems/Compute 取代，并且不支持许多新架构与新 CUDA 版本。只有维护旧环境时才使用 nvprof；新项目以 Nsight 为主。

一、先定义测量边界¶

不要把以下时间混为一个数字：

端到端请求时间
├── Tokenize
├── Queueing
├── Scheduler / Metadata
├── H2D
├── GPU Decode Step
│   ├── Kernel launch gaps
│   ├── Attention
│   ├── Linear / GEMV
│   └── Sampling
└── Decode / Detokenize

优化 Kernel 前先确认它在端到端时间中占比足够高。Amdahl 定律：若某 Kernel 只占总时间 10%，即使无限加速，端到端收益上限也只有约 11%。

二、构造可复现 Benchmark¶

固定以下信息：

GPU 型号与功耗模式
Driver / CUDA / TensorRT / PyTorch 版本
模型与精度
Batch Size、K、N、Context Length
Warmup 次数
测量次数和统计量（Median/P90）
是否启用 CUDA Graph、TP、量化

CUDA Event 测量 GPU 区间：

cudaEventRecord(start, stream);
for (int i = 0; i < iterations; ++i)
    launchKernel(..., stream);
cudaEventRecord(stop, stream);
cudaEventSynchronize(stop);
cudaEventElapsedTime(&milliseconds, start, stop);

Event 适合测 GPU Stream 上的时间，不包含 Queueing 之前的 CPU 工作。端到端延迟使用稳定时钟，并在需要时显式同步完成边界。

三、Nsight Systems：先看全局时间线¶

1. 采集¶

nsys profile \
  --trace=cuda,nvtx,osrt,cudnn,cublas \
  --sample=none \
  --capture-range=cudaProfilerApi \
  --capture-range-end=stop \
  -o reports/decode \
  ./decode_bench

程序中只包围稳态区间：

cudaProfilerStart();
run_decode_iterations();
cudaProfilerStop();

PyTorch 可使用 NVTX 标记：

with torch.cuda.nvtx.range("scheduler"):
    batch = scheduler.schedule()
with torch.cuda.nvtx.range("decode_step"):
    output = runner.run(batch)

2. 首轮只回答五个问题¶

  1. GPU 是否存在大段空闲？
  2. CPU 是否逐个 Launch 导致 Kernel 间有明显缝隙？
  3. H2D 是否位于关键路径并与计算串行？
  4. NCCL 是否阻塞计算 Stream？
  5. 哪类 Kernel 占据最多 GPU 时间？

不要在 Systems 中猜测 Bank Conflict 或寄存器压力，那是 Nsight Compute 的层级。

3. 命令行统计¶

nsys stats --report cuda_gpu_kern_sum reports/decode.nsys-rep
nsys stats --report cuda_api_sum reports/decode.nsys-rep
nsys stats --report cuda_gpu_mem_time_sum reports/decode.nsys-rep

关注总时间、调用次数、平均与中位时间。一个 3 微秒 Kernel 调用一万次，可能比一个 2 毫秒 Kernel 调十次更值得做 Graph/Fusion。

四、Nsight Compute：下钻单 Kernel¶

1. 受控采集¶

ncu \
  --kernel-name regex:decode_linear \
  --launch-skip 20 \
  --launch-count 10 \
  --set full \
  -o reports/decode_linear \
  ./decode_bench

--set full 开销较高，先用 --set basic 或指定 Section；不要对完整长时间服务直接全量采集。

2. 读指标的顺序¶

层级 观察项 要回答的问题
Duration Kernel Time 它是否真的重要？
Throughput DRAM/L2/SM 更接近带宽上限还是计算上限？
Memory Workload Sector、Transaction、Hit Rate 访问是否合并、Cache 是否有效？
Scheduler Eligible/Active Warp、Stall 延迟为何没有隐藏？
Launch Stats Block、Register、SMem、Occupancy 资源是否限制驻留？
Source/SASS 指令与访问位置 哪段代码产生问题？

高 Occupancy 不是目标。若 Kernel 已达到带宽上限，进一步提高 Occupancy 可能没有收益；若为了 Occupancy 降低寄存器导致 Spill，性能反而下降。

五、Decode Linear 为什么是 GEMV 风格¶

Decode 的单请求单 Token Linear 常见形状：

\[ [M,K] \times [K,N], \quad M=1 \]

每个权重元素通常只使用一次，算术强度较低。输入向量 LHS 只有 K 个元素，可以被 L1/Shared Memory 反复使用；权重 RHS 为 K×N，需要按输出 N Tile 流式读取。

flowchart LR
    X["LHS x: K\n常驻 Cache/Shared"] --> DOT["N 个 Dot Products"]
    W["RHS W: K x N\n按 N Tile 流式加载"] --> DOT
    DOT --> Y["Output y: N"]

1. CPU Reference¶

for (int n = 0; n < N; ++n) {
    float sum = bias ? bias[n] : 0.0f;
    for (int k = 0; k < K; ++k)
        sum += x[k] * weight[n * K + k];
    y[n] = sum;
}

首先确认权重是 Row-major [N,K] 还是 [K,N]。布局错误可能仍生成连续访问，却计算了转置结果。

2. GPU 映射基线¶

  • Grid 的 X 维覆盖 N Tile；
  • 一个 CTA 计算多个输出 N；
  • Warp Lane 沿 K 维读取并做 Dot；
  • Q/LHS 可加载到 Shared Memory，或依赖只读/L1 Cache；
  • 权重按向量宽度对齐读取；
  • Warp Shuffle 完成 K 维归约。
template<int N_TILE, int K_TILE>
__global__ void decode_linear(
    const half* x, const half* weight, half* y, int K, int N)
{
    int n0 = blockIdx.x * N_TILE;

3. Tiling 参数不能脱离 Shape¶

对于 K=1280, N=8192，N 足够大，可以提供大量 CTA；对于类似 N=128815 的非常规 Shape，尾部 Tile、向量对齐和 Grid 分布会不同。需要扫描：

N_TILE: 32, 64, 128
K_TILE: 32, 64, 128, 256
WARPS: 4, 8
vector width: 8B, 16B

每组参数记录 Kernel Time、DRAM Throughput、L2 Hit、Register、Occupancy 和数值误差。所谓“适配 Cache 层级”必须由工作集大小与 Profiler 指标支持，不能只凭 Tile 名称判断。

4. 优化顺序¶

  1. 修正连续和对齐访问；
  2. 消除重复读取 LHS；
  3. 用 Half2/向量 Load 提升事务利用率；
  4. 调整 N/K Tile 和 Warp 数；
  5. 融合 Bias、Activation 或量化反缩放；
  6. 对热点固定 Shape 特化；
  7. 与 cuBLAS/cuBLASLt 或 TensorRT Tactic 对比。

10.6% 或 8.2% 的提升应相对于明确基线报告。若基线是成熟库，个位数到十几个百分点可能很有价值；若基线是未合并访问的朴素 Kernel，则这个数字不能证明已接近最优。

六、H2D 优化：先消除分配，再谈重叠¶

常见错误路径：

每个 Decode Step：
malloc host metadata
cudaMalloc device metadata
fill
cudaMemcpy
launch
cudaFree
free host

正确方向：

  1. 初始化时预分配 Device Buffer；
  2. 使用 Pinned Host Ring Buffer；
  3. 每步只写当前 Slice；
  4. cudaMemcpyAsync 到专用或执行 Stream；
  5. 用 Event/Fence 保护 Ring Slice；
  6. Shape 稳定时配合 CUDA Graph 固定地址。
struct MetadataSlot {
    void* pinned_host;
    void* device;
    cudaEvent_t reusable;
};

是否值得拷贝？¶

Block Table 可能只有几 KB。此时问题常不是 PCIe 带宽，而是 API 调用、分配和同步开销。Nsight Systems 中应观察：

  • cudaMalloc/cudaFree 是否出现在稳态路径；
  • H2D 前是否存在隐式同步；
  • Copy 是否真正与前一个 Step 的 GPU 工作重叠；
  • 大量小 Copy 是否可以打包；
  • Unified/Zero-copy 是否反而导致 GPU 细粒度远程访问。

七、旧环境中的 nvprof¶

仅在老 CUDA/老 GPU 环境维护时使用：

nvprof --print-gpu-trace ./decode_bench
nvprof --kernels decode_linear --metrics achieved_occupancy,dram_read_throughput ./decode_bench

不要把旧指标名机械映射到新架构。Ampere、Hopper 及之后的硬件应使用 Nsight 工具提供的架构相关指标和 Section。

九、完成标准¶

  • Systems 时间线能区分 CPU Gap、H2D、Kernel 和 NCCL；
  • Compute 报告能用带宽、指令、Stall 和资源解释瓶颈；
  • Decode Linear 与 CPU/cuBLAS Reference 数值对齐；
  • Tiling 结论绑定具体 Shape；
  • 稳态路径不存在重复 Host/Device 分配；
  • 优化同时报告单 Kernel 和端到端影响；
  • nvprof 只作为旧环境附录，不作为新项目主工具。

这篇实战把第 4.2 节 Tiling、第 5.2 节存储层次、第 5.3 节 Warp 执行、第 8 章 Roofline 与真实工具链连接起来。Profiler 的价值不是给出更多数字，而是把“慢”分解为可证伪的工程假设。
