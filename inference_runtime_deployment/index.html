11.5 Runtime、动态批处理与部署验证实战¶

项目目标¶

本篇把前几篇的算子与缓存机制组装为一个可部署的 C++17 Runtime。最终系统包含：

  • ModelSpec：模型结构与静态规格；
  • IBackend：TensorRT 等执行后端抽象；
  • RuntimeSession：模型实例、Buffer 和执行上下文；
  • Request：Prompt、生成状态和采样参数；
  • KvBlockManager：Logical/Physical Block 生命周期；
  • BatchScheduler：混合长度 Prefill/Decode 组批；
  • Validator：分层数值对齐和压力测试；
  • 端侧输入、推理、解析与失败回退链路。

一、模块化 Runtime 架构¶

flowchart TB
    API["Application / Camera / Text API"] --> REQ["Request Manager"]
    REQ --> SCH["Batch Scheduler"]
    SCH --> KV["KV Block Manager"]
    SCH --> SES["Runtime Session"]
    SES --> BE["IBackend"]
    BE --> TRT["TensorRT Backend"]
    BE --> REF["ONNX/CPU Reference Backend"]
    SES --> BUF["Buffer / Stream / Event Pool"]
    OUT["Output Validator & Parser"] --> API
    SES --> OUT

1. ModelSpec¶

struct ModelSpec {
    std::string model_id;
    int vocab_size{};
    int hidden_size{};
    int num_layers{};
    int num_q_heads{};
    int num_kv_heads{};
    int head_size{};
    int max_model_len{};
    DataType activation_type{};
    DataType kv_type{};

    void validate() const;
};

ModelSpec 只描述模型不变量，不保存某次请求的 Context Length 或 Block Table。它应能从配置文件反序列化，并在创建 Backend 前完成交叉校验。

2. Backend 抽象¶

class IBackend {
public:
    virtual ~IBackend() = default;
    virtual BackendCapabilities capabilities() const = 0;
    virtual void prepare(const ModelSpec&, const EngineConfig&) = 0;
    virtual void enqueue(const BatchView&, OutputView&, StreamHandle) = 0;
};

抽象层应该围绕 Runtime 真正需要的能力，而不是简单包一层 execute()：

  • 是否支持动态 Batch/Sequence Length；
  • 是否支持外部 KV Cache Binding；
  • 支持的数据类型和 Layout；
  • 是否允许 CUDA Graph；
  • Workspace 和 Stream 的所有权规则；
  • 错误是同步返回还是异步暴露。

3. RuntimeSession¶

class RuntimeSession {
public:
    RuntimeSession(ModelSpec spec, std::unique_ptr<IBackend> backend);
    RuntimeSession(const RuntimeSession&) = delete;
    RuntimeSession& operator=(const RuntimeSession&) = delete;

    StepResult run(BatchPlan plan);

private:
    ModelSpec spec_;
    std::unique_ptr<IBackend> backend_;
    DeviceBufferPool buffers_;
    StreamPool streams_;
    KvBlockManager kv_blocks_;
};

RAII 保证 Engine、Execution Context、CUDA Stream/Event、Device Buffer 和 Shared Library Handle 在异常路径也能释放。析构前必须确认 GPU 不再使用资源，RAII 本身不会自动解决异步生命周期。

二、Request 状态管理¶

enum class RequestState {
    Waiting,
    Prefilling,
    Decoding,
    Finished,
    Failed,
    Cancelled
};

struct Request {
    uint64_t id;
    RequestState state{RequestState::Waiting};
    std::vector<int32_t> token_ids;
    size_t prompt_length{};
    size_t cached_tokens{};
    size_t generated_tokens{};
    SamplingConfig sampling;
    std::vector<uint32_t> logical_to_physical;
    std::string error;
};

状态迁移必须集中管理：

Waiting → Prefilling → Decoding → Finished
                    ↘ Failed
Waiting/Prefilling/Decoding → Cancelled

取消请求时不能立即复用 KV Block。若该请求已提交到 GPU，必须等待相关 Event/Fence 完成后再释放物理页。

三、Logical KV Block 管理¶

1. 分离三个对象¶

对象 负责内容
Request Block Table 逻辑页到物理页的映射
Physical Block Pool 空闲页、引用计数和缓存键
GPU KV Buffer 真正的 K/V 数据

把三者合并在一个类中会让调度策略、CPU 元数据和 GPU Buffer 生命周期互相污染。

2. 分配接口¶

class KvBlockManager {
public:
    AllocationResult reserve(Request& request, size_t token_capacity);
    bool canAppend(const Request& request) const;
    void appendBlock(Request& request);
    void retainPrefix(Request& request, PrefixHandle prefix);
    DeferredRelease release(Request& request, GpuEvent completion);
    void collectCompleted();
};

DeferredRelease 把“逻辑请求结束”和“物理页可复用”分开，等价于渲染资源池中用 Fence 延迟回收 Transient Resource。

3. PagedAttention 的系统收益¶

Paged KV Cache 主要解决：

  • 不按 max_model_len 为每个请求预留连续空间；
  • 序列增长时按需增加页；
  • 支持共享不可变 Prefix Block；
  • 动态 Batch 不必聚合复制完整 KV；
  • 抢占与回收可以在 Block 粒度进行。

它不保证 Attention Kernel 自身天然更快。间接寻址可能增加访问成本，收益来自更高的有效显存利用率和更少的数据搬移。

四、动态批处理¶

1. 输入不是 Padding 后的完整历史¶

Decode 每条请求只提交最后一个 Token 的 Q，历史 K/V 已在 Cache 中。Batch 输入：

InputIds      [B]
Positions     [B]
ContextLens   [B]
BlockTables   [B, MaxBlocksInBatch]
SlotMapping   [B]

只有 Block Table 需要在二维 Shape 上 Padding；不应把每条请求的完整 KV 复制到统一连续 Tensor。

2. BatchPlan¶

struct BatchPlan {
    Phase phase;
    std::vector<Request*> requests;
    std::vector<int32_t> input_ids;
    std::vector<int32_t> positions;
    std::vector<int32_t> context_lens;
    std::vector<int32_t> block_tables;
    std::vector<int32_t> slot_mapping;
    int max_blocks_per_request{};
};

Scheduler 输出不可变 BatchPlan，Session 消费它。执行期间不要让另一个线程修改 Request 的 Block Table。

3. 调度策略¶

BatchPlan BatchScheduler::next()
{
    collectFinishedGpuWork();
    admitWaitingRequests();
    if (shouldRunDecode())
        return buildDecodeBatch();
    return buildPrefillBatch();
}

约束：

  • 最大序列数；
  • Prefill Token Budget；
  • 可用 KV Block；
  • Backend 支持的 Shape/Profile；
  • 交互请求的 ITL 目标；
  • 长请求的公平性与等待时间；
  • Graph/TensorRT Optimization Profile 的 Bucket。

4. 并发安全¶

一种清晰模型是单线程 Scheduler 拥有 Request 状态，其他线程通过消息队列提交 Add/Cancel；GPU Completion 也转化为事件消息。这样避免多个线程同时修改 Block Table。

若使用锁：

  • 明确锁顺序；
  • 不在持锁状态下调用可能阻塞的 Backend；
  • 不让回调重新进入同一锁；
  • 把 GPU 异步完成和 CPU 对象生命周期分开。

5. 吞吐报告¶

139.63 tok/s → 275.16 tok/s（+97%） 可以作为某次动态批处理案例，但需要同时报告 Batch 分布和延迟：

版本 Throughput TTFT P50/P99 TPOT P50/P99 Batch 分布
单请求串行 139.63（案例） 待记录 待记录 B=1
动态批处理 275.16（案例） 待记录 待记录 待记录

吞吐翻倍可能伴随排队延迟上升，不能只保留吞吐数字。

五、TensorRT Backend 工程化¶

1. 构建期与运行期分离¶

构建期：

  • 解析 ONNX/Network Definition；
  • 注册 Plugin；
  • 设置 Optimization Profile；
  • 选择精度和 Tactic；
  • 序列化 Engine；
  • 记录 TensorRT/CUDA/GPU Compatibility Metadata。

运行期：

  • 反序列化 Engine；
  • 创建 Execution Context；
  • 设置动态 Shape；
  • 绑定预分配 Buffer；
  • enqueueV3()；
  • 通过 Stream/Event 管理异步完成。

不要在目标设备启动服务时重复构建 Engine，除非产品明确接受构建时延和环境差异。

2. Optimization Profile¶

按真实分布配置 Min/Opt/Max：

Decode profile: B=[1,16,128], query_len=1
Prefill profile: total_tokens=[1,1024,8192]

一个覆盖极宽范围的 Profile 可能使 Tactic 选择折中。Prefill 与 Decode 形状差异明显，通常值得使用不同 Profile 或 Engine。

3. Buffer 复用¶

Session 初始化阶段预分配：

  • 输入/输出 Device Buffer；
  • KV Cache；
  • Block Table/Context Lens/Slot Mapping；
  • Pinned Host Staging Ring；
  • Plugin Workspace；
  • CUDA Stream 与 Event Pool。

稳态 Decode 路径不应出现 cudaMalloc/cudaFree、Engine/Context 创建或 Host Heap 高频分配。

六、端侧与车载环境适配¶

1. 环境清单¶

源码构建成功不等于运行时兼容。应在目标镜像中执行 Engine 反序列化、Plugin 加载和最小推理 Smoke Test。

2. 多模态链路解耦¶

flowchart LR
    CAM["Camera"] --> PRE["Image Preprocess"]
    PRE --> VISION["Vision Encoder"]
    VISION --> ADAPT["Projector / Adapter"]
    ADAPT --> LLM["Text Decoder Runtime"]
    LLM --> PARSE["Structured Parser"]
    PARSE --> RULE["Validation / Fallback"]

视觉编码和文本生成分离可以独立设置 Batch、精度、缓存和失败重试，也便于判断错误来自图像预处理、视觉特征还是语言模型。

3. 可靠性约束¶

  • 所有输入 Shape 和 Buffer Size 在进入 Backend 前校验；
  • 设置请求 Deadline 与取消机制；
  • 输出解析失败时保留原始输出和诊断字段；
  • 业务关键结果使用 Schema/范围/一致性规则验证；
  • GPU OOM、Plugin Error、超时分别分类；
  • 回退逻辑必须可观测，不能静默吞掉模型错误。

七、AWQ 量化验证¶

AWQ 主要量化权重，减少权重带宽与显存，但不同层和场景对误差敏感程度不同。验证不能只看通用困惑度或几条 Demo。

1. 对比矩阵¶

FP16/BF16 Reference
  vs AWQ Engine

比较：
- 中间层抽样张量误差
- 首 Token Logits Top-k 重合率
- 完整生成文本
- 结构化字段准确率
- 业务安全规则触发率
- 延迟、显存和功耗

2. 风险与回退¶

  • 敏感层保留较高精度；
  • 校准数据覆盖真实摄像头、天气、光照和长尾场景；
  • 输出置信不足或 Schema 校验失败时回退高精度模型/规则；
  • 记录量化版本、校准集版本和 Engine Hash；
  • 不把“文本看起来相近”当作业务等价。

八、分层正确性验证体系¶

1. HF → ONNX Runtime → TensorRT¶

flowchart LR
    HF["Hugging Face FP32/FP16"] --> ONNX["ONNX Export"]
    ONNX --> ORT["ONNX Runtime"]
    ORT --> TRT["TensorRT"]
    HF --> CMP1["Logits / Hidden Compare"]
    ORT --> CMP1
    ORT --> CMP2["Layer / Output Compare"]
    TRT --> CMP2

分层定位：

  • HF 与导出前模型不同：模型配置、Tokenizer 或实现问题；
  • HF 与 ORT 不同：ONNX 导出、动态轴、算子语义问题；
  • ORT 与 TensorRT 不同：Tactic、精度、Plugin、Layout 问题；
  • 单步相同但多步不同：KV Cache、Position、Sampling 或状态管理问题。

2. 比较指标¶

max_abs = np.max(np.abs(actual - expected))
max_rel = np.max(np.abs(actual - expected) / np.maximum(np.abs(expected), 1e-6))
cosine = dot(actual, expected) / (norm(actual) * norm(expected))
topk_overlap = len(set(topk(actual)) & set(topk(expected))) / k

阈值应按数据类型、层和业务影响制定。只使用一个全局 allclose 阈值会掩盖不同张量的尺度差异。

3. 大规模测试¶

182 组任务、1918 个请求序列 可以作为一次项目规模记录，但更重要的是覆盖结构：

维度 覆盖内容
Shape 短/长 Prompt、Block 边界、最大长度
Batch 1、常见值、上限、混合长度
内容 正常、空白、特殊字符、多模态长尾
生命周期 完成、取消、超时、抢占、重试
资源 低显存、Block 耗尽、多 Session
精度 FP16、AWQ、敏感层回退

报告通过率时同时保留失败分类和最小复现输入。

4. Compute Sanitizer 与压力测试¶

compute-sanitizer --tool memcheck ./runtime_tests
compute-sanitizer --tool racecheck ./runtime_tests
compute-sanitizer --tool initcheck ./runtime_tests
compute-sanitizer --tool synccheck ./runtime_tests

Sanitizer 运行慢，应使用小而覆盖边界的专用测试集。它不能替代 CPU Reference、数值对齐、生命周期测试和长时间压力测试。

九、阶段性交付顺序¶

  1. CPU Reference Backend + 单请求状态机；
  2. TensorRT Backend + 静态 Shape；
  3. 外部 KV Cache + Logical Block Manager；
  4. 单请求多步 Decode；
  5. 混合长度动态 Batch；
  6. Prefix Cache 与延迟回收；
  7. AWQ Engine 与业务对齐；
  8. 摄像头到结构化输出全链路；
  9. Nsight、Sanitizer、压力和故障注入；
  10. 目标设备部署包与版本清单。

每阶段都必须具备 Reference、自动测试、性能基线和可回滚产物。

十、与前文章节的关系¶

Runtime 问题 对应章节 第一性原理
Request 状态机 2.1、11.1 异步系统必须显式记录拥有权与完成状态
KV Block 4.4、11.3 间接寻址换取按需分配、共享和低碎片
Dynamic Batching 2.3、8 把不规则请求编译为规则 GPU Batch
Buffer/Stream Pool 2.2、2.3 稳态路径复用资源，完成后才能回收
TensorRT Profile 4.2、11.4 Shape 分布决定特化空间
AWQ 8.3 用精度换带宽和容量，收益与风险都需实测
分层验证 10.3 每个编译/执行边界都可能改变数值与布局
端侧回退 软件工程边界 模型输出是非确定组件，业务必须定义失败语义

最终的工程点睛不在某一个优化技巧，而在于：模型推理一旦进入 Runtime，就变成了一个长期运行的异步资源系统。性能来自批处理、数据布局和复用；正确性来自状态、所有权和分层验证；可靠性来自明确的失败边界与回退路径。
