11.7 手搓 mini decode-only Transformer：把零件焊成一台会说话的机器¶

为什么必须自己攒一台¶

到这里，第 7 章讲了每个算子的数学和 CUDA 骨架，11.1~11.3 讲了引擎怎么调度、怎么管显存。但有一件事一直没做：把它们焊到一起，让它真的吐出字来。

这件事的价值不是「学会写 Transformer」——网上一抓一大把。价值在于它会逼你回答一批只有动手才会遇到的问题：

  • RoPE 在 Prefill 时是给 0..n-1 每个位置都转一次，Decode 时只转一个位置——这两条路径的代码怎么统一？
  • KV Cache 拼接之后，q 的长度是 1、k 的长度是 n，注意力矩阵是 [1, n]——这时候还需要 causal mask 吗？
  • GQA 的 KV Head 比 Q Head 少，repeat_kv 到底是在哪一步展开的？展开会不会真的多占显存？
  • SwiGLU 有三个矩阵而不是两个，那 hidden_dim 该设多大才「公平」？

这些问题在面试里的出现频率极高，而且光看代码是记不住的，写错一次才会真正记住。

这一篇的产出是一个约 300 行的 mini_llm.py：

RMSNorm  →  RoPE  →  GQA Attention + KV Cache  →  SwiGLU FFN
                            ↓
                     Pre-Norm 残差流 × N 层
                            ↓
                  LM Head  →  Sampling  →  generate()

跑起来之后，它能加载真实的 Qwen3/TinyLlama 权重，和 HuggingFace 输出完全一致。

和相邻章节的分工

  • 本篇：把算子组装成能跑的模型，重点是接口、数据流和那些「只有拼起来才会暴露」的坑。
  • 11.2：Attention 的 CUDA Kernel 怎么写快。

一、先算账：一个 Block 的参数都花在哪¶

动手之前先做一件事——搞清楚你要写的东西，哪一部分才是大头。这个账不算，你会把 80% 的精力花在 20% 的开销上。

记 \(d\) = hidden size，一个标准的 Decoder Block 有两大块：

Attention（MHA，\(H_q = H_{kv}\)）

矩阵 形状 参数量
\(W_Q\) \([d, d]\) \(d^2\)
\(W_K\) \([d, d]\) \(d^2\)
\(W_V\) \([d, d]\) \(d^2\)
\(W_O\) \([d, d]\) \(d^2\)
合计 \(\mathbf{4d^2}\)

FFN（原始 Transformer，两个矩阵，\(d_{ff}=4d\)）

矩阵 形状 参数量
\(W_1\) \([d, 4d]\) \(4d^2\)
\(W_2\) \([4d, d]\) \(4d^2\)
合计 \(\mathbf{8d^2}\)
\[ \frac{\text{FFN}}{\text{Attention}} = \frac{8d^2}{4d^2} = 2 \]

FFN 占了一个 Block 三分之二的参数和三分之二的 FLOP。

而如果用了 GQA（比如 \(H_q=32,\ H_{kv}=8\)），\(W_K\) 和 \(W_V\) 缩到原来的 1/4，Attention 只剩 \(d^2 + d^2 + 0.25d^2 + 0.25d^2 = 2.5d^2\)，FFN 的占比进一步升到 76%。

这就是为什么「FFN 是什么」是必问题。 很多人把全部注意力放在 Attention 上（因为它「有意思」），但真实的算力和显存带宽，三分之二以上是被那个「没什么技术含量」的两层 MLP 吃掉的。做推理优化时，FFN 的 GEMM 才是第一优化目标。

带上这个认识往下走。

二、RMSNorm：为什么 LLM 集体抛弃了 LayerNorm¶

1. 两个公式的差别¶

LayerNorm：

\[ \mu=\frac{1}{d}\sum_i x_i,\qquad \sigma^2=\frac{1}{d}\sum_i(x_i-\mu)^2,\qquad y_i=\frac{x_i-\mu}{\sqrt{\sigma^2+\varepsilon}}\gamma_i+\beta_i \]

RMSNorm：

\[ y_i=\frac{x_i}{\sqrt{\frac{1}{d}\sum_j x_j^2+\varepsilon}}\cdot\gamma_i \]

去掉了两样东西：减均值和加偏置 \(\beta\)。

2. 从 GPU 的角度看，省掉的是什么¶

这才是关键。LayerNorm 需要两个统计量（\(\mu\) 和 \(\sigma^2\)），RMSNorm 只需要一个（平方和）。

朴素实现下 LayerNorm 要扫两遍数据：第一遍算 \(\mu\)，第二遍才能算 \(\sigma^2\)。而 Norm 是纯访存受限的算子（每个元素只做几次浮点运算），扫两遍就意味着 HBM 流量翻倍。

工程上当然可以用「同时累加 \(\sum x\) 和 \(\sum x^2\)」把它压成一遍（\(\sigma^2 = \overline{x^2}-\bar x^2\)），但这个式子在 FP16 下会有灾难性抵消——两个相近的大数相减，有效位数全丢。所以稳妥的做法要么用 Welford 算法（更复杂），要么老实扫两遍。

RMSNorm 直接绕开了整个问题：一次归约，一遍读取，没有数值陷阱。

class RMSNorm(nn.Module):
    def __init__(self, dim: int, eps: float = 1e-6):
        super().__init__()
        self.weight = nn.Parameter(torch.ones(dim))
        self.eps = eps

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        dtype = x.dtype
        x = x.float()                                    # ← 关键
        rms = torch.rsqrt(x.pow(2).mean(-1, keepdim=True) + self.eps)
        return (x * rms).to(dtype) * self.weight

3. 那个 .float() 不能省¶

归约在 FP16 下累加几千个平方值，误差会随着加法次数线性累积。\(d=4096\) 时，FP16 的尾数只有 10 位，累加到后面小的项直接被吃掉。

而且这不是「精度差一点」的问题：Norm 的输出会乘进残差流，误差被后面每一层放大。逐层对拍时发现「误差随层数指数增长」，第一个要查的就是 Norm 有没有升精度。

注意上面代码里 .to(dtype) 的位置——先转回半精度再乘 weight，这是为了和 HuggingFace 的实现逐位对齐。顺序换一下数值会有细微差别，对拍时会很困惑。

4. Pre-Norm：Norm 放在哪比它本身更重要¶

原始 Transformer 是 Post-Norm：

x → Attention → +x → Norm → FFN → + → Norm

现代 LLM 全是 Pre-Norm：

x → Norm → Attention → +x  →  Norm → FFN → +
    └────────────────────┘
        残差是一条干净的加法主干道

差别在于：Pre-Norm 里残差路径上没有任何 Norm，从第一层到最后一层是一条纯加法的通路。梯度可以无衰减地传回去，所以能堆到几十上百层还稳定训练。Post-Norm 的残差每层都要过一次 Norm，深了就难训。

推理时这个区别体现为一个实用结论：残差流（residual stream）是整个模型的主干，每一层只是往上面「加一点东西」。这也是为什么最后还要补一个 final_norm —— 残差流累加了几十层，量级已经很大，进 LM Head 前必须再归一化一次。

三、RoPE：把位置编码变成旋转¶

1. 它想要什么性质¶

位置编码的核心诉求是：注意力分数应该只依赖两个 token 的相对距离，不依赖它们的绝对位置。

「第 5 个词看第 3 个词」和「第 105 个词看第 103 个词」，距离都是 2，模型应该用同一套逻辑处理。

RoPE 的做法是给 \(q\) 和 \(k\) 各自旋转一个正比于自身位置的角度。取二维情况看，把 \(q\) 在位置 \(m\) 旋转 \(m\theta\)：

\[ R_m=\begin{pmatrix}\cos m\theta & -\sin m\theta\\ \sin m\theta & \cos m\theta\end{pmatrix} \]

那么内积变成：

\[ \langle R_m q,\ R_n k\rangle = q^{\top}R_m^{\top}R_n k = q^{\top}R_{n-m}k \]

（用到旋转矩阵的性质 \(R_m^{\top}R_n = R_{n-m}\)。）

绝对位置 \(m\)、\(n\) 消失了，只剩下 \(n-m\)。 这就是全部的魔法：不需要把位置加到向量里，只需要旋转，相对性由旋转群的结构自动保证。

2. 高维怎么办：拆成 D/2 个二维平面¶

Head Dim \(D\) 维向量拆成 \(D/2\) 组，每组两个分量当成一个复平面，第 \(i\) 组用不同的转速：

\[ \theta_i = \text{base}^{-2i/D},\qquad i=0,1,\dots,\tfrac{D}{2}-1 \]

\(\text{base}\) 通常取 10000。低维转得快（捕捉近距离关系），高维转得慢（捕捉远距离关系）——这和正弦位置编码的多尺度思想一样。

def build_rope_cache(head_dim: int, max_seq_len: int, base: float = 10000.0,
                     device="cuda"):
    inv_freq = 1.0 / (base ** (torch.arange(0, head_dim, 2, device=device).float() / head_dim))
    t = torch.arange(max_seq_len, device=device).float()
    freqs = torch.outer(t, inv_freq)                 # [max_seq_len, head_dim/2]
    return freqs.cos(), freqs.sin()                  # 预先算好，一次算完到处用


def apply_rope(x: torch.Tensor, cos: torch.Tensor, sin: torch.Tensor):
    """x: [B, T, H, D]   cos/sin: [T, D/2]"""
    x1, x2 = x.chunk(2, dim=-1)                      # 前半 / 后半配对
    cos = cos[None, :, None, :]                      # 广播到 [1, T, 1, D/2]
    sin = sin[None, :, None, :]
    return torch.cat([x1 * cos - x2 * sin,
                      x1 * sin + x2 * cos], dim=-1)

3. 两个坑¶

坑一：配对方式有两种，选错了输出全乱。

上面用的是 [x1, x2] = chunk(2)，也就是「前半配后半」（\(x_0\) 配 \(x_{D/2}\)）——这是 HuggingFace LLaMA/Qwen 的做法。而原论文和一些实现用的是「相邻配对」（\(x_0\) 配 \(x_1\)）。

两种方式数学上等价（只是维度置换），但权重是按某一种训练出来的，用错另一种，输出就是彻底的乱码。对拍时如果发现「第一层 hidden 就对不上，但 shape 全对」，八成是这里。

坑二：Decode 时位置是绝对的，不是 0。

# Prefill：位置是 0, 1, ..., n-1
cos_p, sin_p = cos_cache[:n], sin_cache[:n]

# Decode：位置是 n，不是 0！
cos_d, sin_d = cos_cache[n:n+1], sin_cache[n:n+1]

这也是为什么 11.1 第四节里 positions 要从 cached_tokens 开始算，而不是从 0 开始。RoPE 是唯一一个「知道 token 在全局哪个位置」的模块，位置传错了不会崩，只会让模型觉得所有词都堆在开头。

4. 为什么只转 Q 和 K，不转 V¶

因为位置信息只需要影响「谁该看谁」（注意力权重），不需要影响「看到了什么内容」（值本身）。\(V\) 承载的是内容，转了反而破坏它。

这个问题面试出现频率不低，答案就这一句。

四、Attention + KV Cache：从每步重算到增量更新¶

1. 没有 KV Cache 的话有多蠢¶

生成第 \(n\) 个 token 时，如果老老实实把前 \(n-1\) 个 token 重新过一遍模型：

\[ \text{总计算量}\propto\sum_{n=1}^{N}n^2=O(N^3) \]

而每一步里，前 \(n-1\) 个 token 的 K/V 和上一步算出来的一模一样——因为 causal mask 保证了它们看不到后面的东西，所以它们的表示永远不会变。

这就是 KV Cache 的全部依据：因果性 ⟹ 历史 K/V 不变 ⟹ 可以缓存。 复杂度从 \(O(N^3)\) 降到 \(O(N^2)\)。

（这个「因果性」很关键。如果是双向的 encoder，加一个 token 会改变所有 token 的表示，KV Cache 根本不成立。）

2. GQA：repeat_kv 到底发生在哪¶

GQA 让多个 Query Head 共享一组 KV Head。\(H_q=8,\ H_{kv}=2\) 时：

Q head 0,1,2,3  →  KV head 0
Q head 4,5,6,7  →  KV head 1

PyTorch 里最直白的写法是把 KV「展开」到和 Q 一样多：

def repeat_kv(x: torch.Tensor, n_rep: int) -> torch.Tensor:
    """x: [B, T, H_kv, D] -> [B, T, H_kv * n_rep, D]"""
    if n_rep == 1:
        return x
    B, T, H, D = x.shape
    return x[:, :, :, None, :].expand(B, T, H, n_rep, D).reshape(B, T, H * n_rep, D)

这里有个重要的认知点：expand 不复制数据，只是造一个 stride 为 0 的 view；但后面的 reshape 因为内存不连续，会真的分配一块 n_rep 倍大的显存并拷贝。

所以：

  • 缓存里存的是没展开的 KV（\(H_{kv}\) 份），显存收益是真的；
  • 计算时展开成 \(H_q\) 份，这是为了能直接调 torch.matmul。

真正的 CUDA Kernel（11.2 讲的那个）根本不展开——它让同一组的 Q Head 直接读同一份 KV，省掉这次拷贝，还顺带提高了 L2 命中率。PyTorch 版的 repeat_kv 是一个「为了写得出来」的妥协，不是最优实现。 面试问到 GQA 的实现收益时，这是个能体现深度的点。

3. 完整的 Attention 模块¶

class Attention(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.n_heads = cfg.n_heads
        self.n_kv_heads = cfg.n_kv_heads
        self.head_dim = cfg.head_dim
        self.n_rep = self.n_heads // self.n_kv_heads
        self.scale = self.head_dim ** -0.5

        self.q_proj = nn.Linear(cfg.dim, self.n_heads * self.head_dim, bias=False)
        self.k_proj = nn.Linear(cfg.dim, self.n_kv_heads * self.head_dim, bias=False)
        self.v_proj = nn.Linear(cfg.dim, self.n_kv_heads * self.head_dim, bias=False)
        self.o_proj = nn.Linear(self.n_heads * self.head_dim, cfg.dim, bias=False)

    def forward(self, x, cos, sin, kv_cache=None):
        B, T, _ = x.shape

        q = self.q_proj(x).view(B, T, self.n_heads, self.head_dim)
        k = self.k_proj(x).view(B, T, self.n_kv_heads, self.head_dim)
        v = self.v_proj(x).view(B, T, self.n_kv_heads, self.head_dim)

        q = apply_rope(q, cos, sin)
        k = apply_rope(k, cos, sin)          # 注意：V 不转

        if kv_cache is not None:
            k, v = kv_cache.update(k, v)      # 拼上历史，返回完整的 K/V

        k = repeat_kv(k, self.n_rep)
        v = repeat_kv(v, self.n_rep)

        q = q.transpose(1, 2)                 # [B, H, T_q, D]
        k = k.transpose(1, 2)                 # [B, H, T_kv, D]
        v = v.transpose(1, 2)

        scores = (q @ k.transpose(-2, -1)) * self.scale     # [B, H, T_q, T_kv]

        if T > 1:                             # ← 只有 Prefill 才需要 mask
            T_kv = k.shape[2]
            mask = torch.full((T, T_kv), float("-inf"), device=x.device)
            mask = torch.triu(mask, diagonal=T_kv - T + 1)
            scores = scores + mask

        attn = torch.softmax(scores.float(), dim=-1).to(q.dtype)
        out = (attn @ v).transpose(1, 2).reshape(B, T, -1)
        return self.o_proj(out)

4. if T > 1 这一行值得单独讲¶

Decode 时为什么不需要 causal mask？

因为这一步只有一个 Query（就是刚生成的那个 token），而缓存里的每一个历史 K/V 都排在它前面。「不能看未来」这个约束自动满足了——根本没有未来可看。

scores 的形状是 [B, H, 1, T_kv]，一行全都是合法的。加 mask 是纯浪费。

Prefill 时的 mask 也不是标准的下三角。 注意 diagonal=T_kv - T + 1 这个偏移：如果有 Prefix Cache 命中或者 Chunked Prefill，T_kv > T（Key 比 Query 长），mask 必须右移，让每个 Query 能看到它前面所有的 Key。写成 torch.triu(mask, diagonal=1) 在没有缓存时是对的，一旦有历史就全错。

这是从「玩具实现」走向「能接进引擎」的关键一步，也正好对应 11.1 第七节讲的 cu_seqlens_k > cu_seqlens_q。

5. KV Cache 的最简实现¶

class KVCache:
    """教学版：连续预分配。生产版见 11.3 的分页实现。"""
    def __init__(self, B, max_len, n_kv_heads, head_dim, dtype, device):
        shape = (B, max_len, n_kv_heads, head_dim)
        self.k = torch.zeros(shape, dtype=dtype, device=device)
        self.v = torch.zeros(shape, dtype=dtype, device=device)
        self.length = 0

    def update(self, k_new, v_new):
        T = k_new.shape[1]
        self.k[:, self.length:self.length + T] = k_new
        self.v[:, self.length:self.length + T] = v_new
        self.length += T
        return self.k[:, :self.length], self.v[:, :self.length]

这个实现的问题正是 11.3 存在的理由：max_len 必须按最坏情况预留，短请求也占满，多请求之间没法共享。把这几行换成分页版，就是 PagedAttention。

现在你能看清整条演化路径了：

每步重算 (O(N³))
  → 连续 KV Cache (O(N²)，但按 max_len 预留)      ← 本篇
  → 分页 KV Cache (按需分配、可共享)               ← 11.3
  → Prefix Cache (整块复用)                        ← 11.1 §5
  → Radix Cache (token 级复用)                     ← 11.8

五、SwiGLU FFN：Transformer 里最胖的那块¶

第一节算过，FFN 吃掉了三分之二以上的参数和算力。但它的结构反而是全模型最简单的。

1. 从两个矩阵到三个矩阵¶

原始 Transformer 的 FFN：

\[ \text{FFN}(x) = W_2\ \sigma(W_1 x) \]

SwiGLU 版本多了一路：

\[ \text{FFN}(x) = W_{down}\Big(\underbrace{\text{SiLU}(W_{gate}\,x)}_{\text{门}}\ \odot\ \underbrace{W_{up}\,x}_{\text{值}}\Big) \]

多出来的那一路叫门控（gating）：一路算「内容」，另一路算「每个通道该放行多少」，逐元素相乘。

直觉上，\(\text{SiLU}\) 的输出接近 0 时对应通道被抑制，接近 1 时放行。它给了网络一个「按输入内容动态选择激活哪些通道」的能力，而普通 FFN 的激活模式是固定的。这个改动在同等参数量下能稳定提升效果，所以 LLaMA 之后基本成了标配。

2. 面试必问：为什么 \(d_{ff}\) 是 \(\frac{8}{3}d\)¶

这题问的是「你有没有真的想过参数量」。

原始 FFN 两个矩阵，\(d_{ff}=4d\)：

\[ P_{\text{原始}} = d\cdot 4d + 4d\cdot d = 8d^2 \]

SwiGLU 有三个矩阵（gate、up、down）。要保持参数量不变：

\[ 3\cdot d\cdot d_{ff} = 8d^2\quad\Longrightarrow\quad d_{ff} = \frac{8}{3}d \approx 2.667\,d \]

所以 \(\frac{8}{3}\) 不是什么玄学，就是「三个矩阵要和原来两个矩阵一样重」解出来的。

实际模型还会把它对齐到 256 的倍数（为了 Tensor Core 的 tile 对齐和 TP 切分能整除）：

hidden_dim = int(8 * dim / 3)
hidden_dim = multiple_of * ((hidden_dim + multiple_of - 1) // multiple_of)

LLaMA-7B：\(d=4096\)，\(\frac{8}{3}\times 4096 = 10922.7\)，对齐到 256 的倍数 → 11008。这个数字如果你在模型配置里见过又不知道哪来的，现在知道了。

3. SiLU 和 GELU 差在哪¶

\[ \text{SiLU}(x) = x\cdot\sigma(x) = \frac{x}{1+e^{-x}} \]
\[ \text{GELU}(x) = x\cdot\Phi(x)\approx 0.5x\left(1+\tanh\left[\sqrt{\tfrac{2}{\pi}}(x+0.044715x^3)\right]\right) \]

两条曲线几乎重合（SiLU 也叫 Swish-1）。区别在实现成本：

运算 GPU 成本
SiLU 一次 exp + 一次除法 低，可用 __expf 快速路径
GELU（精确） erf 高
GELU（tanh 近似） tanh + 三次多项式 中

效果几乎一样，SiLU 更便宜，所以选 SiLU。 就这么简单，没有更深的理由。

4. 为什么 gate 和 up 要融合成一个矩阵¶

class FFN(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.gate_proj = nn.Linear(cfg.dim, cfg.hidden_dim, bias=False)
        self.up_proj   = nn.Linear(cfg.dim, cfg.hidden_dim, bias=False)
        self.down_proj = nn.Linear(cfg.hidden_dim, cfg.dim, bias=False)

    def forward(self, x):
        return self.down_proj(F.silu(self.gate_proj(x)) * self.up_proj(x))

这是教学写法。推理引擎会把前两个合成一个：

# 引擎里的写法
gate_up = self.gate_up_proj(x)              # [.., 2 * hidden_dim]
gate, up = gate_up.chunk(2, dim=-1)
return self.down_proj(F.silu(gate) * up)

原因在 11.1 第九节讲过：gate 和 up 吃的是同一个 \(x\)。 分开做两次 GEMM，\(x\) 要从 HBM 读两遍；合成一个 \([d, 2d_{ff}]\) 的大矩阵只读一遍，而且 GEMM 更大更容易打满 Tensor Core。

同理，\(W_Q/W_K/W_V\) 也吃同一个输入，所以引擎里合成 qkv_proj。

判断能不能融合的规则就一条：输入是不是同一个张量。 down_proj 的输入是乘完之后的结果，所以它不能被融进去。

5. FFN 是 elementwise 和 GEMM 的分界线¶

从算子分类看，FFN 里有：

  • 三个 GEMM（算力受限，Prefill 时是绝对主力）；
  • 一个 SiLU + 乘法（elementwise，纯访存受限）。

中间那个 elementwise 会产生一个 \([B, T, d_{ff}]\) 的中间张量。\(d_{ff}\) 比 \(d\) 大 2.67 倍，这是整个 Block 里最大的中间激活，也是 Prefill 时显存峰值的主要贡献者（回想 11.1 第八节为什么要 Warmup 测峰值）。

所以 SiLU(gate) * up 是算子融合的头号目标：融合之后中间结果留在寄存器/共享内存里，省掉一次 \([B,T,d_{ff}]\) 的写和两次读。这正是 4.1 算子融合 里那个例子的真实出处。

六、把一层拼起来¶

class Block(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.attn_norm = RMSNorm(cfg.dim, cfg.norm_eps)
        self.attn = Attention(cfg)
        self.ffn_norm = RMSNorm(cfg.dim, cfg.norm_eps)
        self.ffn = FFN(cfg)

    def forward(self, x, cos, sin, kv_cache=None):
        x = x + self.attn(self.attn_norm(x), cos, sin, kv_cache)   # Pre-Norm
        x = x + self.ffn(self.ffn_norm(x))
        return x

四行，就是一个 Transformer Block 的全部。

盯着这两行看一会儿，会发现一个重要的结构：

x ──────────────────────────────┬──→ + ──────────────────┬──→ +  ──→
   └→ Norm → Attention ─────────┘     └→ Norm → FFN ─────┘

   ↑ 这条主干道（残差流）上没有任何非线性、没有任何 Norm

残差流是一条纯加法的传送带，每个 Block 只是往上面「读一点、加一点」。这个视角很有用：

  • 它解释了为什么模型能堆到 100 层：加法不会让梯度衰减；
  • 它解释了为什么 Norm 必须在分支里：主干道要保持干净；
  • 它解释了为什么最后要 final_norm：几十层累加下来，残差流的数值量级已经很大，直接进 LM Head 会溢出或者让 softmax 饱和。

七、模型骨架：Embedding、层堆叠、LM Head¶

@dataclass
class Config:
    vocab_size: int = 32000
    dim: int = 512
    n_layers: int = 8
    n_heads: int = 8
    n_kv_heads: int = 2          # GQA：4 个 Q Head 共享 1 个 KV Head
    head_dim: int = 64
    hidden_dim: int = 1376       # ≈ 8/3 * 512，对齐到 32 的倍数
    norm_eps: float = 1e-6
    rope_base: float = 10000.0
    max_seq_len: int = 2048
    tie_embeddings: bool = True


class MiniLLM(nn.Module):
    def __init__(self, cfg: Config):
        super().__init__()
        self.cfg = cfg
        self.embed = nn.Embedding(cfg.vocab_size, cfg.dim)
        self.layers = nn.ModuleList([Block(cfg) for _ in range(cfg.n_layers)])
        self.final_norm = RMSNorm(cfg.dim, cfg.norm_eps)
        self.lm_head = nn.Linear(cfg.dim, cfg.vocab_size, bias=False)

        if cfg.tie_embeddings:
            self.lm_head.weight = self.embed.weight     # 共享同一块显存

        cos, sin = build_rope_cache(cfg.head_dim, cfg.max_seq_len, cfg.rope_base)
        self.register_buffer("cos_cache", cos, persistent=False)
        self.register_buffer("sin_cache", sin, persistent=False)

    def forward(self, input_ids, start_pos=0, kv_caches=None):
        B, T = input_ids.shape
        x = self.embed(input_ids)

        cos = self.cos_cache[start_pos:start_pos + T]    # ← 绝对位置切片
        sin = self.sin_cache[start_pos:start_pos + T]

        for i, layer in enumerate(self.layers):
            x = layer(x, cos, sin, kv_caches[i] if kv_caches else None)

        x = self.final_norm(x)
        return self.lm_head(x)

三个细节：

start_pos 是整个 KV Cache 机制的位置锚点。 Prefill 时是 0，Decode 时是「已经生成了多少个 token」。传错了模型不会报错，只会输出语义漂移的文本——这是最难查的一类 bug，因为它看起来「像是模型能力不行」。

tie_embeddings 让 LM Head 和 Embedding 共享权重。小模型上这能省掉 vocab_size × dim 的参数（32000×512 = 1600 万，对一个几千万参数的模型是很大一块）。大模型通常不共享，因为词表相对小了、而且解绑效果更好。加载权重时这是个高频坑：共享的话 checkpoint 里可能只有一份，你按两个名字去找就会「漏载」。

persistent=False 让 RoPE 缓存不进 state_dict。它是纯粹算出来的，存进去只会让 checkpoint 变大，还会在改 max_seq_len 时报 shape 不匹配。

八、generate()：两条路径¶

现在把模型跑起来。注意这里的结构和 11.1 讲的引擎是同构的，只是没有调度器：

@torch.inference_mode()
def generate(model, input_ids, max_new_tokens, sampler):
    cfg = model.cfg
    B = input_ids.shape[0]

    kv_caches = [
        KVCache(B, cfg.max_seq_len, cfg.n_kv_heads, cfg.head_dim,
                dtype=model.embed.weight.dtype, device=input_ids.device)
        for _ in range(cfg.n_layers)
    ]

    # ---- Prefill：一次吃完整个 prompt ----
    logits = model(input_ids, start_pos=0, kv_caches=kv_caches)
    next_token = sampler(logits[:, -1, :])            # ← 只要最后一个位置
    out = [next_token]

    # ---- Decode：每次一个 token ----
    for _ in range(max_new_tokens - 1):
        pos = kv_caches[0].length
        logits = model(next_token.unsqueeze(1), start_pos=pos, kv_caches=kv_caches)
        next_token = sampler(logits[:, -1, :])
        out.append(next_token)

    return torch.stack(out, dim=1)

对照一下就会发现，11.1 讲的那一堆机制，全都是从这十几行长出来的：

这里的写法 引擎里变成了什么 为什么要变
logits[:, -1, :] cu_seqlens_q[1:] - 1 的 Gather 变长 batch 里没有统一的「最后一个」
KVCache 连续预分配 Paged KV Cache 省显存、能共享
固定的 B Continuous Batching 请求随时进出
start_pos Sequence.cached_tokens 每条序列的进度不同
Python for 循环 engine.step() 要能插入调度、抢占、流式输出

Prefill 那一步的 logits[:, -1, :] 尤其值得注意：模型其实为 prompt 的每个位置都算了 logits，但我们只用最后一个。11.1 第十节算过这笔账——2048 长的 prompt，全算是 2.5 TFLOP，只算最后一个是 1.2 GFLOP，2048 倍。所以引擎会在 LM Head 之前就把 hidden state 切出来。

在这个 mini 版本里可以先不管，但你要知道这个浪费在哪。

九、Sampling：从 argmax 到 top-p¶

1. Greedy¶

def greedy(logits):
    return logits.argmax(dim=-1)

调试时永远用它。 只有 Greedy 才能做「输出必须完全一致」的对拍，任何随机性都会让你分不清是 bug 还是采样噪声。

2. Temperature¶

probs = torch.softmax(logits.float() / temperature, dim=-1)

\(T<1\) 把分布拉尖（更确定），\(T>1\) 压平（更随机）。\(T\to 0\) 退化成 Greedy。

.float() 不能省——词表 151936 那么宽，FP16 的 softmax 在小 temperature 下会有一堆 0。

3. Top-k¶

只在概率最高的 \(k\) 个里采样：

def top_k_filter(logits, k):
    if k <= 0:
        return logits
    kth = logits.topk(k, dim=-1).values[:, -1:]      # 第 k 大的值
    return logits.masked_fill(logits < kth, float("-inf"))

4. Top-p（Nucleus）：为什么它在 GPU 上不好写¶

Top-p 取「累积概率刚好超过 \(p\) 的最小集合」。它比 top-k 更合理——分布尖锐时自动收窄，平坦时自动放宽。

但看它的实现：

def top_p_filter(logits, p):
    sorted_logits, sorted_idx = logits.sort(dim=-1, descending=True)   # ← 问题在这
    cum_probs = sorted_logits.softmax(-1).cumsum(-1)

    # 保留累积概率首次超过 p 的那个位置及其之前
    remove = cum_probs - sorted_logits.softmax(-1) > p
    sorted_logits = sorted_logits.masked_fill(remove, float("-inf"))

    return sorted_logits.scatter(1, sorted_idx.argsort(-1), sorted_logits)

那个 sort 是对 151936 个元素排序，每条序列都要排一次。 这是整个采样流程里最贵的操作，甚至可能比一层 Transformer 还慢。

工程上的解法是先 top-k 截断再排序：

K = 1024                                     # 经验值，远大于任何实际的 nucleus 大小
top_logits, top_idx = logits.topk(K, dim=-1)  # topk 比全排序快得多
# 之后所有 top-p 逻辑都在这 K 个上做

理由是：如果 nucleus 真的需要超过 1024 个 token，说明分布已经平到接近均匀，此时截断的影响可以忽略。vLLM、TensorRT-LLM 都是这么做的。

「top-p 怎么在 GPU 上高效实现」是推理岗的经典题，考的就是你有没有意识到那个全词表排序。答案的关键词：topk 预截断 + 桶内 cumsum。

5. 组合起来¶

def make_sampler(temperature=1.0, top_k=0, top_p=1.0):
    def sampler(logits):
        if temperature == 0:
            return logits.argmax(dim=-1)
        logits = logits.float() / temperature
        if top_k > 0:
            logits = top_k_filter(logits, top_k)
        if top_p < 1.0:
            logits = top_p_filter(logits, top_p)
        probs = logits.softmax(dim=-1)
        return torch.multinomial(probs, num_samples=1).squeeze(-1)
    return sampler

生产实现会把 multinomial 换成 Gumbel-max（11.1 第十节讲过），因为 multinomial 内部要做前缀和 + 二分查找，对宽词表不友好。

顺序也是有讲究的：temperature → top-k → top-p。先缩放再截断，因为 temperature 会改变分布形状，进而改变 nucleus 的大小。反过来做结果不一样。

十、对拍：怎么确认自己写对了¶

写完不验证等于没写。分层对拍是唯一靠谱的方法，从下往上：

第 0 层：形状和数值范围¶

assert model(torch.randint(0, cfg.vocab_size, (2, 16)).cuda()).shape == (2, 16, cfg.vocab_size)

第 1 层：单算子 vs PyTorch 内置¶

# RMSNorm
ref = torch.nn.functional.rms_norm(x.float(), (cfg.dim,), norm.weight.float(), eps=1e-6)
torch.testing.assert_close(norm(x).float(), ref, rtol=1e-3, atol=1e-3)

# RoPE：验证它的定义性质——内积只依赖相对位置
q = torch.randn(1, 1, 1, cfg.head_dim)
k = torch.randn(1, 1, 1, cfg.head_dim)
for (m, n) in [(0, 3), (5, 8), (100, 103)]:          # 相对距离都是 3
    qm = apply_rope(q, cos[m:m+1], sin[m:m+1])
    kn = apply_rope(k, cos[n:n+1], sin[n:n+1])
    print((qm * kn).sum())                            # ← 这三个数必须相等

RoPE 那个测试特别值得写：它不是和某个参考实现比，而是直接验证「相对位置不变性」这条定义性质。配对方式写错的话，这三个数立刻就不相等了。这种「验证性质而非验证数值」的测试，比对拍更能定位问题。

第 2 层：KV Cache 的等价性¶

这是最关键的一条测试：

ids = torch.randint(0, cfg.vocab_size, (1, 10)).cuda()

# 路径 A：一次性全部前向，不用 cache
logits_full = model(ids, start_pos=0, kv_caches=None)

# 路径 B：先 prefill 前 5 个，再逐个 decode 后 5 个
caches = [KVCache(...) for _ in range(cfg.n_layers)]
model(ids[:, :5], start_pos=0, kv_caches=caches)
outs = []
for t in range(5, 10):
    outs.append(model(ids[:, t:t+1], start_pos=t, kv_caches=caches))

torch.testing.assert_close(logits_full[:, 5:], torch.cat(outs, dim=1),
                           rtol=2e-2, atol=2e-2)

「带 cache 逐步走」和「不带 cache 一次走完」必须得到相同的 logits。 这一条覆盖了 KV Cache、start_pos、RoPE 位置、mask 偏移的全部逻辑。它挂了，上面四个里必有一个错。

十一、跑起来：加载真实权重¶

自己训一个模型不现实，但可以加载现成的权重来验证。以 HF 格式的 LLaMA 系模型为例：

def load_hf_weights(model: MiniLLM, hf_state: dict):
    m = {}
    m["embed.weight"] = hf_state["model.embed_tokens.weight"]
    m["final_norm.weight"] = hf_state["model.norm.weight"]
    if "lm_head.weight" in hf_state:                       # 可能因为 tie 而不存在
        m["lm_head.weight"] = hf_state["lm_head.weight"]

    for i in range(model.cfg.n_layers):
        p, q = f"layers.{i}", f"model.layers.{i}"
        m[f"{p}.attn_norm.weight"] = hf_state[f"{q}.input_layernorm.weight"]
        m[f"{p}.attn.q_proj.weight"] = hf_state[f"{q}.self_attn.q_proj.weight"]
        m[f"{p}.attn.k_proj.weight"] = hf_state[f"{q}.self_attn.k_proj.weight"]
        m[f"{p}.attn.v_proj.weight"] = hf_state[f"{q}.self_attn.v_proj.weight"]
        m[f"{p}.attn.o_proj.weight"] = hf_state[f"{q}.self_attn.o_proj.weight"]
        m[f"{p}.ffn_norm.weight"] = hf_state[f"{q}.post_attention_layernorm.weight"]
        m[f"{p}.ffn.gate_proj.weight"] = hf_state[f"{q}.mlp.gate_proj.weight"]
        m[f"{p}.ffn.up_proj.weight"] = hf_state[f"{q}.mlp.up_proj.weight"]
        m[f"{p}.ffn.down_proj.weight"] = hf_state[f"{q}.mlp.down_proj.weight"]

    missing, unexpected = model.load_state_dict(m, strict=False)
    assert not [k for k in missing if "cache" not in k], f"漏载: {missing}"
    assert not unexpected, f"多余: {unexpected}"
    return model

最后那两个 assert 是重点。 11.1 第九节讲过，「漏载权重」是最阴险的错误——某个矩阵保持随机初始化，模型照样输出通顺的句子，只是内容不对。用 strict=False 加手工检查，比直接 strict=True 更灵活（能放过 RoPE cache 这类 buffer），但必须自己把差集打出来看。

推荐用 TinyLlama-1.1B 做验证：小到能在任何卡上跑，结构是标准的 LLaMA（RMSNorm + RoPE + GQA + SwiGLU），和这篇的实现完全对得上。

十二、你现在应该能回答这些¶

写完并跑通之后，下面这些应该都是脱口而出的：

结构类

  1. 一个 Decoder Block 里，参数和 FLOP 怎么分配？为什么说 FFN 才是大头？
  2. Pre-Norm 和 Post-Norm 差在哪？为什么现代 LLM 全用 Pre-Norm？
  3. 为什么最后还要一个 final_norm？

算子类

  1. RMSNorm 比 LayerNorm 省了什么？为什么归约必须升到 FP32？
  2. RoPE 为什么能保证注意力只依赖相对位置？（写出 \(R_m^{\top}R_n=R_{n-m}\)）
  3. 为什么 RoPE 只作用于 Q 和 K，不作用于 V？
  4. SwiGLU 的 \(d_{ff}\) 为什么是 \(\frac{8}{3}d\)？（推一遍参数量守恒）
  5. SiLU 和 GELU 差在哪？为什么 LLM 选 SiLU？
  6. 哪些矩阵可以融合，判断依据是什么？

推理类

  1. KV Cache 成立的前提是什么？为什么 encoder 不能用？
  2. Decode 时为什么不需要 causal mask？
  3. 有 Prefix Cache 时，mask 的 diagonal 为什么要偏移？
  4. GQA 的 repeat_kv 在 PyTorch 里会真的多占显存吗？CUDA Kernel 里呢？
  5. top-p 在 GPU 上的性能瓶颈是什么？怎么绕过？

动手标准

  • 第十节第 2 层那个「带 cache 逐步走 == 不带 cache 一次走完」的测试能通过；
  • 加载 TinyLlama 权重后，和 HuggingFace 在 Greedy 采样下生成完全相同的 token 序列。
