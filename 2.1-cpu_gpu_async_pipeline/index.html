2.1 CPU-GPU 异步流水线 (Fence, Event, 三重缓冲)¶

概述¶

CPU 和 GPU 是相互独立调度的执行引擎。离散 GPU 通常通过 PCIe 连接并拥有独立显存；集成 GPU 或 Grace Hopper 等平台可能使用统一或一致性更强的内存系统。无论拓扑如何，高效应用都要减少不必要的主机等待并建立清晰的资源生命周期。

本章从你最熟悉的同步机制出发，逐步深入到现代图形 API 和 CUDA 中使用的非阻塞异步流水线模式，最终展示这一思想如何从游戏引擎迁移到大模型推理引擎。

1. 两种同步策略：阻塞等待 vs 非阻塞查询¶

1.1 阻塞等待 (Blocking Wait)¶

这是最直观的同步方式。CPU 提交任务后调用阻塞 API，线程挂起，直到 GPU 完成指定任务。

API 行为 典型场景
DX12: SetEventOnCompletion + WaitForSingleObject 先把 Fence 值绑定到 Event，再阻塞 CPU 线程 等待某个提交点完成
DX12: SetEventOnCompletion 注册 Event，本身不等待 为后续等待或通知做准备
CUDA: cudaDeviceSynchronize() 阻塞 CPU 直到 GPU 上所有任务完成 测试、Debug、Profiling
CUDA: cudaEventSynchronize(event) 阻塞 CPU 直到某个 Event 被 Record 精确等待某个 Kernel 完成

代价：该 CPU 线程不能继续执行当前工作；操作系统可以调度其他线程。等待是否可接受取决于资源复用点、延迟目标和可用的其他 CPU 工作。

1.2 非阻塞查询 (Polling / Query)¶

这就是你说的"计数的打标记点"——CPU 不阻塞，而是去查一个标记是否被 GPU 翻牌，没完成就先去干别的，过会儿再来问。

API 行为 本质
DX12: ID3D12Fence::GetCompletedValue() 查询 Fence 当前值，不阻塞 CPU 看 GPU 进度到哪了
CUDA: cudaEventQuery(event) 查询 Event 是否被 Record，返回 cudaSuccess 或 cudaErrorNotReady CPU 查一下标记到了没
Vulkan: vkGetFenceStatus 查询 Fence 状态 同上

核心优势：非阻塞。CPU 可以继续录制下一帧的 Command List、更新骨骼动画、加载纹理——或者用 CUDA 的语境说，预处理下一个 Batch 的请求、准备 KV Cache。

你的原话："反正就是 CPU 就在一直轮巡这个 fence 的值，这个比 wait for single object，更好的点，是不是渲染那边可以做三重帧缓冲 ring buffer，Next frame 继续 record 以及分配 CPU resource allocation 的更新，以及上传到另一块 gpu buffer 上，以及还有一些杂七杂八的引擎的 CPU 硬核计算。"

完全正确。 这就是帧并行 (Frame Parallelism) 的核心。

sequenceDiagram
    participant CPU
    participant Queue as GPU Queue
    participant Pool as Frame/Batch Resources
    CPU->>Queue: Submit N and signal fence N
    CPU->>Pool: Prepare independent resources N+1
    Queue-->>CPU: Fence N completed
    CPU->>Pool: Reuse resources from N

2. 画面撕裂与双/三重缓冲¶

2.1 画面撕裂的本质¶

你提到的一个经典场景——画面撕裂 (Screen Tearing)——完美解释了为什么需要非阻塞同步。

画面撕裂发生的条件： - 生产者：GPU 渲染管线正在写入帧缓冲区 - 消费者：显示控制器 (Display Controller) 正在读取帧缓冲区 - 速度不匹配：渲染速度超过回传/扫描速度 - 后果：消费者读到了前一半新帧 + 后一半旧帧

这个问题可用生产者/消费者模型理解，但它与分布式训练的计算/通信重叠只共享“并发阶段和同步点”的抽象；资源、时序约束和正确性条件不同。

2.2 垂直同步 (V-Sync)：阻塞方案¶

最简单的解法：让渲染管线等显示控制器读完当前帧，再画下一帧。

渲染管线 → 等待 V-Sync → 写入 Front Buffer → 显示控制器读取
         ← 卡住，不能画下一帧 ←

代价：帧率被限制在显示器刷新率（如 60Hz），GPU 利用率下降。

AI 中的对应：cudaDeviceSynchronize() 或同步 AllReduce——SM 空转等通信完成。

2.3 双重缓冲 (Double Buffering)：空间换时间¶

准备两个后备缓冲 (Back Buffer)，渲染管线写入其中一个，显示控制器读取另一个。

Back Buffer 0: [GPU 正在写入]  →  完成 → [显示控制器读取]
Back Buffer 1: [显示控制器读取] →  完成 → [GPU 正在写入]

仍可能撕裂？ 如果 GPU 写入速度超过 V-Sync 周期，且两者切换时机不对，仍可能出现撕裂。所以典型的双重缓冲仍然配合 V-Sync 使用。

2.4 三重缓冲 (Triple Buffering)：你熟悉的方案¶

你曾在云渲染中亲手实践过：准备 3 个 Render Target。

Frame N:     GPU 写入 Buffer A
Frame N+1:   GPU 写入 Buffer B  ← 不等待，直接切到空闲 Buffer
Frame N+2:   GPU 写入 Buffer C  ← 完全不阻塞
显示控制器:  读取已完成的 Buffer (比如 A)

效果： - 相比双缓冲，多一个可用槽位能降低生产者等待消费者的概率 - 当 GPU、显示或编码端持续跟不上时，三个 Buffer 仍会耗尽，随后必须等待、排队或丢帧 - 代价：多占用一份显存空间

这就是你之前在聊天中说的"我设置了多个 Render Target"在云渲染中的实战应用。

3. 帧并行 (Frame Parallelism) 工程实现¶

3.1 DX12 三重缓冲 + 轮询 Fence 实战¶

// 伪代码：三重缓冲帧循环
const int NUM_FRAMES = 3;
ID3D12Fence* fences[NUM_FRAMES];
UINT64 fenceValues[NUM_FRAMES] = {};

// 主循环
for (int frame = 0; ; frame++) {
    int frameIndex = frame % NUM_FRAMES;

    // 1. 轮询当前帧的 Fence——非阻塞
    if (fences[frameIndex]->GetCompletedValue() < fenceValues[frameIndex]) {
        // GPU 还没干完这一帧的活？跳过这帧（相当于丢帧策略）
        // 或者你可以选择阻塞等（但那就不是高性能路径了）
        continue;
    }

    // 2. CPU 更新这一帧的动态资源（骨骼动画、粒子、上传纹理）
    UpdateSkinnedMesh(frameIndex);
    UploadDynamicBuffers(frameIndex);

    // 3. 录制 Command List（渲染命令）
    cmdList->Reset(cmdAllocator[frameIndex], nullptr);
    RecordDrawCommands(cmdList, frameIndex);
    cmdList->Close();

    // 4. 提交并 Signal Fence（告诉 GPU：这一帧的活来了）
    cmdQueue->ExecuteCommandLists(1, &cmdList);
    cmdQueue->Signal(fences[frameIndex], ++fenceValues[frameIndex]);
}

3.2 CUDA 中完全相同的模式¶

// CUDA 三重缓冲 + 轮询 Event
const int NUM_FRAMES = 3;
cudaStream_t streams[NUM_FRAMES];
cudaEvent_t events[NUM_FRAMES];

for (int batch = 0; ; batch++) {
    int idx = batch % NUM_FRAMES;

    // 1. 非阻塞查询：上一轮的这个 Stream 跑完了吗？
    cudaError_t err = cudaEventQuery(events[idx]);
    if (err == cudaErrorNotReady) {
        // GPU 还没算完，跳过这轮或处理其他请求
        continue;
    }

    // 2. CPU 准备下一批数据（预处理 Token、加载 KV Cache）
    PrepareNextBatchInput(idx);

    // 3. 异步启动 Kernel
    kernel<<<grid, block, 0, streams[idx]>>>(d_input[idx], d_output[idx]);
    cudaEventRecord(events[idx], streams[idx]);

    // 4. CPU 不等待，立刻回去准备下一批
}

边界说明：这段代码展示的是多缓冲资源复用。Continuous Batching 还需要请求级调度、KV Block 管理、Token Budget、采样结果处理和模型执行器；不能只靠 cudaEventQuery 实现。

4. 生产者-消费者溢出与降级策略¶

你提到了另一个深刻的问题："云渲染纹理回传时，GPU 渲染比回传快，导致后面帧重叠"。

这是经典的"生产者-消费者溢出"问题。在图形和 AI 中，降级策略完全对应：

场景 策略 A：等待 / 阻塞 策略 B：丢帧 / 累积
云渲染 阻塞渲染直到编码器空闲 丢帧 (Frame Drop)，跳过低优先级帧
大模型训练 同步 AllReduce，部分阶段等待通信 梯度累积可降低通信频率，但会改变有效 Batch 和优化过程，并非“丢帧”等价物
AI 推理 阻塞等待显存释放 Swap 踢出：把旧 KV Cache 移到 CPU 内存

你的"多 Render Target"实践恰好覆盖了策略 B 的思想——用空间换时间，用多缓冲掩盖延迟。

5. 宏观映射：图形引擎 → AI 推理引擎¶

图形引擎 (DX12 / Vulkan) AI 推理引擎 (vLLM / TensorRT) 本质
准备第 N+1 帧的顶点数据 准备第 N+1 个请求的 KV Cache + Input IDs CPU 预处理，填充 Ring Buffer
轮询 Fence 看第 N 帧是否画完 cudaEventQuery 看第 N 个 Batch 是否算完 非阻塞查进度
用 Ring Buffer 覆盖旧 Vertex Buffer PagedAttention 回收旧 KV Cache Block 资源池复用，避免分配延迟
三重缓冲防止画面撕裂 Ping-Pong Buffer 防止通信读到半成品 空间换时间，消费者/生产者解耦
丢帧策略 梯度累积 / Swap 踢出 资源池满了的降级策略

总结¶

图形渲染中的 CPU/GPU 解耦和资源池经验可以帮助理解推理运行时，但框架调度还要处理请求级状态、动态形状与 KV Cache 生命周期。cudaEventQuery 和 Stream 是底层进度与顺序工具，不等于调度器本身。

一句话总结：多缓冲隔离正在使用的资源，Fence/Event 证明何时可以安全复用；是否真正实现重叠要用时间线验证。
