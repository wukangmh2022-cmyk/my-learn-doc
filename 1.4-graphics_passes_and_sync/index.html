1.4 图形管线中的 Pass 与同步 (RenderPass, Barrier)¶

概述¶

图形渲染管线中的 "Pass" 和 "同步"，是理解 GPU 工作流组织方式的核心概念。在 Vulkan 和 DX12 中，你通过 RenderPass（渲染通道）组织渲染任务，通过 Resource Barrier（资源屏障）保证读写顺序。

AI 推理中的算子与事件也表达 GPU 工作和依赖，但图形 Pass、CUDA Kernel、计算图节点和线程块同步处于不同抽象层级。

一、Pass 的概念：渲染任务的原子单元¶

什么是 Pass？¶

在图形渲染中，一个 Pass 就是一次完整的 GPU 渲染任务：

  1. 绑定 PSO、顶点缓冲、纹理等资源
  2. 执行 Draw Call / Dispatch
  3. 写入 Render Target

多个 Pass 串联起来，构成完整的渲染帧。

Pass 1: 生成 G-Buffer (MRT) → 写入 Position/Normal/Albedo
    ↓ (Resource Barrier: RT → SRV)
Pass 2: 光照计算 → 读取 G-Buffer，写入光照结果
    ↓
Pass 3: 后处理 → 读取光照结果，输出最终颜色

图形 Pass vs AI Kernel（类比边界）¶

维度 图形 Pass AI Kernel
本质 GPU 执行的一个渲染任务 GPU 执行的一个计算任务
输入 Vertex Buffer、Texture Global Memory 中的张量
输出 Render Target（RT） Global Memory 中的输出张量
资源绑定 PSO、Root Signature Kernel 参数、Launch 配置
同步方式 Resource Barrier + Queue Signal/Wait Kernel 边界、同 Stream 顺序或跨 Stream Event；__syncthreads() 仅限单个 Block 内

二、Resource Barrier（资源屏障）：Pass 间的同步¶

图形中的 Barrier¶

在 DX12/Vulkan 中，当一个 Pass 的输出是下一个 Pass 的输入时，你必须插入 Resource Barrier：

// DX12: 纹理从 Render Target 切到 Pixel Shader Resource
resourceBarrier->Transition(
    texture, 
    D3D12_RESOURCE_STATE_RENDER_TARGET,    // 上一个 Pass：写入
    D3D12_RESOURCE_STATE_PIXEL_SHADER_RESOURCE  // 下一个 Pass：读取
);

Barrier 的本质是告诉驱动："请等上一个 Pass 的 Pixel Shader 全部写完这个纹理，再让下一个 Pass 开始读它"。

硬件真相：Barrier 在 CPU 端只是一条命令，插入在 Command List 里，不会阻塞 CPU。它让硬件驱动在 GPU 端插入依赖关系，确保执行顺序正确。

CUDA 中的对应¶

CUDA 中没有 DX12/Vulkan 那样复杂的 Barrier 枚举，但逻辑完全一致：

图形 Barrier 类型 CUDA 对应 说明
Render Target → Shader Resource 同一 Stream 内隐式保证 同一 Stream 里，后一个 Kernel 自动等前一个写完
跨 Queue 同步 cudaEvent + cudaStreamWaitEvent 手动插入依赖关系 = 你手动写 Barrier
Aliasing Barrier __threadfence() 确保内存操作对其他线程可见

关键认知（你的直觉完全正确）：

"CUDA 的 Stream，就是一个能自动维护依赖的、无止境的 Command List。我只需要按顺序 cudaLaunchKernel，它就会自己像渲染管线一样往前走。只有当我需要跨 Stream 操作，或者想搞显存 Pool 复用时，我才需要像在 DX12 里插 Barrier 一样，去插 cudaEvent。"

三、TBDR vs TDS：硬件架构与软件算法¶

TBDR（Tile-Based Deferred Rendering）¶

硬件架构层面——GPU 怎么造。

TBDR 是移动端 GPU（如 Apple M 系列、PowerVR）的渲染管线设计：

  1. 屏幕分成 Tile（如 32×32 像素）
  2. 每个 Tile 的顶点/光栅化处理完 → 存入 片上的 Tile Buffer（极快，类似 SRAM）
  3. 所有像素着色在 片上完成 → 一次性写回主显存

关键：你无法在代码里显式控制这个行为，这是驱动层干的。

TDS（Tiled Deferred Shading）¶

算法层面——软件怎么写。

TDS 是 PC 游戏常用的延迟着色优化策略：

  1. 先算 G-Buffer（存位置、法线、颜色）
  2. 屏幕分 Tile
  3. 用 Compute Shader 把每个 Tile 的光源列表加载到 Shared Memory
  4. 在片上算光照 → 写回最终颜色

关键：这是你写在 Shader 里的逻辑，和硬件无关，任何支持 CS 的 GPU 都能跑。

TBDR vs TDS：核心区别¶

维度 TBDR（硬件架构） TDS（着色算法）
本质 GPU 的渲染管线设计 一种延迟着色的优化策略
分块目的 每 Tile 在片上 SRAM 独立渲染，减少显存读写 每 Tile 在 CS 里算光照，利用局部性
解决什么问题 避免 IMR（立即渲染）的带宽瓶颈和 Overdraw 避免逐像素算光照时反复读取 G-Buffer
适用范围 移动端 GPU（Apple、ARM Mali）+ 部分桌面 GPU 所有 GPU 的渲染算法
依赖硬件 必须有片上 Tile Buffer（硬件特性） 只需要 Compute Shader + Shared Memory
谁控制 驱动（你无法控制） 你（你在 Shader 里写）

四、TBDR/TDS 与 AI 的精准映射¶

层级 TBDR（硬件） TDS（软件） FlashAttention（AI）
分块策略 屏幕分成 32×32 Tile 屏幕分成 Tile，逐 Tile 算光照 注意力矩阵分成 128×128 Block
片上内存 Tile Buffer（片上 SRAM） Shared Memory（groupshared） Shared Memory（__shared__）
避免的操作 避免反复读写 Frame Buffer 避免反复读取 G-Buffer 避免写入中间矩阵 S = Q×K^T
核心收益 减少带宽占用，省电 减少带宽占用，加速 减少 HBM 带宽，加速

你的精准类比：

FlashAttention ≈ TDS（软件算法），TBDR 是让这个算法跑得更快的硬件地基。

五、Pass 合并 vs 算子融合：同一个思想¶

图形中减少 Pass¶

减少 Pass 的目的是 减少同步屏障（Pipeline Stall）：

  • Pass 之间需要切换 Render Target
  • 需要 Flush 状态缓存
  • 需要等待前一个 Pass 的像素全部处理完

代价：GPU 的 SM 在等待，算力空转。

AI 中算子融合¶

算子融合的目的是 减少显存带宽压力：

  • 中间结果不写回 Global Memory
  • 减少 Kernel Launch 次数
  • 减少 Host-Device 通信

代价：Kernel 复杂度增加，需要自己管理 Shared Memory。

本质差异¶

维度 图形 Pass 合并 AI 算子融合
主要瓶颈 Pipeline Stall（状态切换） 显存带宽（中间结果读写）
合并代价 同步等待减少 显存访问减少
收益 GPU 利用率提升 带宽占用减半

你已经理解了这个本质：

图形合并 Pass：减少 Pipeline Flush（状态切换开销） AI 算子融合：减少显存 Round-Trip（带宽占用） 两者都是在减少 GPU 资源的浪费，只是针对的"浪费点"不同。

完整的同步机制对照表¶

概念 DX12/Vulkan CUDA 本质
"阻塞等待" WaitForSingleObject + Fence cudaDeviceSynchronize() CPU 阻塞，直到 GPU 完成
"打标记" Signal() 在 Command List 对 Fence 增加值 cudaEventRecord(event, stream) GPU 在命令流里插入记号
"查进度" GetCompletedValue() cudaEventQuery(event) CPU 查"记号"到了没，不阻塞
"等标记" WaitForSingleObject / SetEventOnCompletion cudaEventSynchronize(event) CPU 阻塞等待特定标记完成
"GPU 等 GPU" Fence + Wait（多 Queue） cudaStreamWaitEvent(stream, event) 一个 GPU 流等另一个流的标记
