11.1 读 Nano-vLLM 源码：一个推理引擎是怎么组装起来的¶

为什么值得读这 1385 行¶

到这里你已经会写 Attention Kernel（11.2），也自己实现过分页 KV Cache 和连续批处理（11.3）。零件都有了，还缺什么？

缺的是把零件装成一台能跑的机器。而这件事的难点不在任何单个零件，在于它们之间的接口：

  • Scheduler 决定这一步跑哪些请求，但它凭什么知道显存够不够？
  • BlockManager 分配了物理页，但 Kernel 怎么知道去哪读、去哪写？
  • GPU 算完了，谁来决定「这一步算数」，谁来决定「这一步作废重来」？
  • 这些状态更新和 GPU 的异步执行之间，怎么保证不打架？

Nano-vLLM 的核心包只有约 1385 行 Python，把 vLLM 的主干（分页 KV、Prefix Cache、Continuous Batching、Chunked Prefill、CUDA Graph、Tensor Parallel）都保留了，但去掉了生产系统里的兼容层、后端抽象和配置爆炸。它是目前能找到的、信噪比最高的推理引擎读物。

把你在 11.3 手写的版本和它对一下，缺口非常清楚：

你在 11.3 造的轮子 Nano-vLLM 对应模块 工业版多出来的东西
BlockManager：分配 / 释放 engine/block_manager.py Prefix Cache：链式哈希 + 引用计数 + 延迟回收
Scheduler：组批 / 抢占 engine/scheduler.py 两种预算、Chunked Prefill、事务化的 postprocess
直接把 tensor 喂给 Kernel engine/model_runner.py Metadata 编译、Pinned 异步上传、显存容量规划
一个 PagedAttention Kernel layers/attention.py Prefill / Decode 双路径 + FlashAttention 后端
—— models/qwen3.py + Loader 权重布局编译、TP 分片
—— engine/llm_engine.py Step 边界、多进程 Worker
—— model_runner.py 后半 CUDA Graph 捕获与重放

这篇的组织方式不是「逐文件讲解」，而是按一个请求在系统里的旅程走一遍：它怎么进来、怎么被分配显存、怎么被编译成 GPU 能消费的数据、算完之后状态怎么落地。每到一个模块，先问「不这么做会怎样」，再看代码。

一、先看清楚：引擎由三个平面组成¶

1. 三个平面¶

初学者读推理引擎源码最容易迷路的原因是：把控制逻辑和计算逻辑混在一起看。实际上它们是两套完全不同的东西，中间靠一层「状态存储」连接。

flowchart TB
    subgraph CONTROL["控制平面（CPU，Python，微秒级）"]
        ENGINE["LLMEngine：收请求、跑循环"] --> SCHED["Scheduler：这一步跑谁"]
        SCHED --> SEQ["Sequence：每条请求的状态机"]
        SCHED --> BM["BlockManager：显存页的账本"]
    end

    subgraph DATA["执行平面（GPU，Kernel，毫秒级）"]
        RUNNER["ModelRunner：编译元数据 + 提交"] --> QWEN["Qwen3 Decoder Layers"]
        QWEN --> ATTN["Attention Kernel"]
        QWEN --> LINEAR["Linear / RMSNorm / RoPE"]
    end

    subgraph MEMORY["状态存储（显存）"]
        KVC["Paged KV Cache：真实数据"]
        TABLE["Block Table / Slot Mapping：地址"]
    end

    SCHED --> RUNNER
    BM --> TABLE
    TABLE --> ATTN
    ATTN <--> KVC

三个平面各回答一个问题：

  • 控制平面：不规则的请求，怎么组成规则的 Batch？（纯 CPU 逻辑，没有一行 CUDA）
  • 执行平面：给定一个规则 Batch，怎么把模型跑完？（纯 GPU，不认识「请求」这个概念）
  • 状态存储：历史 Token 的 K/V 存在哪，下一步怎么找到？（连接两者的桥）

这个划分不是文档里的抽象，是代码的物理边界。 scheduler.py 里没有 torch.cuda；layers/attention.py 里没有 Sequence 对象。中间那道墙就是 ModelRunner —— 它的全部工作就是把 Python 对象编译成显存里的整数数组。

后面每讲一个模块，你都可以先问一句：它在哪个平面？

3. 一次 engine.step() 到底发生了什么¶

整个引擎的外层循环只有一行：while 还有请求: step()。一次 Step 把所有活跃请求往前推一小步：

sequenceDiagram
    participant E as LLMEngine
    participant S as Scheduler
    participant B as BlockManager
    participant R as ModelRunner
    participant A as Attention/KV

    E->>S: schedule()
    S->>B: 这批请求的显存页够不够？
    B-->>S: 够，这是页表
    S-->>E: seqs + is_prefill
    E->>R: run(seqs, is_prefill)
    R->>R: 编译 input_ids / positions / metadata
    R->>A: QKV + block_tables + slot_mapping
    A-->>R: hidden states
    R-->>E: 采样出的 token_ids
    E->>S: postprocess(token_ids)
    S->>B: 发布 Prefix Cache 或释放页

对应到文件：

阶段 模块 职责
请求状态 sequence.py Token、状态、进度、页表
选工作 scheduler.py Prefill/Decode、预算、抢占
分显存 block_manager.py 物理页、引用计数、Prefix Cache
编译输入 model_runner.py Packed Tensor、页表、Slot Mapping
算 models/qwen3.py、layers/* Decoder、Attention、Linear、RoPE
优化 model_runner.py KV Cache、CUDA Graph、TP
循环 llm_engine.py add_request、step、generate

这个 step() 边界非常重要，第十一节会回来讲：流式输出、请求取消、指标采集、异步 Server，全都建立在「一步是一个原子事务」这个假设之上。

二、为什么 is_prefill 这个布尔值贯穿了整个框架¶

读源码时你会发现 is_prefill 到处都是——Scheduler 返回它，ModelRunner 用它分支，Attention 用它选后端，CUDA Graph 用它决定走不走。一个布尔值渗透这么深，通常意味着背后是两种本质不同的负载。

确实如此。同一份 Decoder 权重，面对两种完全不同的执行形态：

Prefill（处理 Prompt） Decode（逐字生成）
每条序列本步输入 几百到几千个 Token 1 个
Linear 形态 大 GEMM，算力密集 小 Batch GEMV，访存密集
Attention Query 长度 Prompt 长度 1
历史 K/V 正在建立（或复用前缀） 反复整段读取
瓶颈 算力、HBM、中间结果显存 KV 带宽、Kernel Launch、调度开销
Shape 稳定性 每次都不一样 按 Batch Size 分桶后很稳定

把最后两行连起来看，就能理解为什么框架必须区分它们：

Prefill 是算力受限的，一次给 GPU 几千个 Token，Kernel 跑几毫秒，CPU 那点提交开销可以忽略。 Decode 是访存受限的，一次只有几十个 Token，单个 Kernel 可能只跑十几微秒，这时候 CPU 的启动开销和 Kernel 执行时间进入同一个量级。

同一套代码路径不可能同时对这两种负载最优。所以 is_prefill 向下影响了四层：

层 Prefill Decode
Scheduler Token 预算，可切 Chunk Sequence 预算，每条 1 个 Token
Metadata Packed Token + cu_seqlens context_lens + Block Table
Attention 后端 Varlen Attention KV Cache Decode Attention
执行方式 Eager（Shape 太动态） CUDA Graph 重放

一个贯穿全文的例子¶

后面每讲一个模块，都会回到这两条请求上：

S0 prompt 长度 = 5
S1 prompt 长度 = 3

第一步（Prefill）：

phase = prefill
input_ids = S0[0:5] + S1[0:3]   # 8 个 Token 压平成一维

第二步（Decode）：

phase = decode
input_ids = [S0 的最后一个 token, S1 的最后一个 token]   # 2 个 Token

注意这里 Batch Size 的含义变了：Prefill 的第一维是「本步 Token 总数」（8），Decode 的第一维是「活跃序列数」（2）。这不是笔误，是两种打包方式。第四节会讲为什么 Prefill 要压平。

三、Sequence：控制平面的唯一真相源¶

1. 一条请求需要记住什么¶

Scheduler 要做决策，光有 Token 列表不够。它还得知道：

  • 这条请求在等待、在跑、还是已完成；
  • Prompt 到哪结束、生成从哪开始；
  • 已经有多少 Token 的 K/V 真正写进显存了；
  • 这一轮批准了多少 Token，但还没算完；
  • 它持有哪些物理页；
  • 什么时候该停（EOS、长度上限）。
from dataclasses import dataclass
from enum import Enum, auto
from itertools import count

@dataclass(slots=True)
class SamplingParams:
    temperature: float = 1.0
    max_tokens: int = 64
    ignore_eos: bool = False

class SequenceStatus(Enum):
    WAITING = auto()
    RUNNING = auto()
    FINISHED = auto()

class Sequence:
    _counter = count()

    def __init__(self, token_ids: list[int], sampling: SamplingParams, block_size: int):
        self.seq_id = next(self._counter)
        self.status = SequenceStatus.WAITING
        self.token_ids = list(token_ids)
        self.prompt_len = len(token_ids)

        self.cached_tokens = 0        # 已写入 KV Cache
        self.scheduled_tokens = 0     # 本轮已批准、尚未提交

        self.block_table: list[int] = []
        self.block_size = block_size
        self.sampling = sampling

    @property
    def num_blocks(self) -> int:
        return (len(self.token_ids) + self.block_size - 1) // self.block_size

    @property
    def last_token(self) -> int:
        return self.token_ids[-1]

2. 三个计数，一个都不能合并¶

这是整个控制平面最容易被忽略、也最容易埋坑的设计：

len(token_ids)      已知的全部 Token（Prompt + 已生成）
cached_tokens       K/V 已经真正落在显存里的 Token 数
scheduled_tokens    本轮批准了、但 GPU 还没算完的 Token 数

为什么不能把后两个合并成一个「进度」？ 因为 GPU 是异步的，而调度决策是同步的。中间那段时间窗口里，「已批准」和「已完成」是两个不同的事实。

拿长度 10 的 Prompt、Chunk 大小 4 举例：

初始：       cached=0, scheduled=0
Step 1 调度后：cached=0, scheduled=4     ← GPU 还没开始算
Step 1 完成后：cached=4, scheduled=0     ← 提交：scheduled 转入 cached
Step 2 调度后：cached=4, scheduled=4
Step 2 完成后：cached=8, scheduled=0
Step 3 调度后：cached=8, scheduled=2     ← 只剩 2 个

这就是一个两阶段提交：scheduled_tokens 是「预备」，cached_tokens 是「提交」。如果你熟悉图形 API，它对应的是「已录入 Command Buffer 但 Fence 还没到」的那段资源范围——在 GPU 真正完成之前，你不能宣称这块资源的新状态成立。

合并的后果是什么？ 假设你只维护一个 progress，调度时就 += 4。这时候 GPU 那一批因为显存不足被抢占取消了，你的 progress 已经是 4，但显存里那 4 个 Token 的 K/V 根本不存在。下一步 Attention 会去读一段未初始化的显存 —— 不会崩溃，不会报错，只会生成一段语义连贯但内容错误的文本。 这类 bug 的定位成本极高，因为所有断言都通过、所有 Shape 都对。

3. 用不变量把这类 bug 挡在源头¶

def validate_sequence(seq: Sequence) -> None:
    assert 0 <= seq.cached_tokens <= len(seq.token_ids)
    assert seq.scheduled_tokens >= 0
    assert seq.cached_tokens + seq.scheduled_tokens <= len(seq.token_ids)
    if seq.status is SequenceStatus.FINISHED:
        assert not seq.block_table          # 完成后必须已经还掉所有页

在 schedule() 出口和 postprocess() 出口各调一次。这几行断言的性价比高得离谱——它们把「CPU 记的进度和 GPU 里的数据错开一个 Token」这类静默错误，变成了一个带行号的 AssertionError。

四、把变长请求压成 GPU 能吃的 Batch¶

1. Padding 的浪费有多大¶

三条请求，长度 3、2、4：

A = [a0, a1, a2]
B = [b0, b1]
C = [c0, c1, c2, c3]

按传统做法 Padding 到最长的 4，喂给 GPU 一个 [3, 4] 的规则张量。代价是 12 个位置里有 3 个在算废数据，利用率 75%。

这个例子还算温和。真实流量里 Prompt 长度从 20 到 4000 都有，一个 Batch 里混进一条长 Prompt，浪费率能到 90% 以上。而 Prefill 是算力受限的，浪费的全是真金白银的 FLOP。

2. Packed / Ragged Batch：压平 + 前缀和¶

Nano-vLLM 的做法是干脆不 Padding，把所有序列首尾相接压成一维：

input_ids  = [a0,a1,a2, b0,b1, c0,c1,c2,c3]     ← 9 个 Token，一个不多
cu_seqlens = [0, 3, 5, 9]                        ← 每条序列的起始位置

cu_seqlens（cumulative sequence lengths）就是长度数组 [3,2,4] 的前缀和。有了它，Kernel 想知道第 \(i\) 条序列在哪，只需要看 cu_seqlens[i] 到 cu_seqlens[i+1]。

这正是 6.2 Scan / 流压缩 里那个 Prefix Sum —— 只不过在这里它的作用不是并行算法的一环，而是变长数据结构的寻址方案。凡是「一堆变长的东西要塞进一个连续 Buffer」，答案基本都是前缀和：GPU 里的粒子系统、可见性剔除后的 Draw 列表、稀疏矩阵的 CSR 格式，全是这个套路。

def pack_prefill(seqs: list[Sequence]):
    input_ids, positions = [], []
    cu_seqlens = [0]
    max_query_len = 0

    for seq in seqs:
        start = seq.cached_tokens                 # 从没算过的地方接着算
        end = start + seq.scheduled_tokens
        query_len = end - start

        input_ids.extend(seq.token_ids[start:end])
        positions.extend(range(start, end))       # RoPE 需要绝对位置
        cu_seqlens.append(cu_seqlens[-1] + query_len)
        max_query_len = max(max_query_len, query_len)

    return input_ids, positions, cu_seqlens, max_query_len

注意 positions 是从 cached_tokens 开始的绝对位置，不是从 0。Chunked Prefill 的第二个 Chunk 里，Token 的位置是 4、5、6、7 —— RoPE 必须拿到真实位置，否则位置编码全错。这是个很典型的 off-by-chunk 错误。

3. 为什么这段前缀和放在 CPU 算¶

看起来是个天然适合 GPU 的并行操作，为什么用 Python for 循环？

  • 数据本来就在 CPU：Scheduler 刚做完决策，长度和状态都在 Python 对象里。放 GPU 算，得先把长度数组传上去。
  • 规模太小：Batch 顶多几百条，几百个元素的前缀和，启动一个 Kernel 的开销（几微秒）比算它本身还贵。
  • 结果马上要用来构造别的元数据：Slot Mapping 依赖它，也在 CPU。

但这个判断是有条件的。 如果 Batch 规模到了几万条，或者调度状态本来就维护在 GPU 上（有些系统这么做），结论会翻过来。读源码时看到「这里用 CPU 循环」，要能说出它成立的前提。

4. 上传：Pinned Memory + 异步拷贝¶

元数据准备好之后要送到显存：

def to_cuda_i32(values: list[int]) -> torch.Tensor:
    host = torch.tensor(values, dtype=torch.int32, pin_memory=True)
    return host.cuda(non_blocking=True)

两个关键词：

  • pin_memory=True：页锁定内存，DMA 引擎可以直接读，不需要先拷到一块临时的锁页缓冲区。如果用普通的可分页内存，CUDA 内部会多做一次 CPU 端的 memcpy。
  • non_blocking=True：把拷贝提交到 Stream 就返回，CPU 继续往下走。注意：只有源是 Pinned 内存时这个参数才真正生效，可分页内存上它会被静默忽略。

这里有个教学代码和工程代码的重要差别：上面每次都新建一个 Host Tensor，靠 PyTorch 的引用计数管生命周期。生产实现会用持久的 Pinned Ring Buffer，但那样就必须用 CUDA Event 确认「这个槽位的上一次拷贝已经完成」才能复写——否则 CPU 会覆盖掉 GPU 还没读走的数据。这是 2.2 Command Buffer 与 Ring Buffer 里的同一个问题，换了个场景。

5. Decode 的打包简单得多¶

def pack_decode(seqs: list[Sequence]):
    input_ids = [seq.last_token for seq in seqs]
    positions = [len(seq.token_ids) - 1 for seq in seqs]
    context_lens = [len(seq.token_ids) for seq in seqs]
    return input_ids, positions, context_lens

每条序列恰好贡献 1 个 Token，所以天然就是规则的，不需要 cu_seqlens。张量第一维就是活跃序列数。

历史 Token 呢？留在 KV Cache 里，由 Attention 通过 Block Table 去读。context_lens 告诉 Kernel「这条序列有多少个历史位置是有效的」。

这就是 Decode 能上 CUDA Graph 而 Prefill 不能的根本原因：Decode 的 Shape 只依赖于「有几条序列在跑」，把它按 1/2/4/8/16/32 分桶后，形状是有限的几种；Prefill 的 Shape 依赖于 Prompt 长度，几乎每次都不一样。第十节会展开。

五、BlockManager：比你的玩具版多了一个 Prefix Cache¶

分页 KV Cache 的基本原理（为什么要分页、页表怎么算、Slot Mapping 怎么来）在 11.3 第二节 里推导过了，这里只快速对一下接口，然后把全部篇幅给工业版真正多出来的东西：Prefix Cache。

1. 快速回顾：Block Table 管读，Slot Mapping 管写¶

逻辑 Token:   [0..3]  [4..7]  [8..11]
逻辑块号:        0       1       2
物理块号:        7       2      11        ← block_table = [7, 2, 11]
\[ \text{slot}(t)=\text{blockTable}\left[\left\lfloor t/B \right\rfloor\right]\times B+(t \bmod B) \]

两个数据结构，方向相反，别搞混：

用途 覆盖范围 谁消费
Block Table 读历史 K/V 这条序列的全部 Token Attention Kernel
Slot Mapping 写本轮新 K/V 本轮新算的那几个 Token KV Store Kernel 
def build_slot_mapping(seq: Sequence) -> list[int]:
    slots = []
    for pos in range(seq.cached_tokens, seq.cached_tokens + seq.scheduled_tokens):
        block = seq.block_table[pos // seq.block_size]
        slots.append(block * seq.block_size + pos % seq.block_size)
    return slots

2. Prefix Cache 要解决的问题¶

先看一个真实场景。你部署了一个客服机器人，每个请求的 Prompt 长这样：

[2000 token 的系统提示词 + 产品文档] + [用户这次问的 20 个字]

每来一个请求，Prefill 都要老老实实把那 2000 个 Token 重算一遍——同样的输入、同样的权重、算出同样的 K/V。QPS 上去之后，绝大部分 GPU 算力都花在重复计算一段一模一样的前缀上。

Prefix Cache 的想法很直白：这段前缀的 K/V 已经在显存里了，直接让新请求指过去就行。

分页在这里给了一个意外的红利：因为 KV Cache 已经被切成块了，共享的粒度天然存在。 如果 KV 还是每条序列一块连续显存，你根本没法「共享一部分」。

S0 的页表 = [7, 2, 5]
S1 的页表 = [7, 2, 9]        ← 前两页物理上是同一块显存
                ↑
         block 7、2 的 ref_count = 2

3. 三个必须回答的问题¶

共享数据听起来简单，但一旦两个请求指向同一块物理显存，就有三件事必须想清楚：

  1. 怎么找到可复用的块？（内容寻址）
  2. 什么样的块才能被复用？（不可变性）
  3. 谁来释放它？（所有权）

Nano-vLLM 的答案分别是：链式哈希、只发布填满的块、引用计数。逐个看。

4. 问题一：链式哈希 —— 为什么不能只哈希块内容¶

先看一个错误做法。假设只用块内 Token 做 key：

content_hash = hash(tuple(tokens))    # ← 错的

反例马上就来了。块大小 4，两条请求：

S0 = [你好, 世界, 请, 介绍]  [北京, 的, 天气, 如何]
S1 = [今天, 是, 星期, 三  ]  [北京, 的, 天气, 如何]
                              ↑ 第二块的内容完全一样

这两个第二块的 Token 序列一模一样，哈希也一样。但它们的 K/V 完全不同 —— 因为 Attention 是因果的，第二块每个 Token 的 K/V 都依赖于它前面所有 Token。前缀不同，K/V 就不同。直接复用会生成彻底错误的结果。

所以哈希必须把整条前缀编进去：

def block_hash(parent_hash: int | None, token_ids: list[int]) -> int:
    return hash((parent_hash, tuple(token_ids)))

每个块的 key = f(上一个块的 key, 本块 Token)。这是一条哈希链，和 Merkle Tree、Git 的 commit 链是同一个构造：key 唯一标识的不是「这段内容」，而是「从头到这里的完整路径」。

链式哈希还顺带给了一个好处：前缀匹配可以从头逐块往下走，一旦断了就停。因为如果第 \(k\) 块匹配不上，第 \(k+1\) 块的 parent_hash 必然也对不上，不可能再命中。

def find_cached_prefix(manager: BlockManager, seq: Sequence) -> list[int]:
    cached_block_ids = []
    parent_hash = None

    # 最后一块留给当前请求自己管：它多半没填满，还要继续追加。
    for logical_block in range(max(0, seq.num_blocks - 1)):
        start = logical_block * seq.block_size
        tokens = seq.token_ids[start:start + seq.block_size]
        content_hash = block_hash(parent_hash, tokens)

        block_id = manager.hash_to_id.get(content_hash)
        if block_id is None:
            break

        block = manager.blocks[block_id]
        if block.token_ids != tuple(tokens):
            break                       # 哈希碰撞，宁可不复用

        cached_block_ids.append(block_id)
        parent_hash = content_hash

    return cached_block_ids

命中之后还要比一次 Token。哈希碰撞的概率很低，但代价是「生成完全错误的内容且无法察觉」—— 这种错误没有任何显式信号，值得用一次 memcmp 换掉。这和内容寻址存储（CAS）里「hash 命中后仍需校验」是同一个工程判断。

5. 问题二：为什么只发布填满的块¶

# 只有 completed_tokens // block_size 这么多个整块会被发布
completed_blocks = (seq.cached_tokens + seq.scheduled_tokens) // seq.block_size

一个没填满的块，未来还会被追加 Token —— 它的内容不是不可变的。给一个还会变的东西建立缓存 key，等于给自己埋雷：别人按 key 找到它、共享了它，然后你往里写第 5 个 Token，别人手里那份数据就被改了。

「不可变才能共享」是并发编程里的老规矩，在这里换了个形式出现。

6. 问题三：发布的时机 —— 一个真实的竞态¶

这是 Prefix Cache 最容易写错的地方，也是最能体现「控制平面和执行平面异步」这件事的地方。

看这段代码的调用位置：

def publish_full_blocks(manager: BlockManager, seq: Sequence) -> None:
    completed_tokens = seq.cached_tokens + seq.scheduled_tokens
    completed_blocks = completed_tokens // seq.block_size
    first_unpublished = seq.cached_tokens // seq.block_size

    parent_hash = None
    if first_unpublished > 0:
        prev_id = seq.block_table[first_unpublished - 1]
        parent_hash = manager.blocks[prev_id].content_hash

    for logical_block in range(first_unpublished, completed_blocks):
        start = logical_block * seq.block_size
        tokens = seq.token_ids[start:start + seq.block_size]
        content_hash = block_hash(parent_hash, tokens)

        block = manager.blocks[seq.block_table[logical_block]]
        block.content_hash = content_hash
        block.token_ids = tuple(tokens)
        manager.hash_to_id[content_hash] = block.block_id
        parent_hash = content_hash

它必须在 postprocess() 里调用，也就是 GPU 算完之后。绝对不能在 schedule() 里调用。

为什么？调度时页表就已经确定了，看起来这时候发布也没问题。但是：

t=0   Scheduler 给 S0 分配 block 7，并（错误地）立刻发布 hash(块内容) → 7
t=1   Runner 提交 Prefill，GPU 开始算 S0 的 K/V
t=2   S1 进来，查 Prefix Cache，命中 block 7，直接指过去
t=3   S1 的 Attention 读 block 7 —— 但 GPU 还没写完，读到的是上一个请求残留的数据

没有崩溃，没有断言失败，只有一段莫名其妙的输出。 而且它取决于时序，QPS 低的时候可能永远复现不了。

正确的顺序就一条规则：「这份数据可以被别人看见」这个状态变更，必须发生在「数据真的写完了」之后。 这条规则在图形里叫资源状态转换要跟在对应的 Fence 之后，在这里叫 postprocess 才能 publish，本质是一回事。

7. 引用计数与延迟回收¶

@dataclass
class Block:
    block_id: int
    ref_count: int = 0
    content_hash: int | None = None
    token_ids: tuple[int, ...] = ()

class BlockManager:
    def __init__(self, num_blocks: int, block_size: int):
        self.block_size = block_size
        self.blocks = [Block(i) for i in range(num_blocks)]
        self.free_ids = deque(range(num_blocks))
        self.used_ids: set[int] = set()
        self.hash_to_id: dict[int, int] = {}

    def allocate_one(self) -> int:
        if not self.free_ids:
            raise RuntimeError("KV cache exhausted")
        block_id = self.free_ids.popleft()
        block = self.blocks[block_id]

        # 关键：这一页要被覆盖了，它的 Prefix Cache 索引必须先失效
        if block.content_hash is not None:
            if self.hash_to_id.get(block.content_hash) == block_id:
                del self.hash_to_id[block.content_hash]

        block.ref_count = 1
        block.content_hash = None
        block.token_ids = ()
        self.used_ids.add(block_id)
        return block_id

    def release(self, block_id: int) -> None:
        block = self.blocks[block_id]
        if block.ref_count <= 0:
            raise RuntimeError("double free")
        block.ref_count -= 1
        if block.ref_count == 0:
            self.used_ids.remove(block_id)
            self.free_ids.append(block_id)

注意 allocate_one 里那段索引失效：一个页被重新分配出去，它上面的 Prefix Cache 记录就是过期的了，必须从 hash_to_id 里删掉。少了这几行，后来的请求会命中一个内容已经被覆盖的页 —— 又是一个静默的错误结果。

再看 release：ref_count 归零后，页进入 free list，但它的 content_hash 和 token_ids 还留着。这意味着在它被真正重新分配出去之前，它仍然可以被 Prefix Cache 命中并「复活」：

for block_id in cached_block_ids:
    block = manager.blocks[block_id]
    if block.ref_count == 0:
        manager.free_ids.remove(block_id)     # 从空闲队列里捞回来
        manager.used_ids.add(block_id)
        block.ref_count = 1
    else:
        manager.retain(block_id)
    seq.block_table.append(block_id)

这就是「延迟回收」：不主动清空，等到显存真的不够、这一页被挑中重用时才失效。等于用「反正闲着也是闲着」的空闲页做了一层免费缓存。

所以整个 Prefix Cache 的本质是一套协议，哈希表只是加速查找的手段：

不可变内容 + 引用所有权 + 延迟回收

这三个词在渲染的 PSO 缓存、纹理流送、Shader 编译缓存里也是同一套。变的是缓存的数据语义，不变的是生命周期管理的骨架。

六、Scheduler：Nano-vLLM 选了哪条路，代价是什么¶

Continuous Batching 的通用原理（为什么要每步重新组批、抢占的两种策略）在 11.3 第四节 讲过。这一节看具体实现的选择——同一个机制，Nano-vLLM 是怎么落地的，它放弃了什么。

1. 两种预算，管两件不同的事¶

max_num_seqs            # 一个 Batch 最多几条序列
max_num_batched_tokens  # 一个 Batch 最多几个 Token

为什么需要两个？因为它们约束的资源不同：

  • max_num_seqs 管的是 Decode。Decode 每条序列贡献 1 个 Token，所以序列数 = Batch Size，它决定了 Decode 的并发度、元数据规模和 Block Table 的行数。
  • max_num_batched_tokens 管的是 Prefill。Prefill 的中间张量（QKV、MLP 的中间激活）都正比于本步 Token 总数，它决定了临时显存的峰值。

一条 4000 Token 的 Prompt 只占 1 个序列名额，却能吃掉全部 Token 预算。两个维度互不替代，所以必须分开限。

2. 主循环：Prefill 优先¶

def schedule(self) -> tuple[list[Sequence], bool]:
    prefill = self._schedule_prefill()
    if prefill:
        return prefill, True          # 有 Prefill 就先干 Prefill
    return self._schedule_decode(), False

这一步就定了整个引擎的延迟特征。 只要队列里有等待的新请求，这一步就不做 Decode —— 意味着已经在跑的请求会被暂停一步。

代价说清楚：

指标 Prefill 优先的影响
TTFT（首 Token 延迟） 好：新请求立刻被处理
TPOT / ITL（Token 间隔） 差：老请求被新请求插队，抖动明显
吞吐 中性偏好：Prefill 的算力利用率高
公平性 差：持续的新请求会饿死长任务

生产系统通常不会这么简单。常见的改法是混合批（一个 Batch 里同时放 Prefill 的 Chunk 和 Decode 的 Token，靠 Chunked Prefill 控制配比），这样 Decode 不会被完全饿死。Nano-vLLM 选简单版是为了可读性。

读源码时要有这个意识：分清哪些是「不这么写就错了」的正确性约束，哪些是「可以换一种写法」的策略选择。 上面这个 if prefill: 是策略；下面 Block 够不够的检查是正确性。

3. Prefill：分配显存 + 切 Chunk¶

def _schedule_prefill(self) -> list[Sequence]:
    selected, used_tokens = [], 0

    while self.waiting and len(selected) < self.max_num_seqs:
        seq = self.waiting[0]
        remaining = self.max_num_batched_tokens - used_tokens
        if remaining == 0:
            break

        if not seq.block_table:
            cached = find_cached_prefix(self.block_manager, seq)
            new_blocks = seq.num_blocks - len(cached)
            # 命中但 ref_count==0 的页要从 free list 里捞回来，也算消耗
            reusable_free = sum(
                self.block_manager.blocks[b].ref_count == 0 for b in cached
            )
            if len(self.block_manager.free_ids) < new_blocks + reusable_free:
                break                          # 显存不够，这条先不上
            allocate_with_prefix(self.block_manager, seq, cached)

        unscheduled = len(seq.token_ids) - seq.cached_tokens

        # 简化：Batch 里已经有请求时，不给下一条长 Prompt 切 Chunk
        if unscheduled > remaining and selected:
            break

        seq.scheduled_tokens = min(unscheduled, remaining)
        used_tokens += seq.scheduled_tokens
        selected.append(seq)

        if seq.cached_tokens + seq.scheduled_tokens == len(seq.token_ids):
            self.waiting.popleft()             # Prompt 处理完了，转 running
            seq.status = SequenceStatus.RUNNING
            self.running.append(seq)
        else:
            break                              # 切了 Chunk，留在队首等下一步
    return selected

有两个细节值得停一下：

reusable_free 那段是新手最容易漏的。Prefix Cache 命中的页可能正躺在 free list 里（ref_count 归零但还没被覆盖），把它「捞回来」也会减少可用页数。只数 new_blocks 会高估空闲量，导致后面分配时才发现不够 —— 而那时候状态已经改了一半。预算检查必须和实际消耗完全一致。

Chunked Prefill 就是那个 min(unscheduled, remaining)。一条 4000 Token 的 Prompt 不再独占一步，而是按预算切成几步做完。好处是单步时长可控（Decode 不会被卡死几百毫秒），代价是：

  • 状态变多了（cached_tokens 就是为它存在的）；
  • 调度次数变多，CPU 开销上升；
  • Attention 要支持「Query 只有一段，但 Key 是全部历史」——这就是下一节 cu_k > cu_q 的由来。

4. Decode：什么时候需要新页，不够了怎么办¶

def needs_new_block(seq: Sequence) -> bool:
    # last_token 还没写进 KV。它落在新页的第 0 格时，就需要开一页。
    return len(seq.token_ids) % seq.block_size == 1

这个判断值得盯一会儿。序列有 \(n\) 个 Token，其中前 \(n-1\) 个的 K/V 已经在缓存里，第 \(n\) 个（也就是上一步刚采样出来的）这一步才会被写入。它的位置下标是 \(n-1\)，落在页内偏移 \((n-1) \bmod B\)。偏移为 0 时，说明要开新页 —— 也就是 \(n \bmod B = 1\)。

差一格就是灾难：算成 n % B == 0 的话，页会晚开一步，这一步的 K/V 会被写到上一页的越界位置。

def _schedule_decode(self) -> list[Sequence]:
    selected = []
    while self.running and len(selected) < self.max_num_seqs:
        seq = self.running.popleft()

        while needs_new_block(seq) and not self.block_manager.free_ids:
            if self.running:
                self._preempt(self.running.pop())    # 牺牲队尾（最晚来的）
            else:
                self._preempt(seq)                   # 只剩自己，只能自己让位
                break
        else:
            if needs_new_block(seq):
                seq.block_table.append(self.block_manager.allocate_one())
            seq.scheduled_tokens = 1
            selected.append(seq)

    self.running.extendleft(reversed(selected))
    if not selected:
        raise RuntimeError("no schedulable sequence")
    return selected

def _preempt(self, seq: Sequence) -> None:
    release_sequence(self.block_manager, seq)        # 把 KV 全还回去
    seq.status = SequenceStatus.WAITING
    self.waiting.appendleft(seq)                     # 插队首，优先恢复

三个设计点：

  • self.running.pop() 牺牲队尾：后进先出。抢占最晚进入的请求，是为了保护已经投入了大量计算的老请求 —— 抢占一条跑了 500 步的序列，等于扔掉 500 步的计算。
  • self.waiting.appendleft() 插队首：被抢占的请求下次优先恢复，避免反复被踢导致饿死。
  • Recompute 而不是 Swap：Nano-vLLM 直接把 KV 扔了，恢复时重新 Prefill。用算力换显存，代码简单，也不占 PCIe 带宽。11.3 第四节对比过 Swap 方案的取舍。

5. postprocess 是事务提交¶

def postprocess(self, seqs, token_ids, is_prefill):
    for seq, token_id in zip(seqs, token_ids):
        if is_prefill:
            publish_full_blocks(self.block_manager, seq)   # 先发布，因为 GPU 已写完

        seq.cached_tokens += seq.scheduled_tokens          # ← 提交点
        seq.scheduled_tokens = 0

        # Chunk 还没吃完整个 Prompt，这一步不产生新 Token
        if is_prefill and seq.cached_tokens < len(seq.token_ids):
            continue

        seq.append_token(token_id)
        hit_eos = token_id == self.eos_token_id and not seq.sampling.ignore_eos
        hit_limit = len(seq.completion_token_ids) >= seq.sampling.max_tokens

        if hit_eos or hit_limit:
            seq.status = SequenceStatus.FINISHED
            release_sequence(self.block_manager, seq)
            self.running.remove(seq)

把第三节的两阶段提交和第五节的发布时机连起来看，这个函数的顺序就是唯一正确的顺序：

GPU 算完（隐含在 run() 返回时）
   → 发布 Prefix Cache（数据已经真的在显存里了）
   → cached_tokens += scheduled_tokens（进度落地）
   → 追加 Token、判断结束
   → 结束则释放页

每一行都依赖前一行成立。 任何一步提前，都会产生一个「不崩溃但结果错」的 bug。

七、ModelRunner：把 Python 对象编译成整数数组¶

1. 它为什么叫 Runner 而不是 Executor¶

因为它的主要工作不是「执行」，是编译。

模型层不应该、也不需要认识 Sequence 这个 Python 对象。Attention Kernel 要的是几个 int32 数组。中间这层翻译就是 Runner：

Sequence 对象（Python，控制平面）
    ↓  编译
input_ids / positions
cu_seqlens_q / cu_seqlens_k
slot_mapping / context_lens / block_tables
    ↓  上传显存
Qwen3 model + Attention Kernel（执行平面）

这和渲染器把 Scene Object、Material、Resource Handle 编译成 Indirect Argument Buffer 是同一件事：高层的、带指针的、面向对象的东西，压成扁平的、面向数据的、GPU 能直接索引的整数。

2. AttentionContext：这一步的全部元数据¶

@dataclass(slots=True)
class AttentionContext:
    is_prefill: bool
    cu_seqlens_q: torch.Tensor | None = None   # Query 的前缀和
    cu_seqlens_k: torch.Tensor | None = None   # Key 的前缀和
    max_seqlen_q: int = 0
    max_seqlen_k: int = 0
    slot_mapping: torch.Tensor | None = None   # 写：本轮 K/V 去哪
    context_lens: torch.Tensor | None = None   # 读：每条序列有多少有效历史
    block_tables: torch.Tensor | None = None   # 读：页表

3. cu_k 为什么可能大于 cu_q¶

这是 Prefill 路径里最容易困惑的一点：

cu_q.append(cu_q[-1] + q_len)      # q_len = scheduled_tokens，本轮新算的
cu_k.append(cu_k[-1] + k_len)      # k_len = cached + scheduled，全部历史

原因就是 Chunked Prefill 和 Prefix Cache：

Prompt 长度 10，第 6~10 个 Token 是本轮的 Chunk：

Query:  [t6 t7 t8 t9]              ← 只有本轮这 4 个需要算输出
Key:    [t0 ... t9]                ← 但它们要和全部 10 个历史做 Attention
        └── 前 6 个来自 KV Cache ──┘

Query 是「这一步要产出什么」，Key 是「要看多少上下文」。 只有在「从零开始、一次算完整个 Prompt」这种最简单的情况下，两者才相等。

Prefix Cache 命中时也一样：命中的那几页 K/V 不需要重算（不在 Query 里），但必须参与 Attention（在 Key 里）。

has_cached_prefix = cu_k[-1] > cu_q[-1]
block_tables = make_block_tables(seqs) if has_cached_prefix else None

没有缓存前缀时，block_tables 是 None —— 这时 K/V 就是本轮刚算出来的连续张量，Attention 可以直接吃，省掉一次间接寻址。有前缀时才必须走页表。

4. Block Table 的 Padding 与它的安全边界¶

每条序列的页数不同，但要拼成一个二维张量：

def make_block_tables(seqs: list[Sequence]) -> torch.Tensor:
    width = max(len(seq.block_table) for seq in seqs)
    rows = [seq.block_table + [-1] * (width - len(seq.block_table)) for seq in seqs]
    return torch.tensor(rows, dtype=torch.int32, pin_memory=True).cuda(non_blocking=True)

这里出现了 Padding —— 但它和第四节说的「Padding 浪费算力」不是一回事。页表 Padding 的成本是几十字节的元数据，Token Padding 的成本是几千次 Attention 计算。 差着好几个数量级，所以这里用 Padding 完全划算。

关键在于 -1 绝不能被真的访问。谁来保证？context_lens：

block_tables = [[7, 2, 11],
                [5, -1, -1]]      ← 第二条只有 1 页
context_lens = [12, 4]            ← Kernel 只会读到第 4 个 token 为止

Kernel 遍历历史 Token 时用 context_lens[i] 作为上界，-1 那些位置根本不会被算到地址里。这是一个「靠约定保证的安全」，不是靠检查。 所以如果你改了 Kernel 的循环边界，务必确认这个约定还成立 —— 否则表现是 block_id = -1 算出一个负地址，Compute Sanitizer 会告诉你非法访存。

5. 完整的 Prefill / Decode 元数据构造¶

def prepare_prefill(seqs: list[Sequence], block_size: int):
    input_ids, positions = [], []
    cu_q, cu_k = [0], [0]
    slot_mapping = []
    max_q = max_k = 0

    for seq in seqs:
        start = seq.cached_tokens
        q_len = seq.scheduled_tokens
        end = start + q_len

        input_ids.extend(seq.token_ids[start:end])
        positions.extend(range(start, end))
        cu_q.append(cu_q[-1] + q_len)
        cu_k.append(cu_k[-1] + end)        # k_len = end = cached + scheduled
        max_q, max_k = max(max_q, q_len), max(max_k, end)
        slot_mapping.extend(build_slot_mapping(seq))

    has_cached_prefix = cu_k[-1] > cu_q[-1]
    return AttentionContext(
        is_prefill=True,
        cu_seqlens_q=to_cuda_i32(cu_q),
        cu_seqlens_k=to_cuda_i32(cu_k),
        max_seqlen_q=max_q,
        max_seqlen_k=max_k,
        slot_mapping=to_cuda_i32(slot_mapping),
        block_tables=make_block_tables(seqs) if has_cached_prefix else None,
    ), to_cuda_i64(input_ids), to_cuda_i64(positions)


def prepare_decode(seqs: list[Sequence], block_size: int):
    input_ids = [seq.last_token for seq in seqs]
    positions = [len(seq.token_ids) - 1 for seq in seqs]
    context_lens = [len(seq.token_ids) for seq in seqs]

    slot_mapping = []
    for seq in seqs:
        pos = len(seq.token_ids) - 1                   # 只写这一个 Token
        block = seq.block_table[pos // block_size]
        slot_mapping.append(block * block_size + pos % block_size)

    return AttentionContext(
        is_prefill=False,
        slot_mapping=to_cuda_i32(slot_mapping),
        context_lens=to_cuda_i32(context_lens),
        block_tables=make_block_tables(seqs),           # Decode 必然要读历史
    ), to_cuda_i64(input_ids), to_cuda_i64(positions)

6. 隐式 Context：一个值得警惕的设计¶

Nano-vLLM 把这一步的 Context 存进一个进程内全局变量，Attention 层直接 get_context() 取：

set_context(ctx)
try:
    hidden = self.run_model(input_ids, positions, is_prefill)
    ...
finally:
    reset_context()          # 异常路径也必须清掉

好处很实在：forward(input_ids, positions) 的签名保持干净，不用把七八个元数据张量一层层往下传三十六层。

代价也很实在：

  • 同一进程同一时刻只能有一个有效 Context；
  • 异常路径必须 reset，否则下一步会读到上一步的脏元数据（finally 就是为这个）；
  • 多 Stream 并发、重入变得极难推理。

建议自己实现时先显式传参，等你确实被三十六层的参数传递烦到了，再改成 Context。这样你会清楚地知道自己换掉了什么。

vLLM 主线现在用的是 ForwardContext + contextvar，本质是同一个模式，只是把「全局」收窄到了「当前执行上下文」。

八、Attention 后端与显存容量规划¶

1. KV Cache 是一整块，不是每层一块¶

[2, num_layers, num_blocks, block_size, kv_heads_per_rank, head_dim]
 ↑
 K / V

一次性分配一个六维大张量，每层 Attention 持有属于自己的一个 view。单个 Block 的字节数：

\[ \text{bytesPerBlock}=2\times L\times B\times H_{kv,\text{rank}}\times D\times \text{bytesPerElem} \]

注意 \(H_{kv,\text{rank}}\) 是本卡上的 KV Head 数 —— TP 之后每张卡只存自己那份。

为什么要一次性分配？ 因为分页的全部意义就是「显存的所有权归引擎，不归 PyTorch 的 caching allocator」。如果每层各自 torch.empty，你就没法回答「还剩多少页可用」这个问题，而 Scheduler 每一步都要问它。

2. 先 Warmup 再分 KV Cache¶

这是一个很容易被跳过、但直接决定服务稳定性的步骤。

一个朴素的做法是：显存总量减去模型权重，剩下的全给 KV Cache。这么干必炸。 因为 Forward 过程本身还要吃显存：

  • 中间激活（QKV、MLP 的 gate/up 输出，正比于本步 Token 数）；
  • Kernel 的 workspace（FlashAttention、cuBLAS 都要）；
  • NCCL 的通信 buffer；
  • PyTorch / cuBLAS / Triton 的编译缓存和上下文。

这些东西的峰值没法用公式算准，因为它取决于具体的 Kernel 实现、算法选择甚至 cuBLAS 的启发式。所以 Nano-vLLM 用了一个很实用的办法：跑一遍最大计划 Shape，量出来。

可用 KV 预算
  = 显存总量 × gpu_memory_utilization
  - 当前非 KV 占用（权重 + 上下文）
  - Forward 峰值临时占用（Warmup 实测）

torch.cuda.empty_cache()
torch.cuda.reset_peak_memory_stats()
self.warmup_forward(max_num_batched_tokens)     # 用最大 Shape 跑一遍
peak = torch.cuda.max_memory_allocated()
...
num_kv_blocks = available_bytes // bytes_per_block

所以 Warmup 在这里不是「让 Kernel 变热」，是一次容量测量。 名字容易误导，读代码时注意它挂在哪个阶段。

顺带一提：gpu_memory_utilization 这个参数（通常 0.9）留出的那 10%，就是给上面这些估不准的东西做安全垫的。调到 0.98 通常换来的是运行几小时后的一次 OOM。

3. 写 KV：一次 Scatter¶

概念上就是按 slot_mapping 散写：

def store_kv(key, value, k_cache, v_cache, slot_mapping):
    flat_k = k_cache.view(-1, key.shape[-2], key.shape[-1])
    flat_v = v_cache.view(-1, value.shape[-2], value.shape[-1])
    valid = slot_mapping >= 0
    flat_k[slot_mapping[valid]] = key[valid]
    flat_v[slot_mapping[valid]] = value[valid]

但 Nano-vLLM 用 Triton 手写了一个 Kernel。为什么不用上面这个 PyTorch 版本？因为它会产生临时张量（slot_mapping[valid]、key[valid] 都是新分配的）、多次 Kernel Launch，而这段代码每层都要跑一次，36 层就是 36 次。

@triton.jit
def store_kv_kernel(
    key_ptr, value_ptr, k_cache_ptr, v_cache_ptr,
    slot_mapping_ptr, token_stride: tl.constexpr, D: tl.constexpr,
):
    token = tl.program_id(0)                    # 一个 program 管一个 Token
    slot = tl.load(slot_mapping_ptr + token)
    offsets = tl.arange(0, D)
    mask = (offsets < D) & (slot >= 0)          # slot=-1 是 Graph Padding

    key = tl.load(key_ptr + token * token_stride + offsets, mask=mask)
    value = tl.load(value_ptr + token * token_stride + offsets, mask=mask)
    tl.store(k_cache_ptr + slot * D + offsets, key, mask=mask)
    tl.store(v_cache_ptr + slot * D + offsets, value, mask=mask)

几个 GPU 层面的点：

  • offsets = tl.arange(0, D)：同一个 program 内的 lane 读连续地址，满足访存合并。这是把「Head 维」放在最内层的直接收益。
  • slot >= 0 必须进 mask：CUDA Graph 的 Padding 槽位是 -1，不 mask 就会往负地址写 —— 而且因为 Graph 里的 Padding 是常态，这个 bug 会稳定复现在生产环境而不是测试环境。
  • 写完之后不需要同步：Attention 在同一个 Stream 上排在它后面，Stream 内的顺序执行天然保证了依赖。不需要 cudaDeviceSynchronize，也不需要 Event。

5. PagedAttention 和 FlashAttention 不是竞争关系¶

这是个常见误解，值得说清楚：

解决什么 优化的对象
Paged KV Cache KV 怎么分配、共享、寻址 系统级：碎片、并发数、前缀复用
FlashAttention QK / Softmax / PV 怎么分块 Kernel 级：中间结果的 HBM 流量

它们正交，可以也应该同时用。 FlashAttention 的现代版本直接支持 block_table 参数，就是为了在分页布局上工作。

要注意的是，分页本身不是免费的：它多了一次间接寻址，还破坏了 K/V 的连续性。单看 Attention Kernel 的耗时，分页版通常比连续版慢一点。它的收益全部来自系统层面 —— 更低碎片、按需增长、前缀共享、省掉 KV 聚合拷贝。

所以评估分页的收益时，看的指标必须是端到端吞吐，不是单 Kernel 耗时。 拿 ncu 测出「分页 Attention 比连续版慢 8%」然后得出「分页不划算」的结论，是典型的局部最优陷阱。

九、Model Adapter 与 Weight Loader¶

1. 框架不重新发明 Transformer¶

models/qwen3.py 做的事很有限 —— 把一个标准 Decoder 接到 Runtime 的约定上：

Runtime 输入契约：input_ids + positions + AttentionContext
        ↓
Qwen3 Adapter
        ├── Linear 换成框架的 TP 版本
        ├── Attention 换成框架的 Paged 后端
        ├── 暴露 KV Cache 的绑定点
        └── 暴露 compute_logits(hidden)
        ↓
Runtime 输出契约：hidden states / logits

读这个文件时只需要盯四件事：

  1. HF 的参数名怎么映射到框架的 Module；
  2. 哪些 Linear 被换成了 TP 版本（决定通信点在哪）；
  3. Attention 从哪里拿到 Context 和 KV Cache；
  4. Hidden State 在哪里进 LM Head。

2. 权重融合：为了少读一次输入¶

qkv = self.qkv_proj(hidden_states)                 # 一次 GEMM
q, k, v = qkv.split([q_size, kv_size, kv_size], dim=-1)

gate_up = self.gate_up_proj(hidden_states)         # 一次 GEMM
gate, up = gate_up.chunk(2, dim=-1)
hidden = F.silu(gate) * up

Q、K、V 三个 Linear 吃的是同一个输入。分开做三次 GEMM，这个输入张量要从 HBM 读三遍；合成一个 [3*out, in] 的大权重，只读一遍，而且 GEMM 的形状更大、更容易打满 Tensor Core。Gate/Up 同理。

这就是 4.1 算子融合 里那个「共享输入的算子应该合并」，在权重布局层面的体现。

代价转移给了 Loader —— 它必须把 HF checkpoint 里独立的 q_proj.weight、k_proj.weight、v_proj.weight 写进大权重的正确切片里。

3. Weight Loader 是一个布局编译器¶

外部 Checkpoint            内部布局
q_proj.weight       ┐
k_proj.weight       ├──→   qkv_proj.weight     = [Q 分片 | K 分片 | V 分片]
v_proj.weight       ┘
gate_proj.weight    ┐
up_proj.weight      ┴──→   gate_up_proj.weight = [Gate 分片 | Up 分片]

它还得同时处理：

  • 按 TP Rank 切片：Column Parallel 切输出维，Row Parallel 切输入维，切错方向数值会全错但不报错；
  • Tied Embedding：有些模型的 LM Head 和 Embedding 共享权重，不能重复加载也不能漏；
  • Shape / Dtype 校验：这是唯一能在加载期发现映射错误的地方；
  • 逐 Tensor 加载：不能先把整个 checkpoint 读进内存再切，那需要双倍内存。

「漏载权重」是这一层最阴险的错误：某个参数名没匹配上，那个权重就保持随机初始化的值。模型照样能跑，输出的还是通顺的句子，只是内容完全不对。所以工程实现会维护一个「已加载参数名」的集合，加载结束后和模型的 named_parameters() 做差集，任何一边有剩余就直接报错。

4. 模型配置同时也是容量规格¶

num_q_heads = 16, num_kv_heads = 2   →   每 8 个 Q Head 共享 1 个 KV Head
Q head 0..7  → KV head 0
Q head 8..15 → KV head 1

GQA 把 KV 的头数从 16 降到 2，KV Cache 的这个维度缩到 1/8。

但注意措辞：这是 KV Cache 那一个维度的缩减，不等于整个推理进程的显存降到 1/8。权重、激活、workspace 都没变。读源码时要留意这类「局部倍数」被误当成「整体倍数」的表述。

Runner 从 HF Config 里读 num_hidden_layers、num_key_value_heads、head_dim 和 dtype，算出单个 Block 的字节数。也就是说 Model Adapter 不只定义计算图，它还向 Runtime 提供容量规划所需的静态规格。 这是它作为「适配层」的第二个职责，很容易被忽略。

十、Runner 闭环与 LLMEngine¶

1. run() 的完整形态¶

class ModelRunner:
    @torch.inference_mode()
    def run(self, seqs: list[Sequence], is_prefill: bool) -> list[int]:
        if is_prefill:
            ctx, input_ids, positions = prepare_prefill(seqs, self.block_size)
        else:
            ctx, input_ids, positions = prepare_decode(seqs, self.block_size)

        set_context(ctx)
        try:
            hidden = self.run_model(input_ids, positions, is_prefill)
            last_hidden = self.select_last_hidden(hidden, seqs, is_prefill)
            logits = self.model.compute_logits(last_hidden)
            temperatures = self.prepare_temperatures(seqs)
            return self.sampler(logits, temperatures).tolist()
        finally:
            reset_context()

初始化的顺序也值得记一下，它有严格的依赖：

读配置 → 绑定 device、建进程组 → 建模型 → 加载权重
       → Warmup 测峰值 → 分配 KV Cache → 捕获 CUDA Graph

KV Cache 必须在 Warmup 之后分配（第八节讲了为什么），Graph 必须在 KV Cache 之后捕获（因为 Graph 里记录了 KV Cache 的地址）。这个顺序不能调。

2. 为什么只算最后一个位置的 Logits¶

Prefill 会为每个 Prompt Token 都产生一个 hidden state。但生成下一个 Token 只需要最后一个位置的那个。

算笔账。Qwen3 的词表约 151936，hidden size 4096，一条 2048 Token 的 Prompt：

FLOP Logits 显存（FP32）
全部 2048 个位置 \(2\times2048\times4096\times151936 \approx 2.5\) TFLOP \(2048\times151936\times4 \approx 1.2\) GiB
只算最后 1 个 \(\approx 1.2\) GFLOP \(\approx 0.6\) MiB

2048 倍的差距，而且那 1.2 GiB 的临时 Buffer 极可能直接 OOM。 LM Head 是全模型最宽的那个矩阵乘，在它上面浪费算力的代价特别高。

选最后位置就是一次 Gather，而 cu_seqlens_q 刚好把每条序列的边界告诉了你：

last_indices = cu_seqlens_q[1:] - 1        # 每条序列最后一个 Token 的下标
last_hidden = hidden[last_indices]

这个 Gather 必须发生在 LM Head 之前，不能在之后。 顺序写反了功能上没错，性能上差 2048 倍。

3. Sampling¶

# Greedy
token_ids = logits.argmax(dim=-1)

# Temperature Sampling（Gumbel-max 技巧）
scaled = logits.float() / temperatures[:, None]
probs = torch.softmax(scaled, dim=-1)
noise = torch.empty_like(probs).exponential_().clamp_min_(1e-10)
token_ids = (probs / noise).argmax(dim=-1)

第二段用的是 Gumbel-max：对指数分布噪声取 argmax(p/g)，等价于按 \(p\) 的分布采样，但避免了 torch.multinomial（它在 GPU 上要做前缀和 + 二分查找，对大词表不友好）。一个 elementwise 除法加一次 argmax reduce 就搞定。

.float() 那一下不能省：FP16 的 softmax 在 151936 这么宽的维度上会丢精度，尤其是 temperature 很小的时候。

生产采样器还要加 Top-k / Top-p、重复惩罚、Logit Bias、可复现的随机数状态 —— 这些都是纯 elementwise + reduce，不影响框架结构。

4. LLMEngine：一切都建立在 step 边界上¶

class LLMEngine:
    def add_request(self, prompt: str, sampling: SamplingParams) -> int:
        token_ids = self.tokenizer.encode(prompt)
        seq = Sequence(token_ids, sampling, self.config.block_size)
        self.scheduler.add(seq)
        return seq.seq_id

    def step(self):
        seqs, is_prefill = self.scheduler.schedule()      # 计划 + 预留资源
        token_ids = self.runner.run(seqs, is_prefill)     # 执行
        self.scheduler.postprocess(seqs, token_ids, is_prefill)   # 提交
        return [s for s in seqs if s.status is SequenceStatus.FINISHED]

    def generate(self, prompts, sampling):
        for prompt in prompts:
            self.add_request(prompt, sampling)
        outputs = {}
        while not self.scheduler.is_finished():
            for seq in self.step():
                outputs[seq.seq_id] = seq.completion_token_ids
        return [self.tokenizer.decode(outputs[i]) for i in sorted(outputs)]

整个引擎的外层就这么点东西。关键不在代码量，在于 step() 是一个原子事务边界：

计划资源 → 构造 GPU 工作 → 执行 → 取结果 → 提交状态

进入 step 之前和退出 step 之后，系统状态都是自洽的。这个性质直接支撑了上层所有能力：

  • 流式输出：每个 step 结束后把新 Token 推给客户端；
  • 请求取消：在 step 边界检查取消标志，安全地释放页；
  • 指标采集：step 边界天然是打点位置（TTFT、ITL 都在这测）；
  • 异步 Server：一个后台线程跑 step 循环，前台 API 只管往队列里塞请求。

如果 step 不是原子的（比如中途异常导致 scheduled_tokens 没清零），上面这些全都会出问题。这就是为什么第三节那几行不变量断言值得写。

十一、CUDA Graph：它优化的是提交，不是计算¶

1. 问题：Decode 的时间去哪了¶

一个 36 层的模型做一次 Decode，要发多少个 Kernel？

粗算一下：每层至少有 RMSNorm、QKV GEMM、RoPE、KV Store、Attention、O GEMM、RMSNorm、Gate/Up GEMM、SiLU-Mul、Down GEMM —— 一层七到十个。36 层就是 250 到 400 次 Kernel Launch，还没算 LM Head 和采样。

而 Decode 的每个 Kernel 都很小：Batch 只有几十个 Token，GEMM 退化成 GEMV。这时候会发生一件事：

CPU:  [launch A][launch B][launch C][launch D]...
GPU:      [A]  空 [B]  空 [C]  空 [D]  空 ...
                ↑ CPU 还没提交下一个，GPU 在等

当单个 Kernel 的执行时间和单次 Launch 的 CPU 开销进入同一量级时，GPU 时间线上就会出现密集的空洞。 这时候瓶颈不在 GPU，在 CPU 的提交速度。

CUDA Graph 的做法是：把这一整串 Kernel 的拓扑结构（谁在谁之后、各自的参数是什么）预先捕获成一张图，之后一次 replay() 就把整张图交给驱动，CPU 只需要一次提交。

具体能省多少，必须自己用 Nsight Systems 量。 它取决于模型层数、Batch 大小、CPU 单核性能、驱动版本。别照抄任何一个博客上的百分比——包括这一篇。第十四节给了怎么量的命令。

2. 它不做什么¶

这一点必须说清楚，否则会产生错误预期：

CUDA Graph 会 CUDA Graph 不会
消除重复的 Launch 开销 ❌ 融合 Kernel
消除重复的参数校验和驱动调用 ❌ 减少 KV Cache 的读取量
让 GPU 时间线更紧凑 ❌ 提高单个 Kernel 的算术强度

每个 Kernel 该跑多久还是跑多久。 如果你的 Decode 瓶颈是 KV 带宽（这很常见），CUDA Graph 的收益会很小 —— 那时候该做的是 GQA、量化或者更好的 Attention Kernel。

先用 Profiler 确认时间线上真有 Launch Gap，再上 Graph。 顺序反了就是在优化一个不存在的问题。

3. Batch 分桶¶

Graph 要求捕获时和重放时的 Shape 完全一致。但真实的 Batch Size 每步都在变。

解法是预先捕获一组桶：

graph_batch_sizes = [1, 2, 4, 8, 16, 32, 48, 64]

真实 Batch = 13 时，用桶 16，多出来的 3 个槽位是 Padding。

代价是算了 3 个假 Token。 值不值？在 Decode 这种访存受限的场景下，Batch 16 和 Batch 13 读取的权重量完全一样（权重读取是固定成本），多算 3 个 Token 的边际成本很低。用一点点冗余计算换掉几百次 Launch，通常是划算的。 但桶设得太稀（比如只有 1/32/64）就不划算了，Batch=33 要按 64 算，浪费近一半。

4. 三个不变量¶

# 捕获时和重放时必须是同一块显存
self.static_input_ids = torch.zeros(max_batch, dtype=torch.int64, device="cuda")
self.static_positions = torch.zeros(max_batch, dtype=torch.int64, device="cuda")
self.static_slot_mapping = torch.full((max_batch,), -1, dtype=torch.int32, device="cuda")
self.static_context_lens = torch.zeros(max_batch, dtype=torch.int32, device="cuda")

重放前只更新内容，绝不换张量：

self.static_input_ids[:bs].copy_(input_ids)      # ✅ 原地写
self.static_positions[:bs].copy_(positions)
self.static_slot_mapping.fill_(-1)               # ✅ 先清成 -1
self.static_slot_mapping[:bs].copy_(slot_mapping)
self.static_context_lens.zero_()
self.static_context_lens[:bs].copy_(context_lens)
graph.replay()

三条必须成立：

  1. 地址不变：Graph 里记录的是指针，不是张量对象。self.static_input_ids = new_tensor 这样一行赋值就会让 Graph 读到一块无关的显存 —— 而且不会报错。所以只能 copy_，不能重新赋值。
  2. 拓扑不变：捕获期间走过的分支，重放时也必须走一样的。任何依赖张量值的 Python 控制流（if tensor.item() > 0）都不能出现在 Graph 里，因为捕获时只会记录当时那一条分支。
  3. Padding 无副作用：slot 填 -1（KV Store Kernel 会 mask 掉），context_len 填 0（Attention 一个历史 Token 都不读），输出结果按真实 batch 裁掉。

第三条是最容易漏的。上面 fill_(-1) 和 zero_() 那两行看着多余 —— 但如果不清，Padding 槽位里会留着上一步的真实 slot 值，于是这一步会往那些页里写垃圾数据，破坏别的序列的 KV。

5. 怎么验证¶

# 唯一可靠的验证方式：同样的输入，Graph 和 Eager 必须输出完全一样的 token 序列
outputs_eager = LLM(model, enforce_eager=True).generate(prompts, greedy)
outputs_graph = LLM(model, enforce_eager=False).generate(prompts, greedy)
assert outputs_eager == outputs_graph

用 Greedy 采样做这个对比，否则随机性会掩盖问题。一旦不一致，几乎必然是上面三个不变量之一被破坏了。

十二、Tensor Parallel：切权重，然后把结果拼回来¶

1. Column Parallel：切输出维¶

W [out, in]
  rank 0 拿 W[0 : out/p, :]
  rank 1 拿 W[out/p : 2*out/p, :]

每个 Rank 拿到完整的输入 \(x\)，算出输出的一部分：

\[ y_r = x W_r^T,\qquad y = [\,y_0\ |\ y_1\ |\ \cdots\,] \]

QKV 和 Gate/Up 用这个切法。算完不需要立刻通信 —— 因为下游正好也是按头/按通道独立的（Attention 的每个头独立，SiLU 是 elementwise）。

2. Row Parallel：切输入维¶

W [out, in]
  rank 0 拿 W[:, 0 : in/p]
  rank 1 拿 W[:, in/p : 2*in/p]

每个 Rank 拿到输入的一部分，算出完整形状的部分和：

\[ y=\sum_r x_r W_r^T \]
def forward(self, x):
    y = F.linear(x, self.weight, self.bias if self.rank == 0 else None)
    if self.world_size > 1:
        dist.all_reduce(y)
    return y

O_proj 和 Down_proj 用这个切法。必须 AllReduce，因为每个 Rank 手里都只是一个部分和。

注意 self.bias if self.rank == 0 else None。 Bias 是加在最终结果上的，不是分片量。如果每个 Rank 都加一遍，AllReduce 之后 bias 就被累加了 \(p\) 次。这是 TP 实现里的经典 bug，而且 \(p=1\) 时测不出来。

3. 为什么这两种切法要配对使用¶

把它们串起来看就明白了：

x  ──Column Parallel──→  y_r（各 rank 拿输出的一段）
                             ↓ 无需通信，正好是下一层的输入分片
                          Row Parallel  ──→  部分和  ──AllReduce──→  完整输出

Column 之后接 Row，中间那次通信被省掉了。 一个 Transformer Block 因此只需要 2 次 AllReduce（Attention 出口一次、MLP 出口一次），而不是 4 次。这个配对不是巧合，是设计出来的。

4. Communication behind compute 的边界在哪¶

4.3 讲过「通信藏在计算背后」。但 TP 的 AllReduce 正好卡在层内的数据依赖上：下一层的 RMSNorm 需要完整的 \(y\)，在 AllReduce 完成前它一个元素都算不了。

所以不能简单地把通信推后。能做的是：

  • 把 GEMM 和 AllReduce 都切成小块，做流水（compute chunk \(i\) 的同时 reduce chunk \(i-1\)）；
  • 用 ReduceScatter + AllGather 替代 AllReduce，配合序列并行；
  • 算子重排，把不依赖通信结果的计算提前。

而且「有独立的通信引擎」不等于「自动重叠」。 NCCL 的 kernel 也要占 SM，和计算 kernel 抢资源。是否真的重叠了，必须在 Nsight Systems 的时间线上看到 NCCL 那一行和 Kernel 那一行在同一时刻都有色块 —— 这是唯一的判据。

5. 一 GPU 一进程，以及 Collective 的顺序协议¶

每个 Rank:
  绑定 CUDA device
  → 初始化 NCCL 进程组
  → 建立完全相同的模型结构
  → 只加载自己那份权重分片
  → 等 Rank 0 下发执行命令（走 SharedMemory）
  → 以完全相同的顺序执行 collective

最后一行是全局协议，也是多卡最常见的死锁来源：

Rank 0:  AllReduce(A) → AllReduce(B)
Rank 1:  AllReduce(A) → （因为某个 if 分支没进去，跳过了 B）
                         ↑
         Rank 0 在 B 上永久等待，程序既不崩溃也不推进

任何依赖本地状态的分支（比如「这个 rank 上没有需要通信的数据就跳过」）都可能导致 Rank 之间的 collective 序列不一致。这也是为什么 TP 里所有 Rank 都要建立完整的模型结构、走完全相同的代码路径 —— 哪怕某些计算对它是冗余的。

卡死时的第一动作：NCCL_DEBUG=INFO 看每个 Rank 最后进入的是哪个 collective，序号对不上的地方就是分歧点。

十三、手推一次完整的 Step Trace¶

前面十二节是分模块的。这一节把它们串起来 —— 强烈建议拿纸笔自己推一遍再往下看。推不下去的那一步，就是你对某个模块的理解还有洞。

设定：

S0: prompt 6 个 token, max_new_tokens = 2
S1: prompt 3 个 token, max_new_tokens = 2
block_size = 4
max_num_batched_tokens = 6

Step 1：S0 Prefill¶

Scheduler:
  S0 需要 6 个 token，预算 6，刚好够
  S0.num_blocks = ceil(6/4) = 2  →  分配 block_table = [7, 2]
  S0.scheduled_tokens = 6
  预算用完，S1 这一步进不来

Runner:
  input_ids   = S0[0:6]
  positions   = [0,1,2,3,4,5]
  cu_seqlens_q = [0, 6]
  cu_seqlens_k = [0, 6]        ← 没有缓存前缀，q == k
  block_tables = None          ← 所以不走页表
  slot_mapping = [28,29,30,31, 8,9]
                  └ block 7 ┘  └ block 2 ┘
                  7*4+0..3      2*4+0..1

GPU:
  K/V 写入物理页 7 和 2
  只对最后一个位置算 logits，采样得到 x0

Postprocess:
  publish_full_blocks: block 7 满了 → 发布；block 2 只有 2/4 → 不发布
  S0.cached_tokens = 6, scheduled_tokens = 0
  S0.token_ids 追加 x0  →  长度变成 7

自检：为什么 slot_mapping 从 28 跳到 8？因为 token 4 跨了页边界，逻辑块从 0 变成 1，物理块从 7 变成 2。这个跳变就是分页的全部意义。

Step 2：S1 Prefill¶

Prefill 优先策略生效，S1 抢在 S0 的 Decode 前面：

S1.num_blocks = ceil(3/4) = 1  →  block_table = [11]
input_ids    = S1[0:3]
slot_mapping = [44, 45, 46]     ← 11*4 + 0,1,2
采样得到 y0，S1.token_ids 长度变成 4

注意 S0 这一步没有前进。 这就是第六节说的「Prefill 优先会增加已有请求的 ITL」——具体到这里，S0 的第二个 token 被推迟了整整一步。

Step 3：S0 与 S1 一起 Decode¶

needs_new_block(S0): len=7, 7 % 4 = 3 ≠ 1  →  不需要新页
needs_new_block(S1): len=4, 4 % 4 = 0 ≠ 1  →  不需要新页

input_ids    = [x0, y0]
positions    = [6, 3]
context_lens = [7, 4]
block_tables = [[7, 2],
                [11, -1]]        ← Padding 到宽度 2
slot_mapping = [10, 47]
                │   └ S1: pos=3 → block 11, offset 3 → 47
                └ S0: pos=6 → 逻辑块 1 → block 2, offset 2 → 10

GPU 只算 2 个新 token，但 Attention 分别读了 7 个和 4 个历史位置 —— 而且 S1 那一行的 -1 页永远不会被碰，因为 context_lens[1] = 4，只覆盖第一页。

自检：为什么 S1 的 block_tables 有 Padding 但没出问题？回到第七节第 4 小节。

Step 4：完成与释放¶

两条都生成了第 2 个 token，命中 max_new_tokens：

S0.status = FINISHED  →  释放 [2, 7]（逆序）
S1.status = FINISHED  →  释放 [11]
free block pool 全部收回

如果 block 7 之前被发布进了 Prefix Cache，它的 ref_count 归零后仍留在 free list 里带着 hash —— 下一个以相同 6 个 token 开头的请求会直接命中它，省掉这段 Prefill。这就是第五节那个「延迟回收」的收益兑现的地方。

十四、调试、性能分析与读码顺序¶

1. 按可验证的顺序搭¶

不要一次写完所有功能再调。每加一层，都要有一个能立刻验证它的手段：

HF Eager 输出（数值 Reference，Greedy 固定输入）
  → Sequence 状态机          ← 纯 CPU 单测
  → Packed Batch Metadata    ← 手算 cu_seqlens、slot 对拍
  → Paged KV                 ← 和连续 KV 的 Reference 对齐
  → Scheduler                ← 预算、抢占、释放的单测
  → Runner + Attention 后端  ← 和 HF logits 逐层对齐
  → Prefix Cache             ← 开关它，输出必须完全一致
  → 抢占与恢复               ← 人为把 KV 调小逼出抢占
  → Chunked Prefill          ← 改 chunk size，输出必须完全一致
  → CUDA Graph               ← enforce_eager 开关 A/B
  → Tensor Parallel          ← TP=1 vs TP=2 token 一致

注意后半段那几个「必须完全一致」。 Prefix Cache、Chunked Prefill、CUDA Graph 都是纯粹的性能优化，不应该改变任何输出。所以它们各自都有一个免费的、极强的验证手段：开关它，比对 Greedy 输出。不一致就是有 bug，没有「误差范围内」这一说。

（TP 是例外：不同的规约顺序会带来浮点误差，所以判据是「数值接近 + token 序列一致」。）

层 怎么测

Scheduler 预算、Chunk、抢占、结束释放

3. 性价比最高的几个断言¶

assert len(slot_mapping) == sum(seq.scheduled_tokens for seq in seqs)
assert max(slot_mapping) < num_kv_blocks * block_size
assert all(b >= 0 for seq in seqs for b in seq.block_table)
assert len(token_ids) == len(seqs)
assert not (used_block_ids & set(free_block_ids))    # 一页不能既在用又空闲

最后一条尤其值得加 —— 引用计数出问题时它是最早报警的，比等到「输出变成乱码」早得多。

5. 给 Step 打 NVTX 标记¶

Profiler 抓出来的一堆 Kernel 名字，不加标记根本对不上框架的哪个阶段。花五分钟加这个，之后每次分析都省半小时：

with torch.cuda.nvtx.range("schedule"):
    seqs, is_prefill = scheduler.schedule()

with torch.cuda.nvtx.range("prepare_metadata"):
    batch = runner.prepare(seqs, is_prefill)

with torch.cuda.nvtx.range("model_forward"):
    token_ids = runner.execute(batch)

with torch.cuda.nvtx.range("postprocess"):
    scheduler.postprocess(seqs, token_ids, is_prefill)

常用命令：

# GPU 时间线、CUDA API、NCCL 和 NVTX
nsys profile --trace=cuda,nvtx,nccl,osrt -o nano_step python example.py

# 下钻单个 Kernel
ncu --kernel-name regex:store_kvcache --set full -o kv_store python example.py

# 自定义 Kernel 的越界检查
compute-sanitizer --tool memcheck python example.py

# NCCL 初始化与 collective 日志
NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,COLL python example.py

正确性问题先别开 Profiler。 用小 Shape、Eager、加断言、加同步边界去缩小范围。Profiler 会改变时序，有时候还会让竞态消失 —— 那是最难受的情况。

6. 性能从哪开始看¶

先看服务指标，别一上来就 ncu：

  • TTFT：请求进来到首 Token；
  • TPOT / ITL：相邻输出 Token 的间隔；
  • Throughput：总输出 Token/s；
  • P50 / P99：常见延迟和尾延迟。

这四个指标会打架。 Continuous Batching 提高吞吐的同时，往往会拉长排队时间，让 TTFT 的 P99 变差。只看 Tokens/s 做优化，很容易做出一个「吞吐很漂亮但用户觉得卡」的系统。

确认是哪个指标有问题后，再往下分层：

engine.step 墙上时间
├── Scheduler CPU
├── Metadata 构造 + H2D
├── Model GPU
│   ├── GEMM / GEMV
│   ├── Attention / KV
│   ├── NCCL
│   └── Launch gaps        ← 这一项大 → 考虑 CUDA Graph
├── Sampling
└── Postprocess

一次只打开一个优化，每次记录正确性、TTFT、TPOT、吞吐、显存和 Shape 分布：

Eager, TP=1, 无 Prefix Cache
  → 开 Paged KV
  → 开 Prefix Cache
  → 开 Chunked Prefill
  → 开 CUDA Graph
  → TP=2 / TP=4

7. 读源码的顺序¶

做完上面这些之后再去读原项目，按依赖从下往上：

  1. sampling_params.py、config.py —— 先知道有哪些旋钮
  2. engine/sequence.py —— 状态机
  3. engine/block_manager.py —— 显存账本
  4. engine/scheduler.py —— 控制平面的核心
  5. utils/context.py —— 两个平面的接缝
  6. layers/attention.py —— 元数据怎么被消费
  7. models/qwen3.py + layers/* —— 模型适配
  8. engine/model_runner.py —— 放最后
  9. engine/llm_engine.py —— 外层循环

model_runner.py 一定放最后。 它是所有概念的汇合点：模型初始化、显存测量、Metadata 编译、KV Cache 分配、CUDA Graph、多进程通信全在里面。前面八个模块没读透就去啃它，只会觉得每一行都很陌生。

学完的标准¶

读完并动手实现之后，下面这些问题应该能不看源码直接答：

  1. 一个请求从 Waiting 到 Finished，经过了哪些状态、每一步谁改了它？
  2. cached_tokens 和 scheduled_tokens 为什么必须分开？合并会出什么 bug？
  3. Prefill 的 Packed Tensor 和 Decode Batch，第一维的含义分别是什么？
  4. Block Table 和 Slot Mapping 分别用于读还是写？覆盖范围有什么不同？
  5. Prefix Cache 的哈希为什么必须是链式的？举一个不链式就会出错的例子。
  6. 为什么只能发布填满的 Block？为什么发布必须在 GPU 写完之后？
  7. cu_seqlens_k 在什么情况下会大于 cu_seqlens_q？
  8. 为什么 KV Cache 要在 Warmup 之后才分配？
  9. 为什么只对最后一个位置算 Logits？省了多少？
  10. CUDA Graph 的三个不变量是什么？它不优化什么？
  11. Row Parallel 为什么要 AllReduce，为什么 bias 只能在一个 Rank 上加？
  12. Recompute 抢占为什么牺牲队尾、为什么恢复时插队首？

另外两个动手标准：

  • 能手推第十三节的完整 Step Trace，每一步的 cached_tokens、页表、slot mapping 都算得出来；
  • 让 HF Reference、Paged Eager、CUDA Graph、TP 四个版本在同一组固定输入 + Greedy 采样下输出完全一致（TP 允许 token 一致、logits 有浮点误差）。

这两条做到了，Nano-vLLM 的主干就真的属于你了。接下来可以往两个方向走：回到 11.3 把 Attention Kernel 自己写一遍，或者去 11.5 看它怎么变成一个能扛流量的服务。
