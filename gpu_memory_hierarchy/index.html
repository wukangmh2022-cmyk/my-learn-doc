title: GPU 存储层次: HBM → L2 → Shared Memory → Register tags: [memory hierarchy, hbm, shared memory, l1, l2, cache, register, sram] description: 深入 GPU 存储层次，理解 HBM、L2、L1、Shared Memory、Register 的区别及其在图形和 AI 中的不同用法

1.3 GPU 存储层次: HBM → L2 → Shared Memory → Register

概述

GPU 的存储层次从慢到快、从大到小依次为：HBM（显存）→ L2 Cache → L1 Cache / Shared Memory → Register。

搞渲染的你最清楚：数据在哪层决定了访问速度。AI 推理优化的本质，就是让数据尽量呆在离计算单元近的存储层级里。

GPU 存储层次全景（以 A100 为例）

存储层级 硬件本质 容量（A100） 延迟 带宽 谁控制
HBM（显存） DRAM 40/80 GB ~400-600 cycles ~2 TB/s 软件分配（cudaMalloc）
L2 Cache SRAM 40 MB（整卡共享） ~200 cycles ~2 TB/s 硬件自动管理
L1 Cache SRAM 192 KB/SM（与 Shared 共享） ~30 cycles 极高 硬件自动管理
Shared Memory SRAM 164 KB/SM（可配置） ~30 cycles 极高 软件显式管理
Register SRAM 256 KB/SM ~1 cycle 最大 编译器分配

存储层次的本质：SRAM vs DRAM

所有片上存储（L1、L2、Shared Memory、Register）都是 SRAM（静态随机存取存储器），而 HBM 是 DRAM（动态随机存取存储器）。

关键区别：

SRAM：速度快、容量小、功耗高、成本高——用于片上缓存 DRAM：速度慢、容量大、功耗低、成本低——用于主存（显存）

但有一个最常见的误解需要澄清：

Shared Memory ≠ L1 Cache。虽然它们在物理上共享同一块片上 SRAM，但在逻辑上是完全独立的两个单元。

Shared Memory vs L1 Cache：核心区别

这是 GPU 存储层次中最关键、也最容易混淆的区别。

维度 L1 Cache Shared Memory
管理方式 硬件自动管理：决定缓存什么、淘汰什么 软件显式管理：你手动 Load/Store
可预测性 尽力而为：缓存不命中就要等几百 cycles 确定性：数据显式加载后绝对在 SRAM 里
用途 透明加速 Global Memory 访问 同一 Block 内线程共享数据，手动 Tiling
控制粒度 你无法控制（硬件决定） 完全控制（你决定何时加载、何时同步）
典型延迟 ~30 cycles（命中时） ~30 cycles（始终）

用你的渲染语言翻译：

L1 Cache = GPU 驱动帮你管理的纹理 Cache——你只管 tex2D，驱动决定什么时候加载、淘汰，你看不到。 Shared Memory = 你自己定义的 groupshared 变量——你显式声明大小，手动 Load/Store，完全掌控。

物理共享的 SRAM

在 NVIDIA GPU 中，Shared Memory 和 L1 Cache 共用同一块物理 SRAM。比如 A100 的每个 SM 有 192KB 片上 SRAM，你可以配置为：

配置模式 Shared Memory L1 Cache
默认 164 KB 28 KB
均衡 128 KB 64 KB
计算优先 48 KB 144 KB

你的直觉：这就像你用 DX12 的 Heap 自己管理内存，还是让驱动自动管理的区别。Shared Memory = 你手写的分配器，L1 Cache = 驱动帮你管理的默认堆。

为什么图形用 Cache，AI 用 Shared Memory？

这是两个领域最根本的设计分歧。

图形渲染：纹理采样的可预测性

在 Pixel Shader 中执行 tex2D 时：

  1. 相邻像素几乎总是采样相邻纹素（空间局部性）
  2. 纹理 Cache 命中率极高（80%+）
  3. 硬件 TMU 会自动预取（Prefetch）连续数据
  4. 你不需要手动管理——硬件自动搞定

AI 推理：访问模式的不可预测性

在 AI Kernel 中执行 __shared__ 加载时：

  1. Attention：Q 的 token i 要和 K 的所有行做点积，是跨步跳跃式访问，完全没有空间局部性
  2. Conv2d：权重是训练出来的随机值，访问模式是时间上复用但空间上离散的
  3. 硬件 Cache 基本无效——因为上一微秒加载的数据和下一条指令访问的地址可能相隔十万八千里

核心结论：图形靠硬件预测（Cache 自动搞定一切），AI 靠软件显式管理（Shared Memory 手动加载），因为 AI 的数据访问模式使硬件无法预测。

用你的渲染语言翻译

场景 图形纹理采样 AI 数据加载
你的代码 float4 c = tex2D(tex, uv); float d = __ldg(&data[ idx ]);
谁管缓存 TMU + Cache（硬件） 你自己（软件）
访问模式 相邻像素采相邻纹素 → 可预测 跨步/随机 → 不可预测
Cache 表现 命中率极高，自动预取 命中率极低，根本无法预取
你的应对 写更少的 Draw Call，合并 Pass 手动 __shared__ Tiling，显式管理局部性

存储层次与 AI 优化策略

优化技术 涉及哪些存储层级 本质
算子融合 HBM（减少读写）→ L1/L2（减少搬运） 减少中间结果在 HBM 的读写次数
Tiling（分块） HBM → Shared Memory → Register 把数据从 HBM 搬进 SRAM，利用片上高速缓存
INT8 量化 HBM（减半数据量） 减少从 HBM 搬运的数据量
FlashAttention HBM → Shared Memory（Online Softmax） 中间矩阵 S=Q×K^T 不写回 HBM
Warp Shuffle Register（零 SRAM 开销） 寄存器级数据交换，不经过 Shared Memory

你的认知固化

图形渲染：Cache 是"高速路旁的加油站"，你开过去的时候（采样纹理），顺便加油（缓存命中）。 AI 推理：Shared Memory 是你自己买的"私人停车场"，你提前把车（数据）都停进去，然后工人（线程）可以零距离随便拿。

如果你的项目是... 你应该优先考虑...
图形渲染（游戏引擎、渲染器） Cache。纹理访问极度规律，硬件自动管理最省心
AI 推理（推理引擎、自定义 Kernel） Shared Memory。数据依赖杂乱，只有你显式控制才能保证不爆显存、不空转

这正是 GPU 给图形工程师准备了 Texture Cache、却给 AI 工程师准备了 Shared Memory 和 __shared__ 的原因——它们是为完全不同的数据流模式而设计的硬件生态位。
