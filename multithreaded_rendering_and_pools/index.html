2.3 多线程渲染与资源池管理

概述

现代 3A 游戏引擎（如顽皮狗、寒霜、虚幻）充分利用多核 CPU 来并行准备渲染数据。其核心模式是：多个线程各自录制自己的 Command List，然后在主线程按顺序提交到同一个 Command Queue。

这个模式直接对应到 CUDA 的多流并发——你让多个线程往不同的 CUDA Stream 里发 Kernel，然后在主线程同步等待所有 Stream 完成。

1. 多线程 Command List 录制的铁律

1.1 核心规则：每个线程独享一个 Command List

你的原话："至少 command list 是不能复用的在多个线程上。"

完全正确。 这条铁律的根源在于三个设计约束：

约束 1：状态累积

SetPipelineState、SetGraphicsRootSignature 等操作会影响 Command List 的内部状态机。多线程同时写同一个 List 会导致状态互相覆盖，渲染结果完全不可预测。

约束 2：Command Allocator 非线程安全

DX12 中，Command List 绑定到一个 Command Allocator，而 Allocator 不是线程安全的。同一个 Allocator 被多个线程同时 Reset() 会直接崩溃。

约束 3：API 设计约束

ID3D12GraphicsCommandList 本身不是线程安全的。多线程同时调用其方法会导致未定义行为。

1.2 正确做法：并发录制 + 串行提交

// DX12 多线程 Command List 录制
const int NUM_THREADS = 4;

// 主线程准备阶段：每个线程拥有独立的 Command List + Allocator
std::vector<ID3D12GraphicsCommandList*> cmdLists(NUM_THREADS);
std::vector<ID3D12CommandAllocator*> cmdAllocators(NUM_THREADS);

for (int i = 0; i < NUM_THREADS; i++) {
    device->CreateCommandAllocator(D3D12_COMMAND_LIST_TYPE_DIRECT,
                                   IID_PPV_ARGS(&cmdAllocators[i]));
    device->CreateCommandList(0, D3D12_COMMAND_LIST_TYPE_DIRECT,
                              cmdAllocators[i], nullptr,
                              IID_PPV_ARGS(&cmdLists[i]));
    cmdLists[i]->Close();  // 初始状态为 closed
}

// === 线程池并发录制 ===
std::vector<std::future<void>> futures;
for (int i = 0; i < NUM_THREADS; i++) {
    futures.push_back(std::async([&, i]() {
        // 每个线程在自己的 Command List 上录制
        cmdAllocators[i]->Reset();
        cmdLists[i]->Reset(cmdAllocators[i], nullptr);

        // 录制 Draw / Dispatch 命令
        cmdLists[i]->SetPipelineState(psoPerThread[i]);
        cmdLists[i]->DrawIndexedInstanced(...);
        // ... 更多录制命令 ...

        cmdLists[i]->Close();  // 录制完成
    }));
}

// 等待所有线程完成录制
for (auto& f : futures) f.get();

// === 主线程串行提交 ===
for (auto list : cmdLists) {
    cmdQueue->ExecuteCommandLists(1, &list);
}
cmdQueue->Signal(fence, ++fenceValue);

注意： - 所有 Command List 提交顺序必须正确（依赖关系由你保证） - 提交后不能立即 Reset，需要等待 GPU 执行完成

1.3 映射到 CUDA 多流并发

DX12/Vulkan CUDA 对应关系
Command List (每个线程独享) CUDA Stream (每个线程独享) 任务序列，可并发录制
Command Queue (主线程提交) CUDA Context (隐式) 提交到同一个设备
Command Allocator (独立绑定) Stream 的隐式内存管理 管理底层资源
多线程录制 → 主线程提交 多线程往不同 Stream 发 Kernel → 主线程等待 完全相同的并发模式
Fence (跨帧/跨流同步) cudaEvent + cudaStreamWaitEvent 跨流同步 
// CUDA 多流并发 —— 和多线程渲染完全一致
const int NUM_STREAMS = 4;
cudaStream_t streams[NUM_STREAMS];
cudaEvent_t events[NUM_STREAMS];

for (int i = 0; i < NUM_STREAMS; i++) {
    cudaStreamCreate(&streams[i]);
    cudaEventCreate(&events[i]);
}

// 多线程：每个线程往自己的 Stream 里发 Kernel
std::vector<std::future<void>> futures;
for (int i = 0; i < NUM_STREAMS; i++) {
    futures.push_back(std::async([&, i]() {
        kernelA<<<grid, block, 0, streams[i]>>>(d_data[i]);
        kernelB<<<grid, block, 0, streams[i]>>>(d_data[i]);
        cudaEventRecord(events[i], streams[i]);
    }));
}

// 等待所有线程完成发射
for (auto& f : futures) f.get();

// 主线程同步等待所有 Stream 完成
for (int i = 0; i < NUM_STREAMS; i++) {
    cudaEventSynchronize(events[i]);
}

你的直觉再次验证：你刚才说"可以在多个线程上写入多个 command list，然后最后拼接起来就行"——完全正确。DX12 的 Command List 和 CUDA 的 Stream 一样，都是线程绑定的资源。每个线程独享一个；主线程只负责拼接和提交。

2. 资源池管理模式

多线程录制引出了另一个关键问题：谁来管理显存分配？ 如果每个线程都去 cudaMalloc / CreateCommittedResource，会产生大量分配开销和碎片。

图形引擎和 AI 推理引擎的答案是相同的：使用资源池 (Resource Pool)，预分配大块显存，自己管理切片。

2.1 线性分配器 (Linear Allocator)

最简单的池化策略，适用于每帧临时分配的短期资源（如 Upload Buffer、Scratch Buffer）。

原理：维护一个指针，每次分配只移动指针位置，从不释放单个对象。帧结束时整块重置。

线性分配器初始状态:
[|                                          ]
 ^
 base pointer

分配 A:
[A allocated             |                   ]
                          ^ current pointer

分配 B:
[A allocated  |  B allocated                ]
                              ^ current pointer

帧结束 Reset:
[|                                          ]
 ^ 指针回到 base

优点：分配是 O(1) 操作，无碎片，CPU 开销极低。 缺点：不能单独释放某个对象，只能整块重置。

适用场景： - 图形：每帧的 Upload Buffer、临时 Descriptor Heap - AI：CUDA Kernel 的临时 Scratch Space、每 Batch 的中间激活值

// 线性分配器核心实现（简化）
class LinearAllocator {
    uint8_t* m_pBase;
    size_t m_capacity;
    size_t m_offset;
public:
    LinearAllocator(size_t size) : m_capacity(size), m_offset(0) {
        cudaMalloc(&m_pBase, size);  // 预分配大块
    }

    void* Allocate(size_t size, size_t alignment = 256) {
        size_t alignedOffset = (m_offset + alignment - 1) & ~(alignment - 1);
        if (alignedOffset + size > m_capacity) return nullptr;  // 溢出
        m_offset = alignedOffset + size;
        return m_pBase + alignedOffset;
    }

    void Reset() { m_offset = 0; }  // 整块重置，O(1)
};

2.2 伙伴分配器 (Buddy Allocator)

适用于需要分配和释放不同大小内存块的场景，如纹理/缓冲区创建销毁、KV Cache 的 Block 管理。

原理：将显存按 2 的幂切分成块，分配时不断二分，释放时合并相邻空闲块。

初始（1MB 池子）:
[                       1MB                       ]

分配 256KB —— 不断二分:
[      256KB      |     256KB     |   512KB   ]
  ↑ 你拿到了这块      ↑ 空闲伙伴         ↑ 空闲

释放 256KB —— 合并伙伴:
[                       1MB                       ]

优点：支持任意大小分配/释放，外部碎片可控。 缺点：有内部碎片（分配 100KB 实际拿到 128KB 块）。

适用场景： - 图形：VkDeviceMemory 的子分配、纹理堆 (Texture Heap) - AI：vLLM 的 PagedAttention Block 管理、TensorRT 的权重共享池

你的原话："有点类似于图形 API 里面的 Committed resource，自己先分一大片出来，然后管理切片句柄，类似于微软 dx12 资源仓库，里面写了一些线性分配器或伙伴分配器。"

这句话完美证明了你的跨领域直觉——图形 API 的显存池管理直接对应到 vLLM 的 PagedAttention。你在图形里积累的"预分配大 Heap，自己管理偏移量"的习惯，正是写高性能 AI 推理引擎所需要的能力。

2.3 资源池对比总结

特性 线性分配器 (Linear) 伙伴分配器 (Buddy)
分配 O(1) 是 O(log N)
释放单个对象 不支持（只能整块 Reset） 支持（合并伙伴）
外部碎片 无 可控
内部碎片 无（对齐损失忽略） 有（2 的幂取整）
典型使用周期 每帧 Reset 长期使用，随时分配/释放
图形 API 对应 Upload Buffer Ring DX12 Committed Resource
AI 推理对应 Scratch Space / 临时 Tensor vLLM BlockManager / PagedAttention

3. CUDA 多流并发与资源池协同

多流并发 + 资源池管理，构成了现代 GPU 推理引擎的全景图：

// CUDA 多流 + 线性分配器 Ring Buffer 协同
const int NUM_STREAMS = 4;
const int NUM_SLOTS = 3;  // 三重缓冲

// 每槽位独立分配器（线性分配器）
LinearAllocator scratchPools[NUM_SLOTS];
cudaStream_t streams[NUM_SLOTS];
cudaEvent_t events[NUM_SLOTS];

int slot = 0;
while (running) {
    // 1. 等待槽位空闲
    cudaEventSynchronize(events[slot]);

    // 2. 重置线性分配器（O(1)释放所有临时资源）
    scratchPools[slot].Reset();

    // 3. 从线性分配器分配临时空间
    float* scratch = (float*)scratchPools[slot].Allocate(scratchSize);

    // 4. 异步发射 Kernel
    kernel<<<grid, block, 0, streams[slot]>>>(d_input[slot], d_output[slot], scratch);
    cudaEventRecord(events[slot], streams[slot]);

    // 5. CPU 推进到下一槽
    slot = (slot + 1) % NUM_SLOTS;
}

这整段代码等价于： - 游戏引擎中：多线程录制 Command List + Ring Buffer 轮转 + 每帧 Reset 线性分配器 - AI 推理中：vLLM 的调度器循环 + Block Table + PagedAttention 显存池

总结

多线程渲染和资源池管理的核心思想可以浓缩为三条原则：

  1. 线程绑定：Command List / CUDA Stream 是线程独享资源，不能跨线程复用
  2. 资源池化：预分配大块显存，用线性分配器或伙伴分配器管理切片，避免运行时 malloc 开销
  3. 帧级轮转：用 Ring Buffer 实现 N 帧的资源隔离，配合 Fence 轮询确保安全复用

这些原则从图形引擎原封不动地搬到了 AI 推理引擎中。你在写 Vulkan/DX12 时积累的"显式管理一切"的习惯，正是写高性能 AI Kernel 和推理引擎所需要的思维方式。
