8. vLLM 推理调优与多卡系统¶

概述¶

第 6、7 章你写了算子，但算子跑在框架里才有意义。vLLM 这类推理引擎的"快"来自两层： - 系统层：CUDA Graph 降低 launch 开销、Continuous Batching 提高有效利用率、量化减少数据流量。 - 多卡层：NCCL 集合通信把一层的大矩阵拆到多张卡（张量并行）或多层（流水线并行）。

这一章偏"调优 & 部署"，读者是想给 vLLM 做性能调优、或读它 csrc/ 源码的人。每个主题都给"是什么 + 为什么影响性能 + 怎么在 vLLM 里用 + 图形映射"。

8.1 CUDA Graph¶

是什么¶

CPU 每次 kernel<<<>>>() 都要走驱动、建命令、提交——单次 launch 开销约几微秒。Decode 阶段成百上千个小 kernel 连续跑，CPU launch 开销会吃掉可观时间。

CUDA Graph 把一串 kernel launch 录制成一张图，之后用一次 graph.launch() 重放，省掉每步的 CPU 提交开销。

cudaGraph_t graph; cudaGraphExec_t exec;
cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);
// ... 录制一堆 kernel launch ...
cudaStreamEndCapture(stream, &graph);
cudaGraphInstantiate(&exec, graph, NULL, NULL, 0);
// 之后每步只调一次：
cudaGraphLaunch(exec, stream);   // 不再逐个 launch

为什么影响 vLLM¶

Decode 每个活跃序列通常新增一个 token，形状集合比 Prefill 更容易分桶，因此适合对常见 Batch Size 捕获多张 Graph 并重放。实际策略随 vLLM 版本和模型而变化，Prefill 或混合阶段也可能使用分段 Graph，不能概括为“永远不捕获”。

局限¶

  • 捕获后的拓扑和资源使用需要可重放；参数和部分节点属性可通过 API 更新，但动态形状通常仍需分桶、多张 Graph 或回退到 eager。
  • 调试困难（断点、Nsight 行为不同）。

图形 → AI 映射¶

概念 图形对应
CUDA Graph 重放 RenderGraph / 录制的 Command List：把一帧的渲染指令录好，之后每帧只 replay，不重建

8.2 Occupancy 深度¶

是什么¶

Occupancy = 一个 SM 上实际驻留的 Active Warp 数 / 该架构每 SM 的最大 Active Warp 数。A100 的上限是 64 Warp/SM，但其他架构应查询设备属性。

\[ W_{block}=\left\lceil\frac{T_{block}}{32}\right\rceil \]
\[ B_{resident}=\min\left( \left\lfloor\frac{R_{SM}}{R_{block}}\right\rfloor, \left\lfloor\frac{S_{SM}}{S_{block}}\right\rfloor, \left\lfloor\frac{W_{max}}{W_{block}}\right\rfloor, B_{\text{arch-max}} \right) \]

实际分配还会按寄存器和 Shared Memory 的硬件粒度向上取整。

  • 寄存器：每个线程用越多寄存器，能驻留的 block 越少。
  • Shared Memory：每个 block 占用越多（见 5.2），能驻留的 block 越少。
  • block 尺寸：blockDim 越大，单 block warp 越多。

误区¶

高 Occupancy 不等于高性能。达到足以隐藏延迟的 Warp 数之后，继续追求 Occupancy 可能迫使编译器减少寄存器、造成 Spill，或缩小本来更高效的 Tile。应结合 Stall Reason、吞吐和端到端时间判断。

怎么看¶

Nsight Compute 直接给 Achieved Occupancy。也可用 __launch_bounds__(max_threads, min_blocks) 提示编译器控制寄存器。

图形 → AI 映射¶

概念 图形对应
Occupancy 受寄存器/SMem 限制 Wave/Threadgroup 占用率：一个 CU 能同时跑几个 wave，受 VGPR/SGPR 和 LDS 限制——DX12 里你也调过

8.3 FP8 / INT8 / W8A8 量化推理¶

为什么重要¶

LLM 推理瓶颈常是权重与 KV Cache 的 HBM 带宽，尤其在小批量 Decode。把数据从 FP16（2 字节）压到 INT8/FP8（1 字节），原始元素流量约减半；相对 FP32 才是四分之一。端到端延迟不会必然同比下降，因为还包括缩放、反量化、元数据、KV 访问和调度开销。

  • INT8 (W8A8)：权重+激活都 INT8，需 per-tensor / per-channel 缩放因子。
  • FP8 (E4M3 / E5M2)：H100 Tensor Core 的理论 FP8 峰值可达相应 FP16 路径的约 2 倍。实际内核和硬件支持取决于模型、vLLM 版本、量化方案与后端。

缩放因子¶

量化核心是为每段数据选一个 scale 把 FP 映射到整数格点：

\[ x_{int8} = \text{clip}\big(\text{round}(x_{fp} / s),\ -128, 127\big),\quad s = \max(|x|)/127 \]

反量化在累加后做。MoE/Attention 的敏感层常保持 FP16（混合精度）。

图形 → AI 映射¶

概念 图形对应
低精度换带宽 BCn / ASTC 纹理压缩：用更少字节存纹素，换取带宽，代价是精度——和你用压缩纹理一个道理

8.4 NCCL 与集合通信¶

flowchart LR
    M["模型与请求形状"] --> TP["张量并行 TP"]
    M --> PP["流水线并行 PP"]
    TP --> C1["层内频繁 Collective"]
    PP --> C2["Stage 间激活传输"]
    C1 --> P["端到端吞吐 / 延迟"]
    C2 --> P
    NET["NVLink / PCIe / 网络拓扑"] --> C1
    NET --> C2

多卡并行的"血液"是集合通信。NCCL（NVIDIA Collective Communications Library）在 NVLink/PCIe 上高效实现它们。

原语 作用 vLLM 用途
AllReduce 所有卡求和后广播给所有卡 张量并行（TP）：每层 matmul 后把所有卡的部分和加起来
AllGather 把各卡的分片拼成完整张量 TP 中把切分的激活拼回
ReduceScatter 求和但结果分散到各卡 TP 的另一半（与 AllGather 配对）
Broadcast 一张卡发全员 初始化权重、广播 prompt

Ring AllReduce（面试常考）¶

把数据分成 \(P\) 份（卡数），两阶段： 1. Scatter-Reduce：沿环传 \(P-1\) 步，每步相邻卡传一份并本地累加 → 每卡拿到一个分片的完整和。 2. All-Gather：再沿环传 \(P-1\) 步，把完整和扩散到所有卡。

每个 Rank 的发送量为 \(2(P-1)n/P = 2(n-n/P)\)；整个系统的链路流量还要再乘参与者数量。Ring 在大消息上通常能较好利用带宽，但小消息延迟、拓扑和实现细节也会影响选型。

图形 → AI 映射¶

概念 图形对应
Ring AllReduce 多 GPU 间的分块拼图：像 SLI / 多卡渲染里把画面分块交给各卡算、再互相交换边界（虽不完全同构，但"分片+交换"思想一致）

8.5 张量并行 & 流水线并行¶

张量并行（Tensor Parallelism, TP）¶

把每一层的权重矩阵按列/行切到多卡：

  • 对 \(Y = X A\)，按输出列切分 \(A\) 时，各卡得到不同的 \(Y_i\)，后续可保持分片或做 AllGather；按归约维切分时，各卡得到部分和，才需要 AllReduce/ReduceScatter。实际 Transformer TP 会配对列并行与行并行层以减少通信。
  • KV 头通常尽量按 Rank 切分；当 num_kv_heads 小于或不能整除 TP Size 时，框架也可能复制 KV 头，具体约束应以模型与版本为准。
  • 集合通信频繁出现在层内投影边界，高带宽低延迟互联通常更有利。

流水线并行（Pipeline Parallelism, PP）¶

把不同层分给不同卡（卡 0 算前几层、卡 1 算后几层），序列像流水一样流过去。

  • 用 micro-batch 填 Pipeline，否则有"气泡"（bubble）空闲。
  • 通信量小（只传激活），但延迟大（要等前一级）。

选型¶

并行 切什么 通信 适用
TP 层内权重 高（每层 AllReduce） 单节点多卡（NVLink）
PP 跨层 低（只传激活） 跨节点、模型太大放不下单卡

vLLM 主要用 TP（配合 NCCL），PP 在超大模型时配合。

8.6 Continuous Batching / Spec Decoding / Prefix Caching¶

Continuous Batching（连续批处理）¶

传统静态 Batch 容易被最长序列拖住。Continuous Batching 在迭代边界移除已完成请求并接纳新请求，减少填充和空槽；GPU 利用率仍会受请求到达率、显存、形状和调度开销限制。

Speculative Decoding（投机解码）¶

用小模型（draft）一次猜多个 token，再用大模型并行验证，全对就一次接受多个。Decode 是 memory-bound（每步只算 1 token），投机解码把它变成"一次验证 k 个"，摊薄每 token 的权重读取成本。

Prefix Caching（前缀缓存）¶

多请求共享同一 system prompt / 长上下文前缀时，可以复用已计算的 KV Block，避免重复 Prefill，并通过引用共享减少重复副本。缓存本身仍占显存，还需要淘汰和引用计数策略。

图形 → AI 映射¶

概念 图形对应
Continuous Batching 帧并行（Frame Parallelism）/ 动态任务队列：做完一帧的线程立刻接新活，不让 GPU 空转
Spec Decoding 预测式着色 / 时间性重投影：先粗估（上一帧预测），再用本帧精修验证
Prefix Caching 着色器缓存 / 纹理缓存复用：相同输入不重算，直接命中缓存

8.8 Roofline 模型¶

判断一个 kernel 是 compute-bound 还是 memory-bound 的利器。

横轴 = 算术强度（Arithmetic Intensity, FLOP/Byte），纵轴 = 可达性能（FLOP/s）。一条"屋顶线"由两点决定：

  • 带宽屋顶：\(\text{峰值 FLOP/s} = \text{带宽} \times \text{算术强度}\)（左侧斜线）
  • 算力屋顶：峰值 FLOP/s（右侧平线）

脊点（Ridge Point） = 带宽屋顶与算力屋顶交点处的算术强度。

  • 算术强度 < 脊点 → memory-bound（优化应砍访存，如量化、Tiling 复用）
  • 算术强度 > 脊点 → compute-bound（优化应砍运算，如 Tensor Core、FP8）

Decode 的 GEMV（7.7）算术强度极低，落在带宽屋顶左侧 → memory-bound → 量化最有效；Prefill 的 GEMM 算术强度高 → 用 Tensor Core。

图形 → AI 映射¶

概念 图形对应
Roofline 判断瓶颈 与图形性能分析一样先区分计算、带宽和延迟限制，但 Roofline 使用明确的 FLOP/byte 与峰值上界
