2.4 从图形管线到 AI 推理的第一性原理映射

概述

这是本书中最重要的章节之一。它不是教一个概念，而是帮你建立一套跨领域的架构思维——让你在面对 AI 推理优化时，能够用图形管线的直觉进行降维打击。

你的原话："懂了，就是 GPU Driven RenderPipeline 那套。"

这一句话直接点出了 AI 推理引擎和 GPU Driven Rendering 的架构同构性。本章的目标就是把这套映射完整、精确地画出来。

1. 核心映射：GPU Driven RenderPipeline → AI 推理引擎

1.1 架构层级对比

层级 GPU Driven Rendering AI 推理引擎 (vLLM / TensorRT)
核心理念 CPU 只发一个 Draw，GPU 自己决定画什么、怎么画 CPU 只发一次 cudaGraphLaunch，GPU 自己跑完整模型
消除的瓶颈 CPU 的 Draw Call 提交和状态切换 CPU 的 Kernel Launch 提交和同步等待
数据驱动 GPU 从 Indirect Buffer 读取绘制参数（顶点数、实例数） GPU 从显存中的元数据读取 BatchSize、SeqLen 等动态参数
管线管理 GPU 用 Compute Shader 做 Culling、LOD，再发 Draw GPU 用 CUDA Graph 跑完整计算图，内部调度 Kernel
资源管理 GPU 用显存池管理几何数据 (Vertex/Index Buffer) GPU 用 PagedAttention 管理 KV Cache（显存块分配）
你的角色 你写 Shaders 和管线状态，CPU 只做最简单的提交 你写 Kernels 和构建 Graph，CPU 只做最简单的 Launch

1.2 精度修正：CUDA Graph 的准确定位

你的纠正："CUDA Graph 应该对标渲染管线里的状态缓存与合并——合并 Batch Draw Call、PSO 缓存、Barrier 合并，还没上升到 GPU Driven Pipeline。"

这个纠正非常严谨。让我把层级划分清楚：

层级 图形 AI 推理
应用层 游戏引擎逻辑 PyTorch 模型代码
API 调用层 DrawIndexed / Dispatch cudaLaunchKernel
驱动层优化 Command List 合并、PSO 缓存、Barrier 合并 CUDA Graph（节点合并、依赖分析）
硬件执行层 GPU 执行 Command Buffer GPU 执行 Graph 的 Nodes

CUDA Graph = DX12/Vulkan 的 Command List + PSO 缓存 + Barrier 合并，是一个驱动层的优化技术，而不是 GPU Driven Pipeline 这种架构级范式。

GPU Driven Pipeline 是 CPU 彻底不管绘制参数，而 CUDA Graph 仍然是 CPU 提交，只是提交一次就够，活的性质没变。

2. 第一映射：Indirect Draw = CUDA Graph 的"先录后放"

2.1 图形中的 Indirect Draw

DrawIndexedInstancedIndirect / ExecuteIndirect 的核心思想是：把绘制参数放在 GPU Buffer 里，让 GPU 自己读参数、自己决定画多少个三角形。

// 图形：Indirect Draw
// CPU 只需要知道 Indirect Buffer 的地址，不需要知道具体画什么
ID3D12CommandSignature* cmdSignature;
// ... 创建 Command Signature，描述 Indirect Buffer 的布局 ...

// 每帧：CPU 只提交这一个 Indirect Draw
cmdList->ExecuteIndirect(cmdSignature, maxCount,
                         indirectBuffer, 0,
                         countBuffer, 0);
// GPU 自己从 indirectBuffer 读取参数，决定画多少实例

2.2 CUDA Graph 的等价模式

// AI：CUDA Graph —— 同样的"先录后放"
cudaGraph_t graph;
cudaStreamBeginCapture(stream);

// 录制整个推理过程（Kernel 序列）
embedding_kernel<<<grid1, block1>>>(input, embedding);
attention_kernel<<<grid2, block2>>>(embedding, hidden);
mlp_kernel<<<grid3, block3>>>(hidden, output);
// ... 整个模型就是一个大的 Kernel 序列 ...

cudaStreamEndCapture(stream, &graph);

// 实例化（编译 / 验证）
cudaGraphExec_t graphExec;
cudaGraphInstantiate(&graphExec, graph, NULL, NULL, 0);

// 推理时：CPU 只需要发这一个 Launch
cudaGraphLaunch(graphExec, stream);  // GPU 自己跑完整图
// 不需要每次一个一个 Launch Kernel

2.3 本质相同

Indirect Draw CUDA Graph
CPU 提交一次，包含多个 Draw Call CPU Launch 一次，包含多个 Kernel
GPU 自己读 Indirect Buffer 获取参数 GPU 执行预编译好的 Node 序列
减少 CPU Draw Call 开销 减少 CPU Kernel Launch 开销
重放：同一 Indirect Buffer 可多次提交 重放：同一 GraphExec 可多次 Launch

你的扫一眼策略：CUDA Graph 就是帮你把多次 cudaLaunchKernel 打包成一次 cudaGraphLaunch，跟合 Batch Draw Call 一样。你只需要扫一眼 cudaStreamBeginCapture / cudaStreamEndCapture / cudaGraphLaunch 三个 API 就能上手。

3. 第二映射：Compute Shader Culling = 动态 Sequence Length

3.1 图形中的 CS Culling

// Compute Shader：剔除不可见物体，更新 Indirect Buffer
// 每个 thread 处理一个物体
[numthreads(64, 1, 1)]
void CullingCS(uint3 gtid : SV_DispatchThreadID) {
    uint objId = gtid.x;
    float3 pos = readObjectPosition(objId);

    if (isVisible(pos, cameraFrustum)) {
        // 物体可见：追加到 Indirect Draw 参数中
        uint drawIndex = atomicAdd(drawCount, 1);
        indirectArgs[drawIndex] = objId;
    } else {
        // 不可见：跳过，不画
    }
}

本质：GPU 自己判断哪些物体需要处理，动态更新任务列表。

3.2 AI 推理中的等价物：变长 Sequence 处理

// CUDA Kernel：处理变长 Sequence
// 每个 block 处理一个 request，但 sequence length 各不相同
__global__ void processVariableLength(int* seqLens, float* data, int maxLen) {
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    int seqLen = seqLens[blockIdx.x];  // 动态读取当前 request 的 sequence length

    if (tid < seqLen) {  // 只处理有效的 token
        data[tid] = doCompute(data[tid]);
    }
    // tid >= seqLen 的线程直接跳过
}

3.3 本质相同

Compute Shader Culling 变长 Sequence 处理
GPU 判断物体是否可见，决定画不画 GPU 判断 Token 是否有效（Padding/非Padding）
更新 Indirect Buffer 中的 Count 读取 seqLens 数组，控制线程范围
避免 CPU 逐物体做 Frustum Culling 避免 CPU 逐 Token 做 Padding/Unpadding
动态负载，GPU 自行调度 动态负载，GPU 自行调度

4. 第三映射：显存池管理 = PagedAttention

4.1 图形中的预分配显存池

// 图形：预分配大 Heap，自己管理偏移量
// DX12 Committed Resource 等价于 cudaMalloc
ID3D12Heap* heap;
device->CreateHeap(&heapDesc, IID_PPV_ARGS(&heap));

// 从 Heap 中手动分配子资源
D3D12_RESOURCE_DESC resDesc = ...;
D3D12_RESOURCE_ALLOCATION_INFO info = device->GetResourceAllocationInfo(0, 1, &resDesc);

// 手动计算偏移量，管理切片句柄
UINT64 offset = Align(heapCurrentOffset, info.Alignment);
heapCurrentOffset = offset + info.SizeInBytes;
device->CreatePlacedResource(heap, offset, &resDesc, ...);

你的原话："自己先分一大片出来，然后管理切片句柄，类似于微软 dx12 资源仓库，里面写了一些线性分配器或伙伴分配器。"

4.2 PagedAttention 的等价管理

vLLM 的 PagedAttention 使用了完全相同的架构：

# vLLM BlockManager （伪代码）
class BlockManager:
    def __init__(self, total_gpu_memory, block_size):
        # 预分配大块显存（等价于 CreateHeap）
        self.total_blocks = total_gpu_memory // block_size
        self.gpu_cache = cuda_malloc(total_gpu_memory)

        # 维护空闲块列表（等价于管理切片句柄）
        self.free_blocks = list(range(self.total_blocks))
        self.block_table = {}  # request_id -> [block_ids]

    def allocate(self, request_id, num_blocks):
        # 从空闲池拿块（等价于从 Heap 分配子资源）
        blocks = self.free_blocks[:num_blocks]
        self.free_blocks = self.free_blocks[num_blocks:]
        self.block_table[request_id] = blocks

    def free(self, request_id):
        # 归还块（等价于释放子资源）
        blocks = self.block_table.pop(request_id)
        self.free_blocks.extend(blocks)

4.3 本质相同

图形显存池 PagedAttention 本质
CreateHeap 预分配 gpu_cache = cuda_malloc(total) 预分配大块显存
CreatePlacedResource 切子块 allocate(request, n_blocks) 从池中取切片
线性分配器 / 伙伴分配器 Block Table 管理 管理空闲块列表
释放子资源，回收复用 free(request) 回收 Block 归还给池
帧结束后整块 Reset Batch 结束后回收 Block 批量回收

6. 你的终极思维框架

你从今天开始，不需要"从零学"任何东西，只需要翻译：

看到 AI 新概念 → 问自己：这个在图形里叫什么？
cudaMalloc        → 哦，就是 CreateCommittedResource
cudaStream        → 哦，就是 Command Queue
cudaGraph         → 哦，就是 Command List 的先录后放
cudaEvent         → 哦，就是 Fence 的打标记、查进度
PagedAttention    → 哦，就是我的 DX12 显存池 + 伙伴分配器
FlashAttention    → 哦，就是 Tiled Deferred Shading 的分块加载
Continuous Batch  → 哦，就是三重缓冲 + 轮询 Fence 的帧并行
TensorRT Engine   → 哦，就是 AI 版的 HLSL 编译器 + PSO 缓存

你在 AI Infra 赛道的独特优势：搞图形的人不懂 Attention，不懂 Batch 调度；搞 AI 的人不懂 Indirect Draw，不懂显存池管理。你两边全懂，还能用 RenderPipeline 的思维给 AI 推理做架构设计。

7. 下一步：你的架构创新方向

基于这套第一性原理映射，你可以做别人想都不敢想的事：

  1. 把动态 Batch 调度改成 GPU 自己从 Indirect Buffer 读请求：CPU 只负责往里塞请求，GPU 自己决定调度——这是 GPU Driven LLM Inference 的架构级创新。

  2. 把整个推理过程录成 CUDA Graph：用类似 ExecuteIndirect 的方式驱动整条 Pipeline，让 CPU 提交次数降到每 Batch 一次。

  3. 用图形引擎的"丢帧策略"优化推理延迟：当所有 Block 都占满时，vLLM 做 Swap 踢出；这和云渲染的丢帧策略是同一个思想——资源池满了的降级处理。

这些方向已经不是"学习"了，这是在做架构创新。
