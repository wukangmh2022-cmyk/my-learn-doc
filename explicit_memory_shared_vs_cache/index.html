5.2 内存层级与显式管理: Shared Memory (__shared__) vs L1/L2 缓存

概述

Shared Memory 是 CUDA 编程中最重要、也最容易误解的概念。它和 L1 缓存共享同一块物理 SRAM，但在管理方式上有本质区别：L1 是硬件自动管理，Shared Memory 是软件显式控制。

一句话结论：Shared Memory 是 SRAM，但不是所有 SRAM 都是 Shared Memory。L1、L2、寄存器也都是 SRAM——区别在于容量、延迟、和管理方式，其中最关键的是：Shared Memory 归你管，L1 归硬件管。

硬件层次拆解

存储层级总览 (以 NVIDIA A100/H100 为例)

存储层级 硬件本质 容量 (A100) 谁控制 用途
寄存器 (Register) SRAM 256 KB / SM 编译器分配 最快，线程私有
L1 缓存 SRAM 192 KB / SM 硬件自动管理 自动缓存全局内存访问
Shared Memory SRAM 164 KB / SM (可配置) 软件显式控制 同一线程块内共享数据
L2 缓存 SRAM 40 MB (整卡共享) 硬件自动管理 缓存全局内存 (跨 SM)
HBM (显存) DRAM 80 GB 软件分配 (cudaMalloc) 大容量全局存储

Shared Memory ≠ L1 缓存

  • L1 是硬件自动管理的缓存——你无法控制存什么、什么时候淘汰。它在你读取全局内存时自动填充命中，本质上是"尽力而为"的透明加速。
  • Shared Memory 是软件显式管理的 Scratchpad Memory——你主动 ldg 加载数据进去，用完即弃。数据只要进去了，就一定在那里，不会有 Cache Miss。

但它们在物理上共用同一块 SRAM 空间：

A100 每个 SM 的片上 SRAM 总量 = 192 KB
├── 可配置方案 A: 164 KB Shared Memory + 28 KB L1
├── 可配置方案 B: 128 KB Shared Memory + 64 KB L1
└── 可配置方案 C: 100 KB Shared Memory + 92 KB L1

这就像你用 DX12 的 Heap 自己管理内存（Shared Memory），还是让驱动自动管理（L1）的区别。它们底层都是同一块显存，但你控制 vs 不控制决定了它们的本质差异。

图形 vs AI：为什么缓存设计截然不同

图形渲染：纹理 Cache（自动）

图形渲染中，纹理采样具有极强的空间局部性：

  • 一个像素采样纹理时，它旁边的像素极大概率会采样邻近的纹素。
  • GPU 的纹理单元 (TMU) 和 L1/L2 Cache 会预取一大块连续数据。
  • 你写 tex2D，硬件在背后默默地把相邻数据塞进 Cache，命中率极高。
  • 结论：硬件帮你把"全局数据"变成了"局部缓存"，你不需要操心。

AI 推理：Shared Memory（显式）

AI 推理的访问模式无法有效地利用纹理 Cache：

  • Attention 机制要算 Q * K^T，Q 的某一行和 K 的所有行做点积——跨行跳跃式访问，完全破坏 Cache 的空间局部性。
  • 硬件 Cache 对这种"全量跳跃"几乎无效：上一微秒刚加载的数据，下一微秒可能就访问到了相隔十万八千里的地址。
  • 结论：硬件 Cache 帮不上忙，你必须手动把数据从全局显存搬进 Shared Memory，人为制造"局部性"。

为什么 AI 必须用 SRAM (Shared Memory)？

  1. 确定性：纹理 Cache 是"尽力而为"的，不保证数据一定在那里。Shared Memory 是显式加载的，数据搬进去后绝对在场。在 AI 这种强依赖流水线中，确定性比概率性命中重要得多。

  2. 多播/重用：K 矩阵加载进 Shared Memory 后，同一个向量会被同一 Block 内的所有线程（处理不同 Q 行）同时读取。在 Cache 里这是"广播"，在 Shared Memory 里是真正的零延迟共享。

  3. 带宽效率：纹理 Cache 本质还是"临时副本"，最终得走 Global Memory 带宽。Shared Memory 把访问变成"寄存器级"，直接砍半 Global Memory 的读写次数。

用你的渲染思维来理解： - 图形 Cache = "高速路旁的加油站"，你路过时顺便加个油（缓存命中了）。 - AI Shared Memory = 你自己花钱买的"私人停车场"，你提前把车都停进去，工人（线程）零距离随便拿，不再需要去高速路上跑。

Tiling：用 Shared Memory 手动制造局部性

标准分块加载 (Synchronous)

// 声明 Shared Memory：一个 Tile 的大小
__shared__ float tile_A[TILE_SIZE][TILE_SIZE];
__shared__ float tile_B[TILE_SIZE][TILE_SIZE];

int tx = threadIdx.x;
int ty = threadIdx.y;

int row = blockIdx.y * TILE_SIZE + ty;
int col = blockIdx.x * TILE_SIZE + tx;

// Step 1: 从 Global Memory 加载数据到 Shared Memory
tile_A[ty][tx] = A[row * stride + col];
tile_B[ty][tx] = B[row * stride + col];

// Step 2: 同步，确保所有线程都加载完成
__syncthreads();

// Step 3: 现在可以安全地使用 tile_A 和 tile_B 进行计算
float sum = 0.0f;
for (int k = 0; k < TILE_SIZE; k++) {
    sum += tile_A[ty][k] * tile_B[k][tx];
}
// ... 写回结果

异步加载 (cuda::memcpy_async, Compute Capability 8.0+)

从 Ampere 架构开始，CUDA 引入了 cuda::memcpy_async，让数据搬运能与计算流水线重叠：

#include <cuda/barrier>

__global__ void async_gemm_kernel(...) {
    __shared__ float tile_A[2][TILE_SIZE][TILE_SIZE];  // 双缓冲
    __shared__ float tile_B[2][TILE_SIZE][TILE_SIZE];

    auto block_barrier = cuda::barrier(cuda::thread_scope_block);

    // 异步加载第一个 Tile
    cuda::memcpy_async(&tile_A[0][ty][tx], &A[block_start], sizeof(float), block_barrier);
    cuda::memcpy_async(&tile_B[0][ty][tx], &B[block_start], sizeof(float), block_barrier);

    // 在等待数据时，可以做不依赖数据的操作（如初始化累加器）
    float sum = 0.0f;

    block_barrier.arrive_and_wait();  // 等待第一批数据到达

    // 计算 Tile 0 的同时，后台已经开始异步加载 Tile 1
    cuda::memcpy_async(&tile_A[1][...], &A[next_block], ..., block_barrier);
    cuda::memcpy_async(&tile_B[1][...], &B[next_block], ..., block_barrier);

    compute(tile_A[0], tile_B[0], &sum);

    block_barrier.arrive_and_wait();  // 等待第二批数据到达
    compute(tile_A[1], tile_B[1], &sum);
    // ...
}

异步加载的核心价值：Communication Behind Compute

同步方式（低效）：
  加载 Tile_0 → 等待 → 算完
  加载 Tile_1 → 等待 → 算完
  加载 Tile_2 → 等待 → 算完
  → 每次加载时 SM 都在空等（100% 访存延迟）

异步方式（高效）：
  加载 Tile_0 ── 可同时计算不依赖 Tile_0 的逻辑
  加载 Tile_1 ────── 同时计算 Tile_0
  加载 Tile_2 ────────── 同时计算 Tile_1
  → 计算和搬运像流水线一样跑起来

这完全等价于图形渲染中的三重缓冲：

图形 CUDA 异步加载
CPU 在准备下一帧数据时，GPU 在渲染当前帧 SM 在计算当前 Tile 时，DMA 引擎在后台加载下一批 Tile
你"算"的是当前帧，不是在等下一帧数据 你"算"的是已经加载好的 Tile，不是在等正在加载的 Tile

图形到 CUDA 的搬运模型映射

操作 图形 (Compute Shader) CUDA (同步方式) CUDA (异步方式)
数据加载 tex2D 自动采样 tile[ty][tx] = global[idx] cuda::memcpy_async + barrier
数据搬运者 硬件 TMU 帮你搬 你亲自写指针搬运 DMA 引擎在后台搬运
缓存管理 隐式 Cache L1/L2 显式 Shared Memory 显式 Shared Memory + 流水线预取
同步 不需要 __syncthreads() cuda::barrier.arrive_and_wait()

实际例子：Shared Memory 配置的注意事项

Bank Conflict

Shared Memory 被分成 32 个 Bank（每 Bank 4 字节）。当同一 Warp 内的多个线程访问同一个 Bank时，发生 Bank Conflict，访问被串行化。

// 有 Bank Conflict：tile[threadIdx.x][0] — 所有线程访问 Bank 0
float val = tile[threadIdx.x][0];  // ❌ 32 个线程全部访问 Bank 0

// 无 Bank Conflict：访问不同行
float val = tile[threadIdx.x][threadIdx.x];  // ✅ 完美广播

// 常见解法：给第二维 +1 Padding
__shared__ float tile[TILE_SIZE][TILE_SIZE + 1];  // 用 Padding 避免冲突

Shared Memory 超额

每个 SM 的 Shared Memory 总量是有限的。如果你的 Kernel 每个 Block 使用超过限额，Occupancy 会下降（一个 SM 能同时驻留的 Block 数减少）。

// A100 SM Shared Memory: 最大 164 KB
// 如果你的 Block 用了 50 KB Shared Memory
// SM 最多只能驻留 3 个 Block（164 / 50 ≈ 3），而不是理想情况下的更多

总结

项目 L1 Cache Shared Memory
管理方式 硬件自动 软件显式
数据确定性 "尽力而为"，可能 Miss 100% 在场
延迟 几十个 Cycle (命中时) 几个 Cycle
容量 可配置（与 Shared Memory 共享物理空间） 可配置（与 L1 共享物理空间）
适用场景 有良好局部性的随机访问 程序员已知的确定数据分块

做图形，你选 Cache——因为纹理访问极度规律，硬件自动打理最省心。 做 AI 推理，你选 Shared Memory——因为数据依赖极度杂乱，只有程序员显式控制才能保证不爆显存、不空转。

你现在完全搞懂了 tex2D 和 __shared__ 的根本区别——它们是为完全不同的数据流模式而设计的硬件生态位。
