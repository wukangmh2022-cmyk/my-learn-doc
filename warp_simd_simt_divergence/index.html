5.3 执行模型: Warp, SIMD, SIMT, 分支分歧¶

概述¶

GPU 的核心执行模型是 SIMT (Single Instruction, Multiple Threads)：一条指令被 32 个线程（一个 Warp）同时执行，但每个线程处理自己独立的数据。这与传统的 CPU SIMD 有本质区别。理解 Warp 的执行方式，是编写高性能 CUDA Kernel 的基础。

核心认知：Warp 是 GPU 调度的基本单位——不是线程，不是 Block，是 32 个线程组成的 Warp。你写在代码里的线程级逻辑，硬件会按 Warp 为单位打包执行。

SIMD vs SIMT¶

概念区分¶

维度 SIMD (单指令多数据流) SIMT (单指令多线程)
并行粒度 指令级：一条指令处理一个向量（如 float4） 线程级：一条指令驱动一组线程（如 32 个线程组成的 Warp）
执行单元 一个核心内的向量处理单元 一个调度器管理的一组线程
数据模型 数据被打包成向量，指令操作整个向量 每个线程处理自己独立的标量数据
控制流处理 无分支，顺序执行 支持分支，但有性能代价
硬件体现 线程内的 float4 加法就是一条 SIMD 指令 GPU 的基本调度单元 Warp 就是 SIMT 的体现
典型代表 CPU 的 SSE/AVX、GPU 的 Tensor Core CUDA 的 Warp、AMD 的 Wavefront

用你的图形背景理解： - SIMD 就像你在 Pixel Shader 里处理一个像素的 float4 向量——一条指令同时操作多个数据元素（RGBA）。 - SIMT 则像你同时调度成千上万个像素线程——一条指令被 32 个线程同时执行，但每个线程处理自己独立的像素。

它们在 GPU 中的协作关系¶

在同一个 GPU SM 内部： 1. SIMT 是顶层调度模型：Warp Scheduler 以 32 线程为单位发射指令。 2. SIMD 是底层计算模型：每个线程内部，编译器会将连续的操作向量化（如 float4 运算）。

         Warp Scheduler (SIMT)
              │
              ▼
     ┌──────────────────┐
     │ 一条指令 (如 FADD)│
     └──────────────────┘
              │
     ┌────────┴────────┐
     │ 32 个线程并行执行  │  ← SIMT 层面
     │ (但各线程数据不同) │
     └────────┬────────┘
              │
     ┌────────┴────────┐
     │ 内部可含 SIMD 操作│  ← 线程内的 float4 运算
     │ (编译器的向量化)   │
     └─────────────────┘

Warp 执行模型¶

Lockstep 执行¶

Warp 内的 32 个线程以 Lockstep（锁步） 方式执行：

  • 所有线程共享同一个 Program Counter（程序计数器）。
  • 在任何一个时刻，Warp 内的所有线程要么执行同一条指令，要么被掩蔽（Masked） 不执行。
  • 线程之间的区别仅在于它们操作的数据（寄存器值）不同。
时间轴 →
┌──────────────────────────────────────────┐
│ Warp 执行: 指令流                          │
│                                           │
│  ┌───┐ ┌───┐ ┌───┐ ┌───┐ ┌───┐         │
│  │LDG│→│FMA│→│STG│→│LDG│→│FMA│→ ...   │
│  └───┘ └───┘ └───┘ └───┘ └───┘         │
│     ↑      ↑      ↑                      │
│  32线程   32线程   32线程                  │
│  同时做   同时做   同时做                  │
└──────────────────────────────────────────┘

Warp 与 Block 的关系¶

  • 一个 Block 通常包含多个 Warp（例如 256 线程 = 8 个 Warp）。
  • Shared Memory 是整个 Block 共享的，不是每个 Warp 独享的。
  • Block 内的 Warp 之间通过 Shared Memory + __syncthreads() 交换数据，Warp 内部则可以通过 __shfl 指令直接交换寄存器数据。
Block (256 线程)
├── Warp 0 (线程 0-31)    ──┐
├── Warp 1 (线程 32-63)   ──┤
├── Warp 2 (线程 64-95)   ──┤ 共享同一块
├── Warp 3 (线程 96-127)  ──┤ __shared__ 数组
├── Warp 4 (线程 128-159) ──┤
├── Warp 5 (线程 160-191) ──┤
├── Warp 6 (线程 192-223) ──┤
└── Warp 7 (线程 224-255) ──┘

分支分歧 (Branch Divergence)¶

分歧的产生¶

由于 Warp 内 32 个线程共享 Program Counter，当遇到 if-else 分支时，如果线程走了不同路径，硬件必须串行化执行：

__global__ void divergence_kernel(float* data, int N) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N / 2) {
        // 分支 A: 线程 0-15 执行
        data[idx] = data[idx] * 2.0f;
    } else {
        // 分支 B: 线程 16-31 执行
        data[idx] = data[idx] + 1.0f;
    }
    // 汇合
}

硬件的实际执行过程：

Warp 中的 32 个线程：
┌── 线程 0-15 ──┬── 线程 16-31 ──┐
│  走 if 分支     │  走 else 分支   │
└──────────────┴──────────────┘

硬件执行：
Step 1: 执行 if 分支   → 线程 0-15 活跃，线程 16-31 被掩蔽
Step 2: 执行 else 分支 → 线程 16-31 活跃，线程 0-15 被掩蔽
Step 3: 汇合继续执行

→ 本应一次完成的工作，现在需要两次吞吐量减半！

Control Divergence vs Memory Divergence¶

它们是一对难兄难弟，经常同时出现：

维度 分支串行化 (Control Divergence) 随机访问 (Memory Divergence)
发生在 指令执行阶段 (ALU) 数据加载阶段 (Memory)
原因 同一 Warp 里线程走了不同分支 同一 Warp 里线程访问了不连续地址
后果 算力浪费 (SM 空转) 带宽浪费 (Cache Miss)
解决思路 数据重排（让相似线程走一起） 数据重排（让连续线程访问连续地址）

用你的渲染思维理解： - 分支串行化 = 做判断时“意见不合”——32 个像素中一部分需要做 A 处理，另一部分需要做 B 处理，硬件只能分两次算。 - 随机访问 = 拿数据时“天女散花”——32 个线程各读各的地址，硬件无法合并显存请求。

与图形 Compute Shader 的对应¶

概念 CUDA 图形 API
调度单位 Warp (32 线程) Wavefront (AMD, 64 线程) / Wave (NVIDIA)
分支性能损失 同一 Warp 线程走不同分支 → 串行化 同一 Wave 的像素走不同分支 → 同样串行化
典型场景 ReLU 中 if (x < 0) x = 0 被编译器优化成 max 指令 Shader 中的 if (clip_pos.w <= 0) discard
避免策略 数据重排、Predication、编译器内建替代 数据预处理、预排序

如何避免/缓解分支分歧¶

1. 编译器自动优化：Predication¶

很多看似分支的代码，编译器会将其编译成条件执行（Predication） 而非分支跳转。最经典的例子是 ReLU：

// 你的代码：
float relu(float x) {
    if (x < 0.0f) return 0.0f;
    else return x;
}

// 编译器实际生成的指令：
// max.f32  r0, r0, 0.0f
// → 一条硬件指令，没有分支！

Predication 的工作原理：编译器为每条指令附加一个谓词（Predicate），决定该线程是否执行这条指令。它避免了分支跳转带来的流水线刷新，但代价是所有线程都执行指令（即使结果被丢弃）。

所以： - 细粒度的 if（如 ReLU）→ 编译器自动优化成 Predication → 无分支开销。 - 粗粒度的 if（如不同线程处理不同任务）→ 编译器无法优化 → 产生真实的分支分歧。

2. 手动数据重排¶

让同一个 Warp 内的线程处理性质相似的数据，减少它们走不同分支的概率：

// 不好的做法：同一 Warp 内混合处理正负数据
// 线程 0-15 全是负数，线程 16-31 全是正数 → Warp 内分支

// 好的做法：数据预处理，将同类数据分组
// 所有负数集中在一个 Block，所有正数集中在另一个 Block → 无分歧

3. 用数学指令替代分支¶

这是最常见的技巧——用连续的数学运算替代条件判断：

// 有分支版本：
float a = (condition) ? val1 : val2;

// Predication 版本（编译器自动处理）：
// 硬件会使用 SEL (Select) 指令

// 避免分支的数学替代：
float a = condition * val1 + (1.0f - condition) * val2;
// 但要注意：这会计算两个分支的值，仅适用于简单场景

Wavefront（AMD）/ Wave（图形）与 Warp 的关系¶

项目 CUDA Warp AMD Wavefront 图形 Wave
线程数 32 64 取决于具体实现
共享 PC 是 是 是
分支损失 32 线程分歧 → 串行化 64 线程分歧 → 串行化更严重 同样问题
寄存器压力 每线程私有寄存器 每线程私有寄存器 每像素私有寄存器

关键洞察：AMD Wavefront 的 64 线程比 CUDA Warp 的 32 线程更容易产生分支分歧（64 个线程意见统一的概率更低），这是 NVIDIA 在设计上将 Warp 定为 32 线程的原因之一。

总结¶

关键概念 一句话总结
SIMT 一条指令控制一组线程，每个线程处理自己的数据——GPU 的本质执行模型
Warp 32 个线程组成的 Lockstep 执行单位——硬件不调度单个线程，调度的是 Warp
分支分歧 Warp 内线程走不同分支导致串行化——性能杀手，需通过数据重排或 Predication 避免
Predication 编译器用条件执行替代分支的优化——细粒度条件语句几乎没有性能损失
图形对应 Wave/Wavefront 与 CUDA Warp 都是硬件执行组；宽度、指令语义和厂商调度细节不同

最终定论：你在图形 Shader 里积累的\"避免在像素/顶点间使用分支\"的经验，直接平移到 CUDA Kernel 编写中——同一个 Warp 里 32 个线程的步调越一致，硬件效率越高。
