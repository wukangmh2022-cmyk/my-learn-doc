11.6 进阶：把分页契约搬到 DX12 与 TensorRT 后端¶

这一篇的前置与定位¶

前置：11.3 PagedAttention 与 Continuous Batching。那一篇已经用 PyTorch 和 CUDA 把分页 KV Cache 跑通并验证过了，你手上应该已经有：

  • 一个 CPU 侧的 BlockManager（分配 / 释放 / 引用计数）；
  • 每个请求的 Block Table；
  • 一份数值可信的 CPU Reference 和一组小到能手算的测试向量。

这一篇要回答的问题：换一套完全不同的后端，这份契约还成立吗？

答案是成立，而且这正是它的价值所在。分页 KV Cache 的本质是一次索引间接——它不依赖任何特定的 GPU API。所以我们把同一件事再做两遍：

后端 显存怎么来 Kernel 用什么写 同步靠什么
CUDA（11.3 已完成） cudaMalloc 一大块 CUDA C++ Stream / Event
D3D12（本篇主体） Default Heap 上的 Committed Buffer HLSL Compute Shader Resource Barrier / Fence
TensorRT（本篇末尾） Plugin Workspace + 外部绑定 CUDA Plugin TensorRT 传入的 Stream

变的是 API，不变的是三样东西：BlockManager 的分配语义、Block Table 的页表公式、Context Length 的含义。做完你会发现，移植的工作量几乎全在资源创建和同步上，Attention 的数学一行没动。

如果你不做图形方向，可以只读最后两节（TensorRT 迁移 + 回到第一性原理）；中间的 D3D12 工程部分是给有图形背景、或者想理解「一套算法怎么在两种资源模型上落地」的读者准备的。

一、关键判断：为什么使用 Committed Default Resource¶

1. “分页”发生在哪一层¶

PagedAttention 的分页是应用层的逻辑分页。它不要求操作系统或 D3D12 为每个 KV Block 建立独立 Resource，也不要求使用 Reserved Resource。

本项目只创建两块大的 GPU Buffer：

KCache: Default Heap Committed Buffer
VCache: Default Heap Committed Buffer

假设 block_size=4、总共有 12 个物理 Block：

KCache physical layout

block 0  block 1  block 2  block 3  ...  block 11
[0..3]   [4..7]   [8..11]  [12..15]      [44..47] token slots

BlockManager 在这块大 Buffer 内分配整数 Block ID。每个请求保存一组页号：

request A block table = [7, 2, 11]
request B block table = [5, 9]

HLSL 用整数页号计算 Buffer Offset。也就是说：

D3D12 Resource 层：一块连续的大 Buffer
应用分页层：许多固定大小的逻辑物理页
请求层：每个请求有自己的逻辑页表

2. Committed、Placed、Reserved 不要混在一起¶

D3D12 资源方式 含义 是否适合本教学项目
Committed Resource 创建 Resource 时由 D3D12 同时为它分配 Heap 适合，代码最清楚
Placed Resource 应用先创建大 Heap，再把多个 Resource 放进去 暂时不需要；可用于管理多个大资源
Reserved Resource 创建虚拟地址范围，再用 Tile Mapping 映射物理页 不需要；这是 D3D12 Sparse/Tiled Resource 机制

这里的 Committed 描述资源与 Heap 的创建方式；Default 描述 Heap 类型。它们可以同时成立：

device->CreateCommittedResource(
    &CD3DX12_HEAP_PROPERTIES(D3D12_HEAP_TYPE_DEFAULT),
    D3D12_HEAP_FLAG_NONE,
    &bufferDesc,
    initialState,
    nullptr,
    IID_PPV_ARGS(&resource));

因此准确表述是：在 Default Heap 上创建 Committed Buffer，再由应用在 Buffer 内实现 KV Block 分页。

3. 为什么不为每个 Block 创建一个 Committed Resource¶

如果每个 KV Block 都是一个 Resource：

  • Resource 对象和 Descriptor 数量迅速增长；
  • 每次 Attention 需要访问 Descriptor 数组或频繁换绑定；
  • 小 Resource 的分配与对齐开销不利于细粒度 Block；
  • 页表不再只是简单整数 Offset。

一个大 Buffer 配合整数 Block ID 更接近 vLLM 的物理 KV Cache，也更适合 HLSL 的 StructuredBuffer 或 ByteAddressBuffer。

二、先看完整的数据与命令流水线¶

flowchart TB
    subgraph CPU["CPU / Runtime"]
        REQ["Request: context length"] --> BM["BlockManager"]
        BM --> BT["Block Table"]
        BT --> UP["Upload Ring"]
    end

    subgraph GPU["GPU / DX12"]
        COPY["Copy BlockTable + ContextLens"] --> QK["QK Shader: page-table gather"]
        QK --> SM["Softmax Shader"]
        SM --> PV["PV Shader: page-table gather"]
        KC["KCache committed default buffer"] --> QK
        VC["VCache committed default buffer"] --> PV
    end

    UP --> COPY
    Q["Q buffer"] --> QK
    PV --> OUT["Output buffer"]

第一版使用三个 Dispatch：

QK → Softmax → PV

这个版本优先保证可观察性，先确认：

  • QK 是否从正确的物理 K Block 读取；
  • Softmax 是否数值稳定；
  • PV 是否使用同一页表从 V Cache 读取；
  • 每一阶段是否与 CPU Reference 对齐。

等分页逻辑完全正确后，再把 QK、Online Softmax、PV 融合。否则一开始就写融合 Kernel，一旦输出错误，很难判断是页表、Reduce 还是数值校正出了问题。

整个实战会反复经过同一条递进路线。第一次看到 Block Table，它是一个地址公式；写到 HLSL 时，它变成 Gather 的访存模式；开始优化时，又会发现物理页排列影响 L2 命中和预取。Softmax 也一样：先把它当数学公式，再实现为 Group Reduce，最后和 QK/PV 融合以缩短中间数据生命周期。每当工程约束变得具体，相关知识就向下再走一层。

一次 Dispatch 前后的 Resource 状态¶

CPU fill upload metadata
    ↓
CopyBufferRegion(upload → default metadata buffer)
    ↓
COPY_DEST → NON_PIXEL_SHADER_RESOURCE
    ↓
Dispatch QK
    ↓ UAV Barrier
Dispatch Softmax
    ↓ UAV Barrier
Dispatch PV
    ↓
Output UAV → COPY_SOURCE（测试读回时）

K/V 如果由前一个 Compute Pass 写入，则需要 UAV 顺序保证；如果本测试从 CPU 初始化，则先通过 Copy Upload 到 Default Buffer，再转为 Shader Resource。

三、准备 Windows 开发环境¶

下面使用 Windows 11、Visual Studio 2022、CMake 和 DXC。命令在 PowerShell 中执行。

1. 安装 C++ 工具链¶

安装 Visual Studio 2022 Community，并包含“使用 C++ 的桌面开发”工作负载：

winget install --id Microsoft.VisualStudio.2022.Community `
  --override "--wait --passive --add Microsoft.VisualStudio.Workload.NativeDesktop --includeRecommended"

安装 CMake：

winget install --id Kitware.CMake

安装后打开新的 “Developer PowerShell for VS 2022”，检查：

cmake --version
cl

DXC 的可用位置取决于 Windows SDK/开发环境。先检查：

Get-Command dxc.exe -ErrorAction SilentlyContinue

若没有找到，可从 Microsoft DirectXShaderCompiler Release 安装，并把 dxc.exe 所在目录加入 PATH。不要继续到 CMake 阶段才排查 Shader 编译器。

3. CMake¶

先让项目可以编译和找到 D3D12：

cmake_minimum_required(VERSION 3.24)
project(dx12_paged_attention LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_executable(dx12_paged_attention
    src/main.cpp
    src/d3d12_context.cpp
    src/block_manager.cpp
    src/paged_attention.cpp
    tests/cpu_reference.cpp)

target_include_directories(dx12_paged_attention PRIVATE src)
target_link_libraries(dx12_paged_attention PRIVATE d3d12 dxgi dxguid)

set(SHADER_DIR ${CMAKE_CURRENT_SOURCE_DIR}/shaders)
set(SHADER_OUT ${CMAKE_CURRENT_BINARY_DIR}/shaders)
file(MAKE_DIRECTORY ${SHADER_OUT})

foreach(shader qk_paged softmax pv_paged)
    add_custom_command(
        OUTPUT ${SHADER_OUT}/${shader}.cso
        COMMAND dxc -T cs_6_6 -E CSMain
            ${SHADER_DIR}/${shader}.hlsl
            -Fo ${SHADER_OUT}/${shader}.cso
            -Zi -Qembed_debug
        DEPENDS ${SHADER_DIR}/${shader}.hlsl)
    list(APPEND SHADER_BINARIES ${SHADER_OUT}/${shader}.cso)
endforeach()

add_custom_target(shaders ALL DEPENDS ${SHADER_BINARIES})
add_dependencies(dx12_paged_attention shaders)

先创建三个可以编译的占位 Shader。第一次构建成功后，编译环境就有了独立验收结果：

$stub = @'

现在配置和构建：

cmake -S . -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Debug

若这里失败，问题只可能位于编译器、SDK、CMake 或 DXC 路径。先把构建链修通，再进入算法实现。一个良好的实战步骤应当让每次失败都只剩少数可能原因。

复用 11.3 的测试资产¶

下面开始 D3D12 的具体工程。在写第一行 D3D12 代码之前，请确认你手上有 11.3 里那套东西：

  • 固定的小测试 Shape（比如 block_size=4、context_len=10、Hq=4、Hkv=2、D=8）——小到可以手算，大到能跨 Block 边界；
  • CPU Reference 的输出，作为 GPU 结果的比对基准；
  • 一组刻意打乱的 Block Table（如 [7, 2, 11]），用来证明物理页不连续也能出正确结果。

这三样在本篇不重新推导，直接当作已知条件用。用同一份测试向量验收两个后端，是这次移植唯一可靠的判据——否则你分不清「DX12 版本错了」还是「DX12 版本对了但和 CUDA 版本理解不一致」。

四、创建 D3D12 设备与调试环境¶

1. Debug Layer 要在创建设备前开启¶

#if defined(_DEBUG)
ComPtr<ID3D12Debug> debug;
if (SUCCEEDED(D3D12GetDebugInterface(IID_PPV_ARGS(&debug)))) {
    debug->EnableDebugLayer();
}
#endif

然后创建 DXGI Factory、选择支持 D3D12 的 Adapter，再创建 Device、Compute Command Queue、Command Allocator、Command List 和 Fence。这些属于常规 DX12 初始化，建议封装到 D3D12Context：

struct D3D12Context {
    ComPtr<ID3D12Device> device;
    ComPtr<ID3D12CommandQueue> queue;
    ComPtr<ID3D12CommandAllocator> allocator;
    ComPtr<ID3D12GraphicsCommandList> commandList;
    ComPtr<ID3D12Fence> fence;
    HANDLE fenceEvent{};
    uint64_t nextFenceValue{1};

    void executeAndWait();
};

教学版本每个测试 Dispatch 后可以 executeAndWait()，让错误边界清楚。确认正确后，再改成多帧/多 Step 异步执行，避免 CPU 每步等待。

2. 开启 GPU-based Validation¶

如果页表错误导致 Descriptor 或 Buffer 越界，GPU-based Validation 比肉眼检查输出更有效：

#if defined(_DEBUG)
ComPtr<ID3D12Debug1> debug1;
if (SUCCEEDED(debug.As(&debug1))) {
    debug1->SetEnableGPUBasedValidation(TRUE);
}
#endif

它会显著降低性能，只用于 Debug Build 和小 Shape。

五、创建真正的物理 KV 页池¶

1. 通用 Committed Buffer Helper¶

现在才创建本项目最重要的资源。先写一个 Helper，把 Heap 类型、Flag 和初始状态显式传入：

ComPtr<ID3D12Resource> createCommittedBuffer(
    ID3D12Device* device,
    uint64_t bytes,
    D3D12_HEAP_TYPE heapType,
    D3D12_RESOURCE_FLAGS flags,
    D3D12_RESOURCE_STATES initialState)
{
    D3D12_HEAP_PROPERTIES heap{};
    heap.Type = heapType;

    D3D12_RESOURCE_DESC desc{};
    desc.Dimension = D3D12_RESOURCE_DIMENSION_BUFFER;
    desc.Width = bytes;
    desc.Height = 1;
    desc.DepthOrArraySize = 1;
    desc.MipLevels = 1;
    desc.SampleDesc.Count = 1;
    desc.Layout = D3D12_TEXTURE_LAYOUT_ROW_MAJOR;
    desc.Flags = flags;

    ComPtr<ID3D12Resource> resource;
    throwIfFailed(device->CreateCommittedResource(
        &heap,
        D3D12_HEAP_FLAG_NONE,
        &desc,
        initialState,
        nullptr,
        IID_PPV_ARGS(&resource)));
    return resource;
}

2. K/V Cache 是 Default Heap Committed Resource¶

测试阶段需要从 CPU 上传初始 K/V，之后 Shader 只读：

const uint64_t kvElements =
    uint64_t(shape.num_physical_blocks)
    * shape.block_size
    * shape.num_kv_heads
    * shape.head_size;
const uint64_t kvBytes = kvElements * sizeof(float);

auto kCache = createCommittedBuffer(
    device,
    kvBytes,
    D3D12_HEAP_TYPE_DEFAULT,
    D3D12_RESOURCE_FLAG_NONE,
    D3D12_RESOURCE_STATE_COPY_DEST);

auto vCache = createCommittedBuffer(
    device,
    kvBytes,
    D3D12_HEAP_TYPE_DEFAULT,
    D3D12_RESOURCE_FLAG_NONE,
    D3D12_RESOURCE_STATE_COPY_DEST);

如果 K/V 由前一个 QKV Pass 在 GPU 写入，应创建为 UAV：

D3D12_RESOURCE_FLAG_ALLOW_UNORDERED_ACCESS

然后在 KV Store Pass 后插入 UAV Barrier，再由 PagedAttention 读取。Resource 仍然是同一个 Committed Default Buffer，变化的是使用状态和访问方式。

3. 其他 Default Buffer¶

auto qBuffer = createCommittedBuffer(
    device, qBytes,
    D3D12_HEAP_TYPE_DEFAULT,
    D3D12_RESOURCE_FLAG_NONE,
    D3D12_RESOURCE_STATE_COPY_DEST);

auto blockTableBuffer = createCommittedBuffer(
    device, blockTableBytes,
    D3D12_HEAP_TYPE_DEFAULT,

3. 稳态时使用 Upload Ring¶

K/V 权重和 Cache 不会每 Step 从 CPU 全量上传。稳态主要更新：

  • Block Table；
  • Context Length；
  • 新 Token、Position 或 Slot Mapping。

为这些小元数据准备 2 至 3 个 Upload Slot：

slot 0: CPU writes step N+2
slot 1: copy for step N+1
slot 2: GPU consumes step N

每个 Slot 记录 Fence Value。CPU 写入前确认 GPU 已完成使用，避免覆盖仍在 Copy 队列中的数据。

这一步把 Communication behind compute 从抽象原则落到了资源生命周期上。想让 Step N+1 的 Metadata Copy 与 Step N 的 Attention 重叠，至少需要两个独立 Slot、正确的 Queue/Stream 依赖，以及足够长的计算窗口。真实重叠由这些条件共同建立；PIX 时间线中的并行区间可以验证流水线是否已经重叠执行。

七、Descriptor、Root Signature 与资源视图¶

1. 为什么页表是 SRV¶

Q、K、V、Block Table、Context Length 都由 Shader 读取，使用 SRV；Scores、Probabilities、Output 由 Shader 写入，使用 UAV。

第一版 Root Signature：

八、第一条关键 Shader：通过页表读取 K¶

现在写 qk_paged.hlsl。第一轮聚焦逻辑 Token 到物理 KCache Offset 的映射，Dot Product 暂时采用容易检查的实现。

一个 Thread Group 处理一个 (batch, query_head)。每个线程负责若干 Token；Head Dim 暂时用循环完成，便于看清索引。

cbuffer AttentionConstants : register(b0)
{
    uint BatchSize;
    uint NumQHeads;
    uint NumKVHeads;
    uint HeadSize;

    uint BlockSize;
    uint MaxBlocksPerSequence;
    uint MaxContextLength;
    float Scale;
};

StructuredBuffer<float> Q           : register(t0);
StructuredBuffer<float> KCache      : register(t1);
StructuredBuffer<float> VCache      : register(t2);
StructuredBuffer<int> BlockTable    : register(t3);
StructuredBuffer<int> ContextLens   : register(t4);

RWStructuredBuffer<float> Scores        : register(u0);
RWStructuredBuffer<float> Probabilities : register(u1);
RWStructuredBuffer<float> Output        : register(u2);

uint KVIndex(uint blockId, uint offset, uint kvHead, uint dim)
{
    return (((blockId * BlockSize + offset) * NumKVHeads + kvHead)
            * HeadSize + dim);
}

[numthreads(64, 1, 1)]
void CSMain(
    uint3 groupId : SV_GroupID,
    uint lane : SV_GroupThreadID)
{
    const uint queryHead = groupId.x;
    const uint batch = groupId.y;
    if (queryHead >= NumQHeads || batch >= BatchSize)
        return;

    const uint contextLen = ContextLens[batch];
    const uint groupSize = NumQHeads / NumKVHeads;
    const uint kvHead = queryHead / groupSize;

    for (uint token = lane; token < contextLen; token += 64) {
        const uint logicalBlock = token / BlockSize;
        const uint offset = token % BlockSize;
        const int physicalBlock =
            BlockTable[batch * MaxBlocksPerSequence + logicalBlock];

        // CPU 已验证有效范围；Debug 时仍保留防御检查。
        if (physicalBlock < 0) {
            Scores[(batch * NumQHeads + queryHead)
                   * MaxContextLength + token] = asfloat(0x7fc00000);
            continue;
        }

        float dot = 0.0f;
        for (uint dim = 0; dim < HeadSize; ++dim) {
            const uint qIndex =
                (batch * NumQHeads + queryHead) * HeadSize + dim;
            const uint kIndex =
                KVIndex(physicalBlock, offset, kvHead, dim);
            dot += Q[qIndex] * KCache[kIndex];
        }

        Scores[(batch * NumQHeads + queryHead)
               * MaxContextLength + token] = dot * Scale;
    }
}

逐层检查地址¶

对于 request 0, token 5：

logicalBlock = 5 / 4 = 1
offset       = 5 % 4 = 1
physical     = blockTable[0,1] = 2
slot         = 2 * 4 + 1 = 9

如果 CPU Reference 和 Shader 都输出相同 slot=9，分页层已经对齐。建议在 Debug Shader 中临时把 Physical Slot 写入一个额外 UAV，先验证地址，再验证 Dot Product。

九、Softmax 与 PV：先保持三个 Pass¶

1. QK 到 Softmax 需要 UAV Barrier¶

Scores 在 QK 中写入，Softmax 随后读取。两个 Dispatch 都使用 UAV 时插入：

auto qkToSoftmax = CD3DX12_RESOURCE_BARRIER::UAV(scoresBuffer.Get());
commandList->ResourceBarrier(1, &qkToSoftmax);

UAV Barrier 要求此前 UAV 访问在后续 UAV 访问前完成并可见。Resource State Transition 负责另一层状态转换。

2. Softmax Shader 的组织¶

每个 Group 处理一行 [context_len]：

row = (batch, query_head)

实现顺序：

  1. 每线程读取多个 Score，计算 Local Max；
  2. Group Shared + Wave Reduce 得到 Row Max；
  3. 计算 exp(score-rowMax) 与 Local Sum；
  4. Reduce 得到 Row Sum；
  5. 写入归一化 Probability。

这里与前文 Reduce、Shared Memory 和 Warp/Wave Shuffle 完全对应。分页逻辑已经在 QK 中完成，Softmax 不需要访问 Block Table。

下面给出可以直接作为 softmax.hlsl 的基线版本。它使用 64 个线程，每个线程处理若干 Score，再在 groupshared 数组中做两次树形 Reduce。代码没有追求 Wave Intrinsic 的最短路径，目的是让 Max Reduce、Sum Reduce 和同步位置都可见：

cbuffer AttentionConstants : register(b0)
{
    uint BatchSize;
    uint NumQHeads;
    uint NumKVHeads;
    uint HeadSize;

    uint BlockSize;
    uint MaxBlocksPerSequence;
    uint MaxContextLength;
    float Scale;
};

StructuredBuffer<int> ContextLens       : register(t4);
RWStructuredBuffer<float> Scores        : register(u0);
RWStructuredBuffer<float> Probabilities : register(u1);

groupshared float Scratch[64];

[numthreads(64, 1, 1)]
void CSMain(
    uint3 groupId : SV_GroupID,
    uint lane : SV_GroupThreadID)
{
    const uint queryHead = groupId.x;
    const uint batch = groupId.y;
    if (queryHead >= NumQHeads || batch >= BatchSize)
        return;

    const uint contextLen = ContextLens[batch];
    const uint rowBase =
        (batch * NumQHeads + queryHead) * MaxContextLength;

    float localMax = -3.402823466e+38F;
    for (uint token = lane; token < contextLen; token += 64)
        localMax = max(localMax, Scores[rowBase + token]);

    Scratch[lane] = localMax;
    GroupMemoryBarrierWithGroupSync();

    for (uint stride = 32; stride > 0; stride >>= 1) {
        if (lane < stride)
            Scratch[lane] = max(Scratch[lane], Scratch[lane + stride]);
        GroupMemoryBarrierWithGroupSync();
    }
    const float rowMax = Scratch[0];

    float localSum = 0.0f;
    for (uint token = lane; token < contextLen; token += 64) {
        const float value = exp(Scores[rowBase + token] - rowMax);
        Probabilities[rowBase + token] = value;
        localSum += value;
    }

    Scratch[lane] = localSum;
    GroupMemoryBarrierWithGroupSync();

    for (uint stride = 32; stride > 0; stride >>= 1) {
        if (lane < stride)
            Scratch[lane] += Scratch[lane + stride];
        GroupMemoryBarrierWithGroupSync();
    }
    const float inverseSum = 1.0f / Scratch[0];

    for (uint token = lane; token < contextLen; token += 64)
        Probabilities[rowBase + token] *= inverseSum;
}

为了避免每个 Shader 重复声明 ContextLens 和常量，实际工程可把公共声明移入 bindings.hlsli。第一次实现时保留重复声明也可以，优先确保每个文件能够独立看懂。

这段代码提供了一个很具体的性能观察点：两次 Reduce 都需要 Group Barrier。后续可以先在 Wave 内用 WaveActiveMax/WaveActiveSum，只把每个 Wave 的部分结果写入 Shared Memory，从而减少同步与 Shared 访问。是否有收益由实际 Wave Size、Context Length 和 PIX 指标决定。

3. PV 再次通过同一页表读取 V¶

pv_paged.hlsl 与 QK 使用同样的地址公式。Lane 沿 Head Dim 展开；每个 Lane 累加一个或多个输出维度，Context 维在寄存器中串行累加。下面的文件可以直接编译：

cbuffer AttentionConstants : register(b0)
{
    uint BatchSize;
    uint NumQHeads;
    uint NumKVHeads;
    uint HeadSize;

    uint BlockSize;
    uint MaxBlocksPerSequence;
    uint MaxContextLength;
    float Scale;
};

StructuredBuffer<float> VCache          : register(t2);
StructuredBuffer<int> BlockTable        : register(t3);
StructuredBuffer<int> ContextLens       : register(t4);
RWStructuredBuffer<float> Probabilities : register(u1);
RWStructuredBuffer<float> Output        : register(u2);

uint KVIndex(uint blockId, uint offset, uint kvHead, uint dim)
{
    return (((blockId * BlockSize + offset) * NumKVHeads + kvHead)
            * HeadSize + dim);
}

[numthreads(64, 1, 1)]
void CSMain(
    uint3 groupId : SV_GroupID,
    uint lane : SV_GroupThreadID)
{
    const uint queryHead = groupId.x;
    const uint batch = groupId.y;
    if (queryHead >= NumQHeads || batch >= BatchSize)
        return;

    const uint contextLen = ContextLens[batch];
    const uint groupSize = NumQHeads / NumKVHeads;
    const uint kvHead = queryHead / groupSize;
    const uint rowBase =
        (batch * NumQHeads + queryHead) * MaxContextLength;

for (uint dim = lane; dim < HeadSize; dim += 64) {
    float sum = 0.0f;

    for (uint token = 0; token < contextLen; ++token) {
        const uint logicalBlock = token / BlockSize;
        const uint offset = token % BlockSize;
        const int physicalBlock =
            BlockTable[batch * MaxBlocksPerSequence + logicalBlock];

        const float probability =
            Probabilities[(batch * NumQHeads + queryHead)
                          * MaxContextLength + token];
        const uint vIndex =
            KVIndex(physicalBlock, offset, kvHead, dim);
        sum += probability * VCache[vIndex];
    }

    Output[(batch * NumQHeads + queryHead) * HeadSize + dim] = sum;
}
}

PV 前对 Probabilities 插入 UAV Barrier。完成后，测试程序把 Output Copy 到 Readback Heap，与 CPU Reference 比较。

2. 误差检查¶

void compareOutputs(
    std::span<const float> expected,
    std::span<const float> actual)
{
    float maxAbs = 0.0f;
    float maxRel = 0.0f;

    for (size_t i = 0; i < expected.size(); ++i) {
        const float absError = std::abs(expected[i] - actual[i]);
        const float relError =
            absError / std::max(std::abs(expected[i]), 1e-6f);
        maxAbs = std::max(maxAbs, absError);
        maxRel = std::max(maxRel, relError);
    }

    std::cout << "max_abs=" << maxAbs
              << " max_rel=" << maxRel << '\n';
    if (maxAbs > 1e-4f && maxRel > 1e-4f)
        throw std::runtime_error("DX12 output mismatch");
}

3. 先改变页表，不改变 K/V¶

最有价值的分页测试：

  1. 使用页表 [7,2] 运行；
  2. 把物理 Block 7 与 2 的数据交换；
  3. 页表同步改成 [2,7]；
  4. 输出应该保持不变。

如果输出变化，说明某处绕过页表，仍按连续 Token 地址读取。

十一、把静态测试推进到真实 Decode Step¶

静态 K/V 只证明“能读页”。真实 Runtime 还需要把新 Token 的 K/V 写到页池。

1. Slot Mapping¶

CPU 根据请求的最后一个逻辑位置计算写入 Slot：

uint32_t slotForToken(
    std::span<const uint32_t> blockTable,
    uint32_t tokenPosition,
    uint32_t blockSize)
{
    const uint32_t logicalBlock = tokenPosition / blockSize;
    const uint32_t offset = tokenPosition % blockSize;
    return blockTable.at(logicalBlock) * blockSize + offset;
}

Block Table 用于 Gather 历史 K/V；Slot Mapping 用于 Scatter 新 K/V。两者来自同一个页表，但服务于不同方向。

2. KV Store Pass¶

QKV Projection 产生本轮 KNew/VNew 后，KV Store Shader 根据 Slot Mapping 写入 KCache/VCache UAV：

uint token = dispatchThreadId.x;
uint slot = SlotMapping[token];

for (uint i = 0; i < NumKVHeads * HeadSize; ++i) {
    KCacheUAV[slot * NumKVHeads * HeadSize + i] = KNew[token * Stride + i];
    VCacheUAV[slot * NumKVHeads * HeadSize + i] = VNew[token * Stride + i];
}

随后插入 KCache/VCache 的 UAV Barrier，再 Dispatch PagedAttention。若都在同一 Command Queue、同一 Command List 中，顺序由命令流保证；不要为了“保险”让 CPU 等 Fence。

3. 请求跨 Block 边界¶

block_size=4，请求已有 4 个 Token：

block_table=[7]

新 Token 位置 4 需要逻辑 Block 1。CPU 先让 BlockManager 追加物理页：

block_table=[7,2]
slot_mapping=2*4+0=8

然后上传更新后的 Block Table 和 Slot Mapping，再录制 KV Store + Attention。已有 Block 7 完全不移动。

这一步跑通后，才真正实现了“请求增长时按页追加”。

十二、从正确版本走向融合版本¶

三 Pass 基线会产生 Scores 和 Probabilities 两个中间 Buffer：

QK writes Scores to HBM
Softmax reads/writes HBM
PV reads Probabilities from HBM

优化版按 KV Tile 流式执行 Online Softmax，并直接累加 PV：

load K/V tile
→ QK tile
→ update running max/sum
→ rescale old accumulator
→ accumulate weighted V
→ next tile

这时页表仍然存在，只是每次根据逻辑 Tile 找到对应物理 Block。若 Tile 跨 Block 边界，需要拆成两个连续物理区间，或让 Block Size 与 KV Tile 对齐。

建议优化顺序：

  1. QK 的 Head Dim 改为 Wave 协作 Dot Product；
  2. 使用 FP16 输入、FP32 累加；
  3. 合并 QK 与 Row Max；
  4. 引入 Online Softmax；
  5. Softmax 权重直接消费 V；
  6. 对常见 head_size、block_size、Context Bucket 特化；
  7. 用 PIX/Nsight 对比显存事务和 Dispatch 时间。

不要在分页正确性尚未通过时做这些优化。融合会减少中间观察点，也会让 Debug Layer 更难指出数学错误。

3. 准备 TensorRT 环境¶

TensorRT 必须与 NVIDIA Driver/CUDA 兼容。先检查：

nvidia-smi
nvcc --version
python3 --version

创建隔离环境并安装 Python 包，用于验证 Runtime 可用：

python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install tensorrt numpy
python - <<'PY'
import tensorrt as trt
print("TensorRT", trt.__version__)
PY

C++ Plugin 还需要 TensorRT SDK Header 和 Library。设置实际安装路径：

export TRT_ROOT=/opt/TensorRT
test -f "$TRT_ROOT/include/NvInfer.h"
find "$TRT_ROOT" -name 'libnvinfer.so*'

如果系统通过 Debian/RPM 安装 TensorRT，Header 和 Library 通常位于系统路径，可以直接使用。确认文件位置后，再把实际路径写入 CMake。

4. Plugin Tensor 契约¶

inputs[0] Q            FP16/FP32 [B,Hq,D]
inputs[1] KCache       FP16/FP32 [NB,BS,Hkv,D]
inputs[2] VCache       FP16/FP32 [NB,BS,Hkv,D]
inputs[3] BlockTable   INT32      [B,MaxBlocks]
inputs[4] ContextLens  INT32      [B]
output[0] O            FP16/FP32 [B,Hq,D]

这与 DX12 的 Resource 形状一一对应。两个后端共享数据契约，各自管理自己的 GPU 资源。

5. Plugin enqueue()¶

在目标 TensorRT 版本支持的 Plugin 接口中，enqueue() 最终都需要取得输入地址、输出地址和 CUDA Stream。核心逻辑如下：

int enqueue(
    const nvinfer1::PluginTensorDesc* inputDesc,
    const nvinfer1::PluginTensorDesc* outputDesc,
    const void* const* inputs,
    void* const* outputs,
    void* workspace,
    cudaStream_t stream) noexcept override
{
    RuntimeParams params = parseAndValidate(inputDesc);

    launchPagedAttention(
        static_cast<const half*>(inputs[0]),
        static_cast<const half*>(inputs[1]),
        static_cast<const half*>(inputs[2]),
        static_cast<const int32_t*>(inputs[3]),
        static_cast<const int32_t*>(inputs[4]),
        static_cast<half*>(outputs[0]),
        params,
        stream);

    return cudaPeekAtLastError() == cudaSuccess ? 0 : 1;
}

enqueue() 中不要：

  • 调用同步 cudaMemcpy；
  • 使用默认 Stream 替代传入 Stream；
  • 每次 cudaMalloc/cudaFree；
  • 把可变请求状态藏在 Plugin 对象内部。

K/V Cache 和 Block Table 由 Runtime Session 管理，并作为 Binding 传入，才能支持并发 Context 和清晰生命周期。

十五、完整验收清单¶

工程能够推进¶

  • Visual Studio、CMake、DXC 命令可执行；
  • Debug 和 Release 都能构建；
  • Shader 编译错误能定位到具体文件；
  • Debug Layer 没有 Resource State/Descriptor 报错。

分页逻辑正确¶

  • BlockManager 分配与释放数量对称；
  • 请求跨越 Block 边界时追加新页，旧 KV 保持原位；
  • 非连续页表输出与 CPU Reference 一致；
  • 交换物理页并同步修改页表后，输出不变；
  • Padding 页号不会被 Shader 访问；
  • GQA 的 Query Head 到 KV Head 映射正确。

GPU 流水线正确¶

  • Upload → Default Copy 后状态转换完整；
  • QK、Softmax、PV 之间有正确 UAV Barrier；
  • KV Store 后 PagedAttention 读取到新 K/V；
  • Readback 用于测试，稳态 Decode 全程保持 GPU 端执行；
  • Upload Ring Slot 在 Fence 完成前不会被覆盖。

后端迁移正确¶

  • TensorRT Plugin 保持相同 Buffer Layout 和页表公式；
  • Plugin 使用 TensorRT 传入的 CUDA Stream；
  • DX12 与 TensorRT 均对齐同一 CPU Reference；
  • 性能报告分别记录后端、硬件、Shape、Dtype 和测量边界。

十六、回到第一性原理¶

这个项目表面上在写 Attention，真正练习的是三层资源抽象：

D3D12 Resource
    一块可被 GPU 高带宽访问的 Default Buffer

Physical KV Block
    应用在 Buffer 内定义的固定大小 Slice

Logical Sequence
    通过 Block Table 看到连续 Token 历史

Committed Resource 解决“这块 GPU 内存如何创建”；BlockManager 解决“物理 Slice 如何分配”；Block Table 解决“逻辑序列如何找到非连续 Slice”；HLSL 解决“Kernel 如何消费这份映射”。

理解这四层后，迁移到 TensorRT、CUDA、Triton 或其他后端时，资源 API、同步原语和 Kernel 语言随之变化；分页契约与生命周期问题继续保留。迁移过程因此能够复用已经验证的工程理解。

回看：这次移植证明了什么¶

三个后端、三套资源 API、三种同步原语，跑出同一个数值结果。这说明分页 KV Cache 的设计里，真正属于「算法」的部分只有一条：

逻辑 Token 序号 → 页表查一次 → 物理槽位

剩下的全是各家 API 的表达方式差异。这也是为什么 vLLM 的 PagedAttention 能被 TensorRT-LLM、SGLang、llama.cpp 各自重新实现一遍——它们抄的不是代码，是这条契约。

回到 11.3 对照着看，你会更清楚哪些是本质、哪些只是 CUDA 的方言。
