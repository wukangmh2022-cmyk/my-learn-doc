11.1 Nano-vLLM 导学：框架架构、技术栈与源码实现¶

这篇文章从哪里开始¶

本文假设已经具备两部分背景。

GPU 与并行计算：

  • GPU 用大量并发任务隐藏单条指令和访存延迟；
  • Register、Shared Memory/L1、L2、HBM 构成多级存储；
  • 合并访问、Bank Conflict、分支分歧会影响有效吞吐；
  • Tiling 用片上复用减少外部内存流量；
  • Reduce、Scan、Scatter、MatMul/GEMM 等并行模式；
  • 异步 Copy、双缓冲和 Communication behind compute 的基本思想。

Transformer Decoder：

  • 知道 Decoder 大致由 Embedding、Attention、MLP、Norm、Residual 和 LM Head 组成；
  • 知道模型按自回归方式生成，历史 K/V 可以缓存；
  • 不要求会手推每一层公式，也不要求会从零实现 Transformer。

本文不假设已经理解：

  • 一个推理框架如何表示请求状态；
  • Scheduler 如何在 Token、序列数和显存预算下组 Batch；
  • Paged KV Cache 的 Block Table 如何连接 CPU Allocator 与 GPU Kernel；
  • ModelRunner 如何把 Python 对象编译为 GPU Metadata；
  • FlashAttention、Triton、NCCL、CUDA Graph 和多进程分别位于哪一层；
  • 出现输出错误、显存错误、NCCL Hang 或性能问题时从哪里调试。

目标不是把 Nano-vLLM 的文件依次念一遍，而是回答三个贯穿全文的问题：

  1. 这个框架由哪些模块和第三方技术组成？
  2. 一次 Step 如何跨越调度、内存管理和 GPU 执行？
  3. 每个工程机制解决了哪个资源或并发问题？

本文参考 Nano-vLLM 0.2.0、提交 bb823b3。原项目核心包约 1385 行 Python。本文实现的是结构等价的教学版，不逐字复制源码。

二、框架为什么必须区分 Prefill 与 Decode¶

这里不重复解释 Transformer 计算，只说明它们对 Runtime 的约束。相同 Decoder 权重面对两类完全不同的执行 Shape：

特征 Prefill Decode
本步每条序列输入 Token 多个 1 个
Linear 形态 较大的 GEMM 小 Batch GEMM/GEMV
Attention Query Length Prompt/Chunk 长度 1
历史 K/V 建立或复用 Prefix 反复读取全部上下文
常见瓶颈 计算、HBM、中间结果 KV 带宽、Kernel Launch、调度
适合 CUDA Graph Shape 更动态 按 Batch Size 分桶后较适合

这一区分向下影响四层：

框架层 Prefill Decode
Scheduler Token Budget，可做 Chunk Sequence Budget，每序列一个 Token
Metadata Packed Tokens、cu_seqlens context_lens、Block Tables
Attention Backend Varlen Attention KV Cache Decode Attention
Execution Eager Shape 较动态 可按 Batch Bucket 捕获 CUDA Graph

因此 is_prefill 不是模型知识补丁，而是贯穿 Scheduler、ModelRunner、Attention Backend 和 Graph Dispatch 的框架模式位。

一个用于后续调试的 Shape 示例¶

两条请求：

S0 prompt length = 5
S1 prompt length = 3

第一次 Step：

phase = prefill
input_ids = S0[0:5] + S1[0:3]  # 共 8 个 Token，压平后送入 GPU

第二次 Step：

phase = decode
input_ids = [S0.last_token, S1.last_token]  # 共 2 个 Token

Prefill 的 Batch Size 更接近“本步 Token 总数”；Decode 的 Batch Size 更接近“活跃序列数”。后面 Scheduler 会分别设置 Sequence Budget 和 Token Budget。

三、阶段 1：实现框架的数据契约与 Sequence 状态机¶

为什么不能只保存 list[int]¶

调度器不仅需要 Token，还要知道：

  • 请求是在等待、运行还是完成；
  • Prompt 与生成结果的边界；
  • 已有多少 Token 写入 KV Cache；
  • 本轮准备计算多少 Token；
  • 该请求持有哪些物理 KV Block；
  • EOS、最大生成长度和温度。

实现 SamplingParams¶

from dataclasses import dataclass

@dataclass(slots=True)
class SamplingParams:
    temperature: float = 1.0
    max_tokens: int = 64
    ignore_eos: bool = False

    def __post_init__(self):
        if self.temperature < 0:
            raise ValueError("temperature must be >= 0")
        if self.max_tokens <= 0:
            raise ValueError("max_tokens must be positive")

实现 Sequence¶

from enum import Enum, auto
from itertools import count

class SequenceStatus(Enum):
    WAITING = auto()
    RUNNING = auto()
    FINISHED = auto()

class Sequence:
    _counter = count()

    def __init__(
        self,
        token_ids: list[int],
        sampling: SamplingParams,
        block_size: int,
    ):
        if not token_ids:
            raise ValueError("empty prompt is not supported")

        self.seq_id = next(self._counter)
        self.status = SequenceStatus.WAITING
        self.token_ids = list(token_ids)
        self.prompt_len = len(token_ids)
        self.cached_tokens = 0
        self.scheduled_tokens = 0
        self.block_table: list[int] = []
        self.block_size = block_size
        self.sampling = sampling

    @property
    def completion_token_ids(self) -> list[int]:
        return self.token_ids[self.prompt_len:]

    @property
    def num_blocks(self) -> int:
        n = len(self.token_ids)
        return (n + self.block_size - 1) // self.block_size

    @property
    def last_token(self) -> int:
        return self.token_ids[-1]

    def append_token(self, token_id: int) -> None:
        self.token_ids.append(token_id)

三个计数不要混淆¶

len(token_ids)      已知的全部 Token：Prompt + 已生成 Token
cached_tokens       已经计算并写入 KV Cache 的 Token
scheduled_tokens    本轮已经批准、但尚未提交完成的 Token

以长度 10 的 Prompt、Chunk Size 4 为例：

初始：cached=0, scheduled=0
Step 1 调度后：cached=0, scheduled=4
Step 1 完成后：cached=4, scheduled=0
Step 2 调度后：cached=4, scheduled=4
Step 2 完成后：cached=8, scheduled=0
Step 3 调度后：cached=8, scheduled=2

scheduled_tokens 类似已录入 Command Buffer 但尚未完成的资源范围。只有 GPU 成功完成并进入 Postprocess 后，才能转入 cached_tokens。

状态不变量¶

def validate_sequence(seq: Sequence) -> None:
    assert 0 <= seq.cached_tokens <= len(seq.token_ids)
    assert 0 <= seq.scheduled_tokens
    assert seq.cached_tokens + seq.scheduled_tokens <= len(seq.token_ids)
    if seq.status is SequenceStatus.FINISHED:
        assert not seq.block_table

状态机的价值不是面向对象，而是让错误尽早暴露。推理引擎最难查的 Bug 往往不是 Kernel Crash，而是 CPU 记录的进度与 GPU 中的 KV 数据错开一个 Token。

四、阶段 2：把多个变长请求编译成 GPU Batch¶

工程问题¶

请求长度分别为 3、2、4：

A = [a0, a1, a2]
B = [b0, b1]
C = [c0, c1, c2, c3]

若 Padding 到长度 4，需要计算 12 个位置，其中 3 个无效。更大的长度差会造成更多浪费。

Nano-vLLM 在 Prefill 使用 Packed/Ragged Batch：

input_ids  = [a0,a1,a2, b0,b1, c0,c1,c2,c3]
cu_seqlens = [0,3,5,9]

cu_seqlens 是 Prefix Sum。它把每条序列的长度 [3,2,4] 转换为起始 Offset [0,3,5,9]。这里直接用到了 Scan 的思想。

CPU 打包代码¶

def pack_prefill(seqs: list[Sequence]):
    input_ids: list[int] = []
    positions: list[int] = []
    cu_seqlens = [0]
    max_query_len = 0

    for seq in seqs:
        start = seq.cached_tokens
        end = start + seq.scheduled_tokens
        query_len = end - start

        input_ids.extend(seq.token_ids[start:end])
        positions.extend(range(start, end))
        cu_seqlens.append(cu_seqlens[-1] + query_len)
        max_query_len = max(max_query_len, query_len)

    return input_ids, positions, cu_seqlens, max_query_len

为什么由 CPU 做¶

Scheduler 已经在 CPU 持有每条请求的长度与状态。元数据量很小，在 CPU 构造后异步 H2D，通常比额外启动 GPU Scan Kernel 更合适。若请求规模非常大或元数据本来就在 GPU，选择可能不同。

CUDA 原语¶

input_ids = torch.tensor(input_ids, dtype=torch.int64, pin_memory=True)
input_ids = input_ids.cuda(non_blocking=True)
  • Pinned Memory 允许 DMA 高效读取 Host Buffer；
  • non_blocking=True 允许异步提交 Copy；
  • 真正重叠仍需要合适的 Stream 与无数据依赖；
  • Ring Buffer 必须用 CUDA Event 保护，避免 CPU 覆盖 GPU 尚未读取的 Slot。

Decode Batch 更简单¶

Decode 每条序列只提供最后一个 Token：

def pack_decode(seqs: list[Sequence]):
    input_ids = [seq.last_token for seq in seqs]
    positions = [len(seq.token_ids) - 1 for seq in seqs]
    context_lens = [len(seq.token_ids) for seq in seqs]
    return input_ids, positions, context_lens

此时 Tensor 第一维等于活跃序列数。历史 Token 不重新放入 Input，而是从 KV Cache 读取。

五、阶段 3：实现 Paged KV Cache 与 Prefix Cache¶

1. KV Cache 到底多大¶

单条序列每个 Token 的 KV 字节数：

$$ bytes_{token}=2 \times L \times H_{kv} \times D \times bytes_{dtype} $$

  • 2：K 和 V；
  • $L$：Decoder Layer 数；
  • $H_{kv}$：KV Head 数；
  • $D$：Head Size。

若按 max_model_len 为每条请求预留连续空间，短请求也占用最大长度。请求结束时间不同，连续大块还会形成外部碎片。

2. 分页的第一性原理¶

把逻辑 Token 序列切成固定大小 Block：

logical tokens: [0..3] [4..7] [8..11]
logical block:     0      1       2
physical block:    7      2      11

逻辑 Token t 的物理位置：

$$ logical_block=\lfloor t/B \rfloor $$

$$ offset=t \bmod B $$

$$ slot=block_table[logical_block]\times B+offset $$

这与虚拟内存页表、虚拟纹理和 Bindless Handle Table 使用相同原则：增加一次间接寻址，换取按需分配、非连续存储、共享和低碎片。

3. Block 与 BlockManager¶

from collections import deque
from dataclasses import dataclass

@dataclass
class Block:
    block_id: int
    ref_count: int = 0
    content_hash: int | None = None
    token_ids: tuple[int, ...] = ()

class BlockManager:
    def __init__(self, num_blocks: int, block_size: int):
        self.block_size = block_size
        self.blocks = [Block(i) for i in range(num_blocks)]
        self.free_ids = deque(range(num_blocks))
        self.used_ids: set[int] = set()
        self.hash_to_id: dict[int, int] = {}

    def allocate_one(self) -> int:
        if not self.free_ids:
            raise RuntimeError("KV cache exhausted")

        block_id = self.free_ids.popleft()
        block = self.blocks[block_id]

        # 这个物理页即将被覆盖，旧 Prefix Cache 索引失效。
        if block.content_hash is not None:
            if self.hash_to_id.get(block.content_hash) == block_id:
                del self.hash_to_id[block.content_hash]

        block.ref_count = 1
        block.content_hash = None
        block.token_ids = ()
        self.used_ids.add(block_id)
        return block_id

    def retain(self, block_id: int) -> None:
        self.blocks[block_id].ref_count += 1

    def release(self, block_id: int) -> None:
        block = self.blocks[block_id]
        if block.ref_count <= 0:
            raise RuntimeError("double free")
        block.ref_count -= 1
        if block.ref_count == 0:
            self.used_ids.remove(block_id)
            self.free_ids.append(block_id)

4. 为请求分配页表¶

def allocate_sequence(manager: BlockManager, seq: Sequence) -> None:
    if seq.block_table:
        raise RuntimeError("sequence already owns blocks")

    required = seq.num_blocks
    if len(manager.free_ids) < required:
        raise RuntimeError("not enough KV blocks")

    for _ in range(required):
        seq.block_table.append(manager.allocate_one())

def release_sequence(manager: BlockManager, seq: Sequence) -> None:
    for block_id in reversed(seq.block_table):
        manager.release(block_id)
    seq.block_table.clear()
    seq.cached_tokens = 0

逆序释放不是正确性的必要条件，但符合“先释放尾部私有页，再释放前缀共享页”的所有权顺序。

5. Slot Mapping：告诉 Kernel 写到哪里¶

Block Table 用于读取整段历史；Slot Mapping 用于写入本轮新产生的 K/V：

def build_slot_mapping(seq: Sequence) -> list[int]:
    start = seq.cached_tokens
    end = start + seq.scheduled_tokens
    slots = []

    for token_pos in range(start, end):
        logical_block = token_pos // seq.block_size
        offset = token_pos % seq.block_size
        physical_block = seq.block_table[logical_block]
        slots.append(physical_block * seq.block_size + offset)

    return slots

例：B=4、页表 [7,2]、写入 Token 3 至 5：

token 3 → block 7, offset 3 → slot 31
token 4 → block 2, offset 0 → slot 8
token 5 → block 2, offset 1 → slot 9

6. Prefix Cache 为什么只发布完整 Block¶

未填满 Block 未来还会追加 Token，内容尚未不可变。只有完整 Block 才能形成稳定缓存键。

链式哈希必须包含此前前缀：

def block_hash(parent_hash: int | None, token_ids: list[int]) -> int:
    return hash((parent_hash, tuple(token_ids)))

相同局部 Token 出现在不同前缀后面时，链式 Hash 不同。Hash 命中后仍应比较 Token 内容，避免碰撞。

先查找可复用的完整前缀：

def find_cached_prefix(
    manager: BlockManager,
    seq: Sequence,
) -> list[int]:
    cached_block_ids = []
    parent_hash = None

    # 最后一个 Block 即使刚好完整，也先留给当前请求继续管理；
    # 教学版只复用“确定在 Prompt 内部”的完整前缀页。
    num_full_prefix_blocks = max(0, seq.num_blocks - 1)

    for logical_block in range(num_full_prefix_blocks):
        start = logical_block * seq.block_size
        end = start + seq.block_size
        tokens = seq.token_ids[start:end]
        content_hash = block_hash(parent_hash, tokens)

        block_id = manager.hash_to_id.get(content_hash)
        if block_id is None:
            break

        block = manager.blocks[block_id]
        if block.token_ids != tuple(tokens):
            break  # Hash 碰撞，不能复用。

        cached_block_ids.append(block_id)
        parent_hash = content_hash

    return cached_block_ids

再把共享页和新页组成该请求的 Block Table：

def allocate_with_prefix(
    manager: BlockManager,
    seq: Sequence,
    cached_block_ids: list[int],
) -> None:
    if seq.block_table:
        raise RuntimeError("sequence already owns blocks")

    new_block_count = seq.num_blocks - len(cached_block_ids)
    reusable_free = sum(
        manager.blocks[block_id].ref_count == 0
        for block_id in cached_block_ids
    )
    required_from_free_list = new_block_count + reusable_free
    if len(manager.free_ids) < required_from_free_list:
        raise RuntimeError("not enough KV blocks")

    for block_id in cached_block_ids:
        block = manager.blocks[block_id]
        if block.ref_count == 0:
            manager.free_ids.remove(block_id)
            manager.used_ids.add(block_id)
            block.ref_count = 1
        else:
            manager.retain(block_id)
        seq.block_table.append(block_id)

    for _ in range(new_block_count):
        seq.block_table.append(manager.allocate_one())

    seq.cached_tokens = len(cached_block_ids) * seq.block_size

GPU 完成本轮 Prefill 后，发布新填满的 Block：

def publish_full_blocks(manager: BlockManager, seq: Sequence) -> None:
    completed_tokens = seq.cached_tokens + seq.scheduled_tokens
    completed_blocks = completed_tokens // seq.block_size
    first_unpublished = seq.cached_tokens // seq.block_size

    parent_hash = None
    if first_unpublished > 0:
        previous_id = seq.block_table[first_unpublished - 1]
        parent_hash = manager.blocks[previous_id].content_hash

    for logical_block in range(first_unpublished, completed_blocks):
        start = logical_block * seq.block_size
        end = start + seq.block_size
        tokens = seq.token_ids[start:end]
        content_hash = block_hash(parent_hash, tokens)
        block = manager.blocks[seq.block_table[logical_block]]
        block.content_hash = content_hash
        block.token_ids = tuple(tokens)
        manager.hash_to_id[content_hash] = block.block_id
        parent_hash = content_hash

注意顺序：先由 GPU 写完 KV，再由 Postprocess 发布 Hash。若调度时就发布，其他请求可能命中一页尚未写完的数据。

7. 引用计数的含义¶

两条请求共享 Prefix Block：

S0 table = [7, 2]
S1 table = [7, 9]
block 7 ref_count = 2

S0 完成时只能把 block 7 引用减为 1，不能放回 Free List。Prefix Cache 的核心不是 Hash Map，而是一套“不可变内容 + 引用所有权 + 延迟回收”协议。

2. 两种预算¶

3. Scheduler 骨架¶

from collections import deque

class Scheduler:
    def __init__(self, config, block_manager: BlockManager):
        self.max_num_seqs = config.max_num_seqs
        self.max_num_batched_tokens = config.max_num_batched_tokens
        self.eos_token_id = config.eos_token_id
        self.block_manager = block_manager
        self.waiting: deque[Sequence] = deque()
        self.running: deque[Sequence] = deque()

    def add(self, seq: Sequence) -> None:
        self.waiting.append(seq)

    def is_finished(self) -> bool:
        return not self.waiting and not self.running

    def schedule(self) -> tuple[list[Sequence], bool]:
        prefill = self._schedule_prefill()
        if prefill:
            return prefill, True
        return self._schedule_decode(), False

4. Prefill 与 Chunked Prefill¶

def _schedule_prefill(self) -> list[Sequence]:
    selected = []
    used_tokens = 0

    while self.waiting and len(selected) < self.max_num_seqs:
        seq = self.waiting[0]
        remaining = self.max_num_batched_tokens - used_tokens
        if remaining == 0:
            break

        if not seq.block_table:
            cached = find_cached_prefix(self.block_manager, seq)
            new_blocks = seq.num_blocks - len(cached)
            reusable_free = sum(
                self.block_manager.blocks[block_id].ref_count == 0
                for block_id in cached
            )
            if len(self.block_manager.free_ids) < new_blocks + reusable_free:
                break
            allocate_with_prefix(self.block_manager, seq, cached)

        unscheduled = len(seq.token_ids) - seq.cached_tokens

        # 简化：Batch 中已有请求时，不让下一条长 Prompt 做 Partial Chunk。
        if unscheduled > remaining and selected:
            break

        seq.scheduled_tokens = min(unscheduled, remaining)
        used_tokens += seq.scheduled_tokens
        selected.append(seq)

        if seq.cached_tokens + seq.scheduled_tokens == len(seq.token_ids):
            self.waiting.popleft()
            seq.status = SequenceStatus.RUNNING
            self.running.append(seq)
        else:
            # 第一条请求只处理一个 Chunk，仍留在 waiting[0]。
            break

    return selected

Chunked Prefill 把超长 Prompt 拆成多个 Step。它和长任务分帧处理具有同样目标：避免一次工作独占整个预算，同时引入更多状态和调度次数。

5. Decode 与抢占¶

Decode 新增 Token 可能跨越 Block 边界。如果没有空闲 Block，Scheduler 需要选择受害请求。

def needs_new_block(seq: Sequence) -> bool:
    # last_token 尚未写入 KV；它位于新 Block 的第一个位置时需要新页。
    return len(seq.token_ids) % seq.block_size == 1

def _schedule_decode(self) -> list[Sequence]:
    selected = []

    while self.running and len(selected) < self.max_num_seqs:
        seq = self.running.popleft()

        while needs_new_block(seq) and not self.block_manager.free_ids:
            if self.running:
                self._preempt(self.running.pop())
            else:
                self._preempt(seq)
                break
        else:
            if needs_new_block(seq):
                seq.block_table.append(self.block_manager.allocate_one())
            seq.scheduled_tokens = 1
            selected.append(seq)

    self.running.extendleft(reversed(selected))
    if not selected:
        raise RuntimeError("no schedulable sequence")
    return selected

def _preempt(self, seq: Sequence) -> None:
    release_sequence(self.block_manager, seq)
    seq.status = SequenceStatus.WAITING
    self.waiting.appendleft(seq)

Nano-vLLM 采用 Recompute Preemption：释放 KV Cache，之后重新 Prefill。它用计算换显存，结构简单。生产系统可能使用 Swap、Priority 或更复杂的受害者选择。

6. Postprocess 是事务提交¶

def postprocess(self, seqs, token_ids, is_prefill):
    for seq, token_id in zip(seqs, token_ids):
        if is_prefill:
            publish_full_blocks(self.block_manager, seq)
        seq.cached_tokens += seq.scheduled_tokens
        seq.scheduled_tokens = 0

        # Chunk 尚未完成整个 Prompt，不产生新 Token。
        if is_prefill and seq.cached_tokens < len(seq.token_ids):
            continue

        seq.append_token(token_id)
        hit_eos = (
            token_id == self.eos_token_id
            and not seq.sampling.ignore_eos
        )
        hit_limit = (
            len(seq.completion_token_ids) >= seq.sampling.max_tokens
        )

        if hit_eos or hit_limit:
            seq.status = SequenceStatus.FINISHED
            release_sequence(self.block_manager, seq)
            self.running.remove(seq)

先执行 GPU，成功后再提交 cached_tokens 和 Token 状态。这个顺序等价于资源状态变更必须发生在对应 GPU 工作真正成立之后。

7. 调度策略不是硬件定律¶

示例实现优先 Prefill：只要选到 Prefill，就不组成 Decode Batch。它容易理解，但会影响已有请求的 Inter-Token Latency。生产系统需要在以下目标间权衡：

  • TTFT：新请求首 Token 延迟；
  • TPOT/ITL：已有请求相邻 Token 延迟；
  • 总吞吐；
  • 公平性与长请求饥饿；
  • KV Cache 压力。

必须区分“资源不能超预算”的正确性约束与“谁先运行”的策略选择。

3. 写入 KV Cache¶

概念上是 Scatter：

def store_kv(key, value, k_cache, v_cache, slot_mapping):
    flat_k = k_cache.view(-1, key.shape[-2], key.shape[-1])
    flat_v = v_cache.view(-1, value.shape[-2], value.shape[-1])
    valid = slot_mapping >= 0
    flat_k[slot_mapping[valid]] = key[valid]
    flat_v[slot_mapping[valid]] = value[valid]

Nano-vLLM 使用 Triton Kernel。一个 Program 处理一个 Token 的全部 KV Head 数据：

@triton.jit
def store_kv_kernel(
    key_ptr, value_ptr, k_cache_ptr, v_cache_ptr,
    slot_mapping_ptr, token_stride: tl.constexpr, D: tl.constexpr,
):
    token = tl.program_id(0)
    slot = tl.load(slot_mapping_ptr + token)
    offsets = tl.arange(0, D)
    mask = (offsets < D) & (slot >= 0)

    key = tl.load(key_ptr + token * token_stride + offsets, mask=mask)
    value = tl.load(value_ptr + token * token_stride + offsets, mask=mask)
    tl.store(k_cache_ptr + slot * D + offsets, key, mask=mask)
    tl.store(v_cache_ptr + slot * D + offsets, value, mask=mask)

GPU 原理：

  • offsets 让同一 Program 的 Lane 读取连续 Head 数据，便于合并；
  • Slot Mapping 是 Scatter 目标；
  • slot=-1 用于 CUDA Graph Padding，必须 Mask；
  • 写入后 Attention 在同一 Stream 执行，Stream 顺序保证依赖，不需要 CPU 同步。

        causal=True,
    )

每条序列只有一个 Query，但读取不同长度、不同物理页的 K/V。

6. PagedAttention 与 FlashAttention 的分工¶

  • Paged KV Cache：解决缓存如何分配、共享和寻址；
  • FlashAttention：解决 QK/Softmax/PV 如何分块，减少中间结果 HBM 流量；
  • 两者可以同时使用，但不是同一个算法。

PagedAttention 增加间接寻址，并不保证单 Kernel 自动变快。系统收益来自更低碎片、按需增长、Prefix 共享和无需聚合复制 KV。

九、阶段 7：实现 Qwen3 Model Adapter 与 Weight Loader¶

1. Model Adapter 的边界¶

框架不重新发明 Transformer Decoder。Qwen3ForCausalLM 的作用是把标准模型接到 Runtime 约定上：

Runtime 输入契约
input_ids + positions + AttentionContext
        ↓
Qwen3 Model Adapter
        ├── 使用框架的 Parallel Linear
        ├── 使用框架的 Paged Attention Backend
        ├── 暴露 KV Cache 绑定位置
        └── 暴露 compute_logits(hidden)
        ↓
Runtime 输出契约
hidden states / selected logits

阅读 models/qwen3.py 时不需要重新学习 Decoder 每层公式，只检查四件事：

  1. 原模型参数名如何映射到框架 Module；
  2. 哪些 Linear 被替换为 TP 版本；
  3. Attention 如何取得本轮 Context 与 KV Cache；
  4. Hidden State 在哪里进入 LM Head。

2. 为执行效率调整内部布局¶

qkv = self.qkv_proj(hidden_states)
q, k, v = qkv.split([q_size, kv_size, kv_size], dim=-1)

gate_up = self.gate_up_proj(hidden_states)
gate, up = gate_up.chunk(2, dim=-1)
hidden = F.silu(gate) * up

融合权重使相同输入只读取一次，并减少 Kernel Launch。代价是 Loader 必须把 Hugging Face 的独立权重写入正确 Slice。

3. Weight Loader 是布局编译器¶

外部 Checkpoint：

q_proj.weight
k_proj.weight
v_proj.weight
gate_proj.weight
up_proj.weight

内部布局：

qkv_proj.weight      = [Q shard | K shard | V shard]
gate_up_proj.weight  = [Gate shard | Up shard]

Loader 还需要：

  • 按 Tensor Parallel Rank 切片；
  • 处理 Tied Embedding；
  • 检查 Shape 与 Dtype；
  • 逐 Tensor 加载，避免同时保留完整模型的额外副本。

这不是辅助 I/O，而是 Checkpoint Schema 到高性能执行 Layout 的转换。

4. 模型配置如何影响 Runtime 容量¶

若 num_q_heads=16、num_kv_heads=2，每 8 个 Q Head 共享一个 KV Head：

Q head 0..7  → KV head 0
Q head 8..15 → KV head 1

KV Head 维度相对 16:16 MHA 缩小到 2/16=1/8。这是 KV Cache 核心维度的理论缩减，不等于整个推理进程显存缩小到八分之一。

Runner 从 Hugging Face Config 读取 num_hidden_layers、num_key_value_heads、head_dim 和 Dtype，计算单个 KV Block 的字节数。也就是说，Model Adapter 不只决定计算图，还向 Runtime 提供容量规划所需的静态规格。

2. run()¶

class ModelRunner:
    @torch.inference_mode()
    def run(self, seqs: list[Sequence], is_prefill: bool) -> list[int]:
        if is_prefill:
            ctx, input_ids, positions = prepare_prefill(seqs, self.block_size)
        else:
            ctx, input_ids, positions = prepare_decode(seqs, self.block_size)

        set_context(ctx)
        try:
            hidden = self.run_model(input_ids, positions, is_prefill)
            last_hidden = self.select_last_hidden(hidden, seqs, is_prefill)
            logits = self.model.compute_logits(last_hidden)
            temperatures = self.prepare_temperatures(seqs)
            return self.sampler(logits, temperatures).tolist()
        finally:
            reset_context()

finally 保证异常时也清理隐式 Context。

3. 为什么只计算最后位置的 Logits¶

Prefill 为多个 Token 产生 Hidden State，但生成只需要每条序列最后一个 Query 位置。若对所有 Prompt Token 执行完整 Vocab Projection，会产生大量无用 GEMM 和 Logits Buffer。

选择末尾位置是一种 Gather：

last_indices = cu_seqlens_q[1:] - 1
last_hidden = hidden[last_indices]

4. Sampling¶

Greedy：

token_ids = logits.argmax(dim=-1)

Temperature Sampling：

scaled = logits.float() / temperatures[:, None]
probs = torch.softmax(scaled, dim=-1)
noise = torch.empty_like(probs).exponential_().clamp_min_(1e-10)
token_ids = (probs / noise).argmax(dim=-1)

这里包含 Elementwise、Softmax Reduce 和 Argmax Reduce。生产采样器还需 Top-k/Top-p、重复惩罚、随机数状态和 Logit Bias。

十一、阶段 9：组装 LLMEngine¶

class LLMEngine:
    def __init__(self, config, tokenizer, runner, scheduler):
        self.config = config
        self.tokenizer = tokenizer
        self.runner = runner
        self.scheduler = scheduler

    def add_request(self, prompt: str, sampling: SamplingParams) -> int:
        token_ids = self.tokenizer.encode(prompt)
        seq = Sequence(token_ids, sampling, self.config.block_size)
        self.scheduler.add(seq)
        return seq.seq_id

    def step(self):
        seqs, is_prefill = self.scheduler.schedule()
        token_ids = self.runner.run(seqs, is_prefill)
        self.scheduler.postprocess(seqs, token_ids, is_prefill)
        return [seq for seq in seqs if seq.status is SequenceStatus.FINISHED]

    def generate(self, prompts, sampling):
        for prompt in prompts:
            self.add_request(prompt, sampling)

        outputs = {}
        while not self.scheduler.is_finished():
            for seq in self.step():
                outputs[seq.seq_id] = seq.completion_token_ids

        return [
            self.tokenizer.decode(outputs[seq_id])
            for seq_id in sorted(outputs)
        ]

为什么 step() 是关键边界¶

一次 Step 完成：

计划资源
→ 构造 GPU 工作
→ 执行模型
→ 取得结果
→ 提交状态

流式输出、异步 Server、指标采集和取消请求都可以建立在 Step 边界之上。

十二、阶段 10：用 CUDA Graph 优化 Decode 提交¶

1. 问题来自哪里¶

Decode 每步输入 Token 少，但模型层数多，会产生大量小 Kernel：

CPU launch kernel A
CPU launch kernel B
CPU launch kernel C
...

如果单 Kernel 很短，Launch Gap 在时间线中占比明显。CUDA Graph 把稳定的 Kernel 拓扑捕获后一次重放。

它优化 CPU 提交，不会自动：

  • 融合 Kernel；
  • 减少 KV Cache 读取；
  • 提高单 Kernel 算术强度。

2. 为什么需要 Batch Bucket¶

Graph 要求 Shape 与地址相对稳定。预先捕获：

graph_batch_sizes = [1, 2, 4, 8, 16, 32, 48, 64]

真实 Batch B=13 使用 Bucket 16，后三条是 Padding。

3. 静态 Buffer¶

self.static_input_ids = torch.zeros(max_batch, dtype=torch.int64, device="cuda")
self.static_positions = torch.zeros(max_batch, dtype=torch.int64, device="cuda")
self.static_slot_mapping = torch.full(
    (max_batch,), -1, dtype=torch.int32, device="cuda"
)
self.static_context_lens = torch.zeros(max_batch, dtype=torch.int32, device="cuda")

每次只 Copy 内容，不替换 Tensor 对象：

self.static_input_ids[:bs].copy_(input_ids)
self.static_positions[:bs].copy_(positions)
self.static_slot_mapping.fill_(-1)
self.static_slot_mapping[:bs].copy_(slot_mapping)
graph.replay()

4. 三个不变量¶

  1. 捕获和重放使用相同 Tensor 地址；
  2. Kernel 拓扑保持稳定；
  3. Padding 无副作用：Slot 为 -1、Context Length 为 0、输出被裁掉。

5. 对应图形框架¶

它最接近“预先录制并重放稳定 Command List”。它不是 RenderGraph，也不是 GPU Driven Rendering：RenderGraph 还负责资源依赖与 Pass 规划，GPU Driven 则把可见性和间接参数生成移到 GPU。

十三、阶段 11：接入 Tensor Parallel Worker¶

1. Column Parallel¶

按输出维切权重：

W[out, in]
→ rank 0 owns W[0:out/p, :]
→ rank 1 owns W[out/p:2out/p, :]

每个 Rank 产生不同输出 Slice。QKV 和 Gate/Up 可以继续本地计算，不立即通信。

2. Row Parallel¶

按输入维切权重：

$$ y=\sum_r x_r W_r^T $$

def forward(self, x):
    y = F.linear(x, self.weight, self.bias if self.rank == 0 else None)
    if self.world_size > 1:
        dist.all_reduce(y)
    return y

Bias 只能在一个 Rank 加，否则 AllReduce 后会重复累加。

3. Communication behind compute 的边界¶

TP 的 AllReduce 位于层内数据依赖上：后续计算需要完整结果时，通信不能无限延后。可以通过分块、Stream、ReduceScatter/AllGather 组合或算子重排寻找重叠，但必须满足依赖。

“存在独立 Copy/Communication Engine”不等于自动重叠。应使用 Nsight Systems 验证 NCCL 与计算是否在时间线上并行。

4. 一 GPU 一进程¶

Nano-vLLM 使用 spawn 创建 Worker，每个 Rank：

bind CUDA device
→ init NCCL process group
→ build same model structure
→ load local weight shard
→ receive run command
→ execute collectives in identical order

Collective 顺序是全局协议。某个 Rank 少进入一次 AllReduce，会导致其他 Rank 永久等待。

十五、框架技术栈与 CUDA 原语对照¶

CUDA/并行原语 在 Nano-vLLM 中解决什么 常见错误
Pinned Memory + Async H2D 上传 Token 和页表元数据 Host Buffer 太早复用、隐式同步
Stream 顺序 KV Store 后再执行 Attention 跨 Stream 缺 Event 依赖
Event 元数据 Ring Buffer 和异步完成 把 Event 当内存屏障使用
Triton/CUDA Scatter 根据 Slot Mapping 写 KV Off-by-one、Padding 写入有效页
Reduce/Softmax Attention、Sampling、Norm 数值不稳定、跨 Block 归约错误
Shared Memory/Tiling Attention/GEMM 片上复用 Bank Conflict、容量压低驻留率
Warp Shuffle Warp 内 Reduce/数据交换 Active Mask 错误
NCCL AllReduce Row Parallel 合并部分和 Collective 顺序不同、Bias 重复
CUDA Graph 重放 Decode Kernel 拓扑 地址变化、Padding 有副作用
Memory Pool 稳态避免频繁分配 GPU 尚未完成就回收 Buffer

这里没有“为了使用 CUDA 原语而使用”。每个原语都对应一个具体工程约束：数据依赖、状态所有权、访存成本或提交开销。

十八、从 GPU 第一性原理重新看整个引擎¶

1. 数据移动比公式更早决定系统结构¶

Transformer 公式没有规定必须有 Paged KV、Prefix Cache 或 CUDA Graph。这些结构来自：

  • KV 历史太大，不能反复重算或连续预留；
  • Decode 每步反复读取历史，HBM 流量重要；
  • 不规则请求需要压成规则 Batch；
  • 小 Kernel 多，CPU 提交间隙不可忽略；
  • 多卡切分后必须合并部分结果。

2. 调度器是一个在线装箱问题¶

Scheduler 每步把不同长度、不同状态的请求装入有限 Token、Sequence 和 KV Block 预算。它类似 Bin Packing，但还带时间、公平性与反馈循环。

3. 页表是一次有价值的间接访问¶

Block Table 增加 Gather/间接寻址，却消除大块连续分配要求，并允许共享与按需增长。和纹理缓存一样，不能只看一次地址计算的成本，要看整个系统减少了多少搬移与浪费。

4. Prefix Cache 是不可变资源复用¶

它的成立条件是：内容完整、Hash 可验证、引用仍有效、物理页尚未覆盖。它与渲染中的 PSO/资源缓存共享“内容寻址 + 生命周期”原则，但缓存的数据语义不同。

5. CUDA Graph 是提交优化¶

它减少重复录制与 Launch，不改变 Attention 的渐进复杂度，也不替代 Kernel Fusion。先用 Systems 证明 CPU Gap 存在，再决定是否捕获。

十九、与渲染框架的准确连接¶

Nano-vLLM 渲染框架中的近似问题 共同原理 不同点
engine.step() Frame/Submit 边界 CPU 计划后提交 GPU 工作 Token 状态跨 Step 反馈
Scheduler 动态 Draw/Pass 批处理 在预算内组 Batch 请求到达和结束更不规则
Packed Metadata Indirect Argument Buffer 高层对象编译为紧凑 GPU 数据 描述变长序列而非 Draw
Block Table Descriptor/虚拟纹理页表 间接寻址解耦逻辑与物理资源 KV 保存时序历史
KV Block Pool Transient Resource Pool 按完成状态回收 可共享 Prefix 引用
Chunked Prefill 大任务拆帧 避免单任务独占预算 会推迟首 Token

Tensor Parallel Multi-GPU 分片 分区计算后通信合并 每层可能频繁 Collective

类比的用途是迁移资源管理直觉，不是宣称两个系统完全同构。
