11.5 Runtime 与部署：从 Scheduler 到生产环境¶

你在 11.3 写了 PagedAttention Kernel，在 11.1 读懂了 vLLM 的 Scheduler 和 BlockManager —— 但它们还只是零件。现在问题是：怎么把这些零件焊成一个能在生产环境跑的系统？

这篇是第 11 章「上生产」的收口：从请求进来到 Token 出去的完整链路、动态批处理的调度策略、TensorRT Backend 的工程化、端侧部署的环境适配、AWQ 量化的验证方法，以及「我的 Runtime 是对的吗」这个问题的分层回答。

本篇和 11.1/11.3 的关系：11.3 造了轮子（Kernel），11.1 读了源码（vLLM 怎么组装的），本篇是你自己动手组装一个。

一、一个请求的完整旅程¶

用户发了一句 "介绍一下大语言模型"，Runtime 要做什么？

1. 接收请求
   ├── Tokenize: "介绍一下大语言模型" → [32789, 235285, ...]
   ├── 创建 Request 对象，状态 = Waiting
   └── 扔进 Scheduler 的队列

2. Scheduler 调度
   ├── 检查 KV Block 够不够（11.1 §5 的 BlockManager）
   ├── 决定这一步跑 Prefill 还是 Decode
   ├── 编译 cu_seqlens / block_table / slot_mapping（11.1 §7）
   └── 输出 BatchPlan

3. H2D + GPU 执行
   ├── 异步拷贝 Metadata 到 GPU（11.4 §10 的 Pinned Memory）
   ├── 调用 Backend（TensorRT / PyTorch / ONNX Runtime）
   ├── Attention 读 KV Cache（11.3 的 PagedAttention Kernel）
   ├── 写回新 KV 到 block_table[seq][last_block][slot]
   └── 输出 next_token_logits

4. Sampling + 回写状态
   ├── logits → token_id（Top-K / Top-P / Temperature）
   ├── Detokenize: token_id → "大语言"
   ├── 更新 Sequence.tokens, Sequence.output_len
   └── 如果遇到 EOS 或超长，标记 Request 为 Finished

5. 返回用户
   ├── Streaming: 立刻推送 "大语言"
   └── Non-streaming: 等全部生成完再返回

这个流程里，哪些是 11.1/11.3 已经讲过的，哪些是本篇要补的？

模块 11.1/11.3 做了什么 本篇补什么
Scheduler 读了 vLLM 的实现（11.1 §6） 怎么处理 Prefill/Decode 混合批，抢占策略怎么选
PagedAttention 写了 Kernel（11.3 §4-7） 怎么和 TensorRT 后端对接，Profile 怎么管理

二、Scheduler 的两难：Prefill 吃延迟，Decode 吃吞吐¶

问题¶

Prefill 是一个大 GEMM（[prompt_len, d] × [d, d]），Decode 是一堆小 GEMV（[1, d] × [d, d]）。它们不能放在同一个 Batch 里高效执行：

  • 如果一起跑，Prefill 的大 GEMM 会拖慢 Decode 的 TPOT（Time Per Output Token），用户看到的打字速度变慢
  • 如果分开跑，GPU 利用率低（Decode 的 Batch 太小，算力空置）

vLLM 的策略是 Chunked Prefill（11.1 §6 提到过，但没展开）：把长 Prompt 切成固定长度的 Chunk，每次只 Prefill 一个 Chunk，然后和 Decode 请求一起组批。

具体做法¶

class SchedulerConfig:
    max_num_seqs: int = 256          # 最大并发请求数
    max_model_len: int = 8192        # 模型支持的最大长度
    max_num_batched_tokens: int = 2048  # ← 关键：一个 Batch 的 token 总数上限
    chunked_prefill_enabled: bool = True
    chunked_prefill_size: int = 512   # 每次 Prefill 最多处理 512 token

调度逻辑（简化版，完整版见 11.1 §6）：

def schedule(self) -> BatchPlan:
    budget = self.max_num_batched_tokens  # 本次 Batch 还能容纳多少 token
    prefill_seqs = []
    decode_seqs = []

    # 1. 先填 Decode（优先保证已有请求的 TPOT）
    for seq in self.running:
        if budget < 1:
            break
        decode_seqs.append(seq)
        budget -= 1  # Decode 每个请求占 1 token

    # 2. 再填 Prefill（Chunk 化）
    for req in self.waiting:
        remaining = req.prompt_len - req.num_computed_tokens
        chunk_size = min(remaining, self.chunked_prefill_size, budget)
        if chunk_size < 16:  # 太小的 Chunk 不值得跑
            continue
        prefill_seqs.append((req, chunk_size))
        budget -= chunk_size
        if budget < 16:
            break

    return BatchPlan(prefill_seqs, decode_seqs)

为什么 max_num_batched_tokens=2048？

  • A100 80GB 的 GEMM 吞吐在 M=2048 左右达到峰值（> 280 TFLOPS）
  • 超过 2048 后，单步延迟会拖累 Decode 的 TPOT（从 20ms 涨到 40ms）
  • 小于 1024 时，GPU 利用率低（< 60%）

这个值需要根据你的硬件和模型 Profile 一遍：跑一组 M ∈ [512, 1024, 2048, 4096] 的 GEMM Benchmark，找到「吞吐 vs 延迟」的 Pareto 前沿。

Prefill/Decode 混合批的 Attention Mask¶

11.3 §6 实现的 PagedAttention 假设了「一个 Batch 内所有请求要么都是 Prefill，要么都是 Decode」。混合批需要改 Kernel 签名：

// 旧版（11.3 §6）
paged_attention(Q, K_cache, V_cache, block_table, cu_seqlens, is_prefill);

// 新版（支持混合批）
paged_attention(Q, K_cache, V_cache, block_table,
                cu_seqlens,        // [B+1]，Prefill 请求的前缀和
                decode_indices,    // [D]，Decode 请求在 Batch 中的位置
                num_prefill_tokens, num_decode_seqs);

Kernel 内部分支：

__global__ void paged_attention_mixed(/* ... */) {
    int tid = blockIdx.x * blockDim.x + threadIdx.x;

    if (tid < num_prefill_tokens) {
        // Prefill 路径：用 cu_seqlens 找到当前 token 属于哪个请求
        int seq_idx = binary_search(cu_seqlens, tid);
        // ... Flash Attention 的计算逻辑（11.3 §5）
    } else {
        // Decode 路径：tid - num_prefill_tokens 对应 decode_indices 中的索引
        int decode_idx = tid - num_prefill_tokens;
        int seq_idx = decode_indices[decode_idx];
        // ... PagedAttention 的单 token 计算逻辑（11.3 §6）
    }
}
