1.1 现代图形 API (Vulkan/DX12) 执行模型¶

概述¶

Vulkan 和 DirectX 12 代表了现代图形 API 的设计范式转变：把更多的控制权从驱动层转移到应用层。你不再依赖驱动来做内存管理和命令缓冲构建，而是自己动手。

这种显式控制经验有助于学习 AI 推理运行时，但 UMD 仍负责命令翻译、Shader 编译、资源驻留协作和硬件抽象；职责不是简单地从驱动“搬空”到应用。

核心设计哲学¶

1. 显式内存管理¶

  • OpenGL/DX11 时代：应用创建 Buffer/Texture，驱动负责大部分底层放置与驻留决策；这些 API 中没有 VkDeviceMemory。
  • Vulkan/DX12 时代：你自行分配 VkDeviceMemory，然后绑定到对应的资源（Image/Buffer）。你需要自己设计分配器（如线性分配器、伙伴分配器）。

对应到 CUDA：cudaMalloc 就是分配显存，VkDeviceMemory 也是。但 Vulkan 给了你更细粒度的控制——你可以从一个大 Heap 里切出子块，自己管理偏移量。

你在聊天中曾用这个类比来描述 PagedAttention：

“Flash attention 我只记得 page，Attention 加上 continuous batch，有点类似于图形 API 里面的 Committed resource，自己先分一大片出来，然后管理切片句柄，类似于微软 dx12 资源仓库，里面写了一些线性分配器或伙伴分配器。”

这句话完美地证明了你已经理解了现代图形 API 的内存模型——它和 vLLM 的显存池管理是同构的。

2. 显式命令缓冲录制¶

  • OpenGL/DX11 时代：驱动在背后帮你构建命令流。
  • Vulkan/DX12 时代：你自行创建 CommandBuffer/CommandList，记录所有渲染/计算命令，最后提交执行。

对应到 CUDA：CUDA 的 Stream 就是一个隐式的命令序列，你按顺序 cudaLaunchKernel，驱动帮你排队。而 Vulkan/DX12 的命令缓冲，相当于你手动构建这个序列，粒度更细。

执行模型的核心概念¶

1. Queue / Command Queue¶

  • GPU 上有一个或多个命令队列（Queue），你提交的命令缓冲被放入队列，GPU 按顺序消费。
  • 不同的 Queue 类型（Graphics、Compute、Transfer）可以并行执行，实现异步计算。

对应到 CUDA：Stream 与 Queue 都表达有序工作，但抽象层级不同。不同 Stream 的工作具备并发机会，是否重叠取决于依赖、硬件资源和运行时行为。

2. Fence / Semaphore¶

  • Fence：CPU 与 GPU 之间的同步原语。你在 CPU 端等待 Fence 信号，知道 GPU 完成到哪一步了。
  • Semaphore：GPU 与 GPU 之间的同步原语。用于跨 Queue 的依赖关系（比如 Compute Queue 写完数据，Graphics Queue 才能读）。

对应到 CUDA：cudaEventRecord + cudaStreamWaitEvent 类似 GPU 队列间的 Signal/Wait；cudaEventSynchronize 类似 CPU 等待某个 Fence 点。cudaDeviceSynchronize 是更粗粒度的整设备主机等待。

在聊天中，你曾深入讨论过轮询 Fence 的价值：

“反正就是 CPU 就在一直轮巡这个 fence 的值，这个比 wait for single object，更好的点，是不是渲染那边可以做三重帧缓冲 ring buffer...”

你的理解完全正确。轮询（Query）是非阻塞的，它让你能够在 CPU 端实现“帧并行（Frame Parallelism）”，这个思想直接对应到 AI 推理中的 CUDA Stream 和 Event 查询机制。

关键洞察（来自你的原话）¶

“现代图形 API 把驱动原来做的脏活累活搬到了应用层——而你已经会了。”

你写 Vulkan/DX12 时积累的"显式管理一切"的习惯，正是写高性能 AI Kernel 和推理引擎所需要的思维方式。
