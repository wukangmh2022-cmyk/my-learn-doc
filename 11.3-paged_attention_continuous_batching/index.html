11.3 PagedAttention 与 Continuous Batching：从 PyTorch 到 CUDA¶

这篇要造什么轮子¶

现代 LLM 推理引擎（vLLM、TensorRT-LLM、SGLang）的吞吐量优势，八成来自两个机制：

  • PagedAttention —— KV Cache 不再是每条序列一块连续显存，而是切成固定大小的页，按需分配；
  • Continuous Batching —— 批次不再是「凑齐一批一起跑完」，而是每一步都重新组批，谁完成谁走人，谁在排队谁补位。

这两个机制经常被分开讲，但它们其实是同一个问题的两半，后面第一节会说清楚为什么。

这篇的路线是：

第一步  PyTorch 把语义跑通       ← 能 print、能断点、能和「朴素版」对拍
第二步  落成可编译的 CUDA Kernel  ← 索引、Online Softmax、越界处理
第三步  进阶：换后端（11.6）      ← 同一套契约搬到 DX12 / TensorRT

为什么先写 PyTorch 再写 CUDA？ 因为分页最容易错的地方是索引算错，而索引错误在 CUDA 里的表现是「输出数值不对」或者干脆非法访存，定位成本极高；在 PyTorch 里，你可以把 slots 张量直接打印出来，一眼看出第 5 个 token 被映射到了哪个物理槽位。先把「对不对」解决掉，再解决「快不快」 —— 这两件事混在一起做，是新手写 Kernel 最大的时间黑洞。

本篇是「自己造轮子」的视角。想看工业框架怎么把这些模块组装起来，去 11.1 Nano-vLLM 导读；想看它怎么上生产，去 11.5 Runtime 与部署。

一、两个机制，一个根源¶

1. 静态批处理浪费了什么¶

假设同时来了 4 条请求，它们各自要生成的 token 数是 10、200、50、300。

传统的静态批处理（Static Batching）把它们凑成一个 batch 一起跑，跑到最长的那条结束为止：

step:   0 ......... 10 ......... 50 ......... 200 ......... 300
req A   ████████████│                                        ← 第 10 步就完事了，之后一直占着位置
req B   ████████████████████████████████████████│            ← 第 200 步结束
req C   ████████████████████████│                            ← 第 50 步结束
req D   ████████████████████████████████████████████████████ ← 第 300 步结束

算一下有效利用率：

\[ \frac{10 + 200 + 50 + 300}{4 \times 300} = \frac{560}{1200} \approx 47\% \]

一半以上的 batch 槽位在算空气。 而且这还是乐观估计——真实流量里请求长度的差异比这个大得多。

Continuous Batching 的做法很直白：每一步结束后重新组批。A 在第 10 步完成就立刻退出，把位置让给队列里等着的新请求。理想情况下 batch 始终是满的。

2. 但是，位置腾出来了，显存呢？¶

这就是关键的一步推理，也是很多教程跳过的地方：

A 退出了，它占的 KV Cache 显存必须能立刻还给 D 或者新来的请求。

如果 KV Cache 是「每条序列预先分配一块连续显存」，这件事做不到，或者做得很难看：

  • 预分配多少？ 你不知道请求会生成多长。按 max_model_len = 4096 预留？那就是按最坏情况买单。
  • 回收后能用吗？ A 释放的那块能装 4096 token，新请求可能只需要 200 token 的空间——外部碎片开始积累。
  • 不够了怎么办？ 序列长到超出预留，就得重新分配一块更大的再把老 KV 拷过去。在 decode 的关键路径上做显存搬迁，灾难。

来算笔账。用 11.2 里那个 8B 模型（36 层，\(H_{kv}=8\)，\(D=128\)，FP16），每个 token 的 KV Cache 是 144 KiB。假设一张卡上有 40 GiB 留给 KV Cache，请求的平均实际长度是 500 token：

方案 每条序列占用 40 GiB 能装几条
按 max_len=4096 预分配 576 MiB 71 条
分页，按实际用量 70 MiB 582 条

8 倍的并发差距。 而 decode 是访存受限的，batch 越大，读一遍权重能摊给越多请求 —— 这 8 倍几乎直接兑换成吞吐量。

3. 所以它们必须一起做¶

把这条链子串起来：

想提高吞吐 → 需要大 batch
需要大 batch → 需要请求随时进出（Continuous Batching）
请求随时进出 → 需要显存随时分配和释放，粒度要细
显存细粒度动态分配 → 必须分页（PagedAttention）

反过来也成立：只做分页不做连续批处理，省下的显存没人用；只做连续批处理不做分页，位置腾出来了显存却卡住。 这就是为什么 vLLM 那篇论文把两者放在一起讲，也是为什么这一篇要合并处理。

二、PagedAttention 的核心：一次索引间接¶

1. 借来的思想¶

操作系统的虚拟内存干的就是这件事：进程看到的是连续的虚拟地址空间，实际物理页散落在内存各处，中间隔着一张页表。

PagedAttention 把同一招用在 KV Cache 上：

操作系统 PagedAttention
虚拟地址 逻辑 token 位置（第几个 token）
页表 Block Table（每条序列一张）
物理页 KV Cache 大 Buffer 里的一个 Block
页大小 4 KiB block_size 个 token（vLLM 默认 16）

但必须说清楚边界：这是应用层的逻辑分页，跟 MMU、跟 CUDA 的虚拟内存管理（cuMemCreate / cuMemMap）没有关系。我们只是 cudaMalloc 了一大块连续显存，然后自己在软件层面把它切成等长的片，用整数下标当"页号"。没有任何硬件地址翻译参与——所有的间接寻址都是 Kernel 里的一次数组访问。

搞混这一点会导致两种错误理解：以为需要 Sparse/Tiled Resource 之类的硬件特性（不需要），或者以为间接寻址是免费的（不是，它是一次真实的内存访问）。

2. 三层地址¶

逻辑层    序列 s 的第 t 个 token                    ← 模型看到的
   ↓      logical_block = t / block_size
   ↓      offset        = t % block_size
页表层    block_table[s][logical_block] = 物理页号 p  ← 一次间接
   ↓
物理层    slot = p * block_size + offset             ← 显存里的实际位置

写成一行公式：

\[ \text{slot}(s, t) = \text{blockTable}[s]\!\left[\left\lfloor t / B \right\rfloor\right] \times B + (t \bmod B) \]

其中 \(B\) 是 block_size。整篇文章的技术核心就是这一行。 后面所有的 PyTorch 代码、CUDA Kernel、DX12 Shader，都只是这个公式在不同语言里的写法。

3. 为什么这样就解决了问题¶

序列从 4 个 token 长到 5 个（block_size=4）：

之前: block_table = [7]          物理页 7 装了 token 0..3
之后: block_table = [7, 2]       追加一页，token 4 落在物理页 2 的第 0 格

页 7 里的 KV 一个字节都没动。 没有搬迁、没有重新分配、没有连续空间要求——只是往一个 Python list 里 append 了一个整数。

序列结束时，把 [7, 2] 里的页号还回空闲池，立刻就能被别的请求拿走。外部碎片消失了，因为所有页大小相同，任何空闲页都能满足任何请求。

代价是内部碎片：最后一页平均浪费半页。block_size=16 时是 8 个 token ≈ 1.1 MiB —— 相比省下的 500 MiB，可以忽略。

4. block_size 怎么选¶

这是个真实的三方权衡：

block_size 内部碎片 页表大小 Kernel 效率
1 零浪费 每 token 一项，页表本身变大 每个 token 都要查一次表，间接寻址开销最大
16（vLLM 默认） ≤15 token 适中 查一次表能连续读 16 个 token，访存合并友好
256 ≤255 token ≈ 36 MiB/序列 很小 合并最好，但短请求浪费惊人

选择逻辑是：block_size 应该大到让 Kernel 一次间接能换来一段值得合并访问的连续数据，小到内部碎片相对请求平均长度可以忽略。 平均长度 500 token 时，16 浪费 1.6%，256 浪费 25% —— 前者显然更合理。

三、用 PyTorch 把语义跑通¶

1. KV Cache 的物理布局¶

先定死张量形状，后面所有代码都依赖它：

# k_cache, v_cache: [num_blocks, block_size, num_kv_heads, head_size]
#                     └─物理页号   └─页内偏移   └─GQA 的 KV 头   └─每个头的维度

为什么维度是这个顺序？ 因为最后两维 [num_kv_heads, head_size] 是一个 token 的完整 KV，必须连续 —— Kernel 拿到一个 slot 后要一次性把这段读走。而前两维 [num_blocks, block_size] 合起来正好是"第几个槽位"，所以可以直接 reshape 成一维：

num_blocks, block_size = k_cache.shape[0], k_cache.shape[1]
k_flat = k_cache.view(num_blocks * block_size, num_kv_heads, head_size)
#                     └─ 这一维就是 slot，从 0 到 num_blocks*block_size-1

这个 view 是零拷贝的（内存布局本来就是这样），但它让第二节那个公式可以直接当索引用。记住这个 flatten，CUDA Kernel 里也是同一套算术。

2. BlockManager：管页号，不管显存¶

class BlockManager:
    """只管理整数页号的分配与回收，完全不碰张量。

    这个分离很重要：显存是启动时一次性分配好的一整块，
    运行期变化的只有「哪个页号归谁」这个映射关系。
    """

    def __init__(self, num_blocks: int, block_size: int):
        self.block_size = block_size
        self.free = list(range(num_blocks))   # 空闲页号
        self.ref = [0] * num_blocks           # 引用计数，为 Prefix Cache 预留

    def allocate(self) -> int:
        if not self.free:
            raise MemoryError("KV block pool exhausted")   # 调度器要能接住这个异常
        block = self.free.pop()
        self.ref[block] = 1
        return block

    def release(self, block: int) -> None:
        assert self.ref[block] > 0, f"double free on block {block}"
        self.ref[block] -= 1
        if self.ref[block] == 0:
            self.free.append(block)

    def ensure_capacity(self, block_table: list[int], num_tokens: int) -> None:
        """保证 block_table 能装下 num_tokens 个 token，不够就追加页。"""
        needed = (num_tokens + self.block_size - 1) // self.block_size
        while len(block_table) < needed:
            block_table.append(self.allocate())

    def free_request(self, block_table: list[int]) -> None:
        for block in block_table:
            self.release(block)
        block_table.clear()

    @property
    def num_free(self) -> int:
        return len(self.free)

三个设计细节值得说：

  • allocate() 抛异常而不是返回 None。 显存耗尽是调度器必须处理的正常业务状态（触发抢占），不是程序错误。让它显式抛出，调度器 try/except 接住，比返回 None 之后一路 NoneType 报错清楚得多。
  • 引用计数现在用不上，但要留。 加 Prefix Cache（多条请求共享相同的 prompt 前缀）时，同一个物理页会被多条序列引用，那时 release 必须减到 0 才真正回收。现在写成 ref 而不是简单的 in_use 布尔值，是为了那一天不用重构。
  • ensure_capacity 用向上取整而不是「满了才加」。 因为调度器需要在执行之前就知道显存够不够，不能等 Kernel 跑到一半发现越界。

先测它，别急着跑模型：

bm = BlockManager(num_blocks=12, block_size=4)
table: list[int] = []

bm.ensure_capacity(table, 1);   assert len(table) == 1    # 1 个 token → 1 页
bm.ensure_capacity(table, 4);   assert len(table) == 1    # 正好装满，不追加
bm.ensure_capacity(table, 5);   assert len(table) == 2    # 溢出 1 个 → 追加

before = bm.num_free
bm.free_request(table)
assert bm.num_free == before + 2                          # 分配与释放对称

第二行那个 ensure_capacity(table, 4) 断言最容易挂 —— 如果你把向上取整写成 num_tokens // block_size + 1，边界正好在这里错。

3. 分页版 Attention：核心就一行¶

import torch

def paged_attention(
    q,             # [num_seqs, num_q_heads, head_size]
    k_cache,       # [num_blocks, block_size, num_kv_heads, head_size]
    v_cache,       # 同上
    block_tables,  # [num_seqs, max_blocks_per_seq]  int32，未用的槽填 -1
    context_lens,  # [num_seqs]                      int32
):
    num_seqs, num_q_heads, head_size = q.shape
    num_blocks, block_size, num_kv_heads, _ = k_cache.shape
    group = num_q_heads // num_kv_heads          # GQA 组大小
    scale = head_size ** -0.5

    k_flat = k_cache.view(num_blocks * block_size, num_kv_heads, head_size)
    v_flat = v_cache.view(num_blocks * block_size, num_kv_heads, head_size)

    out = torch.empty_like(q)
    for s in range(num_seqs):
        T = int(context_lens[s])
        t = torch.arange(T, device=q.device)

        # ↓↓↓ 这三行就是 PagedAttention 的全部 ↓↓↓
        logical_block = t // block_size
        offset        = t %  block_size
        slots = block_tables[s, logical_block] * block_size + offset   # [T]
        # ↑↑↑ 逻辑位置 → 物理槽位，一次间接 ↑↑↑

        k = k_flat[slots]        # [T, num_kv_heads, head_size]  ← gather
        v = v_flat[slots]

        for h in range(num_q_heads):
            kv_h = h // group                       # GQA：多个 Q 头共享一个 KV 头
            scores = (k[:, kv_h] @ q[s, h]) * scale # [T]
            probs  = torch.softmax(scores, dim=0)   # PyTorch 内部已做减 max
            out[s, h] = probs @ v[:, kv_h]
    return out

把 slots 打印出来，这是理解分页最快的方式：

>>> block_tables[0] = [7, 2, -1];  context_lens[0] = 6;  block_size = 4
>>> slots
tensor([28, 29, 30, 31,  8,  9])
#       └── 物理页 7 的 4 个格子 ──┘  └页 2 的前 2 格┘

逻辑上连续的 token 0–5，物理上落在两段完全不挨着的显存里。而 Attention 的数学一个字没改 —— 它看到的仍然是一个 [T, D] 的 K 矩阵。这就是页表的价值：把「数据在哪」和「数据是什么」彻底解耦。

4. 和朴素版对拍：唯一可信的验证¶

上面那段代码看起来对，但 //、%、* 三个运算里任何一个写错，结果都还是个「形状正确的张量」。所以必须和一个绝对朴素的版本比：

def attention_contiguous(q, k, v, context_lens):
    """朴素版：K/V 就是普通的连续张量 [num_seqs, max_T, num_kv_heads, head_size]。
    结构上刻意和分页版完全不同 —— 这样同一个索引 bug 不会在两边同时出现。
    """
    num_seqs, num_q_heads, head_size = q.shape
    group = num_q_heads // k.shape[2]
    scale = head_size ** -0.5
    out = torch.empty_like(q)
    for s in range(num_seqs):
        T = int(context_lens[s])
        for h in range(num_q_heads):
            kv_h = h // group
            scores = (k[s, :T, kv_h] @ q[s, h]) * scale
            out[s, h] = torch.softmax(scores, dim=0) @ v[s, :T, kv_h]
    return out


def test_paging_is_transparent():
    torch.manual_seed(0)
    num_seqs, Hq, Hkv, D = 2, 4, 2, 8
    block_size, num_blocks, max_blocks = 4, 12, 3

    context_lens = torch.tensor([6, 3], dtype=torch.int32)
    # 故意用不连续、不递增的物理页 —— 写成连续 offset 的话这里必挂
    block_tables = torch.tensor([[7, 2, -1],
                                 [5, -1, -1]], dtype=torch.int32)

    q = torch.randn(num_seqs, Hq, D, dtype=torch.float64)
    k_cache = torch.randn(num_blocks, block_size, Hkv, D, dtype=torch.float64)
    v_cache = torch.randn(num_blocks, block_size, Hkv, D, dtype=torch.float64)

    # 把分页数据「摊平」成连续布局，喂给朴素版
    max_T = int(context_lens.max())
    k_lin = torch.zeros(num_seqs, max_T, Hkv, D, dtype=torch.float64)
    v_lin = torch.zeros_like(k_lin)
    for s in range(num_seqs):
        for t in range(int(context_lens[s])):
            b, o = block_tables[s, t // block_size], t % block_size
            k_lin[s, t] = k_cache[b, o]
            v_lin[s, t] = v_cache[b, o]

    ref  = attention_contiguous(q, k_lin, v_lin, context_lens)
    got  = paged_attention(q, k_cache, v_cache, block_tables, context_lens)
    torch.testing.assert_close(got, ref, rtol=0, atol=1e-12)

几个刻意的选择：

  • 用 float64，容差设 1e-12。 这一步验证的是索引逻辑，不是数值精度。用 FP32 跑，容差得放到 1e-5，那时候「索引错了一个 token」和「浮点误差」就区分不开了。精度问题留到 CUDA 那一步再单独处理。
  • 页表写成 [[7,2,-1],[5,-1,-1]]。 非连续、非递增、还带 padding。如果哪天有人把 slots 简化成 t + s * max_T 这种「反正也能跑」的写法，这个测试立刻挂。
  • 摊平那段循环故意写得很笨。 它是 ground truth 的一部分，笨到不可能写错才有价值。

四、Continuous Batching：调度器在决定什么¶

1. 先看清 Prefill 和 Decode 的形状差异¶

这是理解调度的前提：

Prefill Decode
一次处理的 token 数 整个 prompt，几百到几千 每条序列 1 个
计算特征 矩阵 × 矩阵，算力受限 矩阵 × 向量，访存受限
一步耗时 长（正比于 prompt 长度） 短且稳定
KV Cache 一次写入 T 个 token 每步追加 1 个

关键推论：Decode 步的耗时几乎和 batch 大小无关（因为瓶颈是读权重和 KV，而权重只读一次）。所以 batch 越大，每 token 的成本越低 —— 这就是连续批处理拼命想把 batch 填满的原因。

而 Prefill 是算力受限的，塞太多进去只会线性变慢。所以调度器对两者的预算是分开算的。

2. 一次 step() 要做的决策¶

┌─ 有等待中的请求 且 显存够 且 prefill 预算没用完？
│      → 优先跑 Prefill，把新请求拉进 running 集合
│
└─ 否则跑 Decode：
       running 集合里每条序列各生成 1 个 token
       ├─ 谁需要新页？ → ensure_capacity
       ├─ 显存不够了？ → 抢占：踢掉最晚来的，释放它的页
       └─ 谁生成了 EOS 或达到长度上限？ → 完成，释放页，让位

为什么优先 Prefill？ 因为新请求不做 Prefill 就进不了 running 集合，batch 就填不满。这是个「先投资再收租」的关系。但也不能无脑优先——一个 8000 token 的 prompt 会把这一步拖到几百毫秒，让所有正在 decode 的请求卡住（队头阻塞）。工业框架的解法是 Chunked Prefill：把长 prompt 切成几段，每步只做一段，和 decode 混着跑。

3. 抢占：显存不够时怎么办¶

这是连续批处理里最容易被忽略、也最能体现设计的一环。

序列在 decode 过程中会不断变长，也就不断需要新页。总会有一步，某条序列要新页而池子空了。 这时候有两个选择：

策略 做法 代价 适用
Recompute 直接丢掉被抢占序列的所有 KV，把它退回等待队列，将来重新 Prefill 浪费已算过的 Prefill 序列还短时最划算
Swap 把它的 KV 页拷到 CPU 内存，之后再拷回来 占用 PCIe 带宽和 CPU 内存 序列很长、重算太贵时

选谁被抢占？最晚进来的那条（LIFO）。因为它算过的 KV 最少，丢掉损失最小；而且这样能保证先来的请求不会被反复抢占饿死。

4. 一个能跑的最小调度器¶

from dataclasses import dataclass, field
from collections import deque

@dataclass
class Sequence:
    seq_id: int
    prompt_len: int
    max_new_tokens: int
    num_tokens: int = 0                       # 已在 KV Cache 里的 token 数
    num_generated: int = 0
    finished: bool = False
    block_table: list[int] = field(default_factory=list)

    @property
    def needs_prefill(self) -> bool:
        return self.num_tokens == 0


class Scheduler:
    def __init__(self, bm: BlockManager, max_batch: int, prefill_token_budget: int):
        self.bm = bm
        self.max_batch = max_batch
        self.prefill_token_budget = prefill_token_budget
        self.waiting: deque[Sequence] = deque()
        self.running: list[Sequence] = []

    def add(self, seq: Sequence) -> None:
        self.waiting.append(seq)

    def schedule(self) -> tuple[list[Sequence], bool]:
        """返回 (这一步要跑的序列, 是否是 prefill 批)。"""
        # ---- 优先 Prefill：把等待队列里的请求拉进来 ----
        batch, budget = [], self.prefill_token_budget
        while self.waiting and len(self.running) + len(batch) < self.max_batch:
            seq = self.waiting[0]
            if seq.prompt_len > budget:
                break                          # 这一步塞不下了，下一步再说
            try:
                self.bm.ensure_capacity(seq.block_table, seq.prompt_len)
            except MemoryError:
                break                          # 显存不够，先不接新请求
            self.waiting.popleft()
            seq.num_tokens = seq.prompt_len
            budget -= seq.prompt_len
            batch.append(seq)
        if batch:
            self.running.extend(batch)
            return batch, True

        # ---- 否则 Decode：running 里每条各出 1 个 token ----
        for seq in list(self.running):
            try:
                self.bm.ensure_capacity(seq.block_table, seq.num_tokens + 1)
            except MemoryError:
                if not self._preempt():        # 腾不出来了，这一步只能少跑一条
                    self.running.remove(seq)
                    self.waiting.appendleft(seq)
                    self._recompute(seq)
                    continue
                self.bm.ensure_capacity(seq.block_table, seq.num_tokens + 1)
        return list(self.running), False

    def _preempt(self) -> bool:
        """抢占最晚进来的序列（Recompute 策略），成功返回 True。"""
        if len(self.running) <= 1:
            return False                       # 只剩一条，抢占它没意义
        victim = self.running.pop()            # LIFO：最后进来的先出去
        self._recompute(victim)
        self.waiting.appendleft(victim)
        return True

    def _recompute(self, seq: Sequence) -> None:
        """丢弃 KV，退回等待队列。下次调度时重新 Prefill。"""
        self.bm.free_request(seq.block_table)
        seq.num_tokens = 0
        seq.num_generated = 0                  # 注意：已生成的 token 要并进 prompt

    def postprocess(self, batch: list[Sequence], next_tokens, eos_id: int) -> None:
        """模型跑完之后提交状态。这一步必须是原子的。"""
        for seq, token in zip(batch, next_tokens):
            seq.num_tokens += 1
            seq.num_generated += 1
            if token == eos_id or seq.num_generated >= seq.max_new_tokens:
                seq.finished = True
                self.bm.free_request(seq.block_table)     # 立刻还显存
                self.running.remove(seq)

几个必须讲清楚的点：

  • ensure_capacity 在执行之前调用，不是之后。 调度器必须先确认「这一步的显存够」，才能把批交给模型。等 Kernel 跑到一半发现页表里是 -1，那就是非法访存。
  • postprocess 是事务提交点。 模型跑完之前，序列状态不能变——因为这一步可能失败、可能被取消。把「推进状态」和「决定跑什么」分成两个函数，是所有推理引擎的共同结构。
  • 完成的序列立刻 free_request。 这一行就是连续批处理省显存的地方。晚一步释放，下一步就少一个可用页。
  • _recompute 里 num_generated = 0 有个坑：真实实现中，被抢占序列已经生成的 token 必须并入新的 prompt 重新 Prefill，否则重启后会丢输出。这份最小实现为了聚焦调度骨架省略了拼接逻辑，上生产必须补上。

5. 走一遍 trace¶

block_size=4、池子 6 页（24 token）、max_batch=3：

step 1  waiting=[A(prompt=6), B(prompt=3)]  running=[]
        → Prefill A：ensure_capacity(6) → 需 2 页 → table=[0,1]，剩 4 页
        → Prefill B：ensure_capacity(3) → 需 1 页 → table=[2],   剩 3 页
        执行 Prefill 批 [A, B]

step 2  running=[A(6), B(3)]
        → A 要第 7 个 token：⌈7/4⌉=2 页，已有 2 页，不用加
        → B 要第 4 个 token：⌈4/4⌉=1 页，已有 1 页，不用加
        执行 Decode 批 [A, B]                      ← 这一步零分配，很常见

step 3  running=[A(7), B(4)]
        → A 要第 8 个：还是 2 页，够
        → B 要第 5 个：⌈5/4⌉=2 页 → 追加 1 页 → table=[2,3]，剩 2 页
        执行 Decode 批 [A, B]

step 4  B 生成 EOS
        → postprocess：B.finished，free_request([2,3]) → 剩 4 页
        → C 在等待队列里，下一步就能被 Prefill 进来      ← 位置和显存同时腾出

注意 step 2：大多数 decode 步是不分配显存的，只有跨越 block_size 边界那一步才追加。block_size 越大，分配越稀疏——这是选它的另一个考量。

五、落到 CUDA：完整的 PagedAttention Kernel¶

PyTorch 版验证过了，现在把它变成一个真 Kernel。这一节的代码是可以直接编译的。

1. 先想清楚 Grid 怎么映射¶

Decode 时的并行度来源有三个：num_seqs、num_q_heads、head_size。Context 维 \(T\) 是要被归约掉的，不能直接并行。

最直接的映射：

grid  = (num_q_heads, num_seqs)     一个 CTA 负责一条序列的一个 Q 头
block = 128 线程 = 4 个 warp        沿 T 维流式处理，沿 D 维并行

一个 CTA 内的分工：

  • QK 阶段：4 个 warp 各负责 1 个 token，warp 内 32 个 lane 沿 \(D\) 维分摊点积，再用 shuffle 归约。这样 lane 读的是连续地址，访存合并。
  • PV 阶段：128 个线程沿 \(D\) 维分摊输出累加器。

因为一个 CTA 一次只处理 4 个 token，\(T=4096\) 要循环 1024 轮。这是个清晰但不是最优的结构 —— vLLM 的 Kernel 会让每个 warp 一次处理多个 token 来提高 ILP。这里优先可读性，性能优化留给 Profiler 引导（见 11.4）。

2. Kernel 代码¶

#include <cuda_runtime.h>
#include <math_constants.h>

#define WARP_SIZE 32
#define FULL_MASK 0xffffffffu

__inline__ __device__ float warpReduceSum(float v) {
#pragma unroll
    for (int offset = WARP_SIZE / 2; offset > 0; offset >>= 1)
        v += __shfl_down_sync(FULL_MASK, v, offset);
    return v;   // 结果在 lane 0
}

// out         [num_seqs, num_q_heads, HEAD_SIZE]
// q           [num_seqs, num_q_heads, HEAD_SIZE]
// k_cache     [num_blocks, block_size, num_kv_heads, HEAD_SIZE]
// v_cache     同上
// block_table [num_seqs, max_blocks_per_seq]   int32
// ctx_lens    [num_seqs]                       int32
template <int HEAD_SIZE, int NUM_THREADS>
__global__ void paged_attention_decode(
        float* __restrict__       out,
        const float* __restrict__ q,
        const float* __restrict__ k_cache,
        const float* __restrict__ v_cache,
        const int*   __restrict__ block_tables,
        const int*   __restrict__ ctx_lens,
        int   num_q_heads,
        int   num_kv_heads,
        int   block_size,
        int   max_blocks_per_seq,
        float scale)
{
    constexpr int NUM_WARPS = NUM_THREADS / WARP_SIZE;

    const int q_head = blockIdx.x;
    const int seq    = blockIdx.y;
    const int tid    = threadIdx.x;
    const int warp   = tid / WARP_SIZE;
    const int lane   = tid % WARP_SIZE;

    const int ctx_len = ctx_lens[seq];
    const int kv_head = q_head / (num_q_heads / num_kv_heads);   // GQA 映射
    const int* block_table = block_tables + (size_t)seq * max_blocks_per_seq;

    __shared__ float q_s[HEAD_SIZE];        // 当前 Q 头，整个 CTA 复用
    __shared__ float acc_s[HEAD_SIZE];      // 未归一化的输出累加器
    __shared__ float logit_s[NUM_WARPS];    // 本轮 NUM_WARPS 个 token 的 score

    // ---- 载入 Q（顺便把 scale 预乘进去，省掉后面每次点积的一次乘法）----
    for (int d = tid; d < HEAD_SIZE; d += NUM_THREADS) {
        q_s[d]   = q[((size_t)seq * num_q_heads + q_head) * HEAD_SIZE + d] * scale;
        acc_s[d] = 0.0f;
    }
    __syncthreads();

    if (ctx_len <= 0) {                     // 防御：空序列不该进来，但别让它写出 NaN
        for (int d = tid; d < HEAD_SIZE; d += NUM_THREADS)
            out[((size_t)seq * num_q_heads + q_head) * HEAD_SIZE + d] = 0.0f;
        return;
    }

    // ---- Online Softmax 的三个运行状态 ----
    // running_max / denom 每个线程各存一份，但所有线程算出的值完全相同，
    // 因为它们读的是同一份 logit_s。这样就不需要为它们再做跨线程归约。
    float running_max = -CUDART_INF_F;
    float denom       = 0.0f;

    for (int base = 0; base < ctx_len; base += NUM_WARPS) {
        // ================= QK：每个 warp 负责 1 个 token =================
        const int token = base + warp;
        if (token < ctx_len) {
            // ↓↓↓ 第二节那行公式，在 CUDA 里的样子 ↓↓↓
            const int logical_block = token / block_size;
            const int offset        = token % block_size;
            const int phys_block    = block_table[logical_block];
            const size_t slot       = (size_t)phys_block * block_size + offset;
            const float* k_ptr = k_cache + (slot * num_kv_heads + kv_head) * HEAD_SIZE;
            // ↑↑↑ 分页的全部开销：多读一个 int，多做两次整数运算 ↑↑↑

            float partial = 0.0f;
            for (int d = lane; d < HEAD_SIZE; d += WARP_SIZE)   // 跨步 → 访存合并
                partial += q_s[d] * k_ptr[d];
            partial = warpReduceSum(partial);
            if (lane == 0) logit_s[warp] = partial;
        } else if (lane == 0) {
            logit_s[warp] = -CUDART_INF_F;   // 尾部 padding：权重会算成 0
        }
        __syncthreads();                     // logit_s 写完才能读

        // ================= Online Softmax 状态更新 =================
        float tile_max = -CUDART_INF_F;
#pragma unroll
        for (int w = 0; w < NUM_WARPS; ++w)
            tile_max = fmaxf(tile_max, logit_s[w]);

        const float new_max   = fmaxf(running_max, tile_max);
        // 首轮 running_max = -inf，expf(-inf) = 0，正好把初始的 0 状态清成 0，不必特判
        const float correction = __expf(running_max - new_max);

        for (int d = tid; d < HEAD_SIZE; d += NUM_THREADS)
            acc_s[d] *= correction;          // 每个线程只碰自己那几个 d，无竞争
        denom *= correction;

        // ================= PV：把这一轮的 token 累加进去 =================
        for (int w = 0; w < NUM_WARPS; ++w) {
            const int t = base + w;
            if (t >= ctx_len) break;         // 所有线程同时 break，不产生分歧

            const float weight = __expf(logit_s[w] - new_max);
            denom += weight;

            const int logical_block = t / block_size;
            const int offset        = t % block_size;
            const size_t slot = (size_t)block_table[logical_block] * block_size + offset;
            const float* v_ptr = v_cache + (slot * num_kv_heads + kv_head) * HEAD_SIZE;

            for (int d = tid; d < HEAD_SIZE; d += NUM_THREADS)
                acc_s[d] += weight * v_ptr[d];
        }
        running_max = new_max;
        __syncthreads();                     // 下一轮要覆盖 logit_s
    }

    // ---- 全程唯一一次归一化 ----
    for (int d = tid; d < HEAD_SIZE; d += NUM_THREADS)
        out[((size_t)seq * num_q_heads + q_head) * HEAD_SIZE + d] = acc_s[d] / denom;
}

启动方式：

void launch_paged_attention(
        float* out, const float* q, const float* k_cache, const float* v_cache,
        const int* block_tables, const int* ctx_lens,
        int num_seqs, int num_q_heads, int num_kv_heads, int head_size,
        int block_size, int max_blocks_per_seq, cudaStream_t stream)
{
    const dim3 grid(num_q_heads, num_seqs);
    const float scale = rsqrtf((float)head_size);
    // head_size 是编译期常量 → dispatch 到对应特化（见 11.2 第九节）
    switch (head_size) {
    case 64:
        paged_attention_decode<64, 128><<<grid, 128, 0, stream>>>(
            out, q, k_cache, v_cache, block_tables, ctx_lens,
            num_q_heads, num_kv_heads, block_size, max_blocks_per_seq, scale);
        break;
    case 128:
        paged_attention_decode<128, 128><<<grid, 128, 0, stream>>>(
            out, q, k_cache, v_cache, block_tables, ctx_lens,
            num_q_heads, num_kv_heads, block_size, max_blocks_per_seq, scale);
        break;
    default:
        // 生产环境这里要回退到通用实现，而不是静默出错
        break;
    }
}

3. 三个容易写错的地方¶

同步点只有两个，而且都必要。

__syncthreads() #1  在 QK 写完 logit_s 之后    → 保证所有线程读到完整的 logit_s
__syncthreads() #2  在循环末尾                → 保证 PV 读完 logit_s，才被下一轮覆盖

漏掉 #2 是最隐蔽的 bug：小 ctx_len 时可能碰巧不出错（只有一轮循环），长上下文才随机出现数值偏差。

acc_s[d] *= correction 为什么不需要同步？ 因为线程 tid 只碰 d = tid, tid+128, tid+256, ...，各线程的 d 集合互不相交，缩放和累加都是自己读自己写。共享内存不等于必须同步——只有跨线程的读写依赖才需要。

denom 为什么不用归约？ 因为每个线程都读同一份 logit_s、执行同样的加法序列，算出的 denom 逐位相同。用一个冗余计算换掉一次 block 级归约，划算。

4. KV Store：新 token 写到哪¶

Decode 每一步都会产生新的 K/V，得写进 cache 对应的槽位。调度器算好 slot_mapping 递给 Kernel：

// k_new / v_new: [num_tokens, num_kv_heads, HEAD_SIZE]
// slot_mapping:  [num_tokens]，-1 表示 padding，不写
__global__ void store_kv_cache(
        float* __restrict__       k_cache,
        float* __restrict__       v_cache,
        const float* __restrict__ k_new,
        const float* __restrict__ v_new,
        const int*   __restrict__ slot_mapping,
        int num_kv_heads,
        int head_size)
{
    const int token = blockIdx.x;
    const int slot  = slot_mapping[token];
    if (slot < 0) return;                       // padding，跳过

    const int n = num_kv_heads * head_size;     // 一个 token 的 KV 元素数
    const float* src_k = k_new   + (size_t)token * n;
    const float* src_v = v_new   + (size_t)token * n;
    float*       dst_k = k_cache + (size_t)slot  * n;
    float*       dst_v = v_cache + (size_t)slot  * n;

    for (int i = threadIdx.x; i < n; i += blockDim.x) {
        dst_k[i] = src_k[i];
        dst_v[i] = src_v[i];
    }
}

Host 侧算 slot_mapping，和第二节的公式一模一样：

def build_slot_mapping(seqs, block_size):
    """每条序列的下一个待写 token → 物理槽位。"""
    slots = []
    for seq in seqs:
        t = seq.num_tokens                       # 新 token 的逻辑位置
        block = seq.block_table[t // block_size]
        slots.append(block * block_size + t % block_size)
    return torch.tensor(slots, dtype=torch.int32, device="cuda")

这里最常见的 bug 是差一：新 token 的逻辑位置是 num_tokens（还没自增），不是 num_tokens - 1。写错的话，每一步都会覆盖掉上一个 token 的 KV——而输出看起来只是"质量差了点"，很难联想到索引。

5. 和 PyTorch 版对齐¶

def test_cuda_matches_torch():
    torch.manual_seed(0)
    num_seqs, Hq, Hkv, D = 2, 4, 2, 128
    block_size, num_blocks, max_blocks = 16, 64, 8

    ctx_lens     = torch.tensor([37, 5], dtype=torch.int32, device="cuda")  # 非整块
    block_tables = torch.full((num_seqs, max_blocks), -1, dtype=torch.int32)
    block_tables[0, :3] = torch.tensor([9, 1, 40])   # 乱序、不连续
    block_tables[1, :1] = torch.tensor([17])
    block_tables = block_tables.cuda()

    q       = torch.randn(num_seqs, Hq, D, device="cuda")
    k_cache = torch.randn(num_blocks, block_size, Hkv, D, device="cuda")
    v_cache = torch.randn(num_blocks, block_size, Hkv, D, device="cuda")

    ref = paged_attention(q, k_cache, v_cache, block_tables, ctx_lens)   # 第三节的 PyTorch 版
    got = my_ext.paged_attention(q, k_cache, v_cache, block_tables, ctx_lens, block_size)

    torch.testing.assert_close(got, ref, rtol=2e-3, atol=2e-3)

测试数据的每一处都在抓特定 bug：

设计 抓什么
ctx_len=37，block_size=16 37 = 2×16+5，最后一块只用了 5 格。抓尾部越界和 padding 处理
ctx_len=5 < block_size 只占一块的短序列。抓「至少一块」的边界
页表 [9, 1, 40] 乱序 抓把 slot 写成 t 或 logical_block*block_size+offset（漏了查表）
两条序列长度不同 抓 batch 维度上下标串台
容差 2e-3 FP32 + __expf 快速数学的合理范围。收紧到 1e-6 会假报警

注意容差从 PyTorch 那步的 1e-12 放宽到了 2e-3。因为这一步验证的是 Kernel 实现，误差里包含了 __expf 的近似、不同的累加顺序等真实数值差异。分两步、用两个容差，才能把「索引错了」和「精度差异」分开——这正是先写 PyTorch 版的价值所在。

六、Bug 症状速查¶

分页系统的 bug 有很强的规律性，症状能直接指向原因：

症状 大概率原因
非法访存 / illegal memory access 页表里读到了 -1（padding），或 ctx_len 与页表长度不匹配
输出全是 NaN denom 为 0（ctx_len=0），或 Online Softmax 里 -inf - -inf
短序列对、长序列错 跨 block_size 边界的地方算错，或漏了循环末尾的 __syncthreads()
第一个 token 对、后面全错 slot_mapping 差一，新 KV 覆盖了旧的
结果对但和"页表顺序"相关 根本没查表，直接用了连续 offset。换个乱序页表就现形
偶发错误，重跑就好 释放的页被立刻重新分配，但上一步的 Kernel 还没跑完（缺 stream 同步）
显存持续增长直到 OOM free_request 漏调用，或抢占路径上没释放

最后两条特别值得展开：

页的释放必须晚于使用它的 Kernel。 postprocess 里调 free_request 时，上一步的 attention kernel 可能还在 GPU 上跑。如果这个页立刻被分配给别的请求并写入新 KV，就会踩到正在读的数据。解法是让释放和执行在同一个 stream 上有序，或者用 event 卡一道。这是 CPU 侧逻辑正确、GPU 侧数据被踩的典型异步 bug，在单序列测试里永远复现不出来。

引用计数的对称性要用断言守住。 BlockManager 里那句 assert self.ref[block] > 0 不是装饰——双重释放会让同一个页号在空闲列表里出现两次，接着被两条序列同时持有。那之后的错误现象会离案发现场非常远。

七、验收清单¶

分页正确性

  • [ ] BlockManager 分配与释放数量对称（跑一轮压力测试后 num_free 回到初值）
  • [ ] ensure_capacity(n) 在 n 恰好等于 block_size 整数倍时不多分配
  • [ ] 乱序、不连续的页表能出正确结果
  • [ ] 交换两个物理页的内容并同步改页表，输出不变 —— 这条最能证明"只是间接寻址"
  • [ ] ctx_len 不是 block_size 整数倍时不越界
  • [ ] padding 页号（-1）永远不被 Kernel 访问

连续批处理

  • [ ] 序列完成后显存立刻回到池子（对比 num_free 前后）
  • [ ] 池子耗尽时触发抢占而不是崩溃
  • [ ] 被抢占的序列能正确恢复并产出与未被抢占时相同的输出
  • [ ] 不同长度的请求混批，输出与单独跑逐条一致

Kernel

  • [ ] CUDA 版与 PyTorch 版在乱序页表 + 非整块长度下对齐
  • [ ] compute-sanitizer --tool memcheck 无报告
  • [ ] compute-sanitizer --tool racecheck 无共享内存竞争
  • [ ] 释放页与使用它的 Kernel 之间有明确的同步关系

性能（方法见 11.4）

  • [ ] DRAM Throughput 接近带宽上限（decode attention 是访存受限的）
  • [ ] 页表查询没有成为额外的 latency 瓶颈（对比不分页的 baseline）
  • [ ] 每个数字都绑定了硬件、Shape、block_size 和测量范围

八、回到第一性原理¶

这一篇做的两件事，抽象掉实现细节之后是同一句话：

把"资源在哪"和"资源是什么"解耦开，代价是一次间接，换来的是弹性。

  • PagedAttention 在空间上解耦：逻辑序列不必对应连续显存，于是显存可以按需分配、即时回收、跨请求共享。
  • Continuous Batching 在时间上解耦：请求的生命周期不必对齐到批次边界，于是槽位可以随时腾挪。

而它们必须一起做，是因为弹性必须两端都有——时间上腾出的位置，需要空间上腾出的显存来兑现。

这个模式你在图形里见过：Bindless Handle Table 让 Shader 不必知道资源绑定在哪个槽位；虚拟纹理让采样不必要求整张贴图常驻。都是"多查一次表，换掉一个刚性约束"。 区别只在于代价评估：图形里那次间接落在纹理 Cache 上，这里落在 L2 上，值不值得取决于它换来的弹性有多大——本篇第一节算出的 8 倍并发，就是这个答案。
