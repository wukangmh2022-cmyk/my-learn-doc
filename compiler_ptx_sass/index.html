10.3 编译器抽象: PTX / SASS, 寄存器分配, 指令调度¶

概述¶

编译器是程序员和 GPU 硬件之间的 "优化师"。它的职责是把高级语言翻译成 GPU 汇编/机器码，并在翻译过程中做大量你无法（也不需要）手动控制的优化。

你写的 CUDA C++、HLSL、GLSL 代码，最终都要经过一层一层的编译降级，才能在 GPU 上真正运行。

编译流水线总览¶

CUDA 编译流水线¶

CUDA C++ (源代码)
    │
    ├── 编译器前端 (nvcc / Clang)
    │    ├── 词法分析、语法分析
    │    ├── 类型检查、模板展开
    │    └── 生成中间表示 (PTX)
    │
    ▼
PTX (Parallel Thread Execution)  ← 中间表示，类比 LLVM IR
    │
    ├── 编译器后端 (ptxas / NV Compiler)
    │    ├── 指令选择 (Instruction Selection)
    │    ├── 指令调度 (Instruction Scheduling)
    │    ├── 寄存器分配 (Register Allocation)
    │    └── 生成机器码
    │
    ▼
SASS (Streaming Assembler)  ← 最终机器码，GPU 直接执行
    │
    └── 驱动 (KMD) → 写入 Ring Buffer → GPU 执行

图形着色器编译流水线¶

HLSL / GLSL (着色器源代码)
    │
    ├── 编译器前端 (FXC / DXCompiler / glslang)
    │    ├── 词法/语法分析
    │    ├── 语义检查
    │    └── 生成中间表示 (DXIL / SPIR-V)
    │
    ▼
DXIL / SPIR-V  ← 中间表示
    │
    ├── 编译器后端 (驱动内编译)
    │    ├── 指令选择
    │    ├── 寄存器分配
    │    └── 生成 GPU 原生机器指令
    │
    ▼
GPU 原生指令  ← 硬件直接执行

关键类比：PTX、DXIL 和 SPIR-V 都是面向虚拟机/执行环境的中间表示，但语义、可移植范围和编译阶段不同。PTX 仍包含目标能力与 ISA 版本约束；SASS 是特定 NVIDIA 架构的原生机器指令，不宜称为“微码”。

PTX vs SASS: 中间表示 vs 最终机器码¶

维度 PTX SASS
全称 Parallel Thread Execution Streaming Assembler
角色 中间表示 (IR) 最终机器码
硬件绑定 与具体 GPU 架构无关 绑定到具体架构 (如 Ampere, Hopper)
可读性 人类可读的汇编文本 二进制格式，反汇编可读
稳定性 跨代稳定 (PTX 6.x 兼容多代 GPU) 每代架构可能不同
类比 LLVM IR / DXIL x86 机器码 / GPU 原生指令
生成方式 nvcc 前端生成 ptxas 后端生成
分发方式 可在驱动包中携带 (JIT 编译) 预编译为二进制 (性能最佳)

PTX: 面向 NVIDIA 虚拟 ISA 的中间语言¶

// PTX 示例：一个简单的向量加法 Kernel
.version 7.8
.target sm_75
.address_size 64

.visible .entry _Z13vecAddKernelPfS_S_(
    .param .u64 _Z13vecAddKernelPfS_S__param_0,
    .param .u64 _Z13vecAddKernelPfS_S__param_1,
    .param .u64 _Z13vecAddKernelPfS_S__param_2
)
{
    .reg .u32   %r<5>;
    .reg .f32   %f<5>;
    .reg .u64   %rd<8>;

    // 计算全局线程 ID
    ld.param.u64   %rd1, [_Z13vecAddKernelPfS_S__param_0];  // A
    ld.param.u64   %rd2, [_Z13vecAddKernelPfS_S__param_1];  // B
    ld.param.u64   %rd3, [_Z13vecAddKernelPfS_S__param_2];  // C
    mov.u32        %r1, %tid.x;
    mov.u32        %r2, %ntid.x;
    mul.wide.u32   %rd4, %r1, %r2;
    cvta.to.global.u64 %rd5, %rd1;
    // ... (加载、计算、存储)
}

PTX 的关键特性： - 架构无关：同一个 PTX 代码可以在多代 GPU 上运行（驱动负责 JIT 编译成当前硬件的 SASS）。 - 稳定性保证：NVIDIA 承诺 PTX 跨代兼容——你可以在 Volta 上编译 PTX，在 Hopper 上运行。 - 优化边界：PTX 保留了高级语义（如 __syncthreads），但已经丢失了变量名、循环结构等源码信息。

SASS: 真正的硬件指令¶

// 反汇编 SASS 示例 (Ampere 架构, sm_80)
/*0000*/  IMAD.MOV.U32 R1, RZ, RZ, c[0x0][0x28]
/*0010*/  S2R R0, SR_CTAID.X         // 读取线程块 ID
/*0020*/  S2R R2, SR_TID.X           // 读取线程 ID
/*0030*/  IMAD R0, R0, c[0x0][0x2c], R2  // 计算全局线程索引
/*0040*/  ISETP.GE.AND P0, PT, R0, c[0x0][0x30], PT  // 边界检查
/*0050*/  NOP
/*0060*/  EXIT

SASS 的关键特性： - 架构绑定：每代 GPU 架构有自己特有的 SASS 指令集（Turing SASS ≠ Ampere SASS ≠ Hopper SASS）。 - 性能最优：预编译的 SASS 二进制不需要 JIT 编译，且可以针对具体架构做最激进的优化。 - 调试目标：当你关心"为什么这个 Kernel 跑得慢"时，最终需要看 SASS 来理解寄存器压力、指令吞吐。

建议：在 CUDA 应用中携带 PTX 作为回退方案（兼容未来硬件），同时也携带当前主流架构的 SASS 二进制以获得最佳性能。这就是 nvcc 的 -gencode 参数做的事情。

编译器后端的核心技术¶

1. 指令调度 (Instruction Scheduling)¶

编译器后端会重新排列指令顺序，以最大化指令级并行（ILP, Instruction-Level Parallelism）。

// 未优化的指令序列（串行依赖）
LDG R0, [addr0]     // 加载数据  → 等待 Global Memory
FMA R2, R0, R1, RZ  // 乘加运算  → 等待 R0 就绪
LDG R3, [addr1]     // 加载数据  → 等待前一条完成
FMA R4, R3, R5, RZ  // 乘加运算  → 等待 R3 就绪

// 编译器优化后的指令序列（指令级并行）
LDG R0, [addr0]     // 加载数据 0
LDG R3, [addr1]     // 加载数据 1  ← 和上一条并行发射
FMA R2, R0, R1, RZ  // 乘加 0    ← 此时 R0 已就绪
FMA R4, R3, R5, RZ  // 乘加 1    ← 此时 R3 已就绪

编译器通过把独立的加载指令提前，让加载延迟被后续独立计算掩盖——这正是"Communication behind compute"在指令级别的体现。

2. 寄存器分配 (Register Allocation)¶

编译器决定哪些变量放在寄存器，哪些"溢出"（Spill）到 Local Memory（实际上是显存）。

寄存器是 GPU 上最快的存储，但数量有限：

CUDA C++ 代码                        编译器决策
────────────────────────────────     ────────────────
float a = ...;      // 频繁使用  →  分配物理寄存器 (Register)
float b = ...;      // 偶尔使用  →  可能溢出到 Local Memory
float c = ...;      // 只在末尾使用 → 先放寄存器，后溢出

图着色分配算法 (Graph Coloring Register Allocation)：编译器把变量看作图中的节点，变量间的同时活跃关系看作边，然后用图着色算法来最小化所需的寄存器数量。当图无法用可用颜色着色时，部分变量必须溢出到 Local Memory。

  a ─── b       ← a 和 b 同时活跃，不能共用寄存器
   \   /
    c           ← c 与 a、b 都同时活跃
   / \
  d ─── e

需要至少 3 个寄存器 (颜色) 来着色这个图
如果硬件只有 2 个寄存器 → 某个变量必须溢出到显存

寄存器溢出（Register Spill）是性能杀手——溢出意味着数据要写到显存再读回，延迟从几个周期暴涨到数百周期。这就是为什么很多时候"减少一个变量"就能让 Kernel 跑快 20%。

3. 资源估算与 Occupancy¶

编译器还会估算每个 Kernel 需要多少寄存器、多少 Shared Memory，从而决定一个 SM 上能同时驻留多少个线程块（Occupancy）。

// 编译器分析结果 (通过 --ptxas-options=-v 查看)
//    注册数: 32 registers per thread
//    Shared Memory: 8192 bytes per block
//    Occupancy: 64 blocks per SM (假设 SM 有 65536 个寄存器)
//               = 64 * 32 * 32 = 65536 线程 / SM

TensorRT: AI 专用的编译器¶

TensorRT 的 Engine 编译可以看作是 "AI 专用的编译器"：

PyTorch 模型 (计算图)
    │
    ├── TensorRT IBuilder / INetwork
    │    ├── 图优化 (算子融合: Conv+BN+ReLU)
    │    ├── 精度校准 (FP16 / INT8 量化)
    │    ├── 内存复用 (In-Place 优化)
    │    └── Kernel 自动调优 (Tactic Selection)
    │
    ▼
TensorRT Engine (.engine / .plan)
    │
    ├── 包含预编译的 CUDA Kernel (SASS)
    ├── 包含计算图拓扑信息
    └── 包含 Layer 参数和内存分配计划

你可以把 TensorRT Engine 理解成一个 "AI 专门的编译器产物"：

通用编译器 TensorRT
输入: CUDA C++ 源码 输入: ONNX 计算图
输出: SASS 机器码 输出: Engine (含多个 SASS Kernel + 调度计划)
优化: 指令调度 + 寄存器分配 优化: 算子融合 + 量化 + Kernel 自动调优
类比: 写一个 Draw Call 的 Shader 类比: 把整个 RenderGraph 预编译成 PSO

当你调用 TensorRT API 时：

// TensorRT 的 Engine 构建
IBuilder* builder = createInferBuilder(gLogger);
INetworkDefinition* network = builder->createNetwork();

// 添加网络层（类似构建计算图）
auto conv = network->addConvolution(...);
auto relu = network->addActivation(*conv->getOutput(0), ActivationType::kRELU);

// 编译 Engine（类比 ptxas 编译 PTX → SASS）
ICudaEngine* engine = builder->buildCudaEngine(*network);

// 运行时执行（类似 vkQueueSubmit）
context->enqueueV2(buffers, stream, nullptr);

本质：你在 CUDA 层面关注的是单 Kernel 的指令级优化，而在 TensorRT 层面关注的是整个计算图的调度级优化。两者处于不同的抽象层级，但底层共享同一个 PTX/SASS 编译栈。

一张表总结编译层级¶

层级 核心工作 技术栈 程序员管不到的地方
驱动 (Driver) 把 API 调用翻译成硬件指令、管理显存 WDK / Linux Kernel、PCIe、MMIO 页表映射、中断处理、电源管理
编译器 (Compiler) 高级语言 → 机器码，指令调度 + 寄存器分配 LLVM、PTX、SASS、图着色分配 指令级并行 (ILP) 调度、寄存器选择
算子开发 (Kernel) 高效并行算法，手工管理 Shared Memory CUDA C++、Triton、Warp Shuffle 指令顺序 (编译器重排)、寄存器分配
推理框架 (vLLM/TensorRT) 计算图优化、显存管理、批处理调度 Python/C++、CUDA Runtime、CUDA Graph 算子内部实现

你在第二层（编译器）的边缘试探过：你知道 __syncthreads 和 __shared__ 的存在，知道编译器会帮你做指令重排，但不深入到 SASS 层面。如果你想突破，阅读 NVCC 的 PTX 输出是最好的起点。
