6.3 基数排序 (Radix Sort) = 逐位流压缩¶

概述¶

基数排序（Radix Sort）是 GPU 上最快的排序算法之一。但它的本质不是一个\"排序算法\"——它是 Stream Compaction 在每一个二进制位上的逐位应用。

这个视角一旦建立，你就能立刻理解为什么 GPU 上排序这么快，以及它为什么在 MoE 路由、Top-K 选择、GPU BVH 构建等场景中扮演核心角色。

一句话总结¶

基数排序 = 对每个二进制位，做一次并行流压缩（Stream Compaction）。

因为每次流压缩都是 O(n) 的工作量（并行延迟 O(log n)），对 32 位整数做基数排序就是做 32 次流压缩，总复杂度 O(32 × n) = O(n)——比任何基于比较的排序（O(n log n)）都快。

算法可视化：按位分类¶

假设我们要对数组 [3, 1, 4, 1, 5, 9, 2, 6] 从小到大排序（从最低位 LSB 开始）：

第 1 轮：按最低位 (bit 0) 分类¶

元素:   3(011)  1(001)  4(100)  1(001)  5(101)  9(1001)  2(010)  6(110)
bit 0:   1       1       0       1       1       1        0       0

流压缩执行：

  1. Map：标记 bit=0 的元素（保留），bit=1 的元素（保留但不放前段——实际是\"分桶\"，两个桶都保留）
  2. Scan：分别统计两个桶的前缀偏移
  3. Scatter：bit=0 的放到前半段，bit=1 的放到后半段
结果: [4, 2, 6, 3, 1, 1, 5, 9]  (所有偶数在前，奇数在后)

第 2 轮：按次低位 (bit 1) 分类¶

在上一轮结果上重复同样的操作：

bit 1:  0   1   1   1   0   0   0   0

结果继续向有序收敛...

重复直到 32 位（或 64 位）¶

处理完所有二进制位后，数组完全有序。因为每一轮都维持了上一轮的相对顺序（稳定性），整个排序是稳定的。

为什么它在 GPU 上大放异彩¶

维度 归并排序 / 快速排序 基数排序
复杂度 O(n log n) O(b × n) = O(n)（b 是常数）
比较操作 元素间比较（分支分歧严重） 无比较，只有按位分类（无分支）
访存模式 随机访问（对缓存不友好） 顺序扫描 + Scatter（流式访问）
GPU 适配 差：分支分歧导致 Warp 效率低下 完美：流式 + 无分支 + SIMT 友好

GPU 上基数排序快过 CPU 归并排序的核心原因：CPU 前缀和是 O(n) 的串行循环（n 越大等越久），而 GPU 的前缀和虽然总工作量也是 O(n)，但并行延迟只有 O(log n)，所以实际执行时间是 O(b × log n) 的并行深度。

CUDA 实现：逐位流压缩¶

// 排除式前缀和 (Blelloch 算法，在 Shared Memory 内)
__device__ void exclusive_scan(float* shared, int tid, int n) {
    // Up-sweep
    for (int stride = 1; stride < n; stride *= 2) {
        int idx = (tid + 1) * stride * 2 - 1;
        if (idx < n) shared[idx] += shared[idx - stride];
        __syncthreads();
    }
    if (tid == n - 1) shared[tid] = 0;
    __syncthreads();
    // Down-sweep
    for (int stride = n / 2; stride > 0; stride /= 2) {
        int idx = (tid + 1) * stride * 2 - 1;
        if (idx < n) {
            float temp = shared[idx];
            shared[idx] += shared[idx - stride];
            shared[idx - stride] = temp;
        }
        __syncthreads();
    }
}

// 单一位的流压缩 Kernel (基数排序的核心步骤)
__global__ void radix_sort_bit_pass(unsigned int* keys, unsigned int* temp, 
                                     int n, int bit) {
    __shared__ int flags[256];
    __shared__ int scanned[256];

    int tid = threadIdx.x;
    int global_idx = blockIdx.x * blockDim.x + tid;

    // 1. Map: 取出当前位的值 (0 或 1)
    unsigned int bit_mask = 1u << bit;
    int flag = (global_idx < n) ? ((keys[global_idx] & bit_mask) == 0) : 0;
    flags[tid] = flag;
    __syncthreads();

    // 2. Scan: 对 flags 做排除式前缀和
    scanned[tid] = flags[tid];
    // 这里调用 Blelloch 扫描 (简化，实际需完整实现)
    exclusive_scan(scanned, tid, blockDim.x);
    // 此时 scanned[tid] = 排除式前缀和

    // 3. Scatter: 根据前缀和写入临时数组
    if (global_idx < n) {
        int dest;
        if (flag) {
            // bit=0 的元素放到前半段
            dest = scanned[tid] + blockIdx.x * blockDim.x;
        } else {
            // bit=1 的元素放到后半段: 偏移 = block 内 0 的数量 + 当前 1 的偏移
            int num_zeros_in_block = scanned[blockDim.x - 1] + flags[blockDim.x - 1];
            dest = num_zeros_in_block + blockIdx.x * blockDim.x 
                   + (tid - 1 - (scanned[tid]));
            // 注意: 这里的索引计算简化了跨 Block 的汇总
            // 生产环境需处理 Block 之间的全局偏移
        }
        temp[dest] = keys[global_idx];
    }
}

// 主循环: 对每一位调用一次流压缩 Kernel
void radix_sort(unsigned int* d_keys, int n) {
    unsigned int* d_temp;
    cudaMalloc(&d_temp, n * sizeof(unsigned int));

    for (int bit = 0; bit < 32; bit++) {
        radix_sort_bit_pass<<<(n + 255) / 256, 256>>>(d_keys, d_temp, n, bit);
        // 交换指针
        unsigned int* tmp = d_keys;
        d_keys = d_temp;
        d_temp = tmp;
    }

    // 如果最终结果在 d_temp 里，需要拷回 d_keys
    cudaFree(d_temp);
}

生产环境请使用 CUB 库的 cub::DeviceRadixSort::SortKeys，它包含了所有优化（Warp Shuffle、循环展开、负载均衡）。上面的代码只用于展示\"基数排序 = 逐位流压缩\"这个本质。

AI 中的应用：MoE 路由和 Top-K 选择¶

MoE (混合专家模型) 路由¶

MoE 层中，每个 Token 被路由到 Top-K 个专家。不同专家接收的 Token 数量不同，需要用基数排序来做动态负载均衡：

1. 每个 Token 计算它与每个专家的路由分数
2. 选取 Top-K 个专家 (需要 Top-K 选择，基于排序)
3. 对专家 ID 做基数排序 → 同一个专家的 Token 聚集到连续内存
4. 用 Scan (前缀和) 计算每个专家分配到多少个 Token
5. Scatter: 将 Token 数据批量发送到各专家的计算单元

基数排序在这里的角色：把稀疏、不规则的路由结果，转换成连续的、适合 GPU 批量处理的数据布局。

Top-K 选择¶

在推理场景中，Top-K 选择（如 Beam Search、Token 采样）经常用基数排序的变体来实现：

  • 对候选 Token 的 logits 做基数排序（按概率从大到小）。
  • 只取前 K 个结果。
  • 因为基数排序是 O(n) 的，对数十万的词表大小来说比 O(n log n) 的快排快得多。

图形中的对应：透明对象排序¶

在图形渲染中，基数排序的经典应用场景是透明对象排序：

1. 每个物体的深度（Z 值）作为排序 Key
2. 对 Key 做基数排序（32 位 float 的位模式也可以排序）
3. 排序后的物体列表用于 Alpha Blending（从后往前渲染）

这个模式与部分 MoE Token-Expert 路由实现共享“计算 Key，再按 Key 重排数据”的结构；具体实现也可能使用直方图、Prefix Sum 或专用 Dispatch Kernel，不一定执行完整基数排序。

完整推理链¶

Scan (前缀和) → 核心基础设施
    ↓
Stream Compaction (流压缩) → 基于 Scan 的上层算法
    ↓
Radix Sort (基数排序) → 流压缩在每一位上的逐位扩展
    ↓
MoE Routing / Top-K / BVH Sort → 基数排序在 AI 和图形中的应用

\"GPU 上做基数排序，就是在固定的 32 或 64 轮里，每轮跑一次流压缩。因为每轮流压缩都是 O(n) 的，所以基数排序总复杂度也是 O(n)。\"

附录：复杂度澄清¶

表述 是否正确 说明
基数排序工作量是 O(b × n) 正确 时间复杂度一般指这个
基数排序并行延迟是 O(b × log n) 正确 在并行算法分析中讨论 Span 时用
基数排序时间复杂度是 O(b × log n) 错误 这会误以为你没处理所有元素

工程只关心延迟：O(b × log n) 才是实际执行时间。但算法分析课上标准答案必须是 O(b × n)，因为时间复杂度衡量的是总工作量。
